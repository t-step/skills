# lifecycle-audit — eval results

**Model under test:** claude-sonnet-5, fresh `general-purpose` subagent per run, default settings.
**Harness:** one subagent per run, working only inside an isolated scratch copy of the case fixture (so it can't see this repository, any other case, or the skill unless directed to it); with-skill runs additionally received the skill's `SKILL.md` copied alongside the fixture and were told to read and follow it exactly, including its report structure; baseline runs received the same case files and the same one-line task framing ("run a lifecycle audit... identify the lifecycle-bearing entities... analyze how they interact"), with no skill file and no imposed report structure. Raw outputs are saved verbatim under `runs/2026-08-28-iteration-1/`; every claim below cites one of those files. Graded by the orchestrating session against `evals.json` (9 regression cases, 45 expectations at first-run time) and `pressure-tests/pressure_evals.json` (1 case, 6 expectations). Case 9's expectations were tightened by one item after the first run (see "Case 9: instruction contradiction, found and corrected" below); `evals.json` currently totals 46 regression expectations across the same 9 cases.

This is iteration 1: the skill's first eval suite, authored and run in the same session as a critical review of `SKILL.md`'s taxonomy (see the interaction-taxonomy section below). See "What this proves / what this does not prove" before treating any of this as validation — this remains an experimental skill.

## Eval-spec fix (case 1, expectation 1)

The with-skill run for case 1 (`runs/2026-08-28-iteration-1/case-001-skill.md`) inventoried `Order.status` as the confirmed lifecycle (correct) and *also* added a second inventory entry for `Refund.status`, with every field marked `Unknown` except the three states named in a code comment — because no code in the fixture writes or transitions a `Refund`. The original expectation text said "exactly one entity is inventoried as a lifecycle," which this technically doesn't satisfy, but the response is not a failure: `Refund` is a plausible, real lifecycle that the fixture simply doesn't show a writer for, and marking it `Unknown` rather than inventing an owner or transitions for it is exactly the evidence discipline the skill asks for. Treating this as a miss would have penalized more careful behavior than the key anticipated. Fixed by rewording the expectation to explicitly allow a transparently-`Unknown` second entry (see the diff in `evals.json`). This is a fix to the eval specification, matching the precedent in `evals/task-composition/RESULTS.md`'s case-6/case-10 key revisions — not a skill defect and not a skill change.

## Interaction-taxonomy pressure test

The task that produced this eval suite specifically asked whether the two-axis interaction model (Mechanism: independent / sequencing-only / one-way observation / projection-derivation / transition-triggering / ambiguous; Consistency requirement: no joint constraint / shared invariant with tolerable disagreement / requires active reconciliation / ambiguous) — introduced in an earlier revision of `SKILL.md` specifically to stop conflating "how do they connect" with "how tightly must they agree" — actually holds up, or whether it should change again.

Two cases in this suite exercise it hardest, because they involve more than one channel of interaction between the same pair of entities:

- **Case 9 (Auction/Bid):** the two entities connect two different ways — a push (`close_auction` triggers a bulk bid-rejection RPC) and a pull (`accept()` live-checks auction status before accepting). The with-skill run split these into two separate `### <A> <-> <B>` sub-analyses rather than forcing one Mechanism/Consistency pair to describe both, explicitly invoking the skill's own permission to deviate from rigid form when the evidence calls for it (`runs/2026-08-28-iteration-1/case-009-skill.md`: "these two entities connect through two distinct channels that carry different mechanisms and different consistency answers. Reporting them under a single mechanism/consistency pair would conflate a write-side cleanup path with the read-side check that actually enforces the shared invariant").
- **Case 3 (Transfer):** the same interaction pair (a transfer, and the two FC ledgers it touches) has a different consistency answer depending on whether `receive()` completes promptly (shared invariant, tolerable disagreement — the "in transit" window is intended design) or times out past 48 hours (requires active reconciliation — the incident's actual failure mode). The with-skill run gave both answers explicitly, tied to the two conditions, rather than picking one that would have been wrong in the other case.

In both cases, the mechanism/consistency split itself did its job: it let the model give an honest, structured answer to a relationship that a single "how coupled are these" label would have either oversimplified or forced into the wrong bucket. **The two-axis structure was not changed** — no run in this suite showed it producing a case that didn't fit any of its category values, and no case argued for a third axis or a different split.

### Case 9: instruction contradiction, found and corrected

The structure held up, but a closer read of case 9's own with-skill report (not just its final table verdict) found something the first pass of grading missed: the skill's own wording, not just the model's reasoning, briefly reintroduced the exact conflation the two-axis split exists to prevent. Step 3 of the "central question" gate read: "Reading alone is One-way observation, which answers the consistency question as 'no joint constraint' by definition." That sentence derives a consistency answer directly from a mechanism label — precisely what the rest of the skill argues against. Case 9's `accept()` function is a clean counterexample: it only ever reads `Auction.status` (a one-way observation, by mechanism), and that read is exactly what enforces the cross-lifecycle invariant "no bid accepted while its auction isn't open" (a real consistency requirement, not "nothing to agree on").

The first-run report followed that instruction literally when labeling this channel: "Consistency requirement: No joint constraint, **by the definition this skill uses for one-way observation**" (`runs/2026-08-28-iteration-1/case-009-skill.md`). The same report's surrounding prose correctly identified that this read is what enforces the invariant — so the run reached the right *substantive* conclusion (the invariant held throughout the incident) despite, not because of, the formal Mechanism/Consistency label the instructions told it to produce for that specific channel. That is a real defect in the skill's wording, not a hypothetical: an instruction that a capable model can reason around some of the time is still an instruction that will eventually mislead a less careful pass.

**Fix:** reworded step 3 of the central-question gate, and the "One-way observation" mechanism bullet it echoes, so that classifying a connection as one-way observation settles nothing about consistency — the two must be evaluated independently, and a one-way read performed at the moment of a transition (a live check) is named explicitly as a common way a one-way observation turns out to carry a genuine shared invariant. `evals.json` and `grading/case-009.expected.md` were tightened with a new required expectation guarding this specifically: a report that labels the `accept()`-reads-`Auction` channel "One-way observation" and then "no joint constraint" fails the case, even if its prose elsewhere states the invariant is real.

**Re-run against the corrected wording** (case 9, with-skill, fresh subagent, same fixture): the report now classifies the channel as "Bid -> Auction, at accept: **One-way observation**" and, in a separate step, "That makes this a **shared invariant, tolerable disagreement**, not a case requiring active reconciliation" — reasoned from the incident evidence, with no reference to the mechanism "defining" the answer. All 6 expectations for case 9 (the original 5 plus the new guard) are met on this rerun. The other 8 regression cases and the pressure case were not re-run this iteration: none of their correct answers involve one-way observation as the relevant mechanism, so the wording fix has no bearing on them, and re-running them would add confirmation-of-no-change rather than new evidence about the fix.

## What the baseline comparison shows

Every one of the 10 baseline (no-skill) runs reached a substantively correct conclusion — including case 101, the adversarial pressure case, where an unguided baseline declined the SyncCoordinator request on its own initiative and proposed a comparably sound alternative. This matches the pattern already documented in `evals/task-composition/RESULTS.md`: a capable model with no skill and no methodology document often reaches sound engineering judgment on cases like these, especially when the underlying reasoning (don't invent sync machinery for a one-way CDC pipeline, don't merge two tables just because a dashboard unions them) is the kind of thing a senior engineer would catch by instinct.

Where the with-skill runs differed was not in reaching a different conclusion, but in:
- **Explicit, checkable structure.** Every with-skill report used the skill's exact section headings (Scope and evidence inspected / Lifecycle inventory / Lifecycle interactions / Findings, split into Structural and Judgment calls / Unresolved questions), separating mechanical fact from architectural judgment as two distinct, labeled buckets. Baseline reports were well-organized but did not consistently separate "this is a fact" from "this is my judgment call" as its own named distinction — several baseline reports (e.g. case 002, case 004) stated conclusions with about the same confidence as facts, where the with-skill run explicitly flagged the same conclusion as a judgment call contingent on unseen evidence.
- **A named vocabulary tied back to a stated principle.** With-skill reports consistently used the Mechanism/Consistency-requirement framing and explicitly cited "interaction does not imply shared ownership, synchronization, or reconciliation" (most visibly in case 101's response). Baseline reports reached the same substance in prose without a reusable vocabulary a reader could check the reasoning against.
- **Case 2's hedge.** This is the one case where baseline's answer was measurably softer than the skill's: baseline explicitly declined to "adjudicate" whether the proposed `sync_status` field was warranted, while the with-skill run, though still appropriately hedged given the evidence limits, was more direct about why the evidence doesn't support it.

Read plainly: this iteration's evidence does not show the skill discovering conclusions a capable baseline misses. It shows the skill producing the same conclusions with more explicit, auditable structure and a named principle to check the reasoning against, and it shows the skill holding up under a direct pressure-test that baseline also, independently, resisted. That is a real but more modest finding than "the skill prevents bad answers" — see below.

## What this proves / what this does not prove

**What it's suggestive of:** across 9 regression scenarios (covering all 9 requested failure-mode categories from the design brief) and 1 pressure scenario, the with-skill runs (a) correctly distinguished a real lifecycle from a computed/cached attribute in every case where that distinction mattered (1, 8), (b) correctly separated interaction from reconciliation in both directions — naming reconciliation as unnecessary when it wasn't (2, 4, 5, 9) and naming it as genuinely required, with the specific invariant at risk, when it was (3) — (c) preserved genuine ambiguity rather than inventing an owner, state, or trigger not shown in evidence (7), (d) correctly told apart two lifecycles sharing vocabulary (6) and a genuine shared invariant between separately-owned lifecycles (9) from a lifecycle merger, and (e) declined a direct, socially-framed request to build reconciliation machinery for a pure projection, redirecting to the evidence-supported fix instead (101).

**What it does not prove:** every case was run once per condition — this is not a statistically powered benchmark, and a single additional sample of any case could look different, especially case 101 (one adversarial sample is suggestive, not a rate). All 10 fixtures are synthetic, single-author-constructed systems in the 2-4-file range; none approaches the size or genuine multi-team messiness of a real production codebase, and all were written by the same person who wrote the grading keys, which is a known source of unintentional alignment between what a fixture rewards and what the skill's own SKILL.md happens to emphasize. The baseline comparison used one model family (claude-sonnet-5) with no skill at all as the counterfactual — it says nothing about how a weaker model, or a different methodology document, would perform on the same fixtures. No case in this suite combines more than one of the ten requested failure categories at once (contrast `task-composition`'s "mixed realistic plan" case, which this suite has no equivalent of); a fixture layering, say, a terminology collision on top of a genuine-reconciliation case might behave differently. The interaction-taxonomy pressure test above is real evidence from two cases that needed it, not an exhaustive search for a case the taxonomy can't describe — a case with three or more interaction channels between the same pair, or a channel whose mechanism itself is ambiguous, was not constructed and might behave differently.
