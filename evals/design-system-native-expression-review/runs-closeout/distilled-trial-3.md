# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** Provision a new compute "environment" by configuring it across six domains — general identity/region, compute sizing and autoscaling, networking, storage, monitoring, and tags — then submitting once to create it. All configuration lives on one page/route with a single "Create environment" action; there is no evidence of a multi-step or previously-existing-record editing flow in this file.

**Packages / versions:** Resolved via `resolve_versions.py` against `package.json`/`package-lock.json`: `@cloudscape-design/components` 3.0.900 (declared `^3.0.900`), `@cloudscape-design/collection-hooks` 1.0.60, `@cloudscape-design/global-styles` 1.0.45. Only `@cloudscape-design/components` is imported in this file. Both components discussed below (`Wizard`, `TagEditor`) are long-standing components already present at 3.0.900, so no finding here turns on an unresolved version range.

**Authority categories found in this corpus:** Cloudscape exposes both **component guidance** (per-component pages, e.g. `checkbox`, `toggle`, `tag-editor`, `wizard`) and **named patterns** with explicit decision/criteria tables (the `patterns/resource-management/create/` family: an overview page plus dedicated `single-page-create`, `multi-page-create`, and `sub-resource-create` sub-pages). The create-resource overview page includes a genuine composition-level artifact: a criteria table with numeric thresholds (field counts, group counts) differentiating when to use Modal vs. Single page create vs. Multipage create. This is a real composition/pattern tier, not one improvised for this review.

## Findings

### Finding 1 — Six-domain, 20-field single-page form exceeds Cloudscape's own single-page-create thresholds; its own criteria point to multipage create (Wizard)

- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Configure and create a new environment resource spanning six settings domains (general, compute, networking, storage, monitoring, tags) via one submission.
- **Repository evidence:** `CreateEnvironment.tsx` renders one `ContentLayout` > one `Form` > `SpaceBetween` containing six `Container`s in sequence (`General` line 108, `Compute` line 126, `Networking` line 147, `Storage` line 176, `Monitoring` line 194, `Tags` line 208), all on one page/route with a single `Button formAction="submit"` (line 101). `inspect_surface.py`'s factual JSX inventory confirms: `Container: 6`, `FormField: 17`, `Checkbox: 3` (20 discrete input controls total), and no `ExpandableSection` or `Wizard` import anywhere in `design_system_imports` — i.e. every one of the 20 controls sits directly in what Cloudscape's own pattern table calls the "primary section," with none collapsed into an additional/optional section.
- **Authority evidence:** From `https://cloudscape.design/patterns/resource-management/create/` (the create-resource pattern overview page), the Modal / Single page create / Multipage create criteria table states, verbatim:
  - Length — Single page create: "Between 2 and 15 fields in the primary section or up to 5 groups of settings"; Multipage create: "More than 16 fields in primary sections or more than 5 groups of settings."
  - Complexity — Single page create: "Flow does not require any category to have its own page"; Multipage create: "Concepts require in-depth interactions that benefit from having their own page."
  - The page also states, verbatim: "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations."
  - Authority category: **named pattern** (a decision/criteria table on the create-resource pattern page, not a single component's own doc).
  - Disclosure of other rows in the same table not used to decide direction (per the equivalence-check requirement): "Recovery" (mutable vs. immutable input after creation) and "Error handling" (caught on the creation page vs. in every step/summary) are not resolvable from this bounded file and are **not** invoked to reach this finding's direction. "Frequency" is explicitly scoped by the source itself to be used "only... if you're unsure which pattern to use" — not needed here since Length is independently decisive. Complexity is weaker, corroborating evidence (none of the six domains show deep branching sub-decisions); Length is the load-bearing, numerically decisive row.
- **Evidence mode:** VERBATIM (criteria-table cells and the "we recommend" sentence, both copied from the single cited page above).
- **Applicability argument** (four-point test):
  1. Task match: the observed task — provisioning one resource across six configuration domains — is exactly the "long or complex configuration... set of interrelated tasks" scenario the multipage/wizard guidance targets, not a superficial shape match.
  2. Same problem: the current single-page form solves the identical problem (same six domains, same fields, same one-shot "create" semantics) the pattern addresses.
  3. Task preservation: restructuring into a Wizard with the same six domains as steps (plus an optional review step) captures the same fields and produces the same `createEnvironment` payload — no product goal changes.
  4. Materiality: the surface's own counted structure (6 groups vs. a stated "up to 5" ceiling for single-page; 20 always-visible primary-section fields vs. a stated "16" ceiling for multipage's own floor) is a concrete, code-derived overshoot of the single-page-create pattern's own numeric bounds, not a stylistic close call.
- **Current expression:** One `ContentLayout` → one `Form` → `SpaceBetween` of six `Container`s stacked vertically on a single page, no step navigation, no review step, no expandable/optional section to shrink the primary section.
- **Native expression:** Cloudscape's documented multipage-create composition — a `Wizard` (with the surrounding `AppLayout`'s `contentType='wizard'`, per the multi-page-create page's own "Do" guidance) breaking the same six domains into wizard steps, each step reusing the same `Container`/`FormField` groupings already present, plus an optional review step summarizing all six sections before the final "Create environment" action.
- **Why it matters:** Cloudscape's own length thresholds exist to keep a single create page's primary section scannable and each field's validation locally recoverable. This page is roughly 25%–33% over the single-page ceiling on both axes the pattern measures (groups: 6 vs. ≤5; primary fields: 20 vs. ≤15, and past multipage's own ">16" floor), with no per-domain progress signal and no review step — the exact gap the multipage-create pattern and its per-step error-handling model exist to close. It is also a consistency cost: other Cloudscape surfaces sized the way this pattern's own thresholds describe would read as a wizard, so this page looks off-pattern next to them.
- **Boundary check:** This is a judgment about which documented top-level composition (single-page vs. multipage/wizard) the surface's own measured field/group volume calls for under Cloudscape's own numeric criteria table — not a claim about any prop/API defect, and not a subjective "this form feels long" opinion.

### Finding 2 — Fixed Owner / Cost center / Environment tag fields vs. Cloudscape's Tag editor (intent-dependent)

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Attach organizational metadata (owner, cost center, environment classification) to the new environment resource as it is created.
- **Repository evidence:** `CreateEnvironment.tsx` lines 63–65 declare three independent string states (`ownerTag`, `costCenterTag`, `environmentTag`); lines 208–220 render a `Tags` `Container` with three separate `FormField`/`Input` pairs, hardcoded labels "Owner", "Cost center", "Environment tag," no add/remove affordance, and no generic key/value input pair. `inspect_surface.py`'s import list confirms no `@cloudscape-design/components/tag-editor` import anywhere in the file.
- **Authority evidence:** From `https://cloudscape.design/components/tag-editor/`: "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." Its usage guidance (fetched from the same URL) states: "Use the tag editor to manage tags only in create and edit [patterns]" — linking to the create- and edit-resource patterns, i.e. its own documented scope is specifically "resource tags inside a create flow," which is the situation here. Its props documented on the same page describe an open-ended, user-extensible list (a `tags` array, a `tagLimit` capped at 50 by default, add/remove rows, inline key/value validation against AWS tag key/value length and character-set rules). Authority category: **component guidance** only — there is no separate named "tagging strategy" pattern page in this corpus dictating when a fixed set of named metadata fields must become a `TagEditor`.
- **Evidence mode:** PARAPHRASE (component purpose and usage-scope statement) plus INFERRED reasoning connecting it to this specific fixed-3-field case (no citation settles the fixed-schema-vs-open-tagging question itself).
- **Applicability argument:** The tag editor's stated scope ("resource tags... in create") textually matches this section. But TagEditor's documented data model is an open-ended, arbitrary key/value list — materially different from three named, fixed-cardinality fields with dedicated labels and no add/remove semantics. Two readings are both plausible from the code alone:
  - (a) This is a small, fixed, mandatory governance schema — always exactly Owner/Cost center/Environment, nothing else — in which case three explicit, individually-labeled `FormField`/`Input` pairs are arguably *more* correct than `TagEditor`, since `TagEditor` would force users to type generic key names and lose per-field labeling/required-ness.
  - (b) This is meant as general AWS-style resource tagging, where these three are just default/suggested rows and users should be able to add further arbitrary tags — in which case `TagEditor` is the clearly more native fit, and the current implementation silently forecloses adding any other tag.
  - Nothing in this bounded file — no comment, no validation rule, no "add tag" affordance or its absence being load-bearing — resolves which of these is intended. Per the anti-fundamentalism/missing-intent rule, this is reported as intent-dependent rather than picked in either direction.
- **Current expression:** three independent, hardcoded `FormField`/`Input` pairs under a "Tags" `Container` heading.
- **Native expression:** uncertain, contingent on intent — under reading (b), a single `TagEditor` pre-seeded with Owner/Cost center/Environment rows and open to additional rows; under reading (a), the current three-field expression is already a reasonable, arguably preferable expression and no change is warranted.
- **Why it matters:** If reading (b) is correct, capping the UI at exactly three hardcoded keys forecloses any other tag a user might need to attach at creation time — a capability `TagEditor` provides natively, including AWS's own key/value length and character-set validation — which would be a real functional gap relative to how Cloudscape's own component is documented for this exact scenario. If reading (a) is correct, there is no gap at all.
- **Boundary check:** This is a question of which documented component (three fixed `FormField`/`Input` pairs vs. the purpose-built `TagEditor`) fits the underlying data model of the "Tags" section, not a UX complaint about its layout — and it is reported as intent-dependent, not a directional recommendation, specifically because this bounded file does not resolve which tagging model it intends.

## Suppressed (low materiality or weak applicability)

- **Tabs as an alternative container for the six settings domains** — considered and suppressed: no Cloudscape create-resource pattern authority documents Tabs as a composition for a *creation* flow (the "Details page with tabs" / "Details page as a hub" patterns govern viewing/reviewing an *existing* resource, not creating one). The only documented decision space for this exact task is single-page vs. multipage/wizard (Finding 1), so Tabs is not a citable alternative here.
- **Sub-resource create pattern for VPC / Subnet / Security group selection** — considered and suppressed: the bounded surface gives no evidence (no "create new" affordance, nothing indicating the option lists are meant to be extensible) that inline creation of a new VPC/subnet/security group is part of this task. The single-option stub arrays (`VPC_OPTIONS`, `SUBNET_OPTIONS`, `SECURITY_GROUP_OPTIONS`) read as placeholder data rather than a deliberate signal either way, so applicability can't be established from this file alone.

## Orientation notes

- **Checkbox (not Toggle) for `publicIp`, `encryptVolume`, `detailedMonitoring`** — correct as implemented. Cloudscape's own Checkbox guidance states, verbatim (from `https://cloudscape.design/components/checkbox/`): "Don't use for options that take immediate effect, for example to switch between light and dark mode. Use a toggle instead." None of these three settings take effect until the "Create environment" button is submitted — they are deferred, batched form inputs, not immediate-effect switches — so Checkbox, not Toggle, is the documented correct choice here.
- **`Select` for the six single-choice dropdowns** (region, instance type, VPC, subnet, security group, volume type) — correct usage: each stores exactly one chosen value from a small, known, non-typed option set, matching `Select`'s documented purpose; none of these need `Autosuggest` (free-text/typeahead) or a multi-select variant.
- **Container/Header/FormField/SpaceBetween/Form/ContentLayout nesting itself** matches the single-page-create pattern's own "Building blocks" structure (one container per configuration domain, h2 container headings via `Header variant="h2"`, `FormField`-wrapped inputs, action buttons in a `SpaceBetween` at the bottom of `Form`). Only the page-level packaging — single page vs. wizard — is in question (Finding 1); the component vocabulary used to build each section is already native.

## What was not evaluated

- **Implementation correctness**: prop usage (e.g. `type="number"`/`type="email"` on `Input`, controlled value/`onChange` wiring, absence of `constraintText`/inline validation, hardcoded single-option stub arrays for VPC/Subnet/Security group), and any app-owned accessibility mechanics. Out of scope per this skill's boundary regardless of severity.
- **Everything outside this single bounded file**: the surrounding route/`AppLayout` (breadcrumbs, `contentType='form'`/`'wizard'`, navigation), the Info-link/help-panel building blocks the create pattern describes, and any cross-page/cross-surface consistency.
- **General UX/product judgment**: whether creating an "environment" through this many settings at once is the right product decision, copy/microcopy quality, and any information-architecture question beyond the specific single-page-vs-multipage composition question addressed in Finding 1.
