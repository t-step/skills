# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape

**Inferred user task:** A one-time creation flow for a cloud "environment" resource (compute + networking + storage + monitoring + cost-allocation metadata), analogous to launching a virtual machine/compute environment in an AWS-style console. The user configures identity (name/description/region), compute sizing (instance type/count/auto-scaling bounds), networking (VPC/subnet/security group/public IP), storage (volume type/size/encryption), monitoring (detailed monitoring/log retention/alert email), and resource tags, then submits once via a single "Create environment" action.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved); `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60` (resolved); `@cloudscape-design/global-styles` declared `^1.0.45`, locked `1.0.45` (resolved). All fully resolved via `package-lock.json`; current docs fully apply.

**Authority categories found in this corpus:** Cloudscape's own discovery index (`llms.txt`) exposes three meaningful tiers used below: **component guidance** (per-component pages, e.g. Wizard, Tag Editor, Toggle), **named patterns** (a dedicated "Resource Management" pattern family, including a "Creation Flows" sub-family with distinct pages for single-page create, multi-page create, sub-resource create, and defaults — with an explicit cross-option decision table), and **foundations**. The Creation Flows pattern family is a genuine task/decision layer, not merely a worked example.

## Findings

### Finding 1

- **Finding:** The page implements resource creation as one continuous single-page `Form` with six stacked `Container` sections and ~20 form controls, but Cloudscape's own Creation Flows decision table places a form of this size/breadth in the multi-page (Wizard) bucket, not the single-page-create bucket.
- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As stated above — a single-sitting creation flow spanning five independent configuration domains (compute, networking, storage, monitoring) plus identity and tagging metadata, submitted once.
- **Repository evidence:** `CreateEnvironment.tsx` renders one `<Form>` (line 95) whose body is a `SpaceBetween size="l"` (line 107) containing six `Container`s, each with its own `Header variant="h2"`: General (line 108, 3 fields: name, description, region), Compute (line 126, 4 fields: instance type, instance count, auto-scaling min, auto-scaling max), Networking (line 147, 3 fields + 1 checkbox: VPC, subnet, security group, public IP), Storage (line 176, 2 fields + 1 checkbox: volume type, volume size, encrypt volume), Monitoring (line 194, 1 checkbox + 2 fields: detailed monitoring, log retention, alert email), Tags (line 208, 3 fields: owner, cost center, environment tag). `scripts/inspect_surface.py` confirms the raw inventory: 17 `FormField` instances, 6 `Container` instances, 3 `Checkbox` instances (20 total interactive form controls across 6 setting groups), all reached through a single `Button formAction="submit"` (line 101) with no intermediate step boundaries or per-section validation surface.
- **Authority evidence:** From `/patterns/resource-management/create/` (named pattern, decision table), reproduced in full:

  | Criterion | Modal | Single Page | Multipage |
  |---|---|---|---|
  | **Length** | ≤1 field | 2-15 fields or up to 5 setting groups | 16+ fields or 5+ setting groups |
  | **Complexity** | Basic text/simple selects | No category needs its own page | Concepts benefit from dedicated pages |
  | **Recovery** | Input mutable after creation | Input mutable after creation | Input immutable after creation |
  | **Error Handling** | In trigger page | In creation page | In every step and summary |
  | **Frequency** | N/A | Frequent | Infrequent |
  | **Sub-resource Create** | No | Yes | Yes |

  Same page, on what "Length" counts: "length considers required fields without good defaults and fields 80%+ of users expect to see. Additional configuration fields should receive appropriate defaults."

  From `/patterns/resource-management/create/single-page-create/` (named pattern): "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms."

  From `/patterns/resource-management/create/multi-page-create/` (named pattern): "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks," recommended "for long or complex configurations." Structurally: "you may use up to seven pages if necessary, though three to five pages are recommended," "ensure each step is a single page," and "use containers to organize multiple form fields within pages, with each container using an h2 heading" — keeping "the order of sections consistent between the steps and the review page." A review step is "recommended" and should "summarize the choices made in previous steps... in the same order that was presented in the flow," with "inline edit buttons on the review page" that "navigate the user back to each corresponding step page," while avoiding inline-editing interactions directly on the review page itself.

  Component existence confirmation, `/components/wizard/`: the Wizard component is "a multi-page form that guides a user through a complex flow or a series of interrelated tasks," comprising a navigation pane, header, main content area, and action buttons.

- **Evidence mode:** SYNTHESIS. The directional rule itself (length/group count → multipage) is stated on a single page (the decision table); a second page from the same pattern family (single-page-create) supplies the necessary definition of what counts toward "length" (needed to test the counter-argument that many fields carry code defaults — see Applicability argument below); a third page (multi-page-create) establishes that the proposed replacement structure is actually compatible with, not a rewrite of, the surface's existing internal composition. No single page states the complete applicability case standing alone, but no sentence here is invented beyond what these three pages jointly state.
- **Applicability argument:**
  1. *Task match, not superficial shape match:* The surface's own task — configuring five materially independent domains (compute, networking, storage, monitoring) plus identity/tags for a resource, in one sitting — is exactly "creating resources by completing a set of interrelated tasks," the multi-page-create page's own stated trigger condition, not merely a form that happens to be long.
  2. *Same problem, not a different one:* Counting the raw inventory (17 `FormField` + 3 `Checkbox` = 20 controls, 6 `Container` groups) places this well inside the "16+ fields or 5+ setting groups" multipage bucket and outside the "2-15 fields or up to 5 setting groups" single-page bucket on both axes. Anticipating the objection that many fields carry React-state defaults (`instanceType`, `instanceCount`, `autoScalingMin/Max`, `vpc`, `subnet`, `securityGroup`, `volumeType`, `volumeSize`, `encryptVolume`, `detailedMonitoring`, `logRetentionDays` are all pre-populated) and so might not count under the page's own "length" definition ("required fields without good defaults and fields 80%+ of users expect to see"): most of these defaulted fields are still squarely in the "80%+ of users expect to see" half of that same definition — network/security selections (VPC, subnet, security group, public IP) and storage/monitoring choices with real cost or risk consequences are not the kind of field a design-system-fluent implementer would silently hide behind a default, unlike a low-stakes preference. Even excluding only the most plausibly deferrable content — Tags (3 fields, its own group) and Description (1 field) — the remainder is still 16 controls across 5 groups, sitting at or past both stated thresholds. Under the generous count (20/6) or the conservative one (16/5), this task does not fit inside the single-page bucket.
  3. *Same product semantics preserved:* A wizard restructuring would keep every field, label, default, and the final submit action identical — only the wrapping composition changes (one scrolling `Form` → a `Wizard` with steps), and the existing sub-structure is already wizard-step-shaped: each current `Container`/`Header variant="h2"` pairing is precisely the composition multi-page-create's own guidance prescribes for organizing fields *within* a step ("use containers... each container using an h2 heading"). The six existing sections map onto 3-5 (or up to 7) steps as recommended, requiring no field-level rework.
  4. *Material enough to restructure, not just an alternative:* The current implementation has only one error-surfacing point — a single terminal submit after scrolling past all 20 controls across 6 unrelated domains — which is exactly the failure mode the pattern's own "Error Handling" row calls out: single-page is scoped to "in creation page," multipage explicitly calls for handling "in every step and summary." At this scale, a validation problem in, say, Storage is invisible until the user has already filled in Monitoring and Tags and clicked Create. This is the concrete, size-driven cost the documented pattern exists to prevent, not a stylistic preference. The "Sub-resource Create" row (both "Yes") and "Frequency" row (no code evidence either way) do not equalize this decision — they answer different criteria than "Length," and "Length" alone unambiguously separates this surface from the single-page bucket under either counting method above.
- **Current expression:** A single `Form` (line 95) with a single `SpaceBetween` of six `Container`s and one bottom-of-page action pair (Cancel / Create environment), no intermediate steps, no review step.
- **Native expression:** A `Wizard` (per `/components/wizard/` and the multi-page-create pattern) with steps mapping onto the existing six sections — General, Compute, Networking, Storage, Monitoring, Tags could combine into ~5 steps (e.g., merging the small Tags section into a broader step, or keeping it standalone within the recommended 3-7 range) — each step's content unchanged from the corresponding `Container`, plus an optional review step summarizing all sections before the final "Create environment" action, with per-step validation instead of one terminal submit.
- **Why it matters:** This is not an aesthetic preference between two equally-documented options — Cloudscape's own decision table draws a specific numeric line, and this surface sits on the multipage side of that line by both a generous and a conservative count. The concrete cost of staying single-page at this size is the one documented in the same table: validation and error recovery collapse to a single point at the bottom of a long, multi-domain scroll instead of being distributed per step, which is the exact problem the Wizard-backed pattern is designed to solve.
- **Boundary check:** This is a composition/component-selection judgment (which top-level Cloudscape construct — `Form` vs `Wizard` — and which page-level composition fits a task of this measured size/breadth), not an implementation-correctness defect (nothing here is mechanically broken) and not a generic UX complaint (the claim is grounded in this design system's own stated field/group-count criteria, not "this form feels long").

### Finding 2

- **Finding:** The "Tags" section represents AWS-style resource tagging with three fixed, individually labeled `Input` fields (Owner, Cost center, Environment tag) rather than Cloudscape's `Tag Editor` component, which is purpose-built for exactly this concept — but the surface doesn't establish whether these three tags are meant to be a closed, governance-mandated set or a representative subset of an open-ended, user-extensible tag list.
- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium (confidence that this is a genuine, evidence-unresolvable ambiguity — not confidence in either direction)
- **User task:** Attaching metadata tags to the environment being created, as part of the same single creation flow described above.
- **Repository evidence:** `CreateEnvironment.tsx` lines 208-220: a `Container` headed "Tags" containing exactly three `FormField`/`Input` pairs bound to `ownerTag`, `costCenterTag`, `environmentTag`, with no affordance to add, remove, or otherwise vary the set of tag keys.
- **Authority evidence:** `/components/tag-editor/` (component guidance): the Tag Editor is "an extension of the attribute editor that enables users to create, edit, or delete resource tags," and is designed for resource tags, which are "typically arbitrary user-defined key-value pairs rather than fixed, predetermined fields." No "when to use" section or explicit constraint/"don't...instead" guidance was retrievable from this page beyond that description.
- **Evidence mode:** PARAPHRASE (Tag Editor's documented purpose) combined with an acknowledged absence of any page settling which reading applies here — no SYNTHESIS claim is made beyond naming the two readings.
- **Applicability argument:** Reading A — these three tags (Owner, Cost center, Environment) are a closed, org-mandated cost-allocation schema; nothing more should be user-addable, so the current fixed `Input` fields are already the correct, minimal expression and Tag Editor's "arbitrary key-value" model does not apply. Reading B — the section is generically labeled "Tags," which in real AWS-style tagging is inherently open-ended (users commonly need to add tags beyond a starter set), and hardcoding exactly three keys as separate text inputs forecloses that without ever using the component the design system built specifically for this concept. The code gives no signal disambiguating these (no comment, no "add tag" affordance either present or explicitly withheld, no type/schema indicating a fixed set is intentional). This satisfies the "Missing intent" criteria: the two readings imply materially different, differently-native expressions, and nothing in the bounded surface resolves which is intended.
- **Current expression:** Three individually labeled, non-extensible `Input` fields inside a `Container` titled "Tags."
- **Native expression:** Not asserted with confidence — under Reading B it would be a `TagEditor` instance (optionally seeded with Owner/Cost center/Environment as pre-populated rows); under Reading A the current expression is already correct and no change is warranted.
- **Why it matters:** If Reading B is correct, the cost is real: users creating this resource cannot express any tag beyond the three the implementer anticipated, despite the design system shipping a component precisely to avoid that limitation for this exact concept. If Reading A is correct, there is no issue at all. Naming this without picking a side is the responsible outcome given the evidence.
- **Boundary check:** This concerns which documented component (`Input` × 3 vs. `TagEditor`) matches the section's own stated concept ("Tags"), not an implementation defect or general UX preference — it is suppressed from being a confident recommendation, not from being a finding, precisely because intent can't be established.

## Suppressed (low materiality or weak applicability)

- Auto-scaling minimum/maximum as two separate `Input type="number"` fields (lines 138-143): no Cloudscape-documented component or pattern for a paired min/max range was found; two plain numeric inputs is a valid, unremarkable expression of this task. Suppressed for lack of a specific, better-fitting documented alternative.
- VPC / Subnet / Security group as `Select` with single-option, hardcoded lists (lines 149-169): considered against a possible "resource picker" alternative, but Cloudscape documents a dedicated resource-selector pattern only for S3 (`S3 resource selector`), not a generic AWS-resource picker; `Select`'s documented purpose (choosing from a bounded, known list) matches what's shown in code. Suppressed — no applicable, better-fitting documented component found; the single-option arrays read as fixture placeholder data, not evidence of a real selection-cardinality problem.
- Log retention (days), instance count, and volume size as free-text `Input type="number"` rather than a constrained `Select` of valid values: this is a domain/API-level validity constraint (e.g., which retention values a monitoring backend actually accepts), not something Cloudscape's own documentation addresses as a component-selection question. Suppressed as out of this skill's scope.
- Single-page-create's own "optional expandable sections for additional settings" as a competing composition to a full Wizard restructuring: considered and folded into Finding 1's applicability argument (used to pressure-test the field count, per point 2) rather than reported as an independent, competing finding, since re-deriving the count conservatively still crosses the documented single-page ceiling even after treating the most plausibly deferrable content as hidden.
- Button variant choice (`variant="link"` for Cancel, `variant="primary"` for Create, lines 98-103): no retrievable Cloudscape guidance distinguishing button variants for cancel vs. primary submit actions was found on the Button component page. Suppressed for lack of citable authority, not reported as an orientation note either.

## Orientation notes

- `Checkbox` used for `publicIp`, `encryptVolume`, and `detailedMonitoring` (lines 170, 188, 196): correct per the documented distinction that `Toggle` "can result in an immediate change," whereas none of these settings take effect until the whole form is submitted — `Checkbox` is the semantically appropriate choice here. (Component guidance, PARAPHRASE, `/components/toggle/`.)
- `Select` used for Region, Instance type, and Volume type (bounded, small, predetermined option sets): matches `Select`'s documented purpose of choosing among a known, closed set of options; no evidence in this surface calls for a different selection component for these three fields.
- `Container` + `Header variant="h2"` per configuration domain: already the exact sub-composition the multi-page-create pattern itself prescribes for organizing fields within a page/step, which is why Finding 1's proposed restructuring requires no rework of this inner structure — only the outer wrapping component changes.

## What was not evaluated

Implementation correctness — including the hardcoded single-option `VPC_OPTIONS`/`SUBNET_OPTIONS`/`SECURITY_GROUP_OPTIONS` arrays, absence of any client-side required-field validation or `FormField` error text, the `console.log` stub standing in for a real submit handler, `type="number"` usage on `Input`, and any accessibility mechanics on already-chosen components — was not assessed and its absence here should not be read as "checked and fine." General UX/product judgment — page length as a subjective usability concern, field ordering, information density, and copy/labeling quality — was likewise not evaluated except where a specific Cloudscape citation gave concrete, task-preserving grounds for a native-expression finding (Finding 1).
