# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape

**Inferred user task:** The page lets a user configure and submit, in one step, a request to create a new cloud "environment" — naming it and choosing its region; sizing its compute (instance type, count, auto-scaling bounds); placing it on a network (VPC, subnet, security group, public IP); configuring storage (volume type/size, encryption); opting into monitoring and alerting; and applying governance tags (owner, cost center, environment) — then submitting via a single "Create environment" primary action (with a "Cancel" escape hatch).

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved); `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60` (resolved, not imported by this file); `@cloudscape-design/global-styles` declared `^1.0.45`, locked `1.0.45` (resolved, not imported by this file). Resolved via `package.json` + `package-lock.json`. Version specificity doesn't materially bound either finding below — both concern long-stable pattern-level concepts (Container composition, ExpandableSection, Wizard vs. single-page create), not API shape that would change across 3.x minors.

**Authority categories found in this corpus:** component guidance (individual component pages exist, but their "Usage" tab content is client-rendered and not statically retrievable — only short one-line component descriptions were retrievable as text); named/composition patterns, specifically a "Resource Management" pattern family ("Create Resources" → Create resource, Single page create, Multipage create, Sub-resource create, Defaults) and "General" patterns (including "Selection in forms," which contains explicit decision tables); foundations (present in the site's top-level index but not retrieved for this review — not needed to settle either finding). No separate "worked examples"/demos tier was retrieved as text; the pattern pages embed illustrative screenshots only, referenced here as non-normative ("examples and demos illustrate, they don't mandate").

## Findings

### Finding 1

- **Finding:** The page implements this single-page resource-creation task as six separate, always-fully-expanded top-level `Container`s (General, Compute, Networking, Storage, Monitoring, Tags) with no primary/secondary field distinction, instead of the one-container-plus-additional-settings composition Cloudscape's own "Single page create" pattern documents for this exact task.
- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As stated above — a single-page, single-submit resource-creation flow for one new environment.
- **Repository evidence:** `CreateEnvironment.tsx` lines 92–226: `ContentLayout` > `Form` > `SpaceBetween` wrapping six sibling `<Container header={<Header variant="h2">…}>` blocks — General (108–124), Compute (126–145), Networking (147–174), Storage (176–192), Monitoring (194–206), Tags (208–220) — containing 17 `FormField`-wrapped inputs total. No `ExpandableSection` is imported or used anywhere in the file; every field is rendered open and visible simultaneously with no primary/additional split.
- **Authority evidence:** Cloudscape "Single page create" pattern page (`/patterns/resource-management/create/single-page-create/`), authority category: **named pattern**. Quoted verbatim (re-checked against the fetched page text):
  - "In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout. For example: Choosing a database type."
  - "Group related input fields together under a subheading if there are multiple types of configuration inputs." (listed under "Do")
  - "Place as many inputs as possible into the additional settings section for each resource card. This allows the user to keep the primary section as short as possible, so the user can focus on the most important tasks."
  - Primary-section criteria: "Any required field that we can't provide a good default for. For example: password." and "Any field that 80% or more of users would expect to see, and want to know the value of in order to be successful."
  No qualifying or tying row exists elsewhere on this page or the adjacent "Multipage create" page that treats "one container" and "many containers" as equally valid for a single-page create task — the guidance states a default ("in most cases") plus one narrow, illustrated exception (a single highly complex choice), not a decision table with tied cells.
- **Evidence mode:** VERBATIM
- **Applicability argument:** (1) Task match — this file is exactly the composition the "Single page create" pattern targets: `ContentLayout` + `Form` + one submit action, no `Wizard`. (2) The current implementation solves the same problem the pattern addresses (create one resource, one page). (3) The proposed native expression (one container, subheadings replacing the six `Header`/`Container` pairs, an "Additional settings" `ExpandableSection` for secondary fields) preserves every field, label, and the same submit action — no task change. (4) Materiality: none of the six sections is "a choice [that] is highly complex and would benefit from having its own section" in the sense of the docs' own example (a single complex choice like database type) — each is a plain grouping of 2–4 ordinary fields. Conversely, most of the 17 fields fail the documented primary-section bar (not an undefaultable-required field, not something 80%+ of users need to see to succeed) — auto-scaling min/max, volume type, encryption, detailed monitoring, log retention, alert email, and all three tags are pre-filled defaults or governance metadata, not primary decision points — yet none is placed behind the documented "additional settings" mechanism. This clears the anti-fundamentalism bar: it isn't "the design system has a `Container`/`ExpandableSection`" in the abstract, it's that this page's own field set maps cleanly onto the documented primary/additional split and the doc's stated container default, and diverges from both.
- **Current expression:** Six always-expanded `Container`s, each with an `h2` `Header` naming a configuration domain, stacked via `SpaceBetween` inside one `Form`; all 17 fields visible at once with no primary/secondary distinction.
- **Native expression:** One `Container` (per the documented default), using text subheadings for the six domain groupings rather than separate `Container`/`Header` pairs, with an "Additional settings" `ExpandableSection` holding the fields that don't meet the primary-section bar (e.g., auto-scaling bounds, volume type/encryption, detailed monitoring, log retention, alert email, tags), leaving environment name, description, and region (and perhaps instance type) as the visible primary fields.
- **Why it matters:** The current structure requires scanning six full-height, permanently-open containers and all 17 fields before a user can act — precisely the outcome the documented "keep the primary section as short as possible" / "additional expandable section" building blocks exist to prevent. It also departs from the "single container in most cases" default that keeps this create page's visual weight consistent with how other Cloudscape single-page create flows in the same product would read, since none of the six groupings clears the stated bar for a standalone container.
- **Boundary check:** This is a judgment about which documented building blocks (container count, primary/additional split) the "Single page create" pattern establishes for this exact task, not a claim that any individual `Container`, `FormField`, or `Header` is used incorrectly.

### Finding 2

- **Finding:** The configuration's breadth (six domains — general, compute, networking, storage, monitoring, tagging — and 17 fields) sits close to the corpus's own stated boundary between "Single page create" ("simple to medium-complex forms") and "Multipage create" (a "Wizard," for "a complex flow or a series of interrelated tasks"). The file uses no `Wizard`, but neither pattern page states a bright-line criterion (field count, section count, or otherwise) that this file's own code resolves.
- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Same as above.
- **Repository evidence:** The six `Container` sections span distinct AWS-style provisioning domains (compute sizing/auto-scaling, network placement, storage, monitoring/alerting, governance tags) submitted as one atomic action, with no step indicator or per-domain sequencing. The only visible cross-field relationship is Subnet sitting under Networking near VPC (lines 149–162); nothing in the file establishes the other five domains as sequentially or logically interrelated versus independently completable.
- **Authority evidence:** "Single page create" pattern page: "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms." (named pattern, VERBATIM). Same page's cross-reference to the wizard concept: "A multi-page form that guides a user through a complex flow or a series of interrelated tasks." (named pattern, VERBATIM, from the "Wizard" summary on the same create-resource index). Neither page states a numeric or structural threshold (field count, section count, or a rule like "more than N containers → use a wizard") separating "medium-complex" from "complex."
- **Evidence mode:** SYNTHESIS (bridging both pattern pages' self-descriptions; no single cited source states the cutoff between them)
- **Applicability argument:** Anti-fundamentalism points 1–3 are plausible: the observed task could match a wizard's stated problem, the current page solves substantially the same provisioning problem a wizard would, and a wizard would preserve the same task (same fields, same submit outcome, staged instead of flat). Point 4 is exactly what's unresolved: whether an experienced Cloudscape implementer would actually restructure this into a 3–5(–7) step wizard turns on whether these six domains function as "a series of interrelated tasks" or as independently completable configuration groups that a single page — once cleaned up per Finding 1 — already serves adequately. The file's own code doesn't resolve this either way, and the two cited pages differentiate by an unresolved reading of "how complex/interrelated is this," not by a criterion this surface's code, comments, or copy settles. Per "Missing intent," this is reported rather than guessed.
- **Current expression:** A flat single page with no `Wizard`, no step indicator, and no review step.
- **Native expression:** Not stated with confidence — could remain a (cleaned-up, per Finding 1) single page, or become a 3–5 step `Wizard` with a review step; either is a documented, valid expression depending on facts this file alone doesn't establish (e.g., whether later steps genuinely depend on earlier choices beyond Subnet/VPC).
- **Why it matters:** Guessing wrong has a real cost in either direction — imposing a wizard on largely independent settings adds unnecessary navigation friction the "Do" guidance for wizards itself warns against ("Restrict the flow to minimal mandatory inputs and pages"), while leaving genuinely interrelated, complex multi-domain provisioning on one page can undercut the "keep the primary section short" goal Finding 1 is already stretched to satisfy at 17 fields. Naming the question avoids silently defaulting to whichever pattern happens to be already implemented.
- **Boundary check:** This is a composition-tier pattern-selection question (single-page vs. multipage create) reported as an unresolved, evidence-backed candidate rather than a directional recommendation — not an implementation defect or a general UX complaint.

## Suppressed (low materiality or weak applicability)

- **Select vs. Radio group/Tiles for Region, Instance type, VPC, Subnet, Security group, Volume type.** The "Selection in forms" pattern's single-selection criteria table states "2 to 7 options" → Radio group/Tiles, "8+ options" → Select/Autosuggest, and every one of these fields is coded with 1–2 hardcoded options (`REGION_OPTIONS`, `INSTANCE_TYPE_OPTIONS`: 2 each; `VPC_OPTIONS`, `SUBNET_OPTIONS`, `SECURITY_GROUP_OPTIONS`: 1 each; `VOLUME_TYPE_OPTIONS`: 2), which is technically within the smaller tier. Suppressed because these fields represent canonically large or account-scoped catalogs in real deployments (AWS regions, EC2 instance types, and especially per-account VPCs/subnets/security groups routinely exceed 7), and the fixture's arrays read as stand-ins for real, API-populated lists rather than evidence of true production cardinality. The file's own code, comments, and copy give no basis to resolve the real cardinality (an internal governed-platform reading, where these lists stay small and curated, is equally plausible from the "Owner/Cost center/Environment" governance framing) — applying the criteria table's option-count threshold here would mean reasoning from stub data rather than from evidence this surface actually establishes, which the "Missing intent" guidance directs against.
- **Log retention (days) as a fixed-value selector rather than free-text `Input type="number"`.** AWS CloudWatch Logs retention only accepts a specific enumerated set of day values in the real service, which would argue for a `Select`/`RadioGroup` of valid values instead of an open numeric `Input`. Suppressed because nothing in this file's code, comments, or copy establishes that "Log retention (days)" here is specifically CloudWatch-backed (as opposed to this product's own, more permissive retention setting) — asserting the AWS-specific enumeration would import outside domain knowledge not evidenced by the bounded surface.

## Orientation notes

- **Checkbox for `publicIp`, `encryptVolume`, `detailedMonitoring`.** The "Selection in forms" boolean-selection criteria table states, for Checkbox: "The selection takes effect at form submission," and the general guidance adds "Binary choices made by using checkboxes, radio groups, and tiles should take effect at form submission, for example in a creation or edit flow." This is exactly this context (a create flow, values applied only on submit) — `Toggle` (reserved for settings with an immediate, visible effect) would be the misfit here, and the file correctly avoids it.
- **Tags modeled as three fixed `Input` fields (Owner, Cost center, Environment tag) rather than the `TagEditor` component.** Checked `TagEditor`'s stated purpose ("An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags.") — it's built for an open-ended, user-managed set of key/value tag pairs, not a fixed set of named, required governance attributes with predetermined keys. The current three explicit, labeled `Input` fields correctly preserve that these are specific required fields, not an arbitrary add/remove list — adopting `TagEditor` here would be exactly the "existence does not imply a rule" trap, not a genuine improvement.
- **Header and copy conventions.** The page's `h1` ("Create environment") and each container's `h2` ("General," "Compute," "Networking," "Storage," "Monitoring," "Tags") match the pattern's writing guidelines ("Begin page titles with an active verb... Create [resource name]"; "Begin container headings with a noun").
- **Form actions.** The `SpaceBetween(direction="horizontal")` pairing of a link-variant "Cancel" (`formAction="none"`) with a primary "Create environment" (`formAction="submit"`) button matches the documented action-button building block and its button-text guidance ("Cancel" for exit; "[Active verb] [resource type]" for submit).

## What was not evaluated

Implementation correctness — prop usage, `Input`/`type="number"` validation and constraint wiring, `errorText`/`constraintText` presence, accessibility mechanics, and the button-disable behavior noted in the pattern's own "Don't" guidance — was not assessed; its absence from this report is not a certification that it's correct. General UX and product judgment (information density, whether six domains is "too much" in the abstract, field-ordering aesthetics, whether `ColumnLayout` should pair the auto-scaling min/max fields) was likewise out of scope and not evaluated.
