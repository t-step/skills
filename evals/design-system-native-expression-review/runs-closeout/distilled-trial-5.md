# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape Design System (`@cloudscape-design/*`)

**Inferred user task:** A single administrative form for creating a new cloud "environment" (an AWS-style compute+network+storage resource bundle) in one flow: the user names it, picks a region, sizes compute (instance type/count, auto-scaling min/max), configures networking (VPC, subnet, security group, public IP), configures storage (volume type/size, encryption), sets monitoring (detailed monitoring, log retention, alert email), and applies cost/ownership tags, then submits once via a single "Create environment" action (`handleSubmit`, lines 67-90).

**Packages / versions:** Resolved via `resolve_versions.py` against `package.json`/`package-lock.json`: `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900`; `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60`; `@cloudscape-design/global-styles` declared `^1.0.45`, locked `1.0.45`. All fully resolved (not range-only). Both components discussed below (`Wizard`, `Tag editor`) are long-standing, stable Cloudscape components; nothing in this review depends on an unresolved semver range.

**Authority categories found in this corpus:** Cloudscape's `llms.txt` index exposes distinct **component guidance** pages, a **named-pattern** tier under `/patterns/` (including a `resource-management/create` family with an explicit criteria/decision table comparing Modal, Single page create, and Multipage create), **foundations** (e.g. accessibility), **demos**, and implementation-focused **dev-guides** (CSP, i18n, collection-hooks package, etc.). The dev-guides tier is implementation-level and not load-bearing for this review. Both findings below are grounded in the named-pattern and component-guidance tiers, which this corpus does genuinely expose (not projected from elsewhere).

## Findings

### Finding 1

- **Finding:** The entire 6-section, 20-field configuration is expressed as one un-stepped `Form`/`Container` composition on a single page, when Cloudscape's own decision criteria for this exact family of task (creating a resource) place a configuration this size on the multipage-create/`Wizard` side of the line, not single-page create.
- **Type:** combined selection + composition (adopting the documented alternative both substitutes the orchestrating component — `Form` alone → `Wizard` — and restructures the composition into discrete steps plus a review step).
- **Materiality:** high
- **Confidence:** high
- **User task:** Creating one new environment resource by configuring six logical groups of settings (General, Compute, Networking, Storage, Monitoring, Tags) and submitting them together.
- **Repository evidence:** `CreateEnvironment.tsx` lines 92-226. A single `<form>` (line 94) wraps one `<Form>` (line 95) whose `actions` (lines 96-105) contain exactly one Cancel/Create-environment button pair. Inside, one `<SpaceBetween size="l">` (line 107) stacks six `<Container>` sections, each with its own `<Header variant="h2">`: General (lines 108-124, 3 fields: environment name, description, region), Compute (lines 126-145, 4 fields: instance type, instance count, auto-scaling min, auto-scaling max), Networking (lines 147-174, 4 fields: VPC, subnet, security group, public-IP checkbox), Storage (lines 176-192, 3 fields: volume type, volume size, encrypt-volume checkbox), Monitoring (lines 194-206, 3 fields: detailed-monitoring checkbox, log retention, alert email), Tags (lines 208-220, 3 fields). `scripts/inspect_surface.py` confirms the raw counts: `Container: 6`, `FormField: 17`, `Checkbox: 3` (20 interactive fields total), and no `Wizard`, `Steps`, or `ExpandableSection` import anywhere in `design_system_imports`.
- **Authority evidence:** Cloudscape's "Create resource" pattern page (`/patterns/resource-management/create/index.html.md`) states: "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations." It backs this with an explicit criteria table comparing Modal / Single page create / Multipage create. The **Length** row states, verbatim: Single page create = "Between 2 and 15 fields in the primary section or up to 5 groups of settings"; Multipage create = "More than 16 fields in primary sections or more than 5 groups of settings." This fixture has 20 fields and 6 groups (Containers) — past **both** thresholds for multipage create, not just one. Authority category: **named pattern** (this corpus's `patterns/resource-management/create` tier, with its own decision table — a genuine pattern-level authority, not projected from elsewhere). Disclosing other rows in the same table for completeness, per this skill's disclosure rule: the **Complexity** row differentiates by whether "concepts require in-depth interactions that benefit from having their own page" (a softer, more subjective signal that is directionally consistent with, but not required to support, this finding); the **Recovery** and **Error handling** rows describe post-creation editability and per-step vs. per-page error surfacing, which this bounded fixture's mocked `createEnvironment` stub cannot resolve either way, so they are not counted as evidence for or against; the **Frequency** row is explicitly scoped by the table's own text to apply "only... if you're unsure which pattern to use," which does not apply here because the Length row already settles the question unambiguously (no tie exists on that axis).
- **Evidence mode:** VERBATIM
- **Applicability argument:** (1) Task match — this is precisely the "create new resource" task the pattern page addresses, not a superficially similar but different problem. (2) Current implementation solves the same problem the pattern addresses — it is a real, working create-resource form, not a distinct workflow wearing similar UI. (3) The proposed alternative (Wizard-based multipage create with the same six groups spread across steps, ending in a review step) preserves the identical task and identical data being collected — nothing about what the user configures changes, only how it is paginated. (4) Materiality: the fixture exceeds both independent length thresholds (fields: 20 vs. >16 cutoff; groups: 6 vs. >5 cutoff) by a clear margin, not a borderline case one field or group over the line — this is the scenario the decision table's Length criterion exists to catch, and an experienced Cloudscape implementer building a form this size would recognize it as a multipage-create candidate rather than a single-page one.
- **Current expression:** One `Form` component containing all six `Container` groups and all 20 fields simultaneously visible in a single scroll, with one submit action at the very end.
- **Native expression:** A `Wizard` (`@cloudscape-design/components/wizard`) with steps mapping to the existing logical groupings — e.g., General+Compute, Networking, Storage, Monitoring+Tags, within the pattern's recommended 3-5 step range — each step keeping the same `Container`/`FormField` composition already used, plus an optional final review step (a documented multipage-create building block) summarizing all six groups with per-step edit links before the resource is actually created.
- **Why it matters:** As implemented, the user must scroll through and validate an entire compute+network+storage+monitoring+tagging configuration before any single unit of it is confirmed correct, and Cloudscape's own decision table assigns configurations of exactly this size and grouping to the pattern designed to spread that risk and cognitive load across steps with a pre-creation review — not to the pattern optimized for "simple to medium-complex forms." Continuing with single-page create here also forgoes the documented per-step error handling and edit-before-create review page that multipage create provides specifically for configurations this large.
- **Boundary check:** This is a judgment about which documented resource-creation composition (single-page `Form` vs. multipage `Wizard`) Cloudscape's own criteria assign to a configuration of this size — not an implementation defect (the `Form`/`Container`/`FormField` usage is otherwise mechanically valid) and not a generic UX complaint (it is grounded in a specific, quantitative, named-pattern decision table, not "this form feels long").

### Finding 2

- **Finding:** The "Tags" section hard-codes three fixed, independently-typed text fields (Owner, Cost center, Environment tag) instead of using Cloudscape's purpose-built Tag editor, which exists specifically to manage this exact kind of resource metadata in create flows.
- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Attaching cost-allocation/ownership metadata (tags) to the environment resource being created, as part of the same single create-environment flow.
- **Repository evidence:** `CreateEnvironment.tsx` lines 208-220 — a `Container` headed "Tags" containing three separate `FormField`/`Input` pairs bound to three independent `useState` string fields (`ownerTag`, `costCenterTag`, `environmentTag`, declared lines 63-65): "Owner" (lines 210-212), "Cost center" (lines 213-215), "Environment tag" (lines 216-218). `inspect_surface.py`'s `design_system_imports` list contains no import from `@cloudscape-design/components/tag-editor` (or `attribute-editor`) anywhere in the file.
- **Authority evidence:** Cloudscape's Tag editor component page (`/components/tag-editor/index.html.md`) states, verbatim: "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." and, in its Features section: "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)." Its General guidelines "Do" list states, verbatim: "Use the tag editor to manage tags only in create and edit flows." Authority category: **component guidance** (this corpus does not have a separate named "tagging" pattern page beyond this component's own doc — the "Do" scoping bullet is the load-bearing guidance, not a separate pattern tier, and this label reflects that honestly rather than manufacturing a pattern-level citation that doesn't exist here). No qualifying or contradicting statement was found on this page or the related Attribute editor entry — nothing in Cloudscape's own material treats fixed, hand-rolled key-labeled inputs as an equally-valid alternative to Tag editor for this job.
- **Evidence mode:** VERBATIM
- **Applicability argument:** (1) Task match — "Owner," "Cost center," and "Environment tag" are exactly the shape of AWS-style resource tags (conventional cost-allocation/governance tag keys), and the section is explicitly labeled "Tags," matching Tag editor's stated purpose of managing "metadata assigned to a resource, consisting of a key... and a value..." rather than being a superficially similar but conceptually different field group. (2) The current implementation solves substantially the same problem — capturing named key/value metadata to attach to the new resource. (3) The proposed native expression preserves that same task: Tag editor can be pre-populated with the same three keys as default rows (if these three are meant to be the organization's baseline required tags) while still permitting the user to add or remove tags, so nothing about what gets attached to the resource needs to change. (4) Materiality: hardcoding exactly three fixed keys structurally forecloses the open key/value tagging model that is the entire point of "tags" as a concept, and forfeits Tag editor's documented validation (duplicate-key detection, invalid-character rules, the `aws:`-prefix restriction, 128/256-character key/value limits) and its add/remove/undo affordances — differences substantial enough that a Cloudscape-fluent implementer building a resource-create flow would reach for the component the design system built for exactly this job rather than reproduce it by hand.
- **Current expression:** Three independent `FormField`+`Input` pairs, each hard-bound to one fixed label and one string state variable, with no way to add, remove, or otherwise manage additional tags.
- **Native expression:** Replace the three fixed inputs with `@cloudscape-design/components/tag-editor`, optionally seeded with the same three keys (Owner, Cost center, Environment) as default rows if those are meant to be baseline/required tags, while allowing users to add further key/value tags following the component's documented validation, tag-limit, and empty/loading states.
- **Why it matters:** The current structure locks the resource's tag model to exactly three keys chosen by the developer rather than the open key/value set the "tags" concept (and Cloudscape's Tag editor) is built around, and it reimplements — without the documented validation rules, limits, and undo affordances — a job the design system already ships a tested, purpose-built component for; any other create/edit flow in the same product that does use Tag editor for its tags will diverge from this page in both capability and interaction model for what is conceptually the same feature.
- **Boundary check:** This is a judgment about which Cloudscape component is documented for the "manage resource tags in a create flow" job — not an implementation-correctness complaint (the `FormField`/`Input` usage here is itself mechanically valid) and not a generic UX critique (it is grounded in the Tag editor component page's own stated purpose and scoping guidance, which names this exact context).

## Suppressed (low materiality or weak applicability)

- **Select used for 1-2-option lists (Region, Instance type, VPC, Subnet, Security group, Volume type) vs. Cloudscape's single-selection criteria table** (which recommends Radio group/Tiles for 2-7 options and Select for 8+ options): suppressed. `VPC_OPTIONS`, `SUBNET_OPTIONS`, and `SECURITY_GROUP_OPTIONS` are each hard-coded to exactly one mock entry, and `REGION_OPTIONS`/`INSTANCE_TYPE_OPTIONS`/`VOLUME_TYPE_OPTIONS` to two; but these are plainly stand-in/demo data for account-specific, API-populated resource pickers (AWS regions, instance types, VPCs, subnets, security groups) whose real-world cardinality is unknown from this file and plausibly 8+ in production. This skill's own rule against resolving an intent-dependent judgment from "a property of the data itself, like a column's cardinality" applies directly here — using this fixture's mocked option counts to argue for Radio group/Tiles would be exactly that mistake, so the candidate is suppressed rather than reported.
- **Volume size (GB) as a plain `Input` vs. Cloudscape's `Slider`** (whose own "Do" guidance names "storage capacity" as a canonical slider use case): suppressed. That same guidance requires pairing a slider with an accompanying input "where a precise numeric value is required," which is exactly the case for a specific GB value in an infrastructure-provisioning form; the currently-used bare `Input` already supplies that precise-entry mechanism, so replacing it does not read as a documented directional preference — closer to an equally-valid alternative than a material gap.
- **Absence of `BreadcrumbGroup` and an `AppLayout`-level `contentType="form"` wrapper**, both named as building blocks in the create-resource patterns: not reported, insufficient evidence rather than a confirmed finding. Breadcrumbs and the app-shell layout are conventionally supplied by a wrapping layout/router shell, and this review is bounded to the single `CreateEnvironment.tsx` file with no visibility into what wraps it — their absence here cannot be attributed to a page-level composition choice without evidence this review is not permitted to gather.

## Orientation notes

- **Checkbox usage** (`publicIp` line 170, `encryptVolume` line 188, `detailedMonitoring` line 196) checked against Cloudscape's Boolean-selection criteria table and confirmed correct: all three settings only take effect when the form is submitted via "Create environment" (none causes an immediate, visible change the way a `Toggle` implies), matching the table's Checkbox row ("The selection takes effect at form submission") rather than its Toggle row.
- **`Container` + `Header variant="h2"` + `SpaceBetween size="l"` grouping** used for all six sections is the standard, documented composition for grouped form sections under both the Container component's own guidance and the create-resource patterns' "Container" building block; confirmed as native, unremarkable usage.
- **Top-level `Form` with `actions` containing a horizontal `SpaceBetween` of a link-style Cancel button and a primary submit button** (lines 96-105) matches the Form component's documented action-button composition.
- **`Select` for Region/Instance type/VPC/Subnet/Security group/Volume type as a concept** (as distinct from the suppressed cardinality question above) is a semantically correct choice for single-item selection from a resource-identifier list; no issue with using `Select` for this job in principle.

## What was not evaluated

Implementation correctness was not evaluated, including: whether `preventDefault` on the native `<form onSubmit>` (line 94) combined with `Form`'s own `actions` is the recommended wiring; use of `type="number"`/`type="email"` on `Input` and any associated numeric/email validation; the fact that no field on this page carries `errorText`, `invalid`, or any other validation wiring despite Cloudscape's create-flow guidance emphasizing validation; controlled-value handling of `Select`/`SelectProps.Option` objects; and any accessibility-mechanics details (ARIA wiring, focus order) on the already-correctly-chosen components. General UX and product judgment were also not evaluated, including: whether six is the right number of logical groupings, the reasonableness of the supplied defaults, copy/wording quality, and overall information density — none of this was assessed, and its absence here should not be read as "checked and fine."
