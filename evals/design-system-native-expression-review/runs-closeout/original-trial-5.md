# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A single page that lets a user configure and create a new cloud "environment" resource in one submission — naming/describing it, choosing a region, sizing compute (instance type/count and an auto-scaling range), configuring networking (VPC/subnet/security group/public IP), configuring storage (volume type/size/encryption), configuring monitoring (detailed monitoring, log retention, alert email), and assigning resource metadata tags (owner, cost center, environment) — then submitting via a single "Create environment" action. This reads as an infrastructure-provisioning creation flow closely analogous to a cloud console's resource-launch form (e.g., an EC2-style "launch" flow).

**Packages / versions:** Resolved via `resolve_versions.py` against `package.json`/`package-lock.json`: `@cloudscape-design/components` `^3.0.900` → locked `3.0.900`; `@cloudscape-design/collection-hooks` `^1.0.60` → locked `1.0.60`; `@cloudscape-design/global-styles` `^1.0.45` → locked `1.0.45`. All fully resolved (no unresolved semver ranges), so current Cloudscape docs apply without a version-drift caveat.

**Authority categories found in this corpus:** Cloudscape's discovery index (`llms.txt`) exposes both **component guidance** (per-component pages such as Wizard, Tag Editor, Checkbox, Toggle) and a distinct **named pattern** tier under `/patterns/` (e.g., "Create resource," "Single page create," "Multipage create," "Selection in forms"), including at least one explicit decision/criteria table comparing patterns. This corpus does have a task/pattern layer, so composition-level questions can be evaluated against named-pattern authority rather than dropping straight to component-page inference.

## Findings

### Finding 1: Single long-form page for a 6-domain, ~20-field resource creation exceeds Cloudscape's own documented threshold for "single page create" and lands squarely in "multipage create" (Wizard) territory

- **Finding:** The surface implements the entire "create environment" task as one `Form` containing six stacked `Container`s (General, Compute, Networking, Storage, Monitoring, Tags) with roughly 20 field-level controls, all in the primary/visible section with no "Additional settings" deferral. Cloudscape's own create-resource decision table places this shape in the "multipage create" (Wizard) band, not "single page create."
- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** as stated above — a one-shot, multi-domain resource-provisioning creation flow.
- **Repository evidence:** `CreateEnvironment.tsx` — confirmed via `inspect_surface.py`: 6 `Container` elements, 17 `FormField` elements plus 3 standalone `Checkbox` elements (≈20 distinct field-level controls total: `envName`, `description`, `region`, `instanceType`, `instanceCount`, `autoScalingMin`, `autoScalingMax`, `vpc`, `subnet`, `securityGroup`, `publicIp`, `volumeType`, `volumeSize`, `encryptVolume`, `detailedMonitoring`, `logRetentionDays`, `alertEmail`, `ownerTag`, `costCenterTag`, `environmentTag`), one `Form` (lines 95-222), one `Header variant="h1"` page title ("Create environment," line 93) and per-container `Header variant="h2"` sub-titles (General/Compute/Networking/Storage/Monitoring/Tags, lines 108, 126, 147, 176, 194, 208). None of these fields sit in an expandable/optional section — every field is directly visible in the primary flow.
- **Authority evidence:** Cloudscape's "Create resource" pattern page (`/patterns/resource-management/create/`) states the pattern options and gives an explicit criteria table. Authority category: **named pattern**. Full table, reproduced verbatim:

  | | Modal | Single page create | Multipage create |
  | --- | --- | --- | --- |
  | Length | = 1 field | Between 2 and 15 fields in the primary section or up to 5 groups of settings | More than 16 fields in primary sections or more than 5 groups of settings |
  | Complexity | Basic text input fields and simple selects | Flow does not require any category to have its own page | Concepts require in-depth interactions that benefit from having their own page |
  | Recovery | Input is mutable after creation | Input mutable after creation | Input immutable after creation |
  | Error handling | In trigger page | In creation page | In every single step and in summary step |
  | Frequency | n/a | Frequent | Infrequent |
  | Sub-resource create | No | Yes | Yes |

  The same page states: "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms," and "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations." The Wizard component page (`/components/wizard/`) independently confirms: "A multi-page form that guides a user through a complex flow or a series of interrelated tasks."
- **Evidence mode:** VERBATIM (the decision table and the quoted recommendation sentence are copied directly from the fetched pattern page).
- **Applicability argument:** Addressing the four-point test:
  1. *Task match, not superficial shape match:* The Length row's own two triggers — "more than 16 fields in primary sections" **or** "more than 5 groups of settings" — are both independently met here (≈20 primary-section fields, 6 groups/`Container`s). This is the exact dimension the table uses to distinguish the two patterns, not an incidental resemblance.
  2. *Current implementation solves the same problem the composition addresses:* Yes — both single-page create and multipage create exist to let a user configure and submit a new resource in one flow; the current `Form` is doing exactly that, just via the pattern the docs reserve for shorter/simpler configurations.
  3. *Proposed alternative preserves the same task:* A Wizard restructuring (e.g., steps for General/Compute, Networking, Storage, Monitoring, Tags, plus an optional review step) still produces the same "create environment" submission with the same fields; it changes navigation structure, not product intent.
  4. *Materiality of the gap:* The surface exceeds both Length thresholds by a wide margin (≈20 vs. a 15-field ceiling; 6 vs. a 5-group ceiling), not a borderline 1-field overage. The Complexity row's multipage description — "concepts require in-depth interactions that benefit from having their own page" — is also a plausible fit for the Networking (VPC/subnet/security-group) and Storage (volume type/size/encryption) domains, though that reading is corroborating rather than load-bearing; the Length trigger alone already crosses the documented line.

  **Same-tier equivalence check:** The table assigns non-overlapping numeric bands per pattern (1 / 2–15 / 16+ fields; ≤5 / >5 groups) rather than presenting single-page and multipage as an unranked "use X or Y" pair for the same shape — so this is a differentiating table, not a tied one, and the anti-fundamentalism suppression for same-tier equivalence does not apply here.
- **Current expression:** One `ContentLayout` → `Form` → six sequential `Container`s, each holding all of that domain's fields directly (no expandable/optional sections, no step navigation, no review step).
- **Native expression:** A `Wizard` (per `/patterns/resource-management/create/multi-page-create/`) with steps grouping the same domains (e.g., General+Compute, Networking, Storage, Monitoring, Tags, optionally ending in a review step), keeping the existing `Container`/`FormField` building blocks inside each step — the multipage-create building-block guidance explicitly reuses `Container` and `FormField` inside the Wizard, so this does not discard the current low-level composition, only its single-page wrapper.
- **Why it matters:** Cloudscape's own criteria table is the mechanism it publishes for choosing between these two patterns, and this surface sits well past the documented single-page ceiling on both of the table's Length sub-criteria simultaneously. Left as a single page, all ~20 fields' validation errors surface together in one long scroll rather than being scoped per step-and-summary (the table's own "Error handling" row), which is a concrete, documented consequence of picking the smaller pattern for a configuration this large — not a generic "this feels long" complaint.
- **Boundary check:** This is a judgment about which documented Cloudscape creation composition (single-page `Form` vs. `Wizard`-based multipage create) fits the task, evaluated against Cloudscape's own published decision criteria — not a claim about any API misuse, prop, or accessibility mechanic, and not a generic usability preference.

### Finding 2: "Tags" as three fixed-label inputs vs. Cloudscape's `TagEditor` — intent-dependent

- **Finding:** The "Tags" container implements exactly three hard-coded fields ("Owner," "Cost center," "Environment tag") as plain `FormField`/`Input` pairs. Cloudscape ships a purpose-built `TagEditor` component whose stated job is letting users "create, edit, or delete resource tags" as arbitrary key/value rows, used specifically in create and edit flows. Whether `TagEditor` is the more native fit depends on intent this file does not resolve.
- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** attaching identifying/governance metadata (owner, cost center, environment classification) to the environment being created.
- **Repository evidence:** `CreateEnvironment.tsx` lines 208-220 — a `Container` headed "Tags" containing three `FormField`s ("Owner," "Cost center," "Environment tag"), each wrapping a plain `Input` bound to its own `useState` string (`ownerTag`, `costCenterTag`, `environmentTag`). There is no key selector, no "add"/"remove" affordance, and no mechanism to attach any tag beyond these three fixed ones.
- **Authority evidence:** Cloudscape's Tag Editor component page (`/components/tag-editor/`) — authority category: **component guidance**. Verbatim: "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." Its "Do" guidance: "Use the tag editor to manage tags only in create and edit flows." It further states: "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)," and describes built-in "Adding tag rows" / "Removing tag rows" functions via an "Add new tag" button, with a configurable tag limit (default 50).
- **Evidence mode:** VERBATIM (quoted sentences above are copied directly from the fetched component page).
- **Applicability argument:** The container's own heading is literally "Tags," and one field is named "Environment tag" — both signal that the author intends this section to represent AWS-style resource tags, which is precisely `TagEditor`'s documented purpose and this is a create flow, matching its "Do" guidance exactly. However, applicability point 3 (does the proposed alternative preserve the same task?) cannot be confirmed from this file: `TagEditor` is built for an *open, arbitrary* key/value tag set (any key, up to a configurable limit), whereas the current implementation enforces exactly three specific, pre-named attributes with no way to add a fourth or omit one — which could equally be a deliberate governance choice (mandatory fixed keys, no typo risk in key names) rather than an oversight. Nothing in the file indicates whether users are ever expected to attach tags beyond these three, or whether "Owner"/"Cost center"/"Environment" must remain fixed, required keys. Per the "Missing intent" rule, this is not resolved by guessing.
- **Current expression:** Three independent `FormField`/`Input` pairs with fixed, hard-coded labels, each backed by its own string state.
- **Native expression:** Uncertain by design — *if* the intent is open-ended AWS-style resource tagging, a `TagEditor` (optionally pre-seeded with "Owner"/"Cost center"/"Environment" rows) is the documented native fit; *if* the intent is a fixed, mandatory three-attribute metadata schema, the current fixed-field approach may already be appropriate and `TagEditor`'s arbitrary-key model would weaken that enforcement. Both readings are named; neither is asserted as the recommendation.
- **Why it matters:** If the open-tagging reading is correct, the current fixed schema silently forecloses any tag beyond the three baked in, which is a real functional gap `TagEditor` exists to close (add/remove rows, a documented 50-tag limit, and inline key/value validation this surface has none of). If the fixed-schema reading is correct, no change is warranted. Naming what would resolve it: whether product requirements call for users to attach tags beyond Owner/Cost center/Environment, or whether exactly these three keys are mandated and closed.
- **Boundary check:** This is a question of whether the design system's purpose-built resource-tagging component is the right vocabulary choice for this section versus bespoke fixed fields — not an implementation defect (nothing here is mechanically wrong) and not a generic UX complaint (it turns on a specific documented component's stated purpose, not on density/hierarchy/flow).

## Suppressed (low materiality or weak applicability)

- **Auto-scaling minimum/maximum as two independent `Input type="number"` fields** — considered whether a paired-range control would be more native, but no Cloudscape component or documented composition for a numeric min/max range pair was found in the retrieved corpus; would require inventing an authority tier this corpus doesn't expose. Suppressed as `INFERRED`-only with no citable support.
- **VPC → Subnet → Security group as three independent, statically-populated `Select`s** — a cascading/filtered-selection composition might be more native if subnet/security-group options actually depended on the chosen VPC, but the code shows all three option lists as static, unrelated arrays (`VPC_OPTIONS`, `SUBNET_OPTIONS`, `SECURITY_GROUP_OPTIONS`), so there's no evidenced dependent-selection behavior in this surface to judge a composition mismatch against. Naming it would require assuming behavior the code doesn't show.

## Orientation notes

- The per-domain `Container` + `Header variant="h2"` + `FormField` composition, the page title "Create environment," and the button pair "Cancel" (link variant, `formAction="none"`) / "Create environment" (primary, `formAction="submit"`) all match the *Single page create* pattern's own building-block and writing guidance verbatim (page titles "begin with an active verb," e.g. "Create distribution"; submit button format "[Active verb] [resource type]"; exit button labeled "Cancel"). The micro-level composition inside each section is not itself the problem — only the macro-level choice of wrapping it in a single page instead of a Wizard (Finding 1).
- `Checkbox` is the correct choice for "Assign a public IP address" (line 170), "Encrypt volume" (line 188), and "Enable detailed monitoring" (line 196): all three only take effect when the form is submitted via the "Create environment" button, which is exactly the case Cloudscape's Toggle guidance excludes ("Don't use a toggle for options that are activated at form submission... use a checkbox instead") and Checkbox's own guidance covers ("Don't use for options that take immediate effect... Use a toggle instead"). `Toggle` would be the documented misfit here, not `Checkbox`.
- `Select` is used for six fixed, short, enumerable choices (Region, Instance type, VPC, Subnet, Security group, Volume type), which is its documented job; none of these need on/off-state descriptions that would point to `Tiles` or a `RadioGroup` instead.
- `Textarea` for the free-form "Description" field (line 113-114) is the correct choice over `Input` for multi-line text.

## What was not evaluated

Implementation correctness was not evaluated: prop usage, `SelectProps`/`WizardProps` typing, the raw `<form onSubmit={(e) => e.preventDefault()}>` element wrapping the Cloudscape `Form`, numeric-field validation (or its absence) on `instanceCount`/`autoScalingMin`/`autoScalingMax`/`volumeSize`/`logRetentionDays`, the unvalidated `alertEmail` field, and any accessibility mechanics on already-correctly-chosen components are all out of this skill's scope regardless of whether they contain defects. General UX/product judgment (information density, section ordering, whether "environment" is the right product concept at all) was likewise not evaluated — silence on these should not be read as "checked and fine," only as out of scope for this review.
