# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A user creates a new cloud "environment" (a compute/network/storage resource bundle: instance type/count, autoscaling, VPC/subnet/security group, a storage volume, monitoring/alerting, and organizational tags) by filling out a single form and submitting it once via a "Create environment" action. There is no evidence of editing an existing environment (all fields carry creation-time initial state; `createEnvironment` is called once, on submit).

**Packages / versions:** Resolved from `package-lock.json` (exact, not ranges):
- `@cloudscape-design/components`: declared `^3.0.900`, locked `3.0.900`
- `@cloudscape-design/collection-hooks`: declared `^1.0.60`, locked `1.0.60`
- `@cloudscape-design/global-styles`: declared `^1.0.45`, locked `1.0.45`

**Authority categories found in this corpus:** Cloudscape exposes both **component guidance** (per-component pages, mostly brief one/two-line "what it is" statements plus a separate Usage tab) and **named patterns** with explicit decision/criteria tables — a "Resource Management" pattern family (`Create resource`, with `Single page create`, `Multipage create` (Wizard-based), `Modal`, and `Sub-resource create` as documented, cross-linked variants, plus an explicit criteria table comparing them) and "General" patterns (e.g., `Selection in forms`, which also carries explicit criteria tables for single-selection, multi-selection, and boolean-selection component choice). This corpus does have a genuine pattern/composition tier, not just component pages — reasoning below draws on it directly rather than manufacturing it.

## Findings

### Finding 1

- **Finding:** The surface renders all 6 configuration groups (General, Compute, Networking, Storage, Monitoring, Tags — 20 inputs total) as a single, single-submit page, which is past the size Cloudscape's own documented decision criteria assign to `Single page create`; its `Create resource` pattern's criteria table routes this volume of configuration to `Multipage create` (Wizard).
- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Creating a new environment resource with compute, networking, storage, monitoring, and tagging configuration, submitted once via a "Create environment" action.
- **Repository evidence:** `CreateEnvironment.tsx` renders one `ContentLayout` > `Form` (lines 93–95) containing six `Container`s, each with its own `Header variant="h2"`: General (108), Compute (126), Networking (147), Storage (176), Monitoring (194), Tags (208) — all visible simultaneously, with a single `SpaceBetween` (107) stacking them and a single pair of Cancel/Create action buttons (96–105). `inspect_surface.py` confirms 17 `FormField` instances plus 3 `Checkbox` instances (public IP, encrypt volume, detailed monitoring) — 20 distinct configuration inputs — with no step/wizard navigation anywhere in the file.
- **Authority evidence:**
  Authority category: **named pattern** (Cloudscape's "Create resource" pattern, `https://cloudscape.design/patterns/resource-management/create/`), which states: "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms." and "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations." The same page publishes this full criteria table (reproduced in full, not excerpted):

  |  | Modal | Single page create | Multipage create |
  | --- | --- | --- | --- |
  | Length | = 1 field | Between 2 and 15 fields in the primary section or up to 5 groups of settings | More than 16 fields in primary sections or more than 5 groups of settings |
  | Complexity | Basic text input fields and simple selects | Flow does not require any category to have its own page | Concepts require in-depth interactions that benefit from having their own page |
  | Recovery | Input is mutable after creation | Input mutable after creation | Input immutable after creation |
  | Error handling | In trigger page | In creation page | In every single step and in summary step |
  | Frequency | n/a | Frequent | Infrequent |
  | Sub-resource create | No | Yes | Yes |

  Separately, the `Single page create` pattern page (`.../create/single-page-create/`) defines what a "group of settings" is in this table: building block "C. Container — In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout." That page's own "Do" guidance also says: "Group related input fields together under a subheading if there are multiple types of configuration inputs" — describing exactly the one-container-per-category shape this surface already uses.
- **Evidence mode:** SYNTHESIS — the directional claim ("this surface's shape falls on the Multipage side of the table") combines two cited sources: (1) the Length row's numeric ceiling, "up to 5 groups of settings" for single-page vs. "more than 5 groups of settings" for multipage, and (2) the single-page-create page's definition of "container" as the unit corresponding to a "group of settings." Neither page alone states "6 containers = use Multipage"; the bridge (this fixture's 6 `Header`-labeled `Container`s are 6 "groups of settings" in the table's sense) is the reviewer's inferential step, made explicit here.
- **Applicability argument:** (1) The observed task — configuring one new resource across several distinct categories (compute, networking, storage, monitoring, tags) before a single creation action — is exactly the problem the `Create resource` pattern family addresses; this isn't a superficial shape match. (2) The current single-`Form`, single-container-per-category implementation is a textbook instance of the documented `Single page create` shape (one container per category, standard Form actions), so it is solving the same problem the pattern addresses, just via the sibling variant. (3) The alternative — `Multipage create` using `Wizard` — preserves the identical task; it does not add, remove, or repurpose any field, it only re-sequences the same six categories across steps with a review step. (4) Materiality: the table's Length criterion is a hard numeric split, not a stylistic note — 6 groups (General, Compute, Networking, Storage, Monitoring, Tags) exceeds "up to 5 groups of settings" and lands past the ">5 groups" line the table assigns to Multipage. This is not a tie: the table gives directional, non-overlapping numeric bands (single-page ends at 5 groups / 15 primary fields, multipage begins after that), so the "same-tier equivalence" caveat in the anti-fundamentalism rule does not apply here — there is no row in this table that places 6-groups-single-page and multipage in the same tier. The `Recovery`/`Error handling`/`Frequency` rows are not resolvable from this file (the fixture doesn't show whether fields are editable post-creation), but the guidance explicitly treats `Frequency` as a tiebreaker "only... if you're unsure" — Length alone already gives an unambiguous, non-tied answer, so the missing rows don't need to be guessed at to reach this conclusion.
- **Current expression:** A single `ContentLayout`/`Form`/`Container`×6 page, all fields always visible, one submit action.
- **Native expression:** A `Wizard`-based multipage create flow (Cloudscape's documented "Multipage create" building blocks: navigation pane, per-step `Container`s carrying the same six categories — possibly consolidated into 3–5 steps per that pattern's "we recommend using three to five pages" guidance — and an optional review step summarizing all fields before the create action), preserving every current field and default.
- **Why it matters:** This is Cloudscape's own documented decision boundary for exactly this kind of surface, not a stylistic preference — a Cloudscape-fluent implementer reading the `Create resource` pattern's criteria table against a 6-group, 20-field creation form would recognize it sitting past the table's `Single page create` ceiling and would reach for `Wizard`, which also brings along documented, cross-linked support this surface currently lacks entirely (a review step, per-step validation/error scoping, unsaved-changes-on-exit handling scoped per the multipage pattern).
- **Boundary check:** This is a judgment about which top-level, documented create-resource composition (single-page `Form` vs. `Wizard`-based multipage) fits this task's already-observed field/group volume — not a claim about how the existing `Form`/`Container` markup is coded, and not a generic "this page feels long" complaint; the recommendation is anchored to a specific, quoted numeric criterion in Cloudscape's own pattern documentation.

### Finding 2

- **Finding:** The surface shows all 20 inputs unconditionally, with no `ExpandableSection`-based "additional settings" grouping, even though the component's own default values already distinguish which fields are user-decision-required versus which already have a workable default — exactly the split Cloudscape's create-resource pattern documents as "primary" vs. "additional expandable section."
- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** medium
- **User task:** Same as Finding 1 — creating a new environment resource via a form.
- **Repository evidence:** State initialization shows a clear default/no-default split: `envName` and `description` start as empty strings with no default (lines 36–37), as do the three tag fields `ownerTag`/`costCenterTag`/`environmentTag` (63–65). Nearly everything else already carries a concrete, working default: `region` defaults to `REGION_OPTIONS[0]` (38), `instanceType` to `INSTANCE_TYPE_OPTIONS[0]` with `instanceCount='2'` (41–42), `autoScalingMin='1'`/`autoScalingMax='4'` (43–44), `vpc`/`subnet`/`securityGroup` each default to their (sole) option with `publicIp=false` (47–50), `volumeType` defaults with `volumeSize='100'` and `encryptVolume=true` (53–55), and `detailedMonitoring=false` with `logRetentionDays='30'` (58–59). `inspect_surface.py`'s import list contains no `expandable-section` import, and `jsx_tag_counts` contains no `ExpandableSection` — confirmed absent from the file. All 20 inputs nonetheless render unconditionally inside their `Container` (lines 108–220), with no expand/collapse affordance anywhere.
- **Authority evidence:** Authority category: **named pattern**, same "Create resource" family, `Single page create` page building blocks: "D. Primary form fields — Keep the primary configuration section as short as possible. Criteria for primary section inputs: Any required field that we can't provide a good default for. For example: password. Any field that 80% or more of users would expect to see, and want to know the value of in order to be successful." and "E. Additional expandable section - optional — Place as many inputs as possible into the additional settings section for each resource card. This allows the user to keep the primary section as short as possible, so the user can focus on the most important tasks." This is carried into the `Multipage create` page too (building block "I. Additional expandable section — If necessary, include a section for advanced configuration. Follow the guidelines on single page create. Any additional settings present in a form should persist on the review page and be closed by default."), so it applies regardless of how Finding 1 is resolved.
- **Evidence mode:** SYNTHESIS — the guidance states the primary/additional criteria abstractly ("a required field we can't provide a good default for" vs. everything else); the claim that *this file's own fields* sort cleanly along that line is the reviewer's bridge from the cited criteria to this file's `useState` defaults, made explicit above.
- **Applicability argument:** (1) The task-level problem the building block addresses — keeping a creation form's mandatory decision surface short by deferring already-defaulted settings — is exactly what this file's own initial-state choices already imply is possible (12 of the file's ~17 non-tag fields already have a working default baked into `useState`). (2) The current implementation is solving the same underlying problem (it already computed sensible defaults) but doesn't apply the documented UI structure that would let users benefit from those defaults by skipping past them. (3) An `ExpandableSection`-based additional-settings grouping preserves the same task and every field — it only changes default visibility. (4) Materiality: this isn't a stylistic nit — the pattern's own stated purpose for the split ("allows the user to keep the primary section as short as possible, so the user can focus on the most important tasks") is materially unmet when literally none of the 20 inputs are deferred, despite most already carrying safe defaults; no row in the criteria table treats this omission as an acceptable alternative — it's a documented building block ("D"/"E"), not an unranked option.
- **Current expression:** All fields, defaulted or not, always visible inside their respective `Container`, no `ExpandableSection` usage anywhere.
- **Native expression:** Retain `envName`, `description`, `region` (and likely the three tag fields, which have no default) as the always-visible primary section; move the remaining, already-defaulted fields (instance/autoscaling, VPC/subnet/security-group/public-IP, volume type/size/encryption, detailed monitoring/log retention/alert email) into one or more `ExpandableSection`s labeled per their container's heading (e.g., "Additional compute settings"), collapsed by default, per the pattern's explicit guidance.
- **Why it matters:** The pattern's own building blocks tie the primary/additional split directly to "good default" status — this file already computed which fields qualify, but doesn't act on that distinction in the UI, so the create-resource pattern's stated goal (a short, decision-only primary section) goes unmet even though the data needed to satisfy it already exists in the component.
- **Boundary check:** This concerns whether the documented primary/additional-settings composition (and the `ExpandableSection` component it depends on) was adopted for a task that visibly qualifies for it by the pattern's own stated criteria — not a generic "this form is too long" opinion, and not an implementation-mechanics complaint about how `useState` is wired.

## Suppressed (low materiality or weak applicability)

- **Select vs. Radio group/Tiles for Region, Instance type, VPC, Subnet, Security group, Volume type.** Cloudscape's `Selection in forms` pattern publishes a criteria table (`Radio group`/`Tiles`: 2–7 options; `Select`/`Autosuggest`: 8+ options) that, taken at face value against this file's hard-coded option arrays (1–2 options each), would point toward Radio group/Tiles. Suppressed: the option arrays are evidently placeholder/stub data (`REGION_OPTIONS` lists 2 of AWS's 30+ real regions; `VPC_OPTIONS`/`SUBNET_OPTIONS`/`SECURITY_GROUP_OPTIONS` each hard-code exactly one entry), and for account-scoped resources like VPC/subnet/security group the real cardinality is inherently user- and account-dependent and unbounded — this bounded file gives no reliable signal of true production option counts, so the table's "number of options" criterion can't be honestly evaluated here.
- **Auto-scaling minimum/maximum as two separate numeric `Input`s.** Checked whether Cloudscape documents a dual-handle/range control for this shape. `Slider` (`https://cloudscape.design/components/slider/`) is documented as single-value only ("A slider enables users to select a value within a defined range" — one value, not a min/max pair); no dual-range component or pattern exists in this corpus. No native alternative to recommend, so not reported.
- **Gating "Log retention" / "Alert email" behind "Enable detailed monitoring" as a progressive-disclosure sub-option.** The `Selection in forms` pattern documents boolean-selection sub-options ("Boolean options can be used to turn on/turn off a group of sub-options"), which would apply if these fields were dependent on detailed monitoring. Suppressed: nothing in the file establishes that dependency, and in AWS terms detailed monitoring (metric granularity) is conventionally independent of log retention or alert-email configuration — asserting the dependency would be inventing product logic the surface doesn't support.

## Orientation notes

- **`Checkbox` (not `Toggle`) for "Assign a public IP address," "Encrypt volume," "Enable detailed monitoring."** Confirmed correct: the `Selection in forms` pattern's boolean-selection criteria table states Checkbox's selection "takes effect at form submission" while Toggle's "results in an immediate change" (e.g., turning on dark mode); the pattern's guidance reinforces this: "Binary choices made by using checkboxes, radio groups, and tiles should take effect at form submission, for example in a creation or edit flow. Use a toggle for an option that takes effect immediately." All three booleans here only take effect when "Create environment" is submitted (handleSubmit collects them into one payload, lines 67–90) — matching documented Checkbox usage exactly.
- **Overall `ContentLayout` > `Header` (h1) > `Form` > `Container` (h2 each) > `FormField` skeleton.** This is a recognized, valid instance of the `Single page create` pattern's building blocks (page header, one container per configuration category, standard form action buttons) — the base composition shape itself is sound; Finding 1 argues the field/group volume has outgrown it, not that the skeleton is wrong in kind.
- **`Tags` section as three discrete `Input` fields (Owner, Cost center, Environment tag) rather than the `tag-editor` component.** Considered as a candidate finding: Cloudscape ships `tag-editor`, described as "an extension of the attribute editor... with the tag editor, users can create, edit, or delete resource tags," and the three field labels here closely mirror common AWS cost-allocation tag keys. Not reported as a finding: the cited documentation is a single descriptive sentence with no comparative "when to use tag-editor vs. discrete fields" guidance, and this file's own evidence is genuinely ambiguous between two readings — (a) these are meant to be arbitrary, extensible AWS resource tags (favoring `tag-editor`'s add/remove key-value UI), or (b) these are three fixed, organization-mandated metadata fields with a closed schema (favoring the current discrete-`Input` approach), since the code shows no add/remove affordance and treats all three as ordinary flat fields in the submit payload (lines 86–88) identically to every other field. Nothing in this bounded file resolves which reading applies (e.g., whether the backend models tags as an open map or as three named properties), so this is named here rather than reported as a finding or as `intent-dependent` in the Findings section, per the instruction that naming a candidate without pressing a direction is sometimes the right call even without formally filing it.

## What was not evaluated

Implementation correctness — the raw `<form onSubmit>` wrapper mechanics, `useState`-per-field state management, `type="number"`/`type="email"` prop usage on `Input`, absence of client-side validation/error state on any `FormField`, the `console.log` stub standing in for a real submit handler, and any accessibility/ARIA mechanics on already-correctly-chosen components — was not assessed; that is a distinct, lower-level concern this skill does not own. General UX or product judgment (whether six categories are the right taxonomy, how burdensome the form feels, information-architecture opinions beyond what Cloudscape's own documented criteria establish) was likewise not evaluated.
