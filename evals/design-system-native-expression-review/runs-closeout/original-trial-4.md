# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A single-page "create resource" flow for provisioning a cloud compute environment (region, instance type/count with auto-scaling bounds, VPC/subnet/security group/public IP, EBS-style volume, monitoring/alerting, and resource tags), submitted via one "Create environment" action. This reads as a standard infrastructure-provisioning create form, not a wizard-style guided setup, an edit/detail view, or a resource-collection/management view.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked and resolved to `3.0.900`. `@cloudscape-design/collection-hooks` declared `^1.0.60`, resolved to `1.0.60` (not directly imported by this file). `@cloudscape-design/global-styles` declared `^1.0.45`, resolved to `1.0.45` (not directly imported by this file). All three fully resolved via lockfile — no unresolved semver ranges affecting applicability of the guidance below.

**Authority categories found in this corpus:** Component guidance (individual component pages, e.g. Tag editor) and named patterns (the "Create resource" family — Create resource, Single page create, Multipage create, Defaults — and general patterns such as "Selection in forms"), including explicit decision/criteria tables embedded in pattern pages (a Length/Complexity/Recovery/etc. table differentiating Modal/Single page create/Multipage create; an option-count/metadata table differentiating Radio group/Tiles/Select/Autosuggest). This is a genuine composition/pattern tier, distinct from and more specific than the component pages, and it is used below as the primary authority wherever a named pattern directly addresses the candidate judgment.

## Findings

### Finding 1: Fixed "Tags" inputs where Cloudscape ships a purpose-built resource-tagging component

- **Finding:** The "Tags" section is built from three individually hardcoded `Input` fields ("Owner", "Cost center", "Environment tag") instead of the `TagEditor` component that Cloudscape documents specifically for resource-tag key/value data in create flows.
- **Type:** component selection
- **Materiality:** high
- **Confidence:** medium — the applicability match is strong, but see the caveat under "Applicability argument" about whether these three keys are meant to be a locked, mandatory schema rather than free-form tags.
- **User task:** Attaching resource-tag metadata (owner, cost center, environment) to the environment being created, as part of the same single "Create environment" submission.
- **Repository evidence:** `src/pages/CreateEnvironment.tsx` lines 62-65 declare three independent string-state hooks (`ownerTag`, `costCenterTag`, `environmentTag`); lines 208-220 render a `Container` headed "Tags" containing three separate `FormField`/`Input` pairs labeled "Owner", "Cost center", and "Environment tag"; lines 86-88 pass these three fixed keys straight into the submission payload alongside the rest of the form. There is no dynamic key/value structure anywhere in the file — the tag "keys" are the field labels themselves, hardcoded at the JSX level.
- **Authority evidence:** Cloudscape's Tag editor component page (`https://cloudscape.design/components/tag-editor/`), authority category `component guidance`:
  - "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags."
  - "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)."
  - Under "General guidelines / Do": "Use the tag editor to manage tags only in create and edit flows."
- **Evidence mode:** VERBATIM (quotes above are copied character-for-character from the fetched page, re-checked against the raw fetched text before inclusion).
- **Applicability argument:** Applying the anti-fundamentalism four-point test: (1) the observed task — collecting owner/cost-center/environment metadata to attach to a newly created resource — is not a superficial shape match, it is exactly the "metadata assigned to a resource, consisting of a key... and a value" problem the Tag editor's own description states; "Owner", "Cost center", and "Environment" are themselves among the most common real-world AWS resource-tag keys. (2) The current implementation solves substantially the same problem: three text inputs that are, functionally, three tag rows with fixed keys. (3) This is the point of genuine uncertainty: Tag editor's rows normally expose editable keys, so swapping in Tag editor as-is would let a user rename or delete the "Owner"/"Cost center"/"Environment" keys — if this app enforces those three tags as a mandatory, locked governance schema (plausible, and not ruled out by the code), a bare Tag editor would not preserve that constraint without additional seeding/lock-down logic on top of it. (4) Materiality is still high because Cloudscape ships a component whose stated purpose is precisely this UI concept, and a Cloudscape-fluent implementer reaching for three ad hoc `Input` fields to represent "resource tags" would be a visible outlier next to any other tagging surface in the same app family (Tag editor is also used, per its own guidance, "only in create and edit flows" — exactly the flow this page is). Given the point-3 caveat, this is reported as a real, high-materiality opportunity rather than a certainty about the exact replacement shape.
- **Current expression:** Three independently labeled `Input` components inside a "Tags" `Container`, each bound to its own `useState` string.
- **Native expression:** A single `TagEditor` bound to a `tags` array in state (optionally seeded with the three keys pre-populated if they must remain mandatory, with any additional tags added/removed through the component's built-in add/remove/undo affordances), replacing the three fixed `Input`/`FormField` pairs.
- **Why it matters:** Cloudscape's tag editor is not just "a component that exists for tags" — it carries integrated validation (key/value length limits, duplicate-key detection, reserved `aws:` prefix rejection), tag-limit handling, and standard interaction/writing conventions that this hand-rolled version does not get for free and would have to reimplement piecemeal as more tags are needed. It is also the composition an experienced Cloudscape/AWS-console implementer would expect for a "Tags" section in a create flow, making this surface an outlier relative to the rest of a Cloudscape-based application.
- **Boundary check:** This is a judgment about which Cloudscape component represents the "resource tags" concept (Tag editor vs. three hardcoded `Input` fields) — not a critique of the `Input` fields' own implementation (labels, validation, controlled-value wiring) or a general "this form has too many fields" usability complaint.

### Finding 2: Flat, always-visible form structure diverges from the documented single-page-create composition

- **Finding:** The page lays out roughly 20 fields across 6 always-visible top-level `Container`s (General, Compute, Networking, Storage, Monitoring, Tags) with no primary/additional-configuration split and no `ExpandableSection` anywhere, even though most of these fields already ship with code-level defaults. This diverges from Cloudscape's documented single-page-create composition, which calls for a short, defaults-driven primary section plus an additional-configuration expandable section, generally within a single container.
- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Same as above — a single-page create flow for a compute environment, submitted with one primary action, where most configuration already has sensible defaults (region, instance type/count, auto-scaling bounds, VPC/subnet/security group, volume type/size, encryption, monitoring, log retention) and only a handful of fields are inherently required or default-less.
- **Repository evidence:** Lines 36-65 show the majority of state hooks already initialized with concrete defaults (`region` → `REGION_OPTIONS[0]`, `instanceType` → `INSTANCE_TYPE_OPTIONS[0]`, `instanceCount` → `'2'`, `autoScalingMin`/`autoScalingMax` → `'1'`/`'4'`, `vpc`/`subnet`/`securityGroup` → their first option, `volumeType` → `VOLUME_TYPE_OPTIONS[0]`, `volumeSize` → `'100'`, `encryptVolume` → `true`, `detailedMonitoring` → `false`, `logRetentionDays` → `'30'`); only `envName`, `description`, `alertEmail`, `ownerTag`, `costCenterTag`, and `environmentTag` start empty. Lines 107-221 render this as 6 parallel `Container`s (General 108-124, Compute 126-145, Networking 147-174, Storage 176-192, Monitoring 194-206, Tags 208-220), each always rendered, each with equal visual weight; `scripts/inspect_surface.py` confirms `Container: 6`, `FormField: 17` and no `ExpandableSection` import/usage anywhere in the file.
- **Authority evidence:** Cloudscape's "Single page create" pattern page (`https://cloudscape.design/patterns/resource-management/create/single-page-create/`), authority category `named pattern`:
  - "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms."
  - "One-click to create: Use good defaults in as many inputs as possible to allow users to simply click the Create button to have a running resource."
  - "Be critical of the inputs you place in the primary section, and keep it as short as possible."
  - Criteria for primary-section inputs: "Any required field that we can't provide a good default for. For example: password." / "Any field that 80% or more of users would expect to see, and want to know the value of in order to be successful. For example: Knowing the security group associated with the resource, even when we provide a good default."
  - "Additional expandable section — optional: Place as many inputs as possible into the additional settings section for each resource card. This allows the user to keep the primary section as short as possible, so the user can focus on the most important tasks."
  - Container building block: "In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout. For example: Choosing a database type."
- **Evidence mode:** VERBATIM (all quotes copied character-for-character from the fetched pattern page and re-checked before inclusion; all come from this single named-pattern page, not combined across sources).
- **Applicability argument:** (1) The task materially matches the pattern's stated problem — this is explicitly a single-page, one-action "create [resource]" flow, the exact scenario the pattern targets, not a superficially similar but different task. (2) The current implementation solves the same problem the pattern addresses (resource creation via a form) but does so without the pattern's core mechanism (defaults-driven primary/additional split). (3) The proposed native expression — collapsing most of the current containers' contents into one or more "additional configuration" expandable sections, keeping only genuinely primary fields always visible — preserves the exact same task and payload; nothing about the resource being created changes. (4) Materiality is high and concrete, not a stylistic nit: applying the pattern's own two-part criteria, only `Environment name` (required, no viable default) and plausibly `Region` (has a default, but is the pattern's own example of a field users want to see/control "even when we provide a good default") clearly belong in a primary section; the other ~15+ fields (instance sizing, auto-scaling bounds, VPC/subnet/security group, public IP, volume type/size/encryption, monitoring/log retention/alerts) already carry defaults and match none of the primary-section criteria, yet all are rendered flat and always-visible across 5 additional containers rather than housed in an additional-configuration section — a direct, multi-point divergence from the pattern's stated building blocks, not a single minor deviation.
- **Current expression:** Six parallel, always-expanded `Container`s of roughly equal visual weight, with no distinction between fields that need up-front attention and fields that already have working defaults.
- **Native expression:** A structure closer to a single (or minimally split) primary container holding only `Environment name` and `Region`, plus one or more "Additional configuration" `ExpandableSection`s (labeled as nouns per the pattern's writing guidance, e.g. "Compute settings", "Networking settings", "Storage settings", "Monitoring settings") housing the remaining, already-defaulted fields — closed by default, consistent with "place as many inputs as possible into the additional settings section."
- **Why it matters:** The mismatch is not cosmetic: the pattern's whole mechanism for keeping a create flow fast ("one-click to create") depends on separating the few fields users must actively decide from the many fields that already have good defaults. Presenting all ~20 fields with equal, always-visible weight defeats that mechanism and is also the more consistency-costly choice for an app otherwise built on Cloudscape's create-flow conventions, since this is the specific, well-documented pattern for exactly this task.
- **Boundary check:** This is a composition-level judgment about how Cloudscape's own single-page-create building blocks (primary vs. additional-configuration section, container count) should structure this specific create-resource task — not a critique of `Form`/`Container`/`FormField` prop usage or accessibility mechanics, and not a generic "this form is too long" complaint untethered to a specific documented composition.

## Suppressed (low materiality or weak applicability)

- **Select vs. Radio group/Tiles for Region, Instance type, and Volume type.** Cloudscape's "Selection in forms" pattern documents an explicit single-selection criteria table (`Radio group`/`Tiles`: 2 to 7 options; `Select`/`Autosuggest`: 8+ options), and the current `REGION_OPTIONS`, `INSTANCE_TYPE_OPTIONS`, and `VOLUME_TYPE_OPTIONS` arrays each hold only 2 entries — below the documented `Select` threshold. Suppressed because this is very likely a fixture/stub-data artifact rather than evidence about real option cardinality: real-world AWS regions (dozens) and EC2 instance types (hundreds) are well above the 8-option `Select` threshold regardless of what this stub happens to declare, so recommending `Radio group`/`Tiles` here would likely be wrong once real data replaced the stub — exactly the "same shape, different problem" trap the anti-fundamentalism rule warns against. Volume type (`gp3`/`io2`, i.e., EBS volume types) is the one case where the real domain enumeration is plausibly small and stable, but the code alone doesn't establish that scope with confidence, so it is named here rather than reported as a finding. (`VPC_OPTIONS`/`SUBNET_OPTIONS`/`SECURITY_GROUP_OPTIONS` are not included in this suppression at all — those are account-scoped resource lists that are typically open-ended, so `Select` is the appropriate tier for them regardless of the single stub entry each currently holds.)
- **Multipage create (Wizard) instead of single-page create.** The "Create resource" pattern's own Length criteria ("More than 16 fields in primary sections or more than 5 groups of settings" → multipage create) look superficially crossed by this surface's ~20 fields across 6 containers. Suppressed because that criterion is defined over the *primary section* after the primary/additional triage described in Finding 2 — once triaged, the primary section here plausibly holds only `Environment name` (and perhaps `Region`), which sits well inside single-page create's own range. The correct fix is the restructuring in Finding 2, not a switch to Wizard; recommending Wizard here would be judging the surface by its current (undifferentiated) field count rather than by the pattern's own stated denominator.
- **Progressive disclosure of "Log retention (days)" / "Alert email" behind "Enable detailed monitoring".** Cloudscape's selection-pattern guidance documents checkbox-driven progressive disclosure for exactly this shape (a boolean gate revealing dependent settings). Suppressed as intent-dependent: the code doesn't establish whether log retention and alert email are meant to be conditional on *detailed* monitoring specifically, or are independent settings that apply regardless of the monitoring tier — naming a direction without that evidence would be guessing at product intent rather than reading it off the surface.

## Orientation notes

- `Header` is used correctly for both the page-level `h1` (inside `ContentLayout`) and every `Container`'s `h2`, and every container heading begins with a noun ("General", "Compute", "Networking", "Storage", "Monitoring", "Tags"), matching the single-page-create pattern's container-heading writing guidance.
- The form actions (lines 96-105) — a link-variant "Cancel" plus a primary "Create environment" button — match the documented single-page-create action-button structure and the writing convention "[Active verb] [resource type]" (the pattern's own examples are "Create distribution", "Create S3 bucket").
- The page header "Create environment" (line 93) as an `h1` beginning with an active verb matches the documented single-page-create page-header convention ("Begin the title with an active verb... Create [resource name]").
- The three `Checkbox` usages (`publicIp`, `encryptVolume`, `detailedMonitoring`) are settings that take effect at form submission rather than immediately, which is the correct component tier per the "Selection in forms" boolean-selection criteria table (`Checkbox`: "The selection takes effect at form submission," vs. `Toggle`, reserved for settings with an immediate effect) — none of these three should be a `Toggle`.

## What was not evaluated

Implementation correctness — prop usage and controlled-state wiring on `Input`/`Select`/`Textarea`/`Checkbox`, validation logic (or its absence) for required fields like `Environment name`, accessibility mechanics, and the hardcoded literal option arrays — was not assessed and its absence from this report should not be read as "checked and fine." General UX and product judgment — overall information density, whether an environment-creation surface is the right product shape at all, field ordering/grouping choices not tied to a specific documented composition, and copy quality beyond the specific writing-guideline matches noted above — were likewise not evaluated.
