# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape

**Inferred user task:** The user is creating a new cloud "environment" resource in a single submission: naming/describing it and choosing its region, then configuring compute (instance type/count, auto-scaling bounds), networking (VPC/subnet/security group, public IP), storage (volume type/size, encryption), monitoring (detailed monitoring, log retention, alert email), and resource tags (owner, cost center, environment), before clicking "Create environment."

**Packages / versions:** `@cloudscape-design/components` resolved via `package-lock.json` to **3.0.900** (declared range `^3.0.900`). `package.json` also declares `@cloudscape-design/collection-hooks` (`^1.0.60`) and `@cloudscape-design/global-styles` (`^1.0.45`), but neither is imported by this file, so they weren't resolved as relevant to this review.

**Authority categories found in this corpus:** Cloudscape's own `llms.txt` index exposes distinct, named tiers: **component guidance** (per-component pages), **named patterns** (a dedicated `/patterns/` tier, including resource-management patterns such as "Create resource," "Single page create," "Multipage create," and cross-cutting patterns such as "Selection in forms" and "Defaults" — several of which publish explicit numeric criteria/decision tables, not just prose), **foundations**, and **demos/code snippets** (explicitly illustrative). This review draws on the component-guidance and named-pattern tiers, which is where this design system's own authority for create-flow structure and tag management actually lives.

## Findings

### Finding 1: The 20-field, 6-container create form exceeds Cloudscape's own documented threshold for Single page create and matches its criteria for Multipage create (Wizard)

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Create a new environment resource by configuring compute, networking, storage, monitoring, and tag settings in one flow (see above).
- **Repository evidence:** `CreateEnvironment.tsx` renders `ContentLayout > Form > SpaceBetween > Container × 6` ("General," "Compute," "Networking," "Storage," "Monitoring," "Tags"; lines 92–226), each `Container` carrying an `h2 Header` and one or more `FormField`/`Checkbox` controls, with a single `Form actions` bar (Cancel / "Create environment") at the very bottom. There is no `ExpandableSection` or any primary/secondary field distinction anywhere in the file — every field is rendered at equal weight in one continuous scroll. Counting the controls directly from the JSX (confirmed by `scripts/inspect_surface.py`'s `jsx_tag_counts`: `Container: 6`, `FormField: 17`, `Checkbox: 3`, `Select: 6`, `Input: 10`, `Textarea: 1`): 17 `FormField`-wrapped inputs + 3 standalone `Checkbox`es = **20 total fields**, none in an "additional settings" section, spread across **6 groups of settings** (the 6 `Container`s).
- **Authority evidence** (named pattern — "Create resource" pattern page, `/patterns/resource-management/create/index.html.md`): its **Criteria** decision table compares Modal / Single page create / Multipage create. The "Length" row states:

  > "Between 2 and 15 fields in the primary section or up to 5 groups of settings" — Single page create
  > "More than 16 fields in primary sections or more than 5 groups of settings" — Multipage create

  The Multipage create pattern page (`/patterns/resource-management/create/multi-page-create/index.html.md`) states: "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. **We recommend multipage create for long or complex configurations.**" No qualifying row in this table places Single page create and Multipage create in the same tier for a 20-field/6-group form — the two length ranges are disjoint, not tied, so this is a directional match, not an equivalence to suppress.
- **Evidence mode:** VERBATIM (the criteria-table cells and the "We recommend..." sentence are quoted character-for-character from the fetched pages above); the 20-field/6-group count is repository evidence, not authority.
- **Applicability argument:**
  1. *Task match:* the criteria table's stated axis — how many fields/groups of settings a single-resource create flow has — is exactly the axis this surface sits on; it's not a superficial shape match, it's the identical measurement the table is built to classify.
  2. *Same problem:* the current Form/Container composition is a literal instance of "Single page create" (its own building blocks — Container, Form, FormField, action buttons — match that pattern's structure one-for-one), so it is squarely the composition this table is evaluating.
  3. *Task preserved:* moving to Multipage create changes only pagination/review structure, not what's being created or which fields exist — same resource, same fields, same submission outcome.
  4. *Materiality of the gap:* 20 fields (>16) **and** 6 groups (>5) both clear the Multipage-create threshold — not a borderline single-metric case, but both stated metrics agreeing in the same direction, which is the kind of gap an experienced Cloudscape implementer would treat as an "outgrown its pattern" signal, not a stylistic preference.
- **Current expression:** A single always-expanded `ContentLayout > Form > Container(×6)` page (Single page create's own composition), with no primary/secondary distinction and no additional-settings collapsing.
- **Native expression:** A Multipage create flow built on the Wizard component, splitting these 6 logical groupings (or a subset with related groupings combined) across steps — Cloudscape's documented range is "up to seven pages... we recommend using three to five" — each step independently validated, followed by an optional review step per the pattern's "Review page" building block, before final submission.
- **Why it matters:** Cloudscape ties its own recommended create-flow component directly to field/group count via a published, quantified table; staying on Single page create past its documented range means all 20 fields compete for attention in one continuous scroll with none marked primary vs. advanced — working against that very pattern's own "keep the primary section as short as possible" concept — and diverges from how the design system's own criteria says a form this size should be composed, which is also a consistency cost against any other equivalently-sized create flow in the same app built to this pattern correctly.
- **Boundary check:** This is a judgment about which top-level, named Cloudscape create-flow pattern (and its associated Wizard vs. Form/Container composition) fits a form of this measured size — settled by the design system's own published criteria table — not a critique of any prop, validation, or accessibility mechanic on the existing components, and not a generic "this form is long" opinion.

### Finding 2: The fixed Owner / Cost center / Environment tag inputs are a bespoke stand-in for Cloudscape's Tag editor component

- **Type:** component selection
- **Materiality:** high
- **Confidence:** medium
- **User task:** As part of creating the environment, attach ownership/cost-center/environment metadata tags to the new resource.
- **Repository evidence:** State is declared as `ownerTag`, `costCenterTag`, `environmentTag` (lines 63–65) — each variable name is itself suffixed "Tag" — and rendered in a `Container header="Tags"` (lines 208–220) as three independent `FormField` + `Input` pairs labelled "Owner," "Cost center," and "Environment tag." There is no add/remove affordance; the set is hardcoded to exactly these three keys with free-text values and no key/value validation.
- **Authority evidence** (component guidance — Tag editor, `/components/tag-editor/index.html.md`): "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." Its Features section states: "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)." Its "Do" guidance states: "Use the tag editor to manage tags only in create and edit flows." (markdown link syntax around "create"/"edit" stripped for readability; wording otherwise verbatim). The component also documents built-in tag-key/value validation (max lengths, disallowed characters, `aws:`-prefix prohibition, duplicate-key detection) and a configurable tag limit.
- **Evidence mode:** PARAPHRASE (the component's documented purpose and tag model, plus one directly quoted "Do" line).
- **Applicability argument:**
  1. *Task match:* the component's stated job — managing resource tags in create/edit flows — is not a superficial shape match; it's reinforced by this surface's own naming: a container literally titled "Tags" whose three state variables are each suffixed "Tag," which is code-level evidence (not a property of the data, but of the surface's own naming/labels) that these three inputs are the app's realization of resource tags, the exact concept Tag editor exists for.
  2. *Same problem:* the current three-`Input` approach already does the same underlying job — assigning key/value-shaped metadata to the resource at creation time.
  3. *Task preserved:* substituting Tag editor doesn't change what's accomplished; Owner/Cost center/Environment can be pre-seeded as default rows, preserving the same three tags by default.
  4. *Materiality of the gap:* Tag editor provides mechanics the hand-rolled Inputs lack outright — adding arbitrary additional tags, and Cloudscape's documented key/value validation, duplicate-key detection, and tag-limit handling — none of which is a fixable prop on `Input`; it is a component-identity gap, not an implementation defect in the existing fields.
- **Current expression:** Three independent, hardcoded `FormField`+`Input` pairs limited to exactly Owner / Cost center / Environment tag, with no way to add other tags and no tag-specific validation.
- **Native expression:** A single Tag editor instance in the Tags container, optionally pre-populated with Owner/Cost center/Environment as default rows, letting users add, edit, or remove additional tags with Cloudscape's documented validation and limit handling.
- **Why it matters:** Hardcoding three Inputs forecloses arbitrary tagging — a routine resource-management need this design system ships a dedicated, purpose-built component for — and silently re-implements (without the documented validation, duplicate-key checking, or tag-limit UI) behavior Tag editor already provides for exactly this job, which is also a consistency cost against any other Cloudscape-based create/edit flow in the same app that manages tags the standard way.
- **Boundary check:** This is a choice between a bespoke, fixed-field UI and Cloudscape's purpose-built component for the same conceptual job (resource tag management in a create flow) — not a defect in how the existing `Input`/`FormField` components are wired, and not a generic UX opinion about the form.

## Suppressed (low materiality or weak applicability)

- **Select used for the 2-option Region, Instance type, and Volume type fields**, where Cloudscape's "Selection in forms" pattern's Single-selection criteria table recommends Radio group or Tiles for "2 to 7 options" and reserves Select/Autosuggest for "8+ options" — suppressed. The fixture's `REGION_OPTIONS`/`INSTANCE_TYPE_OPTIONS`/`VOLUME_TYPE_OPTIONS` arrays are small, hardcoded stand-ins; nothing in the surface's own code or copy establishes that these lists are meant to stay at exactly 2 options in production (regions, instance types, and volume types are conventionally larger, growable option sets fetched from elsewhere). Resolving this candidate by the on-page option count would mean resolving intent from "a property of the data itself" (its cardinality) rather than from the surface's own code/comments/copy, which this review's own governing rule treats as impermissible — so the candidate is suppressed rather than reported as a directional finding.
- **Select used for the single-option VPC/Subnet/Security group fields** (`VPC_OPTIONS`, `SUBNET_OPTIONS`, `SECURITY_GROUP_OPTIONS` each contain exactly one hardcoded entry) — suppressed for the same reason: a one-item array is self-evidently placeholder/stub data for what would be a dynamically-populated resource list in a real system, not evidence about the intended component choice.

## Orientation notes

- `Checkbox` is used for `publicIp`, `encryptVolume`, and `detailedMonitoring` — all three are boolean settings that "take effect at form submission" (i.e., only on "Create environment," not immediately), which matches the Boolean-selection criteria table's Checkbox row exactly. None of the three gates a group of sub-fields, so the "don't use the same control type for a boolean option and its sub-options" progressive-disclosure rule doesn't apply here — checked, no violation.
- The individual component choices for describing and grouping fields — `ContentLayout`, `Header`, `Form`, `Container`, `FormField`, `Input`, `Textarea`, `Select`, `Checkbox`, `Button`, `SpaceBetween` — each match their own documented purpose (e.g., `Textarea` for the multi-line "Description" field, `Select` for closed-option region/instance/volume-type choices, `Container`+`Header` for grouping related fields under a labeled section). The material issue found (Finding 1) is at the composition/length level, not in any individual component's selection.

## What was not evaluated

Implementation correctness was not evaluated, including: `Input type="number"` usage for count/min/max/size/retention fields, presence or absence of field-level validation and error text, required-field marking, the hardcoded literal `OPTIONS` arrays versus data-driven option sources, loading/disabled states, and ARIA/accessibility mechanics on the existing, already-native components. General UX and product judgment were also not evaluated, including: whether these six categories are the right categories at all, field ordering and copy wording beyond what a cited pattern's writing guidelines require, and whether the overall task itself (a full "environment" launch in one form) is the right product scope.
