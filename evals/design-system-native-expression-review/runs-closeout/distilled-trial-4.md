# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A single page lets a user configure and create a new "environment" (a cloud infrastructure resource) by specifying general identity (name, description, region), compute (instance type/count, auto-scaling bounds), networking (VPC, subnet, security group, public IP), storage (volume type/size, encryption), monitoring (detailed monitoring, log retention, alert email), and resource tags (owner, cost center, environment tag), then submitting via a "Create environment" action or exiting via "Cancel."

**Packages / versions:** `@cloudscape-design/components` resolved to `3.0.900` (declared `^3.0.900`, locked in package-lock.json); `@cloudscape-design/collection-hooks` `1.0.60` and `@cloudscape-design/global-styles` `1.0.45` are declared dependencies but not imported by this file. Only `@cloudscape-design/components` imports appear in the bounded surface (`ContentLayout`, `Header`, `Form`, `Container`, `SpaceBetween`, `FormField`, `Input`, `Textarea`, `Select`, `Checkbox`, `Button`).

**Authority categories found in this corpus:** Cloudscape's documentation index (`llms.txt`) exposes: component guidance (per-component Do/Don't and development guidelines, e.g. Wizard, Select, Checkbox, Tag editor), named resource-management patterns that include explicit decision/criteria tables (Create resource, Single page create, Multipage create, Selection in forms), foundations, and demos/examples. Demos and worked examples are illustrative only; the criteria tables on the named-pattern pages are the load-bearing authority used below.

## Findings

### Finding 1: Six always-visible configuration groups (20 fields) in a single-container `Form`, where Cloudscape's own decision table for this exact task places this configuration past the single-page-create threshold

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high (on the diagnosis that the documented single-page-create capacity is exceeded); the specific remedy is deliberately left open — see "Native expression."
- **User task:** As stated above — creating one environment resource through one form, organized into General/Compute/Networking/Storage/Monitoring/Tags.
- **Repository evidence:** `CreateEnvironment.tsx` renders one `<ContentLayout>` → one `<form>`/`<Form>` (lines 93–223) whose body is a `SpaceBetween` of six `Container`s, each with an `h2` `Header` and always-rendered `FormField`/`Checkbox` children, with no `ExpandableSection` or other progressive-disclosure element anywhere in the file: General (lines 108–124, 3 fields), Compute (126–145, 4 fields), Networking (147–174, 4 fields incl. the `publicIp` checkbox), Storage (176–192, 3 fields incl. `encryptVolume` checkbox), Monitoring (194–206, 3 fields incl. `detailedMonitoring` checkbox), Tags (208–220, 3 fields). `inspect_surface.py` confirms 6 `Container`, 17 `FormField`, and 3 `Checkbox` elements — 20 form fields total, all rendered unconditionally in what the pattern calls the "primary section."
- **Authority evidence:** The "Create resource" pattern page (`https://cloudscape.design/patterns/resource-management/create/index.html.md`) states: *"Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations."* Its **Criteria** table (verbatim):

  | | Single page create | Multipage create |
  | --- | --- | --- |
  | Length | Between 2 and 15 fields in the primary section or up to 5 groups of settings | More than 16 fields in primary sections or more than 5 groups of settings |
  | Complexity | Flow does not require any category to have its own page | Concepts require in-depth interactions that benefit from having their own page |

  This surface has 20 primary-section fields (>16) and 6 groups (>5) — the Length row for Multipage create is met on both of its own sub-criteria. The **Complexity** row, disclosed here in full because it qualifies the direction: this surface's individual fields (text inputs, plain `Select`s, checkboxes) are not shown to require "in-depth interactions," which is the profile the Length row's counterpart, Single page create, describes. I am not treating this as a tied decision-table cell, because the pattern's own summary sentence uses a disjunctive framing — *"long **or** complex"* — meaning the Length criterion alone is sufficient grounds for the recommendation independent of Complexity; the table's two rows are independent tests, not a single ranked cell each pattern must win outright.

  Additionally, the "Single page create" pattern page's own building block guidance (verbatim): *"In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout. For example: Choosing a database type."* Using six containers here is a use of "multiple containers" well beyond the stated "in most cases, use a single container" default, and none of the six groupings is presented as "highly complex" in the sense the exception describes.

  Authority category: **named pattern** (decision/criteria table + building-block guidance). Evidence mode: **VERBATIM**. Authority strength: **RECOMMENDED** ("we recommend," not a "Don't...instead" prohibition).
- **Applicability argument:** (1) The observed task — configuring several genuinely distinct infrastructure concern areas (compute, networking, storage, monitoring, tagging) before creating one resource — is exactly the "set of interrelated tasks" / "long or complex configuration" the Multipage create pattern names as its trigger, not a superficial shape match. (2) The current implementation solves the identical problem (collecting all these fields to create one environment). (3) Either native remedy below preserves the same task and the same submitted data — nothing about the user's goal changes. (4) The threshold is crossed by a wide margin on field count (20 vs. the 15-field ceiling) and exactly at the group-count boundary (6 vs. the 5-group ceiling), which is the kind of quantifiable, documented breach an experienced Cloudscape implementer would notice and act on, not just note as a stylistic alternative.
- **Current expression:** One `ContentLayout` + one `Form` + six always-expanded `Container`s, all 20 fields visible and required-looking on first paint, no primary/secondary field distinction, no review step.
- **Native expression:** Two Cloudscape-documented remedies both address the diagnosis, and this bounded file does not contain evidence to choose between them with confidence:
  1. **Multipage create with the `Wizard` component** — one step per current container (or a consolidated 3–5-step grouping, since the Wizard pattern's own guidance recommends "three to five pages," allows up to seven, and recommends closing with a review step) — the directly-indicated remedy given the pattern's own recommendation text and the Length criterion. Note this also requires removing the current `ContentLayout` wrapper: the Wizard component page states plainly, *"Don't use the wizard inside of a content layout component."* This makes the recommendation genuinely "combined": adopting it substitutes `ContentLayout`+`Form` for `Wizard`, not just a reflow of existing containers.
  2. **Stay with single-page create, but restore the pattern's own progressive-disclosure building block** — move the less-essential groups (e.g. Monitoring, Tags) into the "Additional expandable section" the Single page create pattern documents, which would drop the primary-section count back under 15 fields across 4 groups. This keeps the current top-level composition (`Form` + `Container`s) but requires introducing an `ExpandableSection`.
  Choosing between these requires knowing which of the six groups are "any field that 80% or more users would expect to see" (primary, per the pattern's own Length criteria) versus safely-defaulted advanced settings — a product judgment this file's code does not resolve.
- **Why it matters:** Cloudscape's own resource-creation guidance ties page structure to a measurable field/group budget specifically so that long configurations get either a wizard's per-step validation/review or single-page create's own progressive disclosure; this surface has neither, so every field — including clearly secondary ones like log retention and resource tags — competes for attention with the primary identity/region choices on first paint, which is the documented failure mode long/complex configurations use is engineered to avoid, quite apart from any general "too much on the page" aesthetic complaint.
- **Boundary check:** This is a mismatch between the surface's top-level composition (single always-expanded `Form`/`Container` stack) and Cloudscape's own documented capacity thresholds and progressive-disclosure building block for this exact page type, not a claim about any implementation defect or a generic usability complaint independent of Cloudscape's own guidance.

### Finding 2: Fixed `Owner` / `Cost center` / `Environment tag` inputs, where Cloudscape ships a dedicated component for exactly "resource tags" — `intent-dependent`

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Attaching metadata labels (owner, cost center, environment) to the environment being created.
- **Repository evidence:** The "Tags" `Container` (lines 208–220) renders three separately-labeled `Input` fields bound to three named `useState` variables (`ownerTag`, `costCenterTag`, `environmentTag`) — a fixed, closed set of exactly three key/value pairs, with no add/remove affordance and no way to attach any tag beyond these three.
- **Authority evidence:** The Tag editor component page (`https://cloudscape.design/components/tag-editor/index.html.md`) states, as a "Do": *"Use the tag editor to manage tags only in create and edit flows."* It documents tags as *"metadata assigned to a resource, consisting of a key (mandatory) and a value (optional),"* with built-in add-row, remove-row, and validation behavior for an open-ended, user-extensible set (default limit 50). Authority category: **component guidance**. Evidence mode: **VERBATIM**. Authority strength: **RECOMMENDED** (a "Do" guideline, not phrased as a hard prohibition against any other approach).
- **Applicability argument:** The component-existence and the copy match ("Tags" heading, tag-shaped field names) strongly suggest this section is doing the same job the Tag editor exists for. But the anti-fundamentalism rule requires more than "the design system ships a component for something in this space" — it requires the *same* task, and that cannot be confirmed here: these three fields could equally represent (a) an open-ended resource-tagging capability that this implementation has incompletely/narrowly built (in which case Tag editor is the clear native fit), or (b) a small, fixed set of organization-mandated required tags (a common real-world governance pattern, e.g., AWS tag policies requiring exactly `Owner`/`CostCenter`/`Environment`), where an arbitrary open key/value editor is not the same task at all — it would let a user add or omit the very tags the fixed labels exist to guarantee. Nothing in this file's code, comments, or copy states which of these is intended (no "additional tags" affordance suggesting (a), no comment referencing a required-tags policy suggesting (b)).
- **Current expression:** Three fixed, individually-labeled `Input` fields, one per tag key.
- **Native expression:** Uncertain, and stated as such per the intent-dependent contract: if the task is open resource tagging, `TagEditor` (from `@cloudscape-design/components/tag-editor`) is the documented native expression; if the task is collecting a fixed, mandatory set of governance tags, the current per-field `FormField`/`Input` approach may already be reasonable Cloudscape usage (each required tag gets its own labeled, individually-validatable field) and no change is indicated.
- **Why it matters:** Reported rather than suppressed because the two readings lead to materially different, non-overlapping implementations (open editor vs. fixed fields), and this is exactly the kind of judgment call whoever owns this page can resolve immediately (do other required tags ever get added/removed here?) where a reviewer working only from this file cannot.
- **Boundary check:** This is a question of which documented tagging concept (arbitrary key/value tag management vs. a small fixed set of named fields) the surface is meant to express, not an implementation defect in either reading.

## Suppressed (low materiality or weak applicability)

- **All six `Select` components (Region, Instance type, VPC, Subnet, Security group, Volume type) vs. Radio group/Tiles.** Cloudscape's "Selection in forms" pattern gives a verbatim, quantified criteria table: *"Number of options"* — Radio group/Tiles: "2 to 7 options"; Select/Autosuggest: "8+ options" — with the stated rationale that *"the fastest way for users to ﬁnd and select an option in a list of seven or fewer options is to see all the options at once as a group of checkboxes, radio buttons, or tiles."* Every `Select` in this file is currently backed by a hardcoded mock array of exactly 1–2 options (`REGION_OPTIONS`, `INSTANCE_TYPE_OPTIONS`, `VPC_OPTIONS`, `SUBNET_OPTIONS`, `SECURITY_GROUP_OPTIONS`, `VOLUME_TYPE_OPTIONS`), which on its face falls inside the Radio-group/Tiles band. I am suppressing this candidate rather than reporting it: the skill's own guidance is explicit that resolving an applicability question from "a property of the data itself, like a column's cardinality" is not legitimate grounding, and these option arrays are uniformly small, static, hand-authored mock lists (1–2 items each, with no fetching logic) rather than observed real data — for at least Region and Instance type, real deployments plausibly expose many more than 7 options (many AWS regions; large instance-type catalogs), which would put those two squarely back in Select's own 8+ band. Picking out only one Select (e.g., Volume type, where the real-world option set is plausibly small and stable) to recommend converting would require importing outside domain knowledge the file itself doesn't establish, which is the same move the skill warns against. Checked and cleared, not overlooked.

## Orientation notes

- **Checkbox usage** for `Assign a public IP address`, `Encrypt volume`, and `Enable detailed monitoring` (lines 170, 188, 196) matches the "Selection in forms" pattern's Boolean-selection criteria: *"The selection takes effect at form submission"* is the documented Checkbox behavior, and all three are settings applied when the create-flow form is submitted (not settings with an immediate, visible effect, which would call for a Toggle instead).
- **`Textarea` for `Description`** (line 114) versus `Input` for single-line fields is the documented distinction between multi-line and single-line text entry — correct component choice.
- **Form action buttons** — `Cancel` as a `variant="link"` `Button` and `Create environment` as the primary submit button (lines 98–103) match the Single page create pattern's writing guidance verbatim: *"For the button that allows the user to exit the form, use this text: Cancel"* and *"For the button that allows the user to submit the form, use the format: [Active verb] [resource type]"* (example given: *"Create distribution"*) — "Create environment" follows this format exactly.
- **Page title** `Create environment` as an `h1` `Header` (line 93) matches the documented guidance: *"Begin page titles with an active verb. Most likely it will be: Create"* with examples including *"Create S3 bucket."*
- **No dedicated Cloudscape pattern exists** for the paired `Auto-scaling minimum`/`Auto-scaling maximum` numeric inputs (lines 138–143); two `Input type="number"` fields is unremarkable composition and not flagged for lack of any documented alternative to compare against.

## What was not evaluated

Implementation correctness was not assessed and should not be inferred as "checked and fine," including: the native `<form onSubmit>` element wrapping the Cloudscape `Form` alongside a `Button formAction="submit"` (lines 94–223); absence of any client-side validation, `errorText`, or required-field marking on any `FormField` despite fields like `Environment name` appearing to be required; hardcoded/mock option arrays with no loading or error states; and any accessibility mechanics beyond what Cloudscape's components provide by default. General UX judgment (information density, whether Monitoring's log-retention field should be gated behind the detailed-monitoring checkbox, field ordering, copy quality beyond the specific writing-guideline citations above) was also not evaluated and is out of this skill's scope.
