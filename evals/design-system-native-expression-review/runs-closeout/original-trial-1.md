# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape

**Inferred user task:** The user is creating a new cloud "environment" (an AWS-style compute environment: an EC2-like instance sized by type/count with auto-scaling bounds, placed in a VPC/subnet/security group, backed by an EBS-like volume, with monitoring and cost-allocation tags) by filling in a single long form organized into six labeled groups (General, Compute, Networking, Storage, Monitoring, Tags) and submitting it once via a "Create environment" action.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved via `package-lock.json`) — this is the package the surface imports from. `@cloudscape-design/collection-hooks` (`^1.0.60`, locked `1.0.60`) and `@cloudscape-design/global-styles` (`^1.0.45`, locked `1.0.45`) are declared dependencies of the same project but are not imported by this file.

**Authority categories found in this corpus:** Cloudscape's documentation (per its `llms.txt` index, confirmed by fetching the linked pages) exposes both component guidance (one page per component, e.g. Wizard, Select, Checkbox, Toggle, Tag editor) and named task/product patterns under `patterns/resource-management/` and `patterns/general/`. For the resource-creation task specifically, there is a dedicated pattern family — "Create resource" (parent), with "Single page create," "Multipage create," and "Modal" as named sibling patterns, plus an explicit cross-pattern decision table (see Finding 1). This is a corpus with both tiers available for this task, so composition-level judgments below are grounded in named-pattern authority, not synthesized from component pages alone.

## Findings

### Finding 1: Single-page six-container form should be expressed as a Multipage create (Wizard)

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Creating one compound cloud environment resource by configuring six interrelated groups of settings (general identity, compute sizing/auto-scaling, networking placement, storage, monitoring, and cost-allocation tags) and submitting once.
- **Repository evidence:** `CreateEnvironment.tsx` renders one `ContentLayout` > `Form` > `SpaceBetween` containing six `Container`s, each with its own `Header variant="h2"` ("General," "Compute," "Networking," "Storage," "Monitoring," "Tags"), all rendered simultaneously with no expandable/optional section anywhere in the file. Counting the bound state fields per group: General = 3 (`envName`, `description`, `region`), Compute = 4 (`instanceType`, `instanceCount`, `autoScalingMin`, `autoScalingMax`), Networking = 4 (`vpc`, `subnet`, `securityGroup`, `publicIp`), Storage = 3 (`volumeType`, `volumeSize`, `encryptVolume`), Monitoring = 3 (`detailedMonitoring`, `logRetentionDays`, `alertEmail`), Tags = 3 (`ownerTag`, `costCenterTag`, `environmentTag`) — **20 fields across 6 groups**, all unconditionally visible (there is no "additional settings" expandable section, so every field is effectively in the "primary section" as Cloudscape's own field-classification guidance defines that term). Single `<Button formAction="submit">Create environment</Button>` commits the whole form at once (`handleSubmit`, lines 67-90).
- **Authority evidence:** Cloudscape's "Create resource" pattern page (`https://cloudscape.design/patterns/resource-management/create/index.html.md`) states the choice between its three creation patterns and gives an explicit criteria table. Authority category: **named pattern**. Full table, reproduced verbatim:

  | | Modal | Single page create | Multipage create |
  | --- | --- | --- | --- |
  | Length | = 1 field | Between 2 and 15 fields in the primary section or up to 5 groups of settings | More than 16 fields in primary sections or more than 5 groups of settings |
  | Complexity | Basic text input fields and simple selects | Flow does not require any category to have its own page | Concepts require in-depth interactions that benefit from having their own page |
  | Recovery | Input is mutable after creation | Input mutable after creation | Input immutable after creation |
  | Error handling | In trigger page | In creation page | In every single step and in summary step |
  | Frequency | n/a | Frequent | Infrequent |
  | Sub-resource create | No | Yes | Yes |

  Directly above the table: "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms." and "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations." The Wizard component page (`https://cloudscape.design/components/wizard/index.html.md`) independently describes Wizard itself as "A multi-page form that guides a user through a complex flow or a series of interrelated tasks." Supporting evidence from the Single Page Create pattern (`https://cloudscape.design/patterns/resource-management/create/single-page-create/index.html.md`), building block C: "In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout," and building block E, "Additional expandable section": "Place as many inputs as possible into the additional settings section for each resource card. This allows the user to keep the primary section as short as possible."
- **Evidence mode:** VERBATIM (the table and the two "Use ... if" quotes were re-checked character-for-character against the raw fetched markdown of the "Create resource," "Single page create," and "Wizard" pages).
- **Authority strength:** RECOMMENDED. The pattern page phrases pattern selection as "Use X if..." / "We recommend..." against objective length/complexity criteria, not as an absolute "never do Y" prohibition.
- **Applicability argument:** (1) The observed task — configuring a compound cloud resource's compute, networking, storage, monitoring and tagging in order to provision it — is exactly the "create resource" pattern's stated problem, and the file's own structure (six named, always-visible configuration groups) is exactly the "set of interrelated tasks" the Multipage create pattern names as its trigger. (2) The current implementation already solves this same problem end-to-end (all fields present, one submit action) — it is not attempting a different task, just a different composition of it. (3) A Wizard-based restructuring (one step per current container, with an optional review step) preserves the identical set of inputs and the identical "create one environment" outcome — no product semantics change. (4) Materiality is not a stylistic judgment here: the pattern's own numeric Length criterion is crossed on **both** of its two independent sub-measures at once — 20 fields (versus the single-page cap of 15) and 6 groups of settings (versus the single-page cap of 5) — landing squarely inside the documented Multipage bracket ("more than 16 fields... or more than 5 groups") rather than in an ambiguous zone near the boundary. This is not a same-tier "use X or Y" pairing: the table assigns non-overlapping numeric ranges to each pattern, so there is no tie to resolve in the surface's favor.
- **Current expression:** A single `ContentLayout`/`Form` page (implicitly `contentType='form'` territory) with six `Container`s stacked in one `SpaceBetween`, all 20 fields visible at once, one primary submit button.
- **Native expression:** A `Wizard` component (`contentType='wizard'` in the app layout) with each of the six current containers becoming a wizard step (or grouped into 3-5 steps per the pattern's "three to five pages" recommendation), each step keeping its `Container`/`FormField` composition, plus an optional review step summarizing all steps before commit — per the Multipage create pattern's building blocks. Cloudscape's documented alternative to a full wizard rewrite — keeping single-page but adding an "Additional settings" expandable section (single-page building block E) to shrink the effectively-primary field count under the 15-field/5-group thresholds — remains available if product intent establishes that most of the 20 fields are safe-default, rarely-inspected settings; nothing in the bounded file indicates that split, since every field here is already unconditionally visible with no primary/optional distinction attempted.
- **Why it matters:** The documented criterion this surface crosses (field/group count) is precisely the one Cloudscape uses to route between its two named creation compositions, and crossing it has stated downstream consequences the current single-page structure doesn't provide: per-step validation and a review step ("error handling: in every single step and in summary step" vs. "in creation page"), and inline "edit" navigation back to a specific step instead of scrolling a long page to find and fix one field.
- **Boundary check:** This is a composition-level choice between two named, documented Cloudscape creation patterns for the same "create resource" task — not an implementation-correctness question (no prop/API misuse is being cited) and not generic UX commentary (the recommendation rests on the pattern family's own stated field/group-count criteria, not "this form feels long").

### Finding 2: Fixed Owner/Cost center/Environment tag inputs should be expressed as the Tag editor component

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Same environment-creation task as Finding 1; specifically the "Tags" group, whose purpose (per its container header and field labels) is attaching cost-allocation/ownership metadata to the environment being created.
- **Repository evidence:** Lines 208-220 — a `Container` headed "Tags" containing three fixed `FormField`/`Input` pairs bound to `ownerTag`, `costCenterTag`, and `environmentTag`, labeled "Owner," "Cost center," and "Environment tag." Each is a single free-text `Input`; there is no way in this code to add, remove, or view an arbitrary tag beyond these three hardcoded keys.
- **Authority evidence:** Cloudscape's Tag editor component page (`https://cloudscape.design/components/tag-editor/index.html.md`), authority category: **component guidance**. Description: "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." Under Features: "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)." Under General guidelines / Do: "Use the tag editor to manage tags only in [create] and [edit] flows." The component's built-in validation is explicitly AWS-resource-tag-shaped: "Tag key maximum length: ... 128 [characters]," "Tag value maximum length: ... 256," "Invalid prefix for tag key: Cannot start with `aws:`," "Duplicate of tag key: You must specify a unique tag key," and a configurable tag limit (default 50).
- **Evidence mode:** PARAPHRASE for the component's stated purpose and "create/edit flows" guidance; SYNTHESIS for the applicability bridge, which combines that component-guidance page with this file's own labels ("Tags" container header; "Environment tag" field literally named as a tag) to conclude the three fields represent resource tags rather than unrelated governance fields.
- **Authority strength:** RECOMMENDED. The Tag editor page states affirmatively where the component is meant to be used ("Do: ... only in create and edit flows" — this is exactly a create flow) but does not contain an explicit "Don't hand-roll individual tag inputs instead" prohibition, so this is preferred-practice strength, not an absolute rule.
- **Applicability argument:** (1) The container is explicitly titled "Tags," and one of its three fields is literally labeled "Environment tag" — the surface's own copy identifies this section as the generic AWS-style resource-tagging concept the Tag editor exists for, not an unrelated attributes section that merely happens to be adjacent to it. (2) The current three-`Input` implementation solves a narrow slice of the same problem (recording a fixed set of tag values) that Tag editor is built for. (3) Substituting Tag editor preserves the same task — attaching metadata tags to the environment at creation time — it does not change what the user is accomplishing. (4) The difference is material because the hand-rolled version forecloses exactly what makes "tags" a tagging feature rather than three fixed fields: adding any tag beyond Owner/Cost center/Environment, and it silently drops the domain-specific validation (key/value length limits, the reserved `aws:` prefix, key uniqueness) that Tag editor provides for free. An experienced Cloudscape implementer building a "Tags" section on a cloud-resource create form would reach for Tag editor by default, reserving three fixed inputs only for fields that are demonstrably *not* tags — evidence here points the other way.
- **Current expression:** Three independent `FormField`/`Input` pairs with fixed, non-extensible keys, no key/value validation, and no way to add or remove entries.
- **Native expression:** A `TagEditor` in the "Tags" container, controlled via a `tags` array and `onChange`, optionally pre-populated with rows for `Owner`, `CostCenter`, and `Environment` as a starting default while still allowing users to add further tags — the exact shape (e.g., whether the three keys should remain mandatory/locked) isn't settled by this file alone, so it's stated as the general direction rather than an exact prop-level replacement.
- **Why it matters:** Beyond the missing extensibility, the bespoke inputs bypass Tag editor's built-in AWS-tag validation (length limits, reserved prefix, duplicate-key checks) — meaning any of that validation, if wanted, would have to be reimplemented by hand instead of coming from the design system's own component for this exact job.
- **Boundary check:** This is a component-selection question — which Cloudscape component matches the documented semantic job of collecting resource tags — not an implementation-correctness critique of the existing `Input` fields (they are used correctly for what they are) and not general UX commentary (the citation is to the component's stated purpose and scope, not a usability opinion).

## Suppressed (low materiality or weak applicability)

- **Select vs. Multiselect for "Security group" (Networking section).** Cloudscape's Select guidance implies switching component when more than one item must be chosen, and real AWS EC2-style resources commonly allow multiple attached security groups. Suppressed: the bounded file gives no evidence either way — the field label is singular ("Security group"), state is a single `SelectProps.Option | null`, and the mock option list contains exactly one entry. Concluding multi-selection is needed here would require importing external domain knowledge not evidenced in this surface, which the applicability step of this review cannot do; there's nothing in the code or copy to resolve it.
- **Auto-scaling minimum/maximum as two separate numeric `Input`s.** Checked for a documented paired-range composition (e.g., a slider-based bound picker). No such named pattern or component-level "use a range control for min/max" guidance was found in this corpus for numeric bound pairs; two independent, precisely-editable numeric fields is a reasonable, undifferentiated implementation of this sub-task, so no finding was made.

## Orientation notes

- **Checkbox usage for "Assign a public IP address," "Encrypt volume," and "Enable detailed monitoring."** Confirmed correct against Cloudscape's own Checkbox/Toggle pairing rule. Checkbox's documented "Don't": "Don't use for options that take immediate effect ... Use a toggle instead," and Toggle's documented "Don't": "Don't use a toggle for options that are activated at form submission ... In this case, use a checkbox." All three booleans here take effect only when the form is submitted (`handleSubmit`), not immediately — Checkbox is the documented-correct choice, and Toggle would have been the documented-incorrect one.
- **Select usage for Region, Instance type, VPC, Subnet, Volume type.** Each represents a genuine single-value choice from a list, matching Select's stated purpose ("enable users to choose a single item from a list of items").
- **Textarea for the "Description" field.** Appropriate for open-ended, potentially multi-line free text, as distinct from the single-line `Input`s used elsewhere.
- **Form embedded in a native `<form>` element.** The surface already wraps its `Form` in a native `<form onSubmit={...}>`, matching Cloudscape's own guidance to embed Form/Wizard components inside a `<form>` tag for accessibility and framework form support — this composition detail would carry over unchanged if Finding 1 is adopted.

## What was not evaluated

Implementation correctness was not assessed: prop-level API usage, the `type="number"`/`type="email"` native HTML attributes on `Input`, absence of visible form-field validation/error states, hard-coded mock option arrays, and app-owned accessibility wiring (aria attributes, focus management) are all out of scope for this review regardless of whether they are present or correct. General UX and product judgment were also not assessed: whether "environment" is the right resource abstraction, whether these six categories are the right groupings or the right field-by-field ordering within them, and copy/wording quality are not evaluated here.
