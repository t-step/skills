# Design-System Native-Expression Review: ApiKeys.tsx

**Design system:** Cloudscape

**Inferred user task:** The page lets a user browse, sort, filter, and paginate a read-only list of API keys belonging to the account (name, environment, status, creation date). The header ("API keys", item counter, "Manage API keys for this account.") and route/component name (`ApiKeys`) frame this as an account-scoped resource-list/browse view. No create, edit, revoke, delete, or per-row/bulk action affordances exist anywhere in the given surface, so the task is scoped strictly to "view and locate items in a collection of resources," not resource creation/edit/delete workflows.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900`; `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60`; `@cloudscape-design/global-styles` declared `^1.0.45`, locked `1.0.45`. Resolved from `fixture/package.json` / `fixture/package-lock.json` via `scripts/resolve_versions.py`.

**Authority categories found in this corpus:** Both a component tier and a task/pattern tier exist. Component guidance: individual component pages (Table, TextFilter, CollectionSelectFilter, PropertyFilter, StatusIndicator, ContentLayout, Header) each with "Development guidelines," "Features," and explicit "Do/Don't" sections. Named patterns / composition guides: `patterns/general/filter-patterns` (filter-type selection criteria table), `patterns/resource-management/view/table-view` (table-view composition, including a table-vs-ContentLayout Do/Don't), and `patterns/resource-management/view` (table-vs-card selection criteria table). No separate "foundation" or "worked demo" tier was needed to settle either finding below.

## Findings

### Finding 1: Table `variant="borderless"` is used outside the composition context Cloudscape documents for it

- **Type:** combined selection + composition
- **Materiality:** medium
- **Confidence:** high
- **User task:** As above — a simple, few-column (4 columns), 16-row account resource list, rendered as the entire content of the page.
- **Repository evidence:** `fixture/src/pages/ApiKeys.tsx` — the `Table` (imported line 3) is the sole child of `ContentLayout` (imported line 1), whose `header` prop carries an `h1` `Header` with `counter` and `description` (lines 38–44). The `Table` itself has no `header` prop, no sibling containers, and no surrounding `Container`/`ExpandableSection`/`Modal`/`SplitPanel`. Line 77: `variant="borderless"`. `columnDefinitions` (lines 49–72) lists exactly 4 columns.
- **Authority evidence:** Two sources, cited in full:
  1. `patterns/resource-management/view/table-view/index.html.md`, "Don't" section: *"Don't use the table view pattern for tables that aren't overly content-heavy. Instead, if a table only has a few columns, use a bordered table inside the content layout component, with the default app layout content max-width."*
  2. `components/table/index.html.md`, "Features → Variant" (reproduced in full, all three documented variants):
     - **Container:** *"This table variant has its own visual container with shadows and borders. Use this variant to feature a table in a stand-alone container with its own hierarchy."* Example given: "when using a table on a details page."
     - **Borderless:** *"Use this variant to place a table inside a container with other content, such as key-value pairs."* / *"Use this variant to display a table without the shadows and borders surrounding a container. Use when placing a table inside another container."* Examples given: "a dashboard item, expandable section, modal or within a split panel."
     - **Full page:** *"This variant is for implementing the full page table view pattern. Use it for presenting and managing a table with many columns within a stand-alone page."*
  - Authority category: **named pattern** (source 1) + **component guidance** (source 2).
  - Note on a tension between sources: `components/content-layout/index.html.md`'s own "Don't" section states, generally, *"Don't use the content layout component for productive use cases such as resources creation, view, edit, and delete"* (linking "view" to the table/card/split-view pattern family). Read alone, this would argue against using `ContentLayout` here at all. But the Table-view pattern page's own "Don't...Instead" (source 1 above) is the more specific instruction directly on point for "a table [with] only a few columns," and it explicitly names `ContentLayout` with a "bordered table" as the correct composition for that specific case — which is this surface's exact shape (4 columns, 16 rows, single filter, single page of content). I am treating the more specific, directly-applicable instruction as governing over the general blanket statement, and naming the tension rather than silently picking a side.
- **Evidence mode:** SYNTHESIS — no single sentence in the corpus says "use `variant=\"container\"` instead of `\"borderless\"` inside ContentLayout for a few-column table." The claim bridges: (a) the pattern page's explicit instruction to use "a bordered table inside the content layout component" for this exact table shape, with (b) the component page's explicit mapping of "has its own visual container with shadows and borders" to the **Container** variant, and its explicit statement that **Borderless** removes "the shadows and borders surrounding a container" and is meant for embedding *inside another container alongside other content* (dashboard item, expandable section, modal, split panel) — none of which describes this page, where the table is the entire content.
- **Applicability argument (four-point test):**
  1. Task match: the pattern page's stated problem — "a table [that] only has a few columns" as a page's content — is not superficially similar to this surface, it is this surface: 4 columns, single flat list, one page.
  2. Current implementation solves the same problem: yes, it already composes `ContentLayout` + `Table`, just with the wrong variant.
  3. Preserves the same task: yes — swapping `variant="borderless"` for `variant="container"` changes nothing about filtering, sorting, pagination, or data; it is a pure composition-conformance fix.
  4. Materiality of the gap: Borderless's documented purpose (avoid a second, redundant border/shadow when a table sits *inside another bordered/container element alongside other content*) does not apply here — there is no outer `Container`/`Modal`/`ExpandableSection`/`SplitPanel` to avoid double-bordering against. `ContentLayout` itself does not render a container border. Using Borderless here produces the opposite of Container's stated case ("stand-alone container with its own hierarchy," "example: details page") for a table that, in fact, *is* the entire stand-alone hierarchy of the page — exactly the composition Container is documented for. Checked for a same-tier tie (per the anti-fundamentalism rule): the Variant section states three variants with three distinct, non-overlapping intended contexts (stand-alone / embedded-in-another-container / full-page-many-columns) — nothing in the retrieved material places Container and Borderless in the same tier for "sole content of a ContentLayout page." This is a one-directional mismatch, not a tie.
- **Current expression:** `<Table variant="borderless" ...>` as the only content inside `<ContentLayout header={<Header variant="h1" .../>}>`.
- **Native expression:** `<Table variant="container" ...>` (or the default, since Container is the Table component's default variant), keeping everything else — filtering, sorting, pagination, `useCollection` wiring — unchanged.
- **Why it matters:** The current composition renders the account's primary (and only) content element with no visual container of its own, on a page whose own documentation names this exact shape ("a table [with] only a few columns" as ContentLayout's content) and prescribes "a bordered table" for it. This is a specific, named documented composition for this precise page shape, not a general aesthetic preference — a Cloudscape-fluent implementer building this same page from the pattern docs would produce a bordered (Container) table here, and the current choice diverges from that without any of Borderless's documented preconditions (nested inside another container, alongside other content) being present.
- **Boundary check:** This is a component-selection/composition question — which of Cloudscape's three documented, distinctly-scoped Table variants matches this page's composition — not an implementation-mechanics defect (the `variant` prop is used correctly, just set to a value reserved for a different composition context) and not generic UX critique (no aesthetic judgment is asserted independent of the cited variant guidance).

### Finding 2: TextFilter vs. Collection select filter for the `environment`/`status` columns

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** high (confidence that this is a genuine, undecidable tie given the evidence — not confidence in a direction)
- **User task:** Locating specific API keys within a 16-item list that has two low-cardinality, enumerated properties (`environment`: production/staging; `status`: active/revoked) alongside a free-text `name`.
- **Repository evidence:** `fixture/src/pages/ApiKeys.tsx` line 4 (`TextFilter` import), lines 73–75 (`<TextFilter {...filterProps} filteringPlaceholder="Find API key" filteringAriaLabel="Filter API keys" />`), and `columnDefinitions` lines 56–65: `environment` (plain text cell, values `'production' | 'staging'`) and `status` (rendered via `StatusIndicator`, values `'active' | 'revoked'`) — both closed, two-valued enumerations. `useCollection`'s `filtering` config (lines 29–32) only sets `empty`/`noMatch` copy; nothing in the file states or implies which property(ies) users are expected to search by. There is no comment, TODO, test name, or non-neutral header copy anywhere in the file — the header description is the single neutral line "Manage API keys for this account."
- **Authority evidence:** `patterns/general/filter-patterns/index.html.md`, "Criteria" table, reproduced in full (all four rows, all three columns):

  |  | Text filter | Collection select filter | Table property filter |
  | --- | --- | --- | --- |
  | Complexity of the resource | Simple resource (small set of properties) | Simple resource (small set of properties) | Complex resource (large set of properties) |
  | User goals | Find resources that match an exact text query | Find resources with overlapping, defined values | Find resources with multiple combinations of values |
  | Selection of values | - | Single selection of a value for each property | Multiple selection of values for each property |
  | Operators | - | "And" operator | "And", "Or", "Not", "And not" and "Or not" operators |

  Plus the page's differentiating prose: *"If users tend to know exactly the value or term they are looking for, use the text filter."* and *"If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter. For example: by 'status' or 'type'."*
  Authority category: **named pattern**.
- **Evidence mode:** VERBATIM (table and quotes reproduced exactly as fetched).
- **Applicability argument (four-point test, applied to why this stays a tie rather than becoming a directional finding):** The "Complexity of the resource" row places Text filter and Collection select filter in the *same* documented tier — both "Simple resource (small set of properties)" — which is exactly this surface's shape (4 total columns, 2 of them enumerated). This surface's `status`/`environment` pair is even the literal example the pattern page gives for the collection select filter ("by 'status' or 'type'"), which is suggestive — but the "User goals" row differentiates the two options purely by *user behavior* ("users tend to know exactly the value or term" vs. "the common behavior of users is to filter by only one or two properties"), not by any property of the resource itself. Per the same-tier-equivalence check: a differentiating row phrased as a description of two different user intents is not, by itself, a directional preference — it tells you the design system won't pick between the two without knowing which intent this surface's users actually have. Nothing in `ApiKeys.tsx` — no comment, no test name, no non-neutral copy — resolves which intent applies here. (Property filter is not a live alternative for this task: its documented tier is "Complex resource (large set of properties)," which this 4-column resource does not match — see Suppressed, below.)
- **Current expression:** A single `TextFilter` matching free text against the collection (name matching is the plausible primary use given the `name` values like `billing-key-01`).
- **Native expression:** Not stated with confidence — this is the point of the `intent-dependent` classification. If the account owner's real workflow is "I know the key name I'm looking for," `TextFilter` is already the documented native choice. If the real workflow is "show me all `production` keys" or "show me all `revoked` keys," a `CollectionSelectFilter` (one or two selects, e.g. for `environment` and/or `status`) is the documented native choice for that behavior. Both are equally valid per Cloudscape's own criteria table; picking one would require evidence about actual user search behavior that this bounded surface does not supply.
- **Why it matters:** Naming this candidate (rather than silently accepting the current `TextFilter` or silently recommending `CollectionSelectFilter`) surfaces a genuine, documented decision point with real interaction-model consequences (free-text search vs. structured filtering by the two enumerated columns) that the surface's own evidence cannot resolve — exactly the scenario Cloudscape's filter-patterns guidance is structured to leave to the app team's knowledge of their users, not to the docs.
- **Boundary check:** This is a component-selection question — which of two documented filter components best matches the observed low-cardinality, enumerated column shape for this task — not implementation correctness (`TextFilter` is used correctly as implemented) and not generic UX critique (the candidate is grounded entirely in Cloudscape's own filter-selection criteria table, not general usability intuition); it is reported as `intent-dependent` rather than a confident recommendation because the design system's own authority does not pick a direction and the surface supplies no resolving evidence.

## Suppressed (low materiality or weak applicability)

- **Property filter as an alternative to TextFilter/CollectionSelectFilter** — suppressed: per the Filtering patterns Criteria table above, Property filter's documented tier is "Complex resource (large set of properties)" with multi-value-per-property and boolean-operator needs. This surface has 4 total columns and only 2 low-cardinality, binary-valued candidate filter properties — it does not match "complex resource" or "large set of properties," so citing Property filter's existence here would be availability without applicability.
- **Removing `ContentLayout` in favor of the full-page Table pattern** — suppressed: `ContentLayout`'s own "Don't" language (quoted under Finding 1) generally discourages it for "view" use cases, but the Table-view pattern page's own, more specific "Don't...Instead" directly names `ContentLayout` + a bordered table as the correct composition for a table with only a few columns — which is this surface's shape. Recommending removal of `ContentLayout` would contradict the more specific, directly-applicable instruction in favor of the more general one; not a material finding.

## Orientation notes

- **Table view (not Cards, not Split view) is the right resource-representation pattern.** `patterns/resource-management/view/index.html.md`'s "Choosing between table view and card view" criteria table states Table view fits "9 or more resources in 99% of use cases" with "shared metadata between resources" and "data that is displayed in columns (text, numerical, status...)"; Card view fits "5 or less resources." This surface has 16 items with four shared, columnar-typed properties (text, text, status, date) — squarely Table view. Split view was also considered and ruled out — nothing in the surface (no monitoring/troubleshooting workflow, no in-context detail requirement) evidences the "view or compare resource details in-context" use case that pattern targets.
- **`StatusIndicator` is the correct, native component for the `status` column** — the design system provides a purpose-built status component and it is being used for exactly that job; only the specific `type` value chosen for `'revoked'` (`'stopped'`) is a business-semantics/prop-value judgment on an already-correctly-selected component, which is implementation-level and out of this skill's scope (see below).
- **`TextFilter` + `Pagination` + `useCollection` wiring** (`{...collectionProps}`, `{...filterProps}`, `{...paginationProps}`) matches the canonical `@cloudscape-design/collection-hooks` composition — spreading the hook's returned props onto the matching components rather than hand-rolling filter/sort/paginate state.

## What was not evaluated

Implementation correctness was not assessed: prop-level API usage, the specific `StatusIndicator` `type` value chosen for `'revoked'` (`'stopped'` vs. an alternative), the redundant-looking `empty` configuration present both on `useCollection`'s `filtering.empty` and directly on `<Table empty=...>`, deprecated-prop risk, accessibility mechanics beyond what was cited as supporting evidence, and hard-coded/literal values. General UX and product judgment were also not assessed — e.g., whether this "manage" page should expose create/revoke actions at all, information density, or navigation structure — none of that is evidenced strongly enough by this bounded surface to judge, and doing so would be product-redesign territory outside this skill's scope.
