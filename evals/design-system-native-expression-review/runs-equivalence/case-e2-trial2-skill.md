# Design-System Native-Expression Review: CreateBackupSchedule.tsx

**Design system:** Cloudscape

**Inferred user task:** A single-page create form for a new backup schedule resource. The user names the schedule, chooses how often it runs (Daily / Weekly / Monthly), chooses a retention policy (keep only the latest backup vs. keep full backup history), and submits to create the schedule (or cancels out of the flow). There is no editing, listing, or multi-step configuration in this file — it is a create-only surface.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, resolved via `package-lock.json` to `3.0.900` (`scripts/resolve_versions.py`). `@cloudscape-design/collection-hooks` and `@cloudscape-design/global-styles` are declared in the fixture's `package.json` but are not imported by this file and are not relevant to any finding below.

**Authority categories found in this corpus:** component guidance (per-component "Do/Don't" and "Features" sections), named patterns (resource-management "Create resource" family, including "Single page create"; general "Selection in forms" pattern with an explicit option-count criteria table), and writing guidelines. This corpus does have a task/pattern layer, distinct from the MUI round referenced in this skill's lineage notes — patterns are cited below alongside component guidance.

## Findings

### Finding 1: Frequency is a 3-option enumerated choice expressed with Select; Cloudscape's own documented option-count criterion places 2–7-option single selections in the Radio group / Tiles tier, not Select's

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** As stated above — choosing exactly one of a small, fixed, fully-known set of run frequencies as part of creating a backup schedule.
- **Repository evidence:** `CreateBackupSchedule.tsx` lines 13–17 define `FREQUENCY_OPTIONS` as a static array of exactly three items (`Daily`, `Weekly`, `Monthly`) with no dynamic loading. Lines 58–64 render this via `FormField label="Frequency"` wrapping a Cloudscape `<Select>` bound to `frequency`/`FREQUENCY_OPTIONS`. Immediately below, lines 65–74 render "Retention policy" — also exactly one choice from a small fixed set (2 options: `latest`, `full`) — using `<RadioGroup>` in the same `SpaceBetween`/`Container`, i.e., the author already applies the radio-group pattern to a structurally identical (single choice, small fixed set) field one row down.
- **Authority evidence:**
  - Component guidance — Radio group page, "Do" list (verbatim, `https://cloudscape.design/components/radio-group/index.html.md`):
    > "Use radio group when only one selection can be made from a group of two to seven options. Use select for groups of eight or more options."
  - Named pattern — "Selection in forms" pattern, "Single selection criteria" section (verbatim, `https://cloudscape.design/patterns/general/selection/index.html.md`), reproducing the full criteria table (all four columns, both rows):

    | | Radio group | Tiles | Select | Autosuggest |
    | --- | --- | --- | --- | --- |
    | Number of options | 2 to 7 options | 2 to 7 options | 8+ options | 8+ options, including user generated inputs |
    | Additional metadata per option | Descriptions | Descriptions, lists, and/or images | Icons, descriptions, and/or tags | Icons, descriptions, and/or tags |

    And the accompanying body text (verbatim): "The fastest way for users to find and select an option in a list of seven or fewer options is to see all the options at once as a group of checkboxes, radio buttons, or tiles. For groups of eight or more options, we recommend using a select or autosuggest list. This will reduce the space the selection pattern takes on the page and help the user find options within larger groups."
  - **Authority category:** component guidance + named pattern (both independently state the same option-count criterion; not a synthesis — each source alone settles the question).
- **Evidence mode:** VERBATIM (both quotes retrieved directly from the live pages via `curl` against the documented `.md` endpoints and checked against two independent fetches for consistency).
- **Authority strength:** RECOMMENDED (phrased as a "Do" guideline and a "we recommend" statement, not as an explicit "Don't use Select below 8 options" prohibition — so `RECOMMENDED`, not `REQUIRED`).
- **Applicability argument** (four-point test):
  1. **Task match, not superficial shape match:** the pattern page's own stated scenario is "a single, mutually exclusive choice from a set of options" — this is exactly what the Frequency field does, not an adjacent or differently-shaped problem.
  2. **Current implementation solves the same problem the composition addresses:** yes — Select is being used for a plain single-selection-from-a-short-fixed-list job, the identical job the criteria table is scoped to.
  3. **Proposed alternative preserves the task:** Radio group still yields exactly one selected frequency value bound to the same state (`frequency`), with no change to what the user is accomplishing.
  4. **Materiality of the difference:** 3 options sits well inside the documented "2 to 7" band and nowhere near the "8+" threshold for Select — this is not a boundary case where reasonable implementers might disagree. The same criteria table's "Additional metadata per option" row differentiates Radio group (`Descriptions`) from Tiles (`Descriptions, lists, and/or images`); `FREQUENCY_OPTIONS` carries only bare `label`/`value` pairs with no icon, description, or tag data, so within the Radio-group/Tiles tier the surface's own data shape resolves the (otherwise unranked) tie toward Radio group specifically — Tiles' extra visual/metadata affordances aren't earned by this data, so this is not being flagged as "intent-dependent." Further, the adjacent "Retention policy" field two rows below is structurally identical (single choice, small fixed set, plain text options) and already uses `RadioGroup` correctly — so the recommendation isn't importing an external convention, it's aligning Frequency with a rule the same file already applies correctly elsewhere.
- **Current expression:** A Cloudscape `Select` (closed dropdown) that requires a click to reveal Daily/Weekly/Monthly, then a second interaction to pick one.
- **Native expression:** A Cloudscape `RadioGroup` (mirroring the Retention field immediately below) showing all three frequency options at once, with "Daily" pre-selected the same way the current `useState` default already pre-selects `FREQUENCY_OPTIONS[0]`.
- **Why it matters:** The chosen component sits in the option-count tier the design system's own documentation assigns to a different component family, hides three always-relevant, always-fully-known options behind an unnecessary extra click, and is inconsistent with the sibling Retention field in the very same container that already follows this exact rule — a Cloudscape-fluent implementer reviewing this file would notice the mismatch immediately because the correct pattern is right there in the same form.
- **Boundary check:** This is a judgment about which selection *component* Cloudscape's own documented option-count criterion assigns to a 3-item enumerated choice, not about how `Select` or `RadioGroup` is implemented (props, a11y wiring) and not a generic usability complaint — it is grounded in a specific, quoted, option-count-based decision rule from this design system's own docs.

## Suppressed (low materiality or weak applicability)

- **Tiles as an alternative to Radio group for Frequency** — considered, not reported separately. The "Selection in forms" criteria table places Radio group and Tiles in the same 2–7-option tier (an unranked pair for that dimension), differentiated only by the "Additional metadata" row (Tiles supports descriptions, lists, and/or images; Radio group supports descriptions only). `FREQUENCY_OPTIONS` carries no such metadata, so Tiles would be reaching for capability the data doesn't use. This is folded into Finding 1's applicability argument rather than reported as its own finding or as `intent-dependent`, since the surface's own data (no icons/descriptions/lists) resolves the tie rather than leaving it genuinely ambiguous.
- **Toggle as an alternative to Radio group for Retention policy** — considered and cleared, not a finding. The "Boolean selection criteria" table on the same pattern page reserves Toggle for options whose "selection results in an immediate change" (its own example: light/dark mode), while Radio group/Tiles are for selections that "take effect at form submission" and need visible metadata in *both* states. Retention only takes effect when the schedule is created (form submission), and both options ("Keep only the latest backup" / "Keep full backup history") carry meaningful labels — so the current `RadioGroup` choice is already the documented fit, not a suppressed opportunity.
- **AppLayout-level building blocks (breadcrumbs, side navigation, help panel, `contentType="form"`)** named by the "Single page create" pattern's building blocks A/G/H/I — not reported. This file is a bounded page-body component with no `AppLayout`/`BreadcrumbGroup` import in view; whether those building blocks exist is a property of a parent route/shell component outside this bounded surface, and reporting their absence here would require assuming context the fixture doesn't show.

## Orientation notes

- **Native `<form>` wrapping:** the JSX wraps Cloudscape's `<Form>` in a native `<form onSubmit={...}>` element (line 40). The Form component's own guidance states: "Embed this component inside a `<form>` tag or an element with `role=\"form\"` in order to comply with accessibility guidelines and gain full benefit of your framework's form support." (`https://cloudscape.design/components/form/index.html.md`) — already correct.
- **Form actions composition:** Cancel rendered as `variant="link"` with `formAction="none"`, primary submit rendered as `variant="primary"` with `formAction="submit"`, both inside the `Form`'s `actions` slot via horizontal `SpaceBetween`. This matches the Form component's documented guidance verbatim: "Use the primary button for the main action to submit the form... Use link styling for the action of exiting the form, typically *Cancel*." Neither button is ever disabled, matching both that page's "Do not deactivate the buttons. All form actions should be active by default" and the Single page create pattern's "Don't disable the primary button, even if the user has not completed the required inputs." — already correct.
- **Header levels and copy:** `ContentLayout`'s header uses `Header variant="h1"` with the text "Create backup schedule," matching the Single page create pattern's building block B guidance to "Begin the title with an active verb... *Create [resource name]*," and the Form component's own guidance to "Use the h1 variant of the header component" for the form header. The `Container`'s header uses `variant="h2"` — matching "Form content is organized into sections using containers. Each container has a header..." — already correct.
- **Single container for all configuration:** all three fields sit inside one `Container`, matching the Single page create pattern's building block C: "In most cases, use a single container for all the configuration inputs of a single resource." — already correct, and appropriately did not reach for the Wizard/multipage-create pattern, which the docs reserve for "long or complex configurations" (this is a 3-field form).
- **Pre-selected defaults:** both `frequency` and `retention` state are initialized to a sensible default (`FREQUENCY_OPTIONS[0]` = Daily, `'latest'`), matching Radio group's "Optimize form completion by pre-selecting an option, to reduce users effort" and the Single page create pattern's "one-click to create" concept — already correct.
- **Retention policy as Radio group:** two mutually exclusive, form-submission-time options, each independently and meaningfully labeled — matches Radio group's documented "Do" guidance and is not a case the "Don't use for options that take immediate effect" carve-out applies to — already correct.

## What was not evaluated

Implementation correctness was not assessed: prop usage and API shape on `Select`/`RadioGroup`/`Input`/`Button`, the `console.log` stand-in for a real submit handler, absence of any field-level or page-level validation (`FormField`'s `errorText`/`constraintText` are never used), and accessibility mechanics beyond what a correctly-chosen component provides by default. General UX or product judgment (form copy quality, whether "backup schedule" is the right product concept, information density) was likewise out of scope and not reviewed.
