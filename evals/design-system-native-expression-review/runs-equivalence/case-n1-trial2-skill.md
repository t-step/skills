# Design-System Native-Expression Review: AccountSettings.tsx

**Design system:** Cloudscape Design System (`@cloudscape-design/components`)

**Inferred user task:** A user views and changes two personal account settings — whether two-factor authentication is required for sign-in, and whether email notifications are sent for account activity. Each change is applied to the account immediately (an `onChange` handler fires a `PATCH /api/account/settings` request the instant the control is toggled); there is no visible Save/Submit action, no form container, and no batching of multiple pending edits before committing them.

**Packages / versions:** `@cloudscape-design/components` resolved to `3.0.900` (declared `^3.0.900`, locked in `package-lock.json`). Also present: `@cloudscape-design/collection-hooks` `^1.0.60`, `@cloudscape-design/global-styles` `^1.0.45` (unresolved further; not relevant to this surface, which imports none of them). Version resolution is not materially load-bearing for the finding below — the cited guidance is foundational component-selection/pattern guidance, not version-gated API mechanics.

**Authority categories found in this corpus:** Cloudscape's documentation exposes both component-level guidance (per-component "dos and don'ts" sections, e.g. on `/components/toggle/` and `/components/checkbox/`) and named cross-component patterns with explicit decision/criteria tables (e.g. `/patterns/general/selection/`, titled "Selection in forms"). Both tiers were used below.

## Findings

### Finding 1: Immediate-effect account settings are expressed with `Checkbox` instead of `Toggle`

- **Finding:** Both settings on this page take effect immediately on change (no save/submit step), which is precisely the case Cloudscape's own documentation identifies as the `Toggle` component's job and explicitly tells implementers *not* to use `Checkbox` for.
- **Type:** `component selection`
- **Materiality:** `high`
- **Confidence:** `high`
- **User task:** Let a user immediately turn two account-level behaviors (two-factor-auth requirement, email notifications) on or off, applying each change as soon as it's made, with no separate save/submit step.
- **Repository evidence:** `evals/design-system-native-expression-review/cases/case-n1-account-settings/fixture/src/pages/AccountSettings.tsx`. Both controls are `Checkbox` (imported from `@cloudscape-design/components/checkbox`, lines 6, 28-36, 37-45). Each `onChange` handler synchronously calls `setRequireTwoFactor`/`setEmailNotifications` *and* `updateAccountSetting(key, detail.checked)` (lines 30-33, 39-42), which immediately issues `fetch('/api/account/settings', { method: 'PATCH', ... })` (lines 13-18). There is no `Form`, no submit/save action, and no other control on the page — the entire surface is these two auto-applying settings inside a `Container`/`ContentLayout`.
- **Authority evidence:**
  - Component page `https://cloudscape.design/components/toggle/`, "Toggle dos and don'ts" (Do): *"Use for an option that takes effect immediately, for example toggling versioning on an S3 bucket to enable or disable the storage of multiple versions of objects."* (Don't): *"Don't use a toggle for options that are activated at form submission, such as an acknowledgement of EULA or Terms and Conditions. In this case, use a checkbox."*
  - Component page `https://cloudscape.design/components/checkbox/`, "Checkbox dos and don'ts" (Don't): *"Don't use for options that take immediate effect, for example to switch between light and dark mode. Use a toggle instead."*
  - Named pattern page `https://cloudscape.design/patterns/general/selection/` ("Selection in forms"), criteria table, reproduced in full (all three rows, all four columns):

    | | Checkbox | Toggle | Radio group | Tiles |
    |---|---|---|---|---|
    | Selection | The selection takes effect at form submission. | The selection results in an immediate change. For example, turning on dark mode. | The selection takes effect at form submission. | The selection takes effect at form submission. |
    | Sub-options | The option's sub-elements should not include checkboxes. Checkboxes are used to activate and deactivate groups of sub-elements elsewhere on the page. | The option's sub-elements should not include toggles. Toggles are used to activate and deactivate groups of elements elsewhere on the page. | The option's sub-elements should not include radio groups. | The option's sub-elements should not include tiles. |
    | Additional metadata | Additional metadata, such as a description, can be included only in the selected state. For example, activated, enabled, on. | Additional metadata, such as a description, can be included only in the selected state. For example, activated, enabled, on. | Additional metadata, such as a description, can be included for both the on and off options. | Additional metadata, such as descriptions, lists, and/or images, can be included for both the on and off options. |

    Same page, prose accompanying the table: *"Binary choices made by using checkboxes, radio groups, and tiles should take effect at form submission, for example in a creation or edit flow."* / *"Use a toggle for an option that takes effect immediately, such as turning on a system feature that results in a visible interface change, for example, turn on dark mode."*

    Authority category: `named pattern` (the criteria table and its accompanying prose) plus `component guidance` (the per-component dos/don'ts), used together — but this is not a `SYNTHESIS` in the sense of bridging gaps: both sources state the same rule independently and consistently, so each is cited as direct support for its own half of the claim.
- **Evidence mode:** `VERBATIM` (every quoted string above was re-checked character-for-character against the fetched page content).
- **Authority strength:** `REQUIRED`. Both component pages phrase this as an explicit "Don't X... use Y instead" pairing in both directions (checkbox page tells you not to use it for immediate effect and to use toggle instead; toggle page tells you not to use it for form-submission-activated options and to use checkbox instead), and the named pattern's criteria table states the "Selection" row as a flat factual differentiator with no hedging ("takes effect at form submission" vs. "results in an immediate change"), not one of several equally supported options.
- **Applicability argument:** (1) The task match is not superficial — the pattern's own worked examples ("turning on dark mode," "toggling versioning on an S3 bucket") are themselves account/system preference toggles structurally identical to "require two-factor authentication" and "send email notifications," i.e., single independent boolean settings with no interdependency and no accompanying form. (2) The current implementation solves exactly the problem the Toggle guidance addresses: an option whose change is meant to take effect immediately — this is proven by the surface's own code, not inferred from the label alone: the `onChange` handler fires the PATCH request synchronously, with no batching, no draft state, and no save action anywhere on the page. (3) Swapping `Checkbox` for `Toggle` preserves the exact same user task (turn each setting on/off, applied immediately) — it changes no data model, no API call, no state shape, only the rendered control. (4) The difference is one an experienced Cloudscape implementer would very likely fix: the current choice sits on the wrong side of an explicit, symmetric "Don't do X, do Y instead" pairing that both affected component pages state independently, reinforced by a named pattern's criteria table that treats the "immediate vs. form-submission" axis as a hard differentiator, not a matter of preference. I checked the whole criteria table for a same-tier tie per the anti-fundamentalism rule: the "Additional metadata" row does place Checkbox and Toggle in the same tier, but that row concerns a different property (what metadata can be shown per state) and does not touch, let alone contradict, the "Selection" row's explicit checkbox-vs-toggle differentiation that this finding rests on.
- **Current expression:** Two `Checkbox` components, each independently and immediately persisting its own change via a PATCH request, with no form/save step anywhere on the page.
- **Native expression:** Two `Toggle` components (`@cloudscape-design/components/toggle`) in the same `Container`/`SpaceBetween` composition, each still calling `updateAccountSetting` from its own `onChange`. No other structural change is implied — the existing "auto-apply, no save button" composition is itself the correct shape for this task per the same guidance; only the two component choices are misaligned with it.
- **Why it matters:** This is not a cosmetic difference — Cloudscape's own component and pattern documentation uses the "auto-applying account/system setting" shape (this task's exact shape) as the canonical example distinguishing Toggle from Checkbox, and states the opposite mapping (Checkbox for immediate effect) as an explicit Don't on both sides. An app otherwise built on Cloudscape's checkbox-means-"apply at submission" / toggle-means-"applies now" convention will read this page as inconsistent with that convention, and a user familiar with that convention could reasonably (if incorrectly) expect these checkboxes to require a save action given how the rest of a Cloudscape-conventional app would behave.
- **Boundary check:** This is a component-selection judgment — which documented control communicates "this takes effect immediately" versus "this takes effect at submission" — not a question of whether the checkboxes are implemented correctly (they are) or a generic usability complaint; the guidance being violated is stated in Cloudscape's own component and pattern documentation, not general UX intuition.

## Suppressed (low materiality or weak applicability)

- Whether the two settings should be split into two `Container`s (one for security, one for notifications) instead of one combined "Security and notifications" container — considered, but no Cloudscape component/pattern guidance establishes a rule about grouping unrelated settings into one vs. multiple containers; this is an organizational/aesthetic judgment with no citable applicability, so it was not reported.

## Orientation notes

- The overall page scaffold — `ContentLayout` with an `h1` `Header`, containing a `Container` with its own `h2` `Header`, wrapping form-adjacent content in `SpaceBetween` — is standard, already-native Cloudscape composition for a settings-style page and was not flagged.

## What was not evaluated

Implementation correctness was not assessed: whether the raw `fetch` call in `updateAccountSetting` should use a loading/error-handling pattern, whether the PATCH lacks debouncing or optimistic-update rollback on failure, accessibility mechanics of the `Checkbox`/`Toggle` markup, and any deprecated-prop or API-usage concerns are all out of this skill's scope. General UX judgment (e.g., whether immediate auto-save without confirmation is a good interaction for security-sensitive settings like two-factor authentication) was also not evaluated — that is a product/UX question, not a design-system native-expression question, and is out of scope here regardless of how it's answered.
