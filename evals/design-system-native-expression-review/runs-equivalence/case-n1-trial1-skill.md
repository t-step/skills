# Design-System Native-Expression Review: AccountSettings.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A signed-in user views and changes two independent, boolean account-level settings — "Require two-factor authentication for sign-in" and "Send email notifications for account activity." Each setting is a standalone on/off preference; there is no surrounding create/edit form, no Save/Submit/Cancel action, and each change is persisted to the server (`PATCH /api/account/settings`) the instant the control is toggled, from inside the control's own `onChange` handler.

**Packages / versions:** Resolved via `scripts/resolve_versions.py` against `fixture/package-lock.json`: `@cloudscape-design/components` 3.0.900 (declared `^3.0.900`), `@cloudscape-design/collection-hooks` 1.0.60, `@cloudscape-design/global-styles` 1.0.45. All fully resolved (no unresolved semver range). The cited Checkbox/Toggle usage guidance and the "Selection in forms" pattern are foundational, long-stable guidance (Toggle and Checkbox usage pages both list "Published: May 4, 2020"; the pattern page "Published: June 5, 2020") with no version-gated behavior found, so the resolved version does not affect applicability of the findings below.

**Authority categories found in this corpus:** Component guidance (per-component "Usage" tab: General guidelines with explicit Do/Don't lists, Features, Writing guidelines, Accessibility guidelines) and named patterns (the `Patterns` section, e.g. "Selection in forms," which includes explicit criteria/decision tables comparing components for a stated user problem). Both categories were used below; no separate "composition guide" or "foundation" tier was needed to settle this finding.

## Findings

### Finding 1: Two immediate-effect account settings are implemented as `Checkbox`, where Cloudscape's own component guidance and its "Selection in forms" pattern both direct immediate-effect boolean options to `Toggle`

- **Finding:** Both boolean settings on this page ("Require two-factor authentication for sign-in" and "Send email notifications for account activity") are rendered as `Checkbox` and each persists its new value immediately via a PATCH call fired from inside `onChange`, with no Save/Submit action anywhere on the page. Cloudscape's own component guidance and its dedicated "Selection in forms" pattern both state, directionally, that this exact behavior (immediate effect, no form submission) is the Toggle case, not the Checkbox case.
- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** The user turns two independent account security/notification settings on or off, and expects each change to take effect immediately (the code persists it right away, with no confirmation/submit step in between).
- **Repository evidence:** `evals/design-system-native-expression-review/cases/case-n1-account-settings/fixture/src/pages/AccountSettings.tsx`:
  - Lines 13-18: `updateAccountSetting` fires `fetch('/api/account/settings', { method: 'PATCH', body: JSON.stringify({ [key]: value }) })` — a network write with no batching, no surrounding form submission.
  - Lines 28-36: `<Checkbox checked={requireTwoFactor} onChange={({ detail }) => { setRequireTwoFactor(detail.checked); updateAccountSetting('requireTwoFactor', detail.checked); }}>Require two-factor authentication for sign-in</Checkbox>` — the PATCH is called synchronously inside `onChange`, i.e. on every toggle, not on a later save.
  - Lines 37-45: the second `Checkbox` ("Send email notifications for account activity") follows the identical immediate-PATCH-on-change structure.
  - There is no `Form`, no submit/save `Button`, and no other mechanism in the file that defers the effect of either control past the moment the user flips it.
- **Authority evidence:**
  - Component page, Checkbox, Usage tab, General guidelines, "Don't" list (fetched `https://cloudscape.design/components/checkbox/?tabId=usage`): "Don't use for options that take immediate effect, for example to switch between light and dark mode. Use a toggle instead."
  - Component page, Toggle, Usage tab, General guidelines, "Do" list (fetched `https://cloudscape.design/components/toggle/?tabId=usage`): "Use for an option that takes effect immediately, for example toggling versioning on an S3 bucket to enable or disable the storage of multiple versions of objects."
  - Component page, Toggle, Usage tab, General guidelines, "Don't" list (same page): "Don't use a toggle for options that are activated at form submission, such as an acknowledgement of EULA or Terms and Conditions. In this case, use a checkbox."
  - Named pattern, "Selection in forms" (fetched `https://cloudscape.design/patterns/general/selection/`), "Boolean selection criteria" section, prose: "Binary choices made by using checkboxes, radio groups, and tiles should take effect at form submission, for example in a creation or edit flow." and "Use a toggle for an option that takes effect immediately, such as turning on a system feature that results in a visible interface change, for example, turn on dark mode."
  - Named pattern, "Selection in forms," full criteria table (reproduced in full, all rows and all four columns, per the finding contract):

    | Selection | The selection takes effect at form submission. | The selection results in an immediate change. For example, turning on dark mode. | The selection takes effect at form submission. | The selection takes effect at form submission. |

  - Authority category: **named pattern** (the "Selection in forms" page and its criteria table) corroborated by **component guidance** (the Checkbox and Toggle usage pages' own Do/Don't lists, which independently state the same directional rule from each component's own side).
- **Evidence mode:** VERBATIM (all quotes above copy-pasted from the fetched pages via rendered `document.body.innerText`; the criteria table is reproduced in full — every row, both differentiating and non-differentiating).
- **Applicability argument:** The "Selection" row of the table is not a tied, unranked pairing — it differentiates Checkbox and Toggle by a concrete, observable behavior: "takes effect at form submission" vs. "results in an immediate change." That is exactly the kind of surface-resolvable intent the skill's anti-fundamentalism rule asks to check against the code before treating a differentiating row as settled. Here the surface's own code resolves it unambiguously: `updateAccountSetting` is called synchronously inside each `onChange`, firing a network PATCH before any possible "submission" step, and no `Form`/submit button exists anywhere on the page to defer the effect. This is not a superficial shape match — the observed task (persist a boolean preference the instant it's changed) is precisely the problem the Toggle side of the table and the Toggle "Do" guidance describe (the S3-versioning example is structurally the same: an immediately-effective on/off account/resource setting). The current implementation solves the identical problem the pattern addresses (a boolean, immediate-effect setting), and swapping `Checkbox`→`Toggle` preserves the exact same user task and interaction shape (same label text, same boolean semantics, same immediate persistence) — it changes only which control communicates "this takes effect right now" versus "this takes effect on submission." The other table rows (Sub-options, Additional metadata) do not apply here (no sub-elements, no on/off description asymmetry), so they neither support nor undercut this finding — they are reproduced above only for completeness per the finding contract's whole-table requirement. Given two independent, directly-worded Do/Don't statements (one on each component's own page) plus a named pattern's explicit criteria table all agreeing on the same direction, an experienced Cloudscape implementer would restructure this rather than merely note it as a stylistic alternative.
- **Current expression:** Both settings are implemented with `Checkbox`, each wired to fire an immediate PATCH request in its `onChange` handler, with no form-submission step anywhere on the page.
- **Native expression:** Replace both `Checkbox` instances with `Toggle`, keeping the same labels, the same `checked`/`onChange` wiring, and the same per-field immediate PATCH-on-change behavior already present in the code — only the control itself changes.
- **Why it matters:** Cloudscape's own component guidance uses the on/off control itself as a signal to the user about *when* a change takes effect: Toggle communicates "this applies now," Checkbox (in this corpus's usage guidance) communicates "this applies once you submit/save." Using Checkbox for a setting that Cloudscape's guidance says should read as immediate is a mismatch between the communicated affordance and the actual (already-immediate) behavior of this page, and it diverges from how this design system's own documented settings idiom (and its own worked example, S3 bucket versioning) expresses the identical "flip this account/resource setting on or off, right now" task — a consistency and semantic-correctness cost for any app otherwise built on Cloudscape's documented conventions.
- **Boundary check:** This is a component-selection question — which documented on/off control best communicates the semantics this page's code already implements (immediate effect, no submission step) — not a claim about API correctness, props, styling, or a generic usability complaint; the recommended change is a like-for-like component swap that preserves the exact same task and interaction.

## Orientation notes

- The overall page composition — `ContentLayout` (page-level header) wrapping a single `Container` with its own `Header` (variant `h2`) and a `SpaceBetween` stack of settings controls — is a standard, already-native Cloudscape composition for a single-section settings surface; no named pattern or composition guidance suggests a different top-level structure for this task.
- The absence of a `Form` component and a Save/Submit action is *not* itself a finding: given the surface already commits each change immediately (per-field PATCH on change), wrapping it in `Form` with a submit action would itself be the non-native choice per the "Selection in forms" pattern's own "takes effect at form submission" vs. "immediate change" distinction — the current no-Form, immediate-persistence composition is the correct shape for the Toggle-based expression recommended in Finding 1.
- `SpaceBetween size="l"` used to stack the two settings controls is ordinary, correctly-scaled usage; no deviation from documented spacing guidance was found.

## What was not evaluated

Implementation correctness was not evaluated and should not be read as "checked and fine," including: whether firing a raw `fetch` PATCH directly from a UI event handler (with no loading state, error handling, retry, or optimistic-update rollback on failure) is a sound pattern; whether `updateAccountSetting`'s fire-and-forget promise handling is acceptable; TypeScript/prop correctness of the `Checkbox`/`Toggle` usage; and any accessibility implementation mechanics. General UX and product judgment were also not evaluated, including whether these two settings belong on the same page, whether additional settings are missing, information architecture, or copy quality beyond what was needed to establish the user task.
