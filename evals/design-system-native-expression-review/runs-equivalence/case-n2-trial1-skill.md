# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape

**Inferred user task:** Create a new cloud compute "environment" (an AWS-EC2-style resource: region, instance type/count, auto-scaling bounds, VPC/subnet/security group/public IP, storage volume, monitoring, and resource tags) by filling in a single page of grouped configuration fields and submitting via a "Create environment" action. This is a first-time resource-creation flow, not an edit/view of an existing resource (all fields are seeded with defaults or empty, and the submit handler only logs a create payload).

**Packages / versions:** `@cloudscape-design/components` — declared `^3.0.900` in `fixture/package.json`, resolved/locked to `3.0.900` in `fixture/package-lock.json` (via `resolve_versions.py`).

**Authority categories found in this corpus:** Two meaningful tiers were used for this review: (1) **component guidance** — per-component pages under `/components/` with explicit "Do"/"Don't" usage sections (Select, Toggle, Checkbox, Wizard, Tag editor); (2) **named patterns** — task-level pages under `/patterns/resource-management/create/`, including an explicit criteria/decision table that differentiates Modal, Single page create, and Multipage create by length, complexity, recovery, error handling, frequency, and sub-resource support. No separate "composition guide" or "foundation" tier was needed for either finding below.

## Findings

### Finding 1: Page-level composition exceeds Cloudscape's own documented threshold for single-page create

- **Finding** — The surface implements resource creation as one long single-page `Form` with six `Container` groups and 20 fields, but Cloudscape's own create-resource criteria table places a form this size in the "multipage create" (`Wizard`) tier, not "single page create."
- **Type** — `combined selection + composition`
- **Materiality** — `high`
- **Confidence** — `high`
- **User task** — Creating a new environment resource by configuring six logically distinct categories of settings (General, Compute, Networking, Storage, Monitoring, Tags) before a single "Create environment" submission.
- **Repository evidence** — `CreateEnvironment.tsx`: one `ContentLayout` → `Form` → `SpaceBetween` wrapping six `Container`s, each with an `h2` `Header` (General L108, Compute L126, Networking L147, Storage L176, Monitoring L194, Tags L208), with no `ExpandableSection` (confirmed absent from `inspect_surface.py`'s import list) separating "primary" from "additional" fields. Counted interactive fields: General 3 (L110-122), Compute 4 (L128-143), Networking 4 incl. 1 checkbox (L149-172), Storage 3 incl. 1 checkbox (L178-190), Monitoring 3 incl. 1 checkbox (L196-204), Tags 3 (L210-218) = **20 fields across 6 Container groups**, matching `inspect_surface.py`'s tag counts (`FormField`: 17, `Checkbox`: 3).
- **Authority evidence** — `https://cloudscape.design/patterns/resource-management/create/`, criteria table (reproduced in full):

  | | Modal | Single page create | Multipage create |
  | --- | --- | --- | --- |
  | Length | = 1 field | Between 2 and 15 fields in the primary section or up to 5 groups of settings | More than 16 fields in primary sections or more than 5 groups of settings |
  | Complexity | Basic text input fields and simple selects | Flow does not require any category to have its own page | Concepts require in-depth interactions that benefit from having their own page |
  | Recovery | Input is mutable after creation | Input mutable after creation | Input immutable after creation |
  | Error handling | In trigger page | In creation page | In every single step and in summary step |
  | Frequency | n/a | Frequent | Infrequent |
  | Sub-resource create | No | Yes | Yes |

  Same page: "Use single page create if you want your users to create a resource on a single page. This component is optimized for simple to medium-complex forms." / "Use the multipage create, which employs the wizard component, when you want users to create resources by completing a set of interrelated tasks. We recommend multipage create for long or complex configurations." Also, `https://cloudscape.design/components/wizard/` (Usage tab), "Don't" list: "Don't use the wizard inside of a content layout component." and "Do": "Apply the recommended max content area width and default panel states by setting `contentType='wizard'` in the app layout component." Authority category: **named pattern** (criteria table) plus **component guidance** (Wizard Do/Don't) for the implied component-level consequence.
- **Evidence mode** — `VERBATIM`
- **Applicability argument** — (1) Task match: the create-resource pattern page's stated problem is exactly this surface's problem — creating a resource via a form of grouped settings; this is not a superficial shape match, it's the named pattern's literal subject. (2) Current implementation solves the same problem the pattern addresses (resource creation via categorized settings), just packaged as one page. (3) The proposed Wizard/multipage alternative is explicitly documented as an alternate composition for the *same* create-resource task — it does not change what is being created or which fields exist, only how they're paged. (4) Materiality: the surface crosses the documented "Length" threshold on **two independent, non-overlapping axes at once** — 20 fields (>16) and 6 groups (>5) — not a borderline case. The "Frequency" row is explicitly marked "Only use frequency as a criterion if you're unsure which pattern to use," so it doesn't apply here and doesn't create a tie; no row in this table places single-page and multipage create in the same tier for this surface's numbers — every row differentiates directionally. This finding therefore survives the same-tier equivalence check.
- **Current expression** — A single `ContentLayout` > `Form` containing 6 `Container`s in a vertical `SpaceBetween`, all fields visible on one continuous scroll, one set of Cancel/Create actions at the end.
- **Native expression** — A Cloudscape `Wizard` (not nested inside `ContentLayout`, per its documented "Don't"), with the app layout's `contentType` set to `'wizard'`, collapsing the six existing `Container`s into a small number of wizard steps (the pattern recommends three to five, and permits up to seven), each step keeping its existing `Container`/`FormField` content, followed by an optional review step summarizing all sections with per-step edit links — per the multipage create pattern's documented building blocks. The exact step grouping (e.g., whether Monitoring and Tags merge into one step) is an implementation choice not settled by the cited authority.
- **Why it matters** — The design system's own numeric criteria, applied to this surface's own field/group counts, place it in the multipage-create tier the corpus explicitly recommends for "long or complex configurations." Leaving it as a single page also diverges from the same table's paired guidance on recovery and error handling for forms this size (multipage create expects "In every single step and in summary step" error handling and treats input as immutable after creation, versus the single-page tier's "In creation page" handling) — an experienced Cloudscape implementer reading this table against a 20-field, 6-group form would restructure it, not merely note it as a stylistic alternative.
- **Boundary check** — This is a composition-level design-system concept selection (single-page create vs. wizard, per Cloudscape's own decision table) grounded in an explicit, numeric, documented criterion — not an implementation-correctness matter (no API/prop defect is being claimed) and not a generic UX complaint ("too long a form"), since the materiality claim rests on the corpus's own stated thresholds rather than the reviewer's aesthetic judgment.

### Finding 2 (intent-dependent): Fixed "Owner / Cost center / Environment" tag fields vs. the documented Tag editor component

- **Finding** — The "Tags" section hard-codes three named free-text `Input` fields (Owner, Cost center, Environment tag) instead of using Cloudscape's purpose-built `TagEditor`, whose own guidance names exactly this context ("create... flows") as its intended use — but whether that substitution is actually native depends on unresolved product intent.
- **Type** — `intent-dependent`
- **Materiality** — `medium`
- **Confidence** — `medium`
- **User task** — Attaching Owner / Cost center / Environment metadata to the new environment resource at creation time.
- **Repository evidence** — `CreateEnvironment.tsx` L208-220: `Container` header "Tags" with three independent `FormField`+`Input` rows bound to separate `useState` strings (`ownerTag`, `costCenterTag`, `environmentTag`), each submitted as its own payload key in `handleSubmit` (L86-88). No mechanism exists to add, rename, or remove a tag.
- **Authority evidence** — `https://cloudscape.design/components/tag-editor/` (Usage tab): description — "An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags." Features — "Tags are metadata assigned to a resource, consisting of a key (mandatory) and a value (optional)." General guidelines, "Do": "Use the tag editor to manage tags only in create and edit flows." Authority category: **component guidance**.
- **Evidence mode** — `VERBATIM`
- **Applicability argument** — Owner/Cost center/Environment are the textbook examples of AWS-style resource tags (key/value metadata used for cost allocation and ownership), and this surface is literally a "create" flow — the exact context the Tag editor's own "Do" names. That satisfies task-match (point 1) *only if* these three fields are meant to be an open-ended, user-extensible tag set. But the current code hard-codes exactly three named fields with no add/remove/rename affordance, which reads equally plausibly as a deliberate, fixed compliance schema (organizations commonly mandate exactly these three tags on every resource) — a reading under which a generic, arbitrary-key `TagEditor` would *not* preserve the same task (point 3 fails): it would let users omit or mistype the very keys the product may intend to require. Nothing in the file's copy, comments, or types resolves which reading applies.
- **Native expression** — Not stated with confidence. If the intent is open-ended tagging, the native expression is a `TagEditor` seeded with `Owner`/`Cost center`/`Environment` as default rows. If the intent is a fixed mandatory schema, the current three-`FormField` approach may already be the more task-preserving choice, and adopting `TagEditor` would change the task (arbitrary tagging) rather than realign it.
- **Why it matters** — Resolving this wrong could either quietly let users drop or rename organization-mandated tags (compliance-schema reading) or leave the app hand-rolling a narrower, non-extensible version of key/value tag management that Cloudscape already ships as a dedicated, spec'd component with its own limit/validation/removal behavior (arbitrary-tag reading) — but only one of these is actually a finding, and the surface doesn't say which.
- **Boundary check** — This is a component-selection question (was the design system's dedicated resource-tagging component considered before hand-rolling three fixed name/value inputs), gated entirely on product intent the surface doesn't establish — not a generic complaint about typing three fields, and reported as `intent-dependent` rather than picked in either direction per the skill's missing-intent handling.

## Suppressed (low materiality or weak applicability)

- **Select with very short/hard-coded option lists (Region 2, VPC 1, Subnet 1, Security group 1, Instance type 2, Volume type 2 options) — considered swapping for RadioGroup/Tiles.** Suppressed: Select's own fetched usage guidance states no option-count threshold that redirects short lists to RadioGroup/Tiles (its only relevant "Don't" targets action-initiating selects with large option sets, inapplicable here); and these arrays are visibly fixture stub data for fields whose real cardinality (AWS regions, VPCs, subnets, security groups) is normally large in production, so judging component fit against the stub's artificially small count would fabricate intent the surface doesn't establish.
- **Splitting the 20 fields into a primary section + collapsible "Additional settings" `ExpandableSection`, while remaining single-page.** Suppressed as a partial fix subsumed by Finding 1: even after such a split, the fields would still be organized under 6 named `Container`s, exceeding the single-page-create pattern's own "up to 5 groups of settings" ceiling on its own — reporting this separately would split one underlying recommendation into two.
- **Auto-scaling minimum/maximum as two separate numeric `Input`s (no dedicated dual-bound control).** No Cloudscape component or documented pattern for a numeric min/max pair was found in this corpus; nothing beyond bare inference would ground a finding, so none is reported.

## Orientation notes

- `Checkbox` (not `Toggle`) used for "Assign a public IP address" (L170-172), "Encrypt volume" (L188-190), and "Enable detailed monitoring" (L196-198) is correct: Toggle's own "Don't" list states "Don't use a toggle for options that are activated at form submission, such as an acknowledgement of EULA or Terms and Conditions. In this case, use a checkbox." (`cloudscape.design/components/toggle/`). All three options here only take effect on the "Create environment" submit (L67-90), matching this rule directly.
- Form actions — "Cancel" as a link-variant `Button` and the primary submit `Button` labeled "Create environment" (L98-103) — match the create-resource pattern's writing guidelines: "For the button that allows the user to exit the form, use this text: *Cancel*" and the submit-button format "*[Active verb] [resource type]*" (`cloudscape.design/patterns/resource-management/create/single-page-create/`).
- Page header "Create environment" as an `h1` `Header` (L93) matches the same page's guideline to begin the form page title with an active verb (*Create [resource name]*).
- All `Select` instances are wrapped in `FormField` with a visible label (Region, Instance type, VPC, Subnet, Security group, Volume type), matching Select's documented "Do": "Always include a visible label. In forms, use the form field." (`cloudscape.design/components/select/`).

## What was not evaluated

Implementation correctness — e.g., `type="number"`/`type="email"` passed to Cloudscape's `Input` rather than a dedicated numeric/validation mechanism, the native `<form onSubmit>` wrapper's interaction with `Form`'s own `actions` slot, hard-coded stub option arrays, and app-owned accessibility mechanics — was not evaluated. General UX/product judgment — whether 20 fields across 6 categories is the right amount of configuration to expose at all, field ordering, default values chosen, or whether "environment" is the right resource abstraction — was also not evaluated.
