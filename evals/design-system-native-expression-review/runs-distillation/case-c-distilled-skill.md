# Design-System Native-Expression Review: WorkspaceDetails

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** View the details of a single workspace resource ("eng-platform-prod"): its stable, cross-cutting identity/configuration facts (name, owner, region, plan tier, created date, status), plus two further groupings of task-specific information about that same resource — its members (a multi-row, comparable collection) and its activity history (a linear read-only log) — reachable by switching tabs, with page-level Edit/Delete actions available throughout.

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked to `3.0.900` (resolved from `package-lock.json` via `resolve_versions.py`). The findings below concern component/composition concepts (Tabs, Table, Key-value pairs, Container, details-page structure) that have been stable across recent 3.x releases; no finding here depends on an unresolved semver range.

**Authority categories found in this corpus:** Cloudscape's discovery index (`llms.txt`) exposes distinct **component guidance** pages, a **named-pattern** layer (including a dedicated Resource-management → Resource-details family: "Details page," "Details page with tabs," "Details page as a hub," "Resource details"), **foundations**, and **demos**. Composition-level guidance for this task lives inside the named-pattern pages themselves (their "Building blocks" sections); there is no separate, distinct "composition guide" tier beyond the named patterns.

## Findings

**Finding 1 — The workspace's general configuration is expressed as a single-row Table inside an "Overview" tab, when Cloudscape's own Details-page-with-tabs pattern documents this exact content as a persistent Key-value-pairs summary container positioned outside the tab set.**

- **Type:** `combined selection + composition`
- **Materiality:** `high`
- **Confidence:** `high`
- **User task:** Same as above — view a workspace's stable, read-mostly identity/config facts alongside tabbed access to its members and activity history.
- **Repository evidence:** `fixture/src/pages/WorkspaceDetails.tsx`. Lines 30–33 contain the developer's own stated intent: "name, owner, region, plan tier, created date, and status are the workspace's own general configuration facts: stable, read-mostly, and relevant no matter which tab a user is currently looking at (Members or Activity). Tabs organize the rest." Despite that, lines 62–91 implement this content as the `'overview'` entry inside the `Tabs` component's `tabs` array, rendered via a `Table` with `columnDefinitions` for Name/Owner/Region/Plan/Created/Status and a single fabricated row (`items={[{}]}`, `trackBy={() => 'workspace-overview-row'}`) — an artifact of forcing singleton attribute-value data into Table's row-collection data model.
- **Authority evidence:**
  - Named pattern, *Details page* (`https://cloudscape.design/patterns/resource-management/details/details-page/`), building block D: `"Details summary container — Place the most relevant information about the resource in this container. To organize content, use key-value pairs."` Its writing guidelines add: `"For the details summary container, use this text: General configuration [Resource type] settings"` — verbatim-confirmed against the page's raw HTML.
  - Named pattern, *Details page with tabs* (`https://cloudscape.design/patterns/resource-management/details/details-page-with-tabs/`), building block D ("Details summary container - optional"): `"For a details page with tabs, this section serves as a summary that is always visible when users switch between the tabs."` and `"Use it to display important information that applies to tasks in all the tabs."` This page's own component-specific guidelines state: "Breadcrumbs, buttons and containers — Follow the guidelines for details page," explicitly importing the base pattern's key-value-pairs instruction into the tabs variant. Both quotes verbatim-confirmed against raw HTML.
  - Component guidance, *Key-value pairs* (`https://cloudscape.design/components/key-value-pairs/`): `"Key-value pairs are lists of properties (labels) followed by their corresponding values."`
  - Component guidance, *Table* (`https://cloudscape.design/components/table/`, meta description): `"Presents data in a two-dimensional table format, arranged in columns and rows in a rectangular form."`
  - Authority category: `named pattern` (primary), `component guidance` (supporting).
- **Evidence mode:** `SYNTHESIS` — the component-selection half (use key-value pairs) and the composition-placement half (keep the summary persistent, outside the tabs) are each individually verbatim-stated, on two pages of the same pattern family, and the tabs-variant page explicitly cross-references the base page's container guidance rather than leaving the bridge to reviewer inference.
- **Applicability argument:** (1) Task match is exact, not superficial: this is precisely "a single resource's configuration details plus tabbed related-information groupings," the stated problem of the Details-page-with-tabs pattern. (2) The current code solves the identical problem — it isn't repurposed for something else. (3) The proposed change (move the same six facts into a persistent Key-value-pairs container above the tabs; reduce `Tabs` to Members/Activity) preserves the exact same data and task, only relocating and re-componenting it. (4) The difference is behavioral, not stylistic: today the "always visible" information disappears the moment a user opens Members or Activity, which is precisely the failure mode the pattern's summary-container building block exists to prevent — and the surface's own code comment already states the intended behavior that the current structure fails to deliver. No tied/decision-table language appears in either pattern page for this building block — its role is stated directionally ("serves as a summary that is always visible"), so the same-tier-equivalence check does not apply.
- **Current expression:** General configuration facts rendered as a `Table` with one synthetic row, nested as the `'overview'` tab inside `Tabs` — invisible whenever `Members` or `Activity` is active.
- **Native expression:** A `Container` (titled "General configuration," per the pattern's own writing guidance) holding a `KeyValuePairs` list of Name/Owner/Region/Plan/Created/Status, placed in `ContentLayout` above the `Tabs`, which then holds only `Members` and `Activity`.
- **Why it matters:** The current structure defeats the specific, documented function of the building block it's attempting to implement (an always-visible cross-tab summary) and asks `Table` — documented as a two-dimensional rows-and-columns concept — to represent singleton attribute-value data, requiring a fabricated one-item array just to satisfy Table's API shape. This is also a consistency cost: any Cloudscape-fluent engineer extending this page toward the standard "resource details" shape will need to undo the current structure rather than build on it.
- **Boundary check:** This is a component/composition judgment — which documented building block (Key-value pairs summary container vs. Table-as-tab) matches the stated task — not an implementation defect (no prop/API is misused) and not a subjective usability complaint (the pattern page states the container's persistence function directly).

## Suppressed (low materiality or weak applicability)

- **Activity tab's `List` of concatenated strings vs. a structured event-log component.** Checked List's component page and the pattern index for an "activity/history" named pattern or usage guideline differentiating List from Table for chronological structured events; found none — List's documentation is limited to a one-line description with no comparative guidance. Reporting a swap here would rest on the component's mere existence, which the anti-fundamentalism rule blocks.
- **Breadcrumb depth (`Workspaces > eng-platform-prod`, two levels) vs. the Details-page pattern's example structure (`[Service name] > [Resource type] > [Resource name/ID]`, three levels).** The pattern shows a three-level example, but whether this app has a distinct "service name" tier above "Workspaces" can't be established from this bounded file; downgraded as intent-dependent-leaning and low materiality (content/labeling, not component/composition selection).
- **Members table lacking a `Header` (title/counter) composed via the `header` prop.** No documented rule found requiring every in-tab Table to carry its own `Header`; pursuing this would read as generic UX polish wearing a citation.
- **Replacing `Tabs` with plain stacked sections for Members/Activity.** "Details page with tabs" is itself a fully valid named pattern matching the current approach exactly; nothing in the retrieved guidance directionally prefers sections over tabs for this data shape, so treating one as more native than the other would be reporting an equally-valid alternative.

## Orientation notes

- `Header` with `SpaceBetween`-grouped `Button` actions (Edit, Delete) matches the Details-page pattern's building block C verbatim guidance ("Use when the actions will affect the entire resource. For example: Edit or Delete") — correct, already-native usage.
- `BreadcrumbGroup` is the correct component for building block A; its item-depth is a content question addressed separately above, not a component-selection issue.
- The Members `Table<Member>` (Name/Email/Role, real per-row data, `empty` state, `trackBy="email"`) correctly matches Table's own documented purpose — a genuine multi-row collection — in clear contrast to the Overview misuse above.
- `Tabs` used to separate Members and Activity aligns with the pattern's "one tab, one task" / "organize... into mutually exclusive, meaningful content groups" guidance.

## What was not evaluated

Implementation correctness — `trackBy` usage, `ariaLabels`/`ariaLabel` completeness, the synthetic single-item array as an API-usage detail beyond what was needed as component-mismatch evidence, and any other prop/accessibility mechanics — was not assessed. General UX and product judgment (information density, whether Edit/Delete should be split into per-tab contextual actions, breadcrumb wording/content beyond structure, role-badge styling) were likewise not evaluated; their absence from this report should not be read as "checked and fine."
