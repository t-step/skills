# Design-System Native-Expression Review: Route ETA / Stop Dialog flow

**Design system:** Material UI (`@mui/material` + `@mui/icons-material`)

**Inferred user task:** A user looks up a specific bus route, browses its full ordered list of stops with live/scheduled ETAs and fare information (any stop can be expanded inline, in-place, without leaving the route page), and can drill from any stop into a focused, near-fullscreen detail view for that single stop (bookmark it, launch external map/directions, or navigate to that stop's own page). A page-level banner also invites the user to reload route data when the server has newer schedule data than what's cached locally.

**Packages / versions:** `@mui/material` 5.15.11 and `@mui/icons-material` 5.15.11, both resolved (locked) from `hk-independent-bus-eta/yarn.lock` against the declared `^5.15.11` range in `package.json`. Nothing below depends on an unresolved semver range.

**Authority categories found in this corpus:** Component guidance pages only. Each retrieved MUI page (`react-alert`, `react-dialog`, `react-accordion`, `react-snackbar`) bundles its own introduction/anatomy, a "Usage" section, and worked demos/customization examples directly on the component page. `mui.com/llms.txt` does not resolve (404), and none of the four pages retrieved exposed a separate named-pattern, task-pattern, or composition-guide tier comparable to Cloudscape's pattern library. Where a composition-level question had no dedicated pattern-tier source, reasoning below is labeled `SYNTHESIS`/`INFERRED` rather than treated as resting on a composition-guide.

## Findings

### Finding 1 — `RouteUpdateNotice` reimplements Alert's job with a bespoke Box

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Tell the user, in-line on the page (not blocking it), that fresher route data exists on the server than what's cached locally, and let them trigger a reload.
- **Repository evidence:** `src/components/route-eta/RouteUpdateNotice.tsx:29-33` renders a plain `Box` (with `onClick={renewDb}`) wrapping a `Typography` containing a literal emoji (`⁉️`) plus a translated string; styling at lines 38-49 hand-rolls a bordered, padded, pointer-cursor surface (`borderStyle: "solid"`, `borderWidth: 1`, `cursor: "pointer"`). No MUI notification component (`Alert`, `Snackbar`) is imported anywhere in this file — confirmed by `inspect_surface.py`, whose `design_system_imports` for this file lists only `Box`, `SxProps`, `Theme`, `Typography`.
- **Authority evidence:** The MUI Alert page's own Introduction and Usage sections describe Alert's job as giving the user brief, potentially time-sensitive information without interrupting the rest of the app, explicitly contrasted with Dialog (reserved for blocking/critical decisions) — this is the same "non-blocking, in-flow" job `RouteUpdateNotice` performs. The Actions section documents an `action` prop for attaching a click affordance (any element, including a `Button`) to the right of the alert message, and the Severity/Icon sections document a built-in `severity`-driven color+icon system (`success`/`info`/`warning`/`error`) for exactly this kind of status framing. Authority category: **component guidance**.
- **Evidence mode:** PARAPHRASE (multiple facts from the single Alert page, restated in my own words; not a single copy/paste sentence).
- **Authority strength:** RECOMMENDED — the Alert page's Usage section states, in normative terms, what Alert is for and explicitly differentiates it from Dialog, i.e., it establishes Alert as the preferred vocabulary for this job; it does not, however, contain an explicit "don't hand-roll this with a Box" prohibition, so REQUIRED would overstate it.
- **Applicability argument:** (1) `RouteUpdateNotice`'s stated problem — a short, non-blocking, actionable, in-flow status message — is exactly the problem Alert's Usage section describes itself as solving, not a superficial shape match. (2) The current Box+Typography does solve the same problem today, just without any of Alert's semantics. (3) Swapping to `Alert` (with an `action` `Button` calling `renewDb`, and a `severity` matching this notice's intent — e.g. `info`) preserves the same task: same trigger condition, same click-to-reload behavior, same placement in the page flow. (4) The difference is material: the current version discards Alert's entire severity/icon/color vocabulary and its documented `action` slot in favor of an ad hoc emoji-and-border banner that shares no visual or semantic language with any other MUI-driven notification in the app; an MUI-fluent implementer maintaining consistency across the app's notification surfaces (this same page already uses `Snackbar` correctly, see Orientation notes) would very plausibly restructure this into `Alert`.
- **Current expression:** Custom `Box` with `onClick`, a `Typography` containing an emoji used as a pseudo-severity-icon, and a manually styled border/padding approximating an alert surface.
- **Native expression:** `<Alert severity="info" action={<Button onClick={renewDb} color="inherit">…</Button>}>{t("db-renew-text")}</Alert>` (or `warning` severity, depending on how urgently stale data should read) — giving the notice a real icon, theme-consistent coloring, and a keyboard-reachable action button instead of an emoji and a whole-block click target.
- **Why it matters:** The surface already has one other data-freshness/status affordance in this same flow (`Snackbar` for the copy confirmation, see Orientation notes) built on MUI's own component vocabulary; `RouteUpdateNotice` is the one place in this bounded surface that steps entirely outside that vocabulary for a functionally identical "status + action" job, so it neither picks up theme severity coloring nor benefits from `Alert`'s already-built action-slot layout — a real consistency and vocabulary-reuse cost, not merely an aesthetic one.
- **Boundary check:** This is a component-selection question — whether MUI's own `Alert` (rather than a bespoke `Box`+`Typography` banner) is the right vocabulary for an in-flow, actionable status message — not a critique of how the current banner happens to be coded or a generic complaint about its UX.

### Finding 2 — `StopDialog`'s title bar carries the dialog's action buttons instead of `DialogActions`

- **Type:** documented composition
- **Materiality:** medium
- **Confidence:** high
- **User task:** From within a route's stop list, open a focused detail view for one stop and let the user bookmark it, launch external directions/map apps, jump to that stop's own page, or dismiss the view.
- **Repository evidence:** `src/components/route-eta/StopDialog.tsx:69-93`. The `DialogTitle` (lines 69-93) contains five `IconButton`s in a single flex row: bookmark toggle (71-73), directions (76-78), map (79-81), "open stop page" (82-86), and close (89-91) — all siblings of the stop name text, inside `DialogTitle`. `DialogActions` is never imported (confirmed by `inspect_surface.py`'s import list for this file: `Box, Dialog, DialogContent, DialogTitle, IconButton, SxProps, Theme` — no `DialogActions`).
- **Authority evidence:** The Dialog page's Introduction section enumerates Dialog's constituent parts and states that `DialogActions` is an optional container purpose-built for a dialog's buttons, distinct from `DialogTitle` and `DialogContent`. Two of MUI's own worked examples on the same page apply this split consistently: the "Customized Dialogs" demo keeps `DialogTitle` to the title text plus a single top-right close `IconButton`, placing its "Save changes" action button in `DialogActions`; the "Full-screen dialogs" demo's `AppBar`/`Toolbar` header holds only a leading close icon and the title (`flex: 1`), with a single trailing action button, not a cluster of unrelated actions. Authority category: **component guidance** (anatomy definition) plus two illustrative demos on the same page.
- **Evidence mode:** SYNTHESIS (the anatomy line naming `DialogActions`'s purpose, combined with the consistent header shape shown across two separate demos on the same page).
- **Authority strength:** INFERRED — no cited text says buttons must not live in `DialogTitle`; the case rests on combining the anatomy definition with a repeated example pattern, and per the "examples illustrate, they don't mandate" rule that repetition alone can't be elevated to REQUIRED/RECOMMENDED.
- **Applicability argument:** (1) `StopDialog`'s bookmark/directions/map/link-out actions are exactly the kind of "dialog's buttons" `DialogActions` is documented to hold, not a superficially similar but different problem. (2) The current title row already performs that same job today, just via a different slot. (3) Moving those four buttons into `DialogActions` (keeping only the stop name and a close affordance in `DialogTitle`, mirroring MUI's own two demos) preserves the same task and the same set of user-facing actions. (4) The difference is material: five icon buttons currently sit flush against the dismiss control in one crowded row, a shape neither of MUI's own two documented Dialog headers uses — both reserve the title band for identity + dismissal only.
- **Current expression:** All five actions (bookmark, directions, map, stop-page link, close) rendered together as `IconButton`s inside `DialogTitle`.
- **Native expression:** Keep the stop name and a close `IconButton` in `DialogTitle` (per the "Customized Dialogs" pattern); move bookmark/directions/map/stop-page actions into a `DialogActions` footer (or a `Toolbar` row, per the full-screen-dialog pattern, if they need to stay near the top).
- **Why it matters:** `DialogActions` exists specifically so a Dialog's business actions are visually and semantically separated from its title/dismissal affordance; collapsing that distinction here means the title row is doing two jobs MUI's own vocabulary treats as separate, at the one place (five icon buttons instead of MUI's documented one-or-two) where the difference is most visible.
- **Boundary check:** This is about which documented Dialog sub-component (`DialogActions` vs. `DialogTitle`) is the right home for the stop's non-dismissal actions — a composition question about MUI's own Dialog vocabulary — not a critique of the icons chosen or how many actions exist.

### Finding 3 (intent-dependent) — `StopDialog` is unconditionally near-fullscreen rather than responsively so

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** high (on the facts; the uncertainty is about which native expression applies, not about what the code does)
- **User task:** Present the stop-detail view large enough to comfortably show its route list, on whatever device the app is viewed on.
- **Repository evidence:** `src/components/route-eta/StopDialog.tsx:103-108` (`rootSx`) forces `& .MuiPaper-root` to `width: "100%"`, `marginTop: "90px"`, `height: "calc(100vh - 100px)"` unconditionally — i.e., on every viewport size, not gated by any breakpoint or `useMediaQuery` check. `fullScreen` (Dialog's own prop for this) is never used; `inspect_surface.py` confirms only `Dialog, DialogContent, DialogTitle, IconButton` (no `useMediaQuery`) are imported here.
- **Authority evidence:** MUI's Dialog page has an explicit "Responsive full-screen" guide stating that a dialog can be made responsively full screen using `useMediaQuery` (`const fullScreen = useMediaQuery(theme.breakpoints.down('md')); return <Dialog fullScreen={fullScreen} />`), i.e., full-screen only under a breakpoint, centered/sized normally above it. The separate "Full-screen dialogs" section is a worked demo only (no surrounding normative prose beyond the code itself), so per the "examples illustrate, they don't mandate" rule it is cited here only to show what the built-in `fullScreen` prop actually renders, not as an independent rule. Authority category: **component guidance** (one explicit guide sentence + one illustrative demo).
- **Evidence mode:** SYNTHESIS (the "Responsive full-screen" guide sentence plus the "Full-screen dialogs" demo's shape).
- **Authority strength:** OPTIONAL — the guide's own language ("You may make a dialog responsively full screen…") presents this as one supported technique, not a stated preference over an unconditional full-bleed dialog.
- **Two plausible readings, and why I'm not picking one:** (A) This app may be intentionally optimized for a mostly-mobile audience (a bus-arrival lookup tool), in which case an unconditionally near-fullscreen stop dialog on every viewport is a deliberate simplification, and the "responsive" technique doesn't apply because there's no meaningfully different desktop-vs-mobile intent to serve. (B) The app may be treated as a general responsive web surface (the rest of this bounded surface — `RouteHeader`'s multi-column layout, the accordion list — reads as viewport-agnostic, not mobile-only), in which case forcing a full-bleed modal at any width, including desktop, diverges from MUI's own documented responsive-fullScreen composition for exactly this "large detail dialog" job. Nothing in this bounded surface's own code, comments, or copy states which of these is the actual product intent — no breakpoint handling, no mobile-only branch, and no comment explaining the `90px`/`calc(100vh - 100px)` values appears anywhere in the five files reviewed.
- **What would resolve it:** Evidence that this Dialog (or its sibling dialogs elsewhere in the app, outside this bounded surface) is deliberately never meant to be centered/width-capped on desktop — e.g., a project-level decision to only ever render this app as an installed/mobile PWA — versus evidence that the app is treated as a normal responsive site where other modals do adapt by breakpoint.
- **Current expression:** Fixed-pixel near-fullscreen `sx` override on `.MuiPaper-root`, applied identically regardless of viewport.
- **Native expression:** Uncertain without resolving the intent above. If reading (B) holds, the supported native expression is `fullScreen={useMediaQuery(theme.breakpoints.down(<breakpoint>))}` in place of the hard-coded `rootSx` override, falling back to a normal centered/`maxWidth`-capped Dialog on larger viewports.
- **Boundary check:** This is a question of which of MUI's own two documented Dialog-sizing compositions (unconditional near-fullscreen vs. `fullScreen` gated by `useMediaQuery`) fits the app's actual target-device intent — not a critique of the specific `90px`/`100px` values chosen.

## Suppressed (low materiality or weak applicability)

- **`StopAccordion`'s icon-button row → `AccordionActions`.** `AccordionActions` is documented as "an optional wrapper that groups a set of buttons," and `StopAccordion.tsx:142-202` does group five `IconButton`s — a superficial match. But `AccordionActions`'s own default layout places buttons in a distinct row below `AccordionDetails`, whereas the current layout deliberately keeps `TimeReport` and the action icons side-by-side in one compact row (`accordionDetailsRootSx: display:flex, justifyContent:"space-between"`) — load-bearing for a scrollable list of many stops (`StopAccordionList.tsx` sets `overflowY: "scroll"` on the whole list). Adopting `AccordionActions`'s documented shape would add a full extra row per stop across a long list, which may not preserve the apparent per-row-density intent; the docs' own demo only illustrates a bottom-aligned Cancel/Agree pair, not a dense inline icon cluster. Applicability point 4 (would an experienced MUI dev actually restructure this) is too weak to clear the materiality bar — suppressed.
- **`RouteHeader`'s three-column layout → `CardHeader`.** Considered because `CardHeader` documents a title/subheader/action composition. `RouteHeader`'s actual shape (a left action button, a centered title+subtitle column, and a right-side divider+button) doesn't match `CardHeader`'s title-left/action-right, single-action-slot shape closely enough to establish real applicability; no authority differentiates a 3-column symmetric header from `CardHeader`'s composition one way or the other. Suppressed as weak applicability, not a confirmed match either way.

## Orientation notes

- **`StopAccordion`/`StopAccordionList`'s single-expand-at-a-time behavior** (`stopIdx === idx` driving each `Accordion`'s `expanded` prop, changes routed through a shared `handleChange` callback) matches MUI's own documented "Only one expanded at a time" controlled-accordion customization exactly — state lives one level up and is fed into `expanded`, which is precisely the documented technique (here via the route URL/index rather than local `useState`, a valid variant of the same controlled pattern).
- **`StopAccordionList`'s `Snackbar`** for the "copied to clipboard" confirmation after the Share action (`StopAccordionList.tsx:65-73`) is a correct, canonical use of `Snackbar` per its own Usage section, which explicitly frames Snackbar as the component for brief, non-blocking process confirmations, distinct from `Alert` (in-flow) and `Dialog` (blocking) — the contrast that makes Finding 1 above legible.
- **`StopDialog`'s top-level component family** (`Dialog` / `DialogTitle` / `DialogContent`) is the right choice for a focused, blocking, single-stop detail view triggered from a list item — not a case for `Drawer`, `Popover`, or `Menu`. The composition problems inside it are scoped to Findings 2 and 3 above, not to the choice of `Dialog` itself.
- **`IconButton` for the repeated per-stop toggle actions** (alarm, pin/star, share, info) inside each accordion row is an appropriate, documented use of `IconButton` for compact, icon-only, repeated controls in a dense list context.

## What was not evaluated

Implementation correctness was intentionally out of scope, including: the several `style={{ backgroundColor: "transparent" }}` inline-style props on `IconButton`s in `StopAccordion.tsx` (flagged by `inspect_surface.py`'s `style_class_usage` output) rather than `sx`; whether `RouteUpdateNotice`'s clickable `Box` is keyboard-reachable/focusable; the specific `90px`/`100px` pixel values in `StopDialog`'s `rootSx`; and any component-API/props currency questions (e.g., `TransitionProps` vs. newer slot-based APIs) for the resolved 5.15.11 version. General UX/product judgment — information density, whether five per-stop actions is too many, dialog animation feel, or whether the update-notice copy is worded well — was also not evaluated; its absence here should not be read as "checked and fine."
