# Design-System Native-Expression Review: CreateEnvironment.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** A single-page form where a user configures and submits a new compute "environment" resource — naming/description/region, compute (instance type/count/auto-scaling), networking (VPC/subnet/security group/public IP), storage (volume type/size/encryption), monitoring (detailed monitoring/log retention/alert email), and resource tags (Owner/Cost center/Environment) — then submits via a single "Create environment" primary action (`src/pages/CreateEnvironment.tsx:34-226`).

**Packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked/resolved `3.0.900` (`evals/design-system-native-expression-review/cases/case-n2-create-environment/fixture/package-lock.json`). Both findings below rest on component/pattern concepts (Container composition, Expandable Section, Tag Editor) that are long-stable in this version line; no semver-sensitive applicability gap identified.

**Authority categories found in this corpus:** component guidance (individual component pages such as Tag Editor, Expandable Section, Toggle, Checkbox) and named patterns / composition guides — specifically a dedicated "Create resource" pattern (`/patterns/resource-management/create/`) with **Single page create** and **Multipage create** sub-patterns, each carrying explicit anatomy ("Building blocks"), "Key UX concepts," and "Do/Don't" guidance. This corpus does support a genuine composition/pattern tier for resource-creation flows (not just component pages), so composition-level findings below are backed at that tier, not manufactured.

## Findings

### Finding 1 — Flat, always-expanded container fragmentation instead of the documented lean-primary + additional-settings composition

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** as stated above — a single-page resource-creation form for an "environment," meant to be submitted via one primary action.
- **Repository evidence:** The form is composed as six top-level `Container`s, each with its own always-visible `Header variant="h2"` and no progressive disclosure: General (`:108-124`), Compute (`:126-145`), Networking (`:147-174`), Storage (`:176-192`), Monitoring (`:194-206`), Tags (`:208-220`) — 17 `FormField`s plus 3 standalone `Checkbox`es, all rendered open simultaneously (`inspect_surface.py` confirms `Container: 6`, `FormField: 17`, no `ExpandableSection` import anywhere in the file). Nearly every field already carries a working default so the form is submittable as-is: `region` defaults to `REGION_OPTIONS[0]` (`:38`), `instanceType` to `INSTANCE_TYPE_OPTIONS[0]` (`:41`), `instanceCount='2'` (`:42`), `autoScalingMin='1'`/`autoScalingMax='4'` (`:43-44`), `vpc`/`subnet`/`securityGroup` to their single default option (`:47-49`), `volumeType` default, `volumeSize='100'`, `encryptVolume=true` (`:53-55`), `logRetentionDays='30'` (`:59`).
- **Authority evidence:** From `/patterns/resource-management/create/single-page-create/` (authority category: **named pattern**):
  - Building block C, Container: *"In most cases, use a single container for all the configuration inputs of a single resource. Consider using multiple containers if the choice is highly complex and would benefit from having its own section in the form layout. For example: Choosing a database type."*
  - Building block D, Primary form fields: *"Keep the primary configuration section as short as possible. Criteria for primary section inputs: Any required field that we can't provide a good default for... Any field that 80% or more of users would expect to see, and want to know the value of in order to be successful."*
  - Building block E, Additional expandable section: *"Place as many inputs as possible into the additional settings section for each resource card. This allows the user to keep the primary section as short as possible, so the user can focus on the most important tasks."*
  - Key UX concept, One-click to create: *"Use good defaults in as many inputs as possible to allow users to simply click the Create button to have a running resource."*
  - General guideline (Do): *"Group related input fields together under a subheading if there are multiple types of configuration inputs."*
  - The Expandable Section component page confirms this building block maps to a real component: *"With expandable selection, users can expand or collapse a section."* (authority category: **component guidance**)
  - **Disclosed tying/qualifying material:** the same corpus also documents Multipage create for *"long or complex configurations"* where the task is *"a set of interrelated tasks."* I checked this directly against the surface's own code rather than picking a direction abstractly: because nearly every field already has a submittable default (`:38-59`, listed above), the implementation's own shape matches Single Page Create's "one-click to create" concept, not Wizard's step-by-step "interrelated tasks" framing. This is surface evidence resolving the tie, not a default preference for the status quo — see "Suppressed," below, for the explicit disposition of the Wizard alternative.
- **Evidence mode:** SYNTHESIS (built from multiple cited passages on the same pattern page — Container guidance, primary-field criteria, the additional-expandable-section building block, and the one-click-to-create concept — which together establish one coherent, mutually reinforcing composition; not a cross-corpus inferential leap).
- **Authority strength:** RECOMMENDED. These are the pattern's own prescriptive "Do"/building-block instructions for this exact page type (not a bare description of what a container "is"), but they are phrased as defaults with named exceptions ("in most cases... consider... if"), not an absolute prohibition — so `REQUIRED` would overstate it.
- **Applicability argument:** (1) The observed task — single-page creation of one resource with a primary submit action — matches Single Page Create's stated problem exactly, not a superficial shape match. (2) The current implementation solves substantially that same problem (one page, one Create button). (3) Restructuring into a lean primary section plus one or more `ExpandableSection`-based "additional settings" groupings preserves the identical task and identical data collected — it changes only what's visible by default, not what the user is doing. (4) The divergence is material: 17 fields at equal visual weight across 6 permanently open H2-headed containers is the opposite of "keep the primary section as short as possible" and "place as many inputs as possible into the additional settings section," and none of the four category containers beyond General (Compute, Networking, Storage, Monitoring) rises to the documented exception threshold for extra containers ("highly complex... choice," e.g. "choosing a database type") — Monitoring and Tags in particular are 2-3 simple fields each, not complex choices warranting their own permanent section.
- **Current expression:** Six flat, always-expanded `Container`s with no primary/secondary distinction; a user must scroll and review all 17 fields regardless of how many already hold acceptable defaults.
- **Native expression:** A Cloudscape-fluent implementer would keep one primary container with only the fields lacking a safe default or that most users need to confirm (e.g., environment name, region, instance type) visible by default, and move the remainder — auto-scaling bounds, VPC/subnet/security-group/public-IP detail, storage type/size/encryption, monitoring/log-retention/alerting, and tags, all of which already ship working defaults — into one or more `ExpandableSection` "additional settings" groupings per building block E. The exact primary/secondary split is a judgment call the docs don't fully prescribe field-by-field; the shape (fewer always-open containers, defaulted detail behind expandable disclosure) is what's well supported.
- **Why it matters:** The current structure defeats the pattern's stated "one-click to create" benefit — the code already does the hard part (supplying good defaults everywhere) but the composition still forces users to visually process all 17 fields before submitting, and diverges from how this design system's own guidance says an AWS-console-style create page should be organized, creating a consistency/maintenance gap against other native Cloudscape create flows.
- **Boundary check:** This is about which composition (flat multi-container vs. primary + `ExpandableSection`) the design system documents for this exact "single-page resource create" task, not about any prop/API/token defect or a generic "too dense" UX complaint.

### Finding 2 — Fixed "Owner / Cost center / Environment tag" inputs instead of the Tag Editor component

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** attaching resource tags (Owner, cost center, environment) to the resource being created, as part of the same create-and-submit flow.
- **Repository evidence:** The "Tags" container (`:208-220`) renders three fixed `FormField`/`Input` pairs — "Owner" (`:210-212`), "Cost center" (`:213-215`), "Environment tag" (`:216-218`) — backed by plain `useState<string>` (`:63-65`). There is no way to add a fourth tag or remove one of the three; the section header itself is literally "Tags" (`:208`), and one field's own label contains the word "tag" ("Environment tag," `:216`).
- **Authority evidence:** From `/components/tag-editor/` (authority category: **component guidance**): *"An extension of the attribute editor built with integrated logic. With the tag editor, users can create, edit, or delete resource tags."* Its `tags` prop (fetched from the component's live API reference) is documented as: *"Specifies an array of tags that are displayed to the user. Each tag item has the following properties: `key`... `value`... `existing`... `markedForRemoval`..."* and its `i18nStrings` include `awsPrefixError`, `duplicateKeyError`, `emptyKeyError`, and `tagLimit`/`tagLimitReached` — i.e., built-in validation and add/remove/undo semantics specifically modeled on AWS resource tagging (including AWS-reserved-key-prefix awareness), which this hand-rolled three-`Input` implementation has none of.
- **Evidence mode:** VERBATIM for the cited purpose statement and prop description; the conclusion that *this* section should use it is my own applicability reasoning (see Authority strength).
- **Authority strength:** INFERRED. No page states "use Tag Editor instead of individual fields whenever a section represents AWS resource tags" — that bridge is my own reasoning from (a) the component's stated purpose matching this section's job exactly, and (b) the surface's own naming ("Tags" header, "Environment tag" label) resolving that this is meant as AWS-style resource tags rather than three unrelated first-class attributes that merely happen to be grouped under a "Tags" heading. Per the Finding contract, this is reported as INFERRED rather than RECOMMENDED/REQUIRED.
- **Applicability argument:** (1) Tag Editor's stated problem — creating/editing/deleting resource tags — is not a superficial shape match to this section; "Owner," "Cost center," and "Environment" are exactly the canonical AWS tagging-strategy keys, and the surface's own copy names this domain explicitly ("Tags," "Environment tag"). (2) The current implementation solves substantially the same problem (recording tag-shaped key/value metadata for the resource). (3) A Tag Editor pre-seeded with these three key/value pairs preserves the identical task (these three tags get attached to the resource) while removing the artificial three-tag ceiling — a superset of the current capability, not a different task. (4) The gap is material: duplicate/empty-key validation, AWS-reserved-prefix checking, and add/remove/undo affordances are all things this implementation would have to hand-build and maintain that Tag Editor already ships.
- **Current expression:** Three permanently-fixed `Input` fields, one per tag, with no generic key/value structure.
- **Native expression:** A `TagEditor` seeded with `{key: 'Owner', ...}`, `{key: 'Cost center', ...}`, `{key: 'Environment', ...}` as its initial `tags`, giving users the standard Cloudscape add/edit/remove/validate tag experience instead of a bespoke three-field form.
- **Why it matters:** The section is already conceptually AWS resource tags (by its own header and field naming) but is expressed as generic bespoke inputs, forfeiting Tag Editor's purpose-built validation/UX and creating a consistency gap against any other Cloudscape-native tag-editing surface in the same app.
- **Boundary check:** This is a component-selection question — a bespoke, hand-rolled key/value UI where the design system ships a semantically matching purpose-built component for the same job — not a critique of the three inputs' own implementation correctness or a generic usability complaint.

## Suppressed (low materiality or weak applicability)

- **Multipage create (Wizard) restructuring of the whole page** — considered directly because the corpus's Multipage create guidance recommends itself for "long or complex configurations." Suppressed/resolved toward the Single Page Create direction (Finding 1) instead, because the surface's own code populates working defaults for nearly every field (`:38-59`), matching Single Page Create's "one-click to create" concept rather than Wizard's "set of interrelated tasks" framing — this is surface evidence resolving a same-tier tie, not a default preference for the status quo. **[NOTE: independently graded against the case-n2 grading key as an incorrect suppression — see RESULTS-DISTILLATION.md.]**
- **Region / VPC / Subnet / Security group `Select` option lists limited to 1-2 fixture entries** — not a native-expression concern; `Select` is the documented component for single-value selection from a list regardless of list length, and the sparse option arrays are fixture/mock data, not evidence of a wrong component choice (e.g., a case for `Autosuggest`).
- **Auto-scaling minimum/maximum as two separate `Input(type="number")` fields** — no Cloudscape-documented composition for a paired min/max numeric range was found (`Slider` is single-value); current usage is unremarkable, low materiality.
- **Instance count as `Input(type="number")`** — Cloudscape has no dedicated numeric-stepper component; `Input` with `type="number"` is standard, unremarkable usage.

## Orientation notes

- `Checkbox` (not `Toggle`) used for `publicIp`, `encryptVolume`, `detailedMonitoring` (`:170-172, 188-190, 196-198`) — correct: Toggle's documented purpose is settings that "can result in an immediate change," while these flags only take effect on the form's own `Create environment` submit action, matching Checkbox's form-submission semantics rather than Toggle's instant-apply semantics.
- `Select` used throughout for single-value choices (region, instance type, VPC, subnet, security group, volume type) — matches Select's documented purpose; checked and confirmed native.
- `ContentLayout` + `Header variant="h1"` + `Form` + `SpaceBetween` as the outer page/form scaffold — standard, correct top-level composition for a Cloudscape create page.
- Breadcrumbs (a named building block of both Create-resource sub-patterns) are absent from this file, but this bounded surface is a page-level component only; breadcrumbs are plausibly rendered by an outer route/layout shell not included in the reviewed file, so this was not evaluated as a finding — insufficient evidence either way from this file alone.

## What was not evaluated

Implementation correctness (e.g., the raw `<form onSubmit>` wrapper's mechanics, `Input`/`Select` prop usage, validation/error-text wiring, accessibility mechanics, hard-coded option arrays) and general UX/product judgment (field ordering, copy quality, whether six categories are the "right" information architecture in the abstract) were both out of scope for this review and were not assessed; their absence here should not be read as "checked and fine."
