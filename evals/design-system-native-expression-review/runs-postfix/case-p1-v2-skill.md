# Design-System Native-Expression Review: MessageQueues.tsx (case-p1-message-queues)

**Design system:** Cloudscape (`@cloudscape-design/components`, `@cloudscape-design/collection-hooks`, `@cloudscape-design/global-styles`)

**Inferred user task:** An operator views every message queue in the account side by side to compare throughput and backlog age across all of them at once, in order to decide which queues need scaling attention right now. The operator can search queues by name, and the page's own description states the operator also wants to narrow the list down to a specific status or region while triaging. ## Findings

### Finding 1: A 24-item, single-metadata-shape, comparison-driven collection is expressed with `Cards` where the documented pattern criteria point to `Table`

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** See "Inferred user task" above — comparing throughput and backlog age across all 24 queues at once to decide which need scaling attention.
- **Repository evidence:** `MessageQueues.tsx` renders all 24 generated queues (`QUEUES: MessageQueue[] = Array.from({ length: 24 }, ...)`, line 18) through `Cards` (lines 56-98), with `cardDefinition.sections` exposing four fields — `status` (via `StatusIndicator`), `region` (plain string), `messagesPerSecond` (number), `oldestMessageAgeSec` (number) — identical in shape and type across every item. `useCollection` is configured with `sorting: {}` (line 41), but `Cards`' `cardDefinition` has no `sortingField`/comparator hookup and no clickable-header UI, so that sorting capability is inert here — a Cloudscape `Table` would be able to expose it as clickable, sortable columns for exactly the throughput/age comparison the task describes. The whole surface is also wrapped in `ContentLayout` (lines 44-45, 55) around a `Cards` component that never sets `variant="full-page"` (default container variant is used, per `inspect_surface.py`'s `jsx_tag_counts` showing a single `Cards` usage with no variant prop observed in source).
- **Authority evidence:**
  - `patterns/resource-management/view/index.html.md` ("View resources"), "Choosing between table view and card view" criteria table: **Number of resources** — "9 or more resources in 99% of use cases" → Table, "5 or less resources in 99% of use cases" → Card. **Metadata being displayed** — "Shared metadata between resources" → Table, "Different metadata across resources" → Card. **Metadata type** — "Data that is displayed in columns (text, numerical, status, sparkline)" → Table, "Data that can be displayed as visuals (charts, videos)" → Card. Same page, prose: "Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on. Use the card view if users will not be comparing between a large number of resources to determine which to take action on."
  - `patterns/resource-management/view/table-view/index.html.md`, "Do": "Use table view pattern for static data with multiple attributes displayed in a tabular format. The best data type for a table view is data that is structured, easily comparable, and sortable." Same page, "Don't": "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the table component to implement this pattern." The identical "Don't...Instead" pairing (substituting "cards" for "table") also appears verbatim in `patterns/resource-management/view/card-view/index.html.md`.
  - `patterns/resource-management/view/table-view/index.html.md`, "Key UX concepts" → "Sort": "Table view of all user resources sorted on a certain data set by the user. Each individual table column can be sorted in ascending or descending order," directly matching the inert `sorting: {}` already wired into `useCollection` in the current code.
  - Authority category: **named pattern** (the "View resources" decision table and the Table view / Card view pattern pages).
- **Evidence mode:** SYNTHESIS — the finding combines the "View resources" criteria table (which of the three characteristics apply to this dataset), the table-view pattern's own Do/Don't text, and the card-view/table-view patterns' shared "Don't use content layout" constraint. Each contributing fact is quoted verbatim above and attributed to its source page; the bridge is: 24 shared-shape, all-columnar-data items being compared to decide on action is the exact scenario the criteria table maps to Table, and the current page structure (`ContentLayout` + default-variant `Cards`) does not match the full-page pattern structure either pattern documents.
- **Applicability argument:** (1) The observed task — comparing throughput and backlog age across every queue to decide which need scaling attention — is not a superficial shape match; it is the literal condition the criteria table names ("your users will be comparing resources to determine which to take action on"). (2) The current `Cards` implementation solves the same display problem (show all queues, all fields, filterable and paginated) that the criteria table is choosing between. (3) Switching to `Table` preserves the exact same task — same fields, same filter/pagination affordances, same 24 items — it changes only the presentational vocabulary, not the product goal. (4) The mismatch is material: all three of the table's own criteria (item count, shared metadata, columnar/non-visual data type) point the same direction, and the current code already tried to wire up sorting (`sorting: {}`) that only a `Table`'s column headers can expose — an experienced Cloudscape implementer would restructure this, not just note it as an alternative. Re-reading the full criteria table for a same-tier equivalence: there is no "cards is equally valid for large, homogeneous, columnar collections" language anywhere in the retrieved material — every row differentiates directionally in favor of Table for this shape of data, so point 4 of the anti-fundamentalism rule is satisfied, not neutralized.
- **Current expression:** `ContentLayout` wraps a default-variant `Cards` list of 24 uniformly-shaped, purely textual/numeric/status items, with `TextFilter` + `Pagination` wired through `useCollection` (including an unused `sorting: {}` config).
- **Native expression:** A full-page `Table` (`variant="full-page"`) as the first/only content under the page (no `ContentLayout` wrapper, per the pattern's own "Don't" — an `h1`-variant `Header` sits directly above the table, optionally sticky), with columns for status, region, throughput, and oldest message age, sortable per-column so operators can rank queues by backlog age or throughput to triage — the exact comparison behavior the task's own description names.
- **Why it matters:** The current composition already tried to support sorting (`sorting: {}` in `useCollection`) but the chosen presentation component has no UI to expose it, so an already-declared piece of the intended interaction is functionally dead. Beyond that, `Cards` is documented as fitting small (≤5-in-99%-of-cases), heterogeneous, visually-rich collections; a 24-item, single-shape, all-columnar dataset used specifically for cross-item comparison is the opposite of that profile and is the profile `Table` is documented for — this is a maintenance/consistency cost against how the rest of a Cloudscape-based console would present this exact kind of operational triage view.
- **Boundary check:** This is a component/composition alignment question (which top-level collection component and page-structure pattern best express "compare 24 uniform, columnar records to decide which need action"), not an implementation-correctness defect (nothing here is invalid Cloudscape usage) and not a generic UX complaint (the recommendation is grounded in an explicit, applicable decision table naming this exact scenario).

### Finding 2: The task's stated need to narrow by status or region has no structured filter component — only free-text `TextFilter` is present

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Same as above; specifically the part of the task the page's own `Header` `description` and file comment state explicitly: "Operators can search by queue name, or narrow the list down to a specific status or region while triaging."
- **Repository evidence:** The only filter control wired up is `TextFilter` (`MessageQueues.tsx` lines 89-95), bound to `useCollection`'s generic `filterProps`/`filteringText`. There is no `CollectionSelectFilter` (or `PropertyFilter`) anywhere in the file, and `inspect_surface.py`'s import inventory confirms only `content-layout`, `header`, `cards`, `text-filter`, `pagination`, and `status-indicator` are imported from `@cloudscape-design/components`. `status` has exactly two finite values (`'healthy' | 'backlogged'`, line 12) and `region` has exactly two finite values (`'us-east-1' | 'us-west-2'`, line 13) in the `MessageQueue` type — i.e., precisely the low-cardinality, small-property-count shape the task's own description names as a narrowing need.
- **Authority evidence:**
  - `patterns/general/filter-patterns/index.html.md`, criteria table: "User goals" row — Text filter: "Find resources that match an exact text query"; Collection select filter: "Find resources with overlapping, defined values." Prose: "If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter. For example: by 'status' or 'type'."
  - `components/collection-select-filter/index.html.md`, "Do": "Use a select filter if users need a maximum of two properties to find a specific item. If more than two are required, use a property filter instead." And: "Use a select filter for commonly used properties and values." Same page, "Collection view" → "Displaying results": "The collection is filtered as soon as the user selects a value from a select filter or enters text into the accompanying text filter" — i.e., the documented composition explicitly pairs a select filter alongside a text filter, not as a replacement for it.
  - `components/text-filter/index.html.md`, "Do": "Use the text filter to provide basic filtering in a collection" — confirming the existing `TextFilter` is itself valid usage for the name-search part of the task, just not for the status/region part.
  - Authority category: **named pattern** (`filter-patterns`) plus **component guidance** (`collection-select-filter`, `text-filter`).
- **Evidence mode:** SYNTHESIS — combining the filter-patterns decision table's "one or two properties → collection select filter" guidance with `collection-select-filter`'s own "maximum of two properties" Do-rule and its documented text-filter-plus-select-filter pairing. Each source is quoted above; the bridge is that `status` and `region` are exactly two finite-valued properties named as the narrowing target in the task's own description, which is the documented sweet spot for `CollectionSelectFilter` used together with the existing `TextFilter`, not `TextFilter` alone.
- **Applicability argument:** (1) The task explicitly names status and region as narrowing dimensions — not a superficial resemblance to a filtering example, but the literal stated goal. (2) The current `TextFilter` nominally could match this task only incidentally (by users typing "healthy" or "us-east-1" into free text, relying on undocumented default string-matching behavior of `useCollection`'s filtering function), which is not the same interaction the design system documents for property narrowing. (3) Adding `CollectionSelectFilter` for status and region preserves the exact same task and even the exact same `TextFilter` for name search — nothing about the product goal changes. (4) The gap is material: the property-count and value-cardinality match the collection select filter's stated scope exactly ("maximum of two properties," "commonly used properties and values"), and there's no equalizing language in the filtering-patterns table suggesting text filter alone is an equally valid choice once structured property narrowing is the stated goal — the table differentiates by user goal, and "narrow to a specific status or region" is worded identically to the collection-select-filter's own worked example ("by 'status' or 'type'").
- **Current expression:** A single `TextFilter` bound to free text across the collection; no first-class UI exists for narrowing by status or region.
- **Native expression:** Keep the existing `TextFilter` for name search, and add one or two `CollectionSelectFilter` controls (Status, Region) alongside it, per the collection-select-filter documentation's own "select filter... or enters text into the accompanying text filter" composition — combined with an "and" operator by default, matching both properties' small, finite value sets.
- **Why it matters:** As written, the page's own stated triage capability ("narrow... to a specific status or region") isn't backed by a documented, discoverable filter control — it depends on incidental substring matching inside a general-purpose text box, which is not how Cloudscape's own filtering-pattern guidance says to serve a "one or two finite-valued properties" narrowing need. This is a genuine expressiveness gap against the design system's own documented vocabulary for the specific interaction the surface's copy promises.
- **Boundary check:** This is about which filter *component* was chosen for a documented low-cardinality property-narrowing task, not about `TextFilter`'s implementation correctness (it's valid, working Cloudscape usage) and not a generic "filters would be nice" UX complaint — it's grounded in an explicit property-count criterion from the filtering-patterns page that matches this task's stated properties exactly.

## Suppressed (low materiality or weak applicability)

- **Property filter instead of / in addition to collection select filter** — checked and cleared. `filter-patterns`' criteria table reserves Property filter for "Complex resource (large set of properties)" and collections needing "and/or/not" combinations; `MessageQueue` has exactly two low-cardinality narrowing properties and the task names only simple "and"-style narrowing ("a specific status or region"), which is precisely what Collection select filter's own Do-rule ("maximum of two properties") targets. Recommending Property filter here would be over-provisioning past the task's actual complexity — suppressed as the weaker-fit alternative to Finding 2.
- **Split view (Table/Cards + `SplitPanel`)** — checked and cleared. The "View resources" pattern scopes split view to workflows needing "an additional layer of details" beyond the collection view itself. The `MessageQueue` type and the rendered `Cards` sections already surface all four known fields (status, region, throughput, oldest message age) with nothing held back for a detail panel to reveal, so there's no evidence of the "additional layer of details" problem split view addresses — applicability point 2 (current implementation solving the same problem the composition addresses) fails. Named here rather than silently dropped since "monitoring/troubleshooting" language in the split-view criteria could otherwise look superficially relevant to a triage page.
- **Resource details page per queue** — same reasoning as split view: no evidence in the bounded surface of additional per-queue data or a navigation affordance implying a richer detail view exists; recommending one would invent product scope beyond what the file supports.

## Orientation notes

- `StatusIndicator` used for the `status` field is the correct, documented semantic component for compact resource-state display in a card/table cell (`components/status-indicator/index.html.md`: "communicates the state of a resource... in a compact form that is easily embedded in a card, table, list, or header view") — confirmed as already-native regardless of the Cards-vs-Table finding above; it transfers unchanged to a `Table` column.
- `Header` usage (`variant="h1"`, `counter`, `description`) matches documented header composition for a collection's title/count/description; no finding.
- `Pagination` paired with `useCollection`'s `paginationProps` is standard, documented collection-hooks wiring; no finding.
- `TextFilter` itself, for the name-search part of the task, is valid, on-label usage per `components/text-filter/index.html.md`'s own Do guidance — the issue in Finding 2 is incompleteness against the rest of the stated task, not misuse of `TextFilter`.

## What was not evaluated

Implementation correctness (API usage, prop validity, the client-side `QUEUES` mock-data generator, hard-coded `pageSize: 12`, absence of loading/error states, ARIA/keyboard mechanics beyond what's visible in JSX) and general UX/product judgment (information density, card/column ordering, color choices, whether 24 queues is the "right" amount of data to show at once) were not assessed and their absence here should not be read as "checked and fine."
