# Design-System Native-Expression Review: ntfy web — SubscribeDialog / PublishDialog

**Design system:** Material UI (`@mui/material`, `@mui/icons-material`)

**Inferred user task:** Two related dialog-driven form flows in the ntfy web app: (1) `SubscribeDialog` lets a user subscribe to a notification topic — enter/generate a topic name, optionally reserve it with an access-control level, optionally point at another ntfy server, and optionally log in if the topic requires auth; (2) `PublishDialog` lets a user compose and send a notification to a topic — a message/title plus a progressively-disclosed set of optional fields (click URL, email, phone call, file/URL attachment, delay, tags, priority, markdown rendering) surfaced on demand via a row of action chips.

**Packages / versions:** `@mui/material` declared `^9.1.2`, locked `9.3.1`; `@mui/icons-material` declared `^9.1.1`, locked `9.3.1` (resolved via `resolve_versions.py` against `web/package.json` + `web/package-lock.json`). Both packages resolve to the same MUI v9 release, so the fetched v9-era docs apply directly to the installed version.

**Authority categories found in this corpus:** Component guidance pages only (`## Components` in the `llms.txt` index — one page per component, each with a short "what it's for" statement, worked examples/demos, and an API reference). The remaining index sections (Customization, Guides, Getting Started, Integrations, Migration) are infrastructure/theming/versioning references, not a task- or pattern-level layer. There is no named "task pattern" or composition-guide tier comparable to what a system like Cloudscape exposes — no page documents "how to build a publish form" or "how to build a settings dialog." Findings below are therefore grounded in individual component pages' own stated purpose, explicit "when to use" language, and worked examples/API vocabulary — never in a fabricated pattern tier.

## Findings

### Finding 1: Field-bound action controls (generate, open-picker, reset) are composed as sibling elements outside the `TextField`/`Select`, not as `InputAdornment`

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** medium-high
- **User task:** attaching a single interactive action to a single input field — generating a random topic name into the topic field, opening the emoji picker to insert into the tags field, and clearing/resetting one optional field's value — inside a modal form dialog.
- **Repository evidence:**
  - `SubscribeDialog.jsx:171-197` — a bare `<div style={{ display: "flex" }}>` wraps a `TextField` (topic name) and a sibling `Button` ("Generate") with manual inline styling (`style={{ flexShrink: "0", marginTop: "0.5em" }}`) to visually align it next to the field.
  - `PublishDialog.jsx:403-409` — a bare `<div style={{ display: "flex" }}>` wraps a custom `DialogIconButton` (opens the emoji picker) as a sibling of the `tags` `TextField` at line 410.
  - `PublishDialog.jsx:791-803` (`ClosableRow`) — a hand-rolled `Row` wrapper that renders a field (or field pair) plus a sibling `DialogIconButton` with a `Close` icon to clear/reset that field. Used six times: base URL/topic reset (306-349), click URL (461-487), email (488-514), call/`Select` (515-544), attach URL/filename (545-606), delay (622-652).
  - `PublishDialog.jsx:805-820` (`DialogIconButton`) — the shared wrapper hardcodes `height: "45px"` and `marginTop: "17px"` specifically to line the icon button up with an adjacent `variant="standard"` field, i.e. manual pixel alignment substituting for the input's own adornment slot.
- **Authority evidence:** `https://mui.com/material-ui/react-text-field.md`, "Input Adornments" section: **"The main way is with an `InputAdornment`. This can be used to add a prefix, a suffix, or an action to an input. For instance, you can use an icon button to hide or reveal the password."** Authority category: `component guidance` (prose statement plus a worked example showing exactly this shape — an `IconButton` inside `InputAdornment` inside the field, toggling a related state). The doc's separate "Icons" section (same page, lines 538-591) does show a manual `Box`/`sx` sibling-flex layout as one of "multiple ways to display an icon with a text field" — but that example (`AccountCircle`) is a static, non-interactive icon, not a clickable action; the action-specific guidance quoted above is stated only for `InputAdornment`, with no manual-layout alternative shown for actionable content.
- **Evidence mode:** VERBATIM
- **Applicability argument:**
  1. Task match: MUI's own stated problem for `InputAdornment` — "add ... an action to an input" via an icon button — is exactly the shape of "generate into this field," "open a picker that writes into this field," and "clear this field," each bound to one specific input.
  2. Current implementation solves the same problem: each site pairs one field with one bound action.
  3. Preserves the same task: moving the action into the field's own `startAdornment`/`endAdornment` slot changes nothing about what the action does, only where the design system expects it to be expressed.
  4. Materiality: this is not a single site but a recurring shape (7 occurrences across two files), and the current expression required inventing and hand-tuning a bespoke wrapper (`DialogIconButton`) with magic-number offsets to fake what `InputAdornment` provides for free — a concrete maintenance cost, not just an aesthetic one. The one weaker sub-case is the base-URL/topic and attach-URL/filename `ClosableRow`s, where a single close action spans *two* fields at once — `InputAdornment` binds to one input, so that pairing doesn't map as cleanly (noted, not treated as full support for this finding).
- **Current expression:** manual flex-row siblings (`Button`, or a shared `DialogIconButton` wrapper with hand-tuned inline offsets) placed next to `TextField`/`Select`, outside the field itself.
- **Native expression:** for the clean single-field cases (topic-generate, tags/emoji-picker, click URL, email, delay, and — per the docs' own demo comment about coexisting with the `Select` chevron — the call `Select`), bind the action via the field's `slotProps.input.startAdornment`/`endAdornment` with `InputAdornment` wrapping an `IconButton`, matching MUI's password-visibility-toggle demo shape.
- **Why it matters:** the current composition is mechanically valid MUI usage, but it re-derives (via a custom wrapper and literal pixel offsets) alignment behavior that `InputAdornment` is specifically documented to provide as "the main way" to pair an action with an input — a design-system-fluent implementer reading this surface would recognize the `DialogIconButton` height/margin hack as working around the absence of the adornment slot MUI already ships for this exact job.
- **Boundary check:** this is a composition/component-selection question — which documented slot an input-bound action lives in — not an implementation-mechanics nitpick; it's cited because MUI names `InputAdornment` as the primary documented vehicle for exactly this recurring UI concept.

### Finding 2: The `tags` field is a raw comma-separated string in a `TextField`, not MUI's documented `Autocomplete` "tags" composition

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** medium-high
- **User task:** letting the user build up a list of discrete tag values (plain words or emoji shortcodes/characters) to attach to a published notification, including inserting values via an emoji picker.
- **Repository evidence:** `PublishDialog.jsx:410-425` — a single `TextField` bound to a `tags` string state. `PublishDialog.jsx:276-278` — `handleEmojiPick` appends a picked emoji into that same string via manual concatenation: `` `${prevTags.trim()}, ${emoji}` ``. There is no per-tag visual separation, and removing one tag requires editing the raw comma-separated string by hand; nothing in the UI represents "a tag" as a discrete, individually addressable unit.
- **Authority evidence:** `https://mui.com/material-ui/react-autocomplete.md`, "Multiple values" section (function name `Tags()`, demo ids `tags-standard`/`tags-outlined`/`tags-filled`, ~line 3597-3660): a worked example combining `multiple`, `freeSolo`, and `renderValue` rendering each entered value as a `Chip`. This naming is corroborated by the component's own API vocabulary elsewhere on the same page: the CSS slot table names `tag`, `tagSizeMedium`, `tagSizeSmall` ("Styles applied to the tag elements, for example the chips") and the `limitTags`/`getLimitTagsText` props. Authority category: `synthesis` (a worked example section plus the API reference section of the same component page, combined).
- **Evidence mode:** SYNTHESIS — the "Multiple values" demo shows the composition; the API slot names (`tag`, `tagSizeMedium`, `limitTags`) independently confirm that MUI's own vocabulary for this `Autocomplete` configuration is literally "tags," not merely a generically-multi-select widget repurposed for this. Neither source alone states "use this for tag entry"; combining the demo's shape with the API's naming is what supports that reading.
- **Applicability argument:**
  1. Task match: the Autocomplete "tags" demo's stated problem — entering multiple freeform values into one field, each individually represented and removable — is materially the same problem as ntfy's tag list, not a superficial shape match; `freeSolo` specifically fits ntfy's tags being arbitrary strings rather than a closed vocabulary.
  2. Current implementation solves the same problem via a single string field parsed by comma.
  3. A `multiple`+`freeSolo` `Autocomplete` with `Chip` rendering preserves the same output (a list of tag strings) and the same emoji-insertion affordance (appending to the value array instead of the string).
  4. Materiality: tags are a named, first-class feature of this dialog (not incidental), and the gap between "type commas into a string" and "each tag is a removable chip" is the kind of difference a design-system-fluent implementer would restructure toward, not merely note — especially since MUI's own component vocabulary already calls this configuration "tags."
- **Current expression:** one `TextField`, string state, comma-joined, manual string concatenation for emoji insertion.
- **Native expression:** `Autocomplete` with `multiple` and `freeSolo`, rendering each entered value as a `Chip` per the documented "Multiple values" composition; emoji picks append a new array entry instead of mutating a string.
- **Why it matters:** the current field is valid `TextField` usage, but it reimplements — with weaker editing affordances (no per-item delete, no visual separation) — exactly the composition MUI ships and names for this task, at a component-selection level, not just a styling one.
- **Boundary check:** this is a component-selection-plus-composition question — which component represents "a list of freeform values" — not a UX preference about density or hierarchy; the recommendation is grounded in the design system's own named vocabulary for the task, not a generic "chips look nicer" claim.

### Finding 3: Two standalone single-option toggles in `PublishDialog` use `Checkbox` where MUI's own guidance directs single options to `Switch`

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** high
- **User task:** letting the user turn on, independently, (a) markdown rendering of the message and (b) "keep the dialog open to publish another message after sending" — each a single, standalone on/off preference, not one item in a list of related options.
- **Repository evidence:** `PublishDialog.jsx:387-402` — a lone `FormControlLabel`/`Checkbox` pair for `markdownEnabled`, not grouped with sibling checkboxes. `PublishDialog.jsx:757-772` — a lone `FormControlLabel`/`Checkbox` pair for `publishAnother`, likewise standalone. For contrast, `SubscribeDialog.jsx:198-223` and `224-264` use `Switch` (not `Checkbox`) for two comparably standalone options ("reserve this topic," "use another server") — i.e. the same app already applies the documented rule correctly elsewhere.
- **Authority evidence:** `https://mui.com/material-ui/react-checkbox.md`, opening paragraph: **"If you have multiple options appearing in a list, you can preserve space by using checkboxes instead of on/off switches. If you have a single option, avoid using a checkbox and use an on/off switch instead."** Corroborated by `https://mui.com/material-ui/react-switch.md`, "Switches with FormGroup" section: **"`FormGroup` is a helpful wrapper used to group selection controls components that provides an easier API. However, you are encouraged to use Checkboxes instead if multiple related controls are required."** Authority category: `component guidance` (both are the component pages' own stated purpose/usage rules, not an example).
- **Evidence mode:** VERBATIM
- **Applicability argument:**
  1. Task match: both cited sentences state the rule directly in terms of single-option vs. list-of-options presentation — exactly the axis distinguishing `markdownEnabled`/`publishAnother` (single, standalone) from a legitimate checkbox list (multiple related items in one group).
  2. Current implementation: both are genuinely standalone — neither sits in a `FormGroup` with sibling checkboxes.
  3. Swapping to `Switch` preserves the same task (toggle a boolean preference before submitting) with no change to submission semantics.
  4. Materiality: the rule is phrased as an explicit "avoid X, use Y instead" directive (not merely descriptive), and the same codebase already follows it correctly for `SubscribeDialog`'s comparable standalone toggles — making the `PublishDialog` checkboxes a visible, citable inconsistency within the app's own established MUI vocabulary, not a hypothetical one.
- **Current expression:** `Checkbox` + `FormControlLabel`, standalone, for both `markdownEnabled` and `publishAnother`.
- **Native expression:** `Switch` + `FormControlLabel`, matching the pattern `SubscribeDialog` already uses for its own standalone toggles.
- **Why it matters:** this is valid `Checkbox` usage in isolation, but MUI's own component-selection rule for this exact single option vs. list-of-options distinction is stated as an explicit "avoid/instead" directive, and the same review surface already demonstrates the correct choice for structurally identical toggles elsewhere — so the deviation isn't a matter of taste, it's inconsistent application of a documented, already-adopted rule.
- **Boundary check:** this is a component-selection question (`Checkbox` vs. `Switch` for a single option) grounded in the component docs' own stated selection rule, not a generic "checkboxes feel form-y" UX opinion.

## Suppressed (low materiality or weak applicability)

- **Dialog close (`X`) icon button in the corner of `DialogTitle`.** MUI's Dialog "Customization" demo shows a close `IconButton` positioned top-right of `DialogTitle` ("The dialog has a close button added to aid usability."), which neither `SubscribeDialog` nor `PublishDialog` uses. Suppressed: this is one customization example among several Dialog demos (the "Basics" and "Form dialogs" examples have no such button), not a stated requirement, and both dialogs already provide equivalent dismissal via a Cancel/Back button and backdrop-click `onClose` — an equally-valid alternative, not a material gap.
- **Wrapping dialog form content in a native `<form>` element with a `type="submit"`/`form`-attribute-linked submit button**, matching the Dialog docs' "Form dialogs" demo. Considered but suppressed: neither dialog wraps its fields in `<form>`, so pressing Enter in a field doesn't submit. This sits closer to raw-HTML/keyboard-submission mechanics than to a design-system component or composition choice — MUI doesn't ship a `<form>` primitive, and the finding would really be about HTML form semantics, which this skill's scope fences off as implementation correctness.
- **`ReserveTopicSelect`'s four-option icon+label `Select` as a `ToggleButtonGroup` instead.** MUI documents `ToggleButtonGroup` for "related options" and it could plausibly render four small options with icons more compactly. Suppressed: no comparative guidance exists between `Select` and `ToggleButtonGroup` for this cardinality/shape in either component's docs — this would be "the design system has a component for this" with no applicability evidence, which the anti-fundamentalism rule requires suppressing.
- **File attachment via a raw hidden `<input type="file">` (`PublishDialog.jsx:607`).** Not a candidate: Material UI ships no file-upload/file-input component (absent from the fetched `llms.txt` component index), so there is no design-system alternative to compare against.

## Orientation notes

- **Responsive full-screen dialogs.** Both `SubscribeDialog.jsx:56,67` and `PublishDialog.jsx:91,295` use `useMediaQuery(theme.breakpoints.down("sm"))` + `fullScreen={fullScreen}` on `Dialog`, which matches the Dialog docs' "Responsive full-screen" section verbatim in shape (same hook, same prop wiring) — already-native.
- **Chips as action triggers.** `PublishDialog.jsx:657-742` uses `Chip` with `onClick`/`clickable` to reveal each optional field (click URL, email, call, attach URL, attach file, delay, topic). The Chip docs state directly: "Chips allow users to enter information, make selections, filter content, **or trigger actions**," with a dedicated "Clickable" example matching this exact `onClick` shape — already-native, not a finding.
- **`Switch` for standalone options in `SubscribeDialog`.** `SubscribeDialog.jsx:198-223` (reserve-topic toggle) and `224-264` (use-another-server toggle) correctly use `Switch` rather than `Checkbox` for single, standalone options, matching the same Checkbox-docs rule cited against Finding 3 — confirmed correct usage, used here as the app's own internal precedent for that finding.
- **`Autocomplete freeSolo` for the "use another server" base-URL field.** `SubscribeDialog.jsx:241-261` uses `Autocomplete freeSolo` with a list of previously-used base URLs as suggestions while still accepting arbitrary input — matches the Autocomplete docs' "Free solo" / "Search input" composition ("the textbox can contain any arbitrary value... advantageous to suggest possible values") — already-native.
- **`EmojiPicker`'s `Popper` + `ClickAwayListener` + `Fade` composition (not `Popover`).** `EmojiPicker.jsx:47-113` manually composes `Popper`, `ClickAwayListener`, and `Fade` for an anchored, non-modal panel that dismisses on outside click. This is not a deviation: the Popper docs state plainly, "Clicking away does not hide the Popper component. If you need this behavior, you can use the Click-Away Listener," documenting exactly this composition, and the Popover docs note "Popover blocks scrolling and dismisses on click-away by default, unlike Popper" — meaning `Popover`'s modal/scroll-blocking behavior would be the *wrong* fit for a lightweight picker meant to stay open over an interactive `Dialog`. Already-native and, if anything, the more applicable choice of the two.

## What was not evaluated

Implementation correctness was not assessed: prop usage/deprecation status, the empty `<InputLabel />` elements paired with `Select`'s `label` prop instead of a `labelId`/`htmlFor` association (`PublishDialog.jsx:426-427`, `524-525`; `ReserveTopicSelect.jsx`), inline `style={{...}}` and hard-coded hex/px values flagged by `inspect_surface.py` (e.g. `SubscribeDialog.jsx:255`, `PublishDialog.jsx:447`), the `aria-label`-only labeling pattern used throughout instead of `slotProps.htmlInput.id` + `<label htmlFor>`, and the missing native `<form>`/submit-on-Enter wiring noted above. General UX and product judgment were also not assessed: whether the chip-triggered progressive-disclosure flow is the right amount of complexity for this dialog, dialog sizing/density, copy, or the overall information architecture of either flow. None of these were evaluated for correctness or quality — their absence from the findings above should not be read as "checked and fine."
