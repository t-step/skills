# Design-System Native-Expression Review: hk-independent-bus-eta — Route ETA / Stop ETA / Bookmarked Stop flow

**Design system:** Material UI (`@mui/material`, `@mui/icons-material`)

**Inferred user task:** A rider looks up a specific bus route, sees its stops in sequence with live ETAs, expands one stop at a time to see arrival times and per-stop actions (share, notify, pin, star/save), and can open a full-detail dialog for a stop (bookmark it, get directions, view on a map, or jump to that stop's own page). A companion pair of pages (`StopEtaListPage`, `BookmarkedStopPage`) let the rider look up ETAs by stop directly and manage a set of bookmarked stops. `RouteUpdateNotice` is a secondary, non-blocking notice that appears on the route page when the underlying route/stop database is stale and offers a one-tap way to refresh it.

**Packages / versions:** `@mui/material` 5.15.11 (resolved from `yarn.lock`, declared range `^5.15.11`), `@mui/icons-material` 5.15.11 (resolved from `yarn.lock`, declared range `^5.15.11`).

**Authority categories found in this corpus:** Component guidance (one page per component, each with an "Introduction"/description, usage sections, and worked examples/demos) and general Customization/Guides tiers (e.g. "Composition," "Responsive UI," "How to customize") that document React composition *mechanics* (slots, prop forwarding, styling overrides), not named task- or product-level patterns. No task/pattern layer comparable to a system like Cloudscape exists in this corpus — reasoning below stays at the component-guidance tier, or synthesizes across a component's own examples where no single sentence states a rule, and is labeled accordingly.

## Findings

### Finding 1 — Stop detail dialog stacks functional actions inside `DialogTitle` instead of `DialogActions`

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** From `StopDialog.tsx` — a rider who tapped a stop (from the accordion list or a route point) sees that stop's full detail (its routes/ETAs via `StopRouteList`) in a modal, and from that same modal can bookmark the stop, get walking directions, view it on a map, jump to the stop's own page, or close the dialog.
- **Repository evidence:** `src/components/route-eta/StopDialog.tsx` lines 67–98. The `<Dialog>` renders a single `<DialogTitle sx={titleSx}>` containing two `<Box>` groups: the first holds four `IconButton`s (bookmark toggle, "get directions," "view on map," "open stop page") plus the stop's name as inline text; the second holds a fifth `IconButton` (close). `<DialogContent>` holds only `<StopRouteList>`. `DialogActions` is never imported or used anywhere in the file.
- **Authority evidence:** `https://mui.com/material-ui/react-dialog.md`, "Introduction" section (component guidance): *"Dialog Actions: an optional container for a Dialog's Buttons."* and *"Dialog Title: a wrapper used for the title of a Dialog."* (VERBATIM, re-checked against the fetched page). Every other worked example on the same page that has functional buttons (Alerts, Transitions, Form dialogs, Optional sizes, Responsive full-screen, Confirmation dialogs, Draggable dialog, Scrolling long content — 8 of the page's demos) places them inside `<DialogActions>`, never inside `<DialogTitle>`. The one demo that puts an `IconButton` in the title region is "Customization," whose surrounding prose states: *"The dialog has a close button added to aid usability."* (VERBATIM) — and in that demo's code the close `IconButton` is a sibling of `<DialogTitle>`, absolutely positioned, while the demo's actual task button ("Save changes") still lives in `<DialogActions>`.
  - **Authority category:** synthesis (built from the Introduction's per-component role description plus the consistent placement pattern across the page's own demos).
- **Evidence mode:** SYNTHESIS — the Introduction states what `DialogActions` and `DialogTitle` are each for; no single sentence on the page states "don't put action buttons in the title," so the applicability argument bridges that structural description with the observed, consistent example pattern (title reserved for text plus, at most, a single close-affordance; every other functional button goes in `DialogActions`).
- **Applicability argument:** (1) The observed task — a modal offering several real actions tied to the dialog's subject (bookmark, directions, map, navigate) — is exactly the class of problem `DialogActions` is documented to hold ("an optional container for a Dialog's Buttons"), not a superficial shape match. (2) The current implementation solves that same problem (it does offer those actions), just via a different container. (3) Moving the four action `IconButton`s into a `<DialogActions>` row (leaving, at most, a single close icon as a title decoration per the Customization demo) preserves the exact same task and every current interaction. (4) This is material, not cosmetic: `DialogTitle`'s documented job is being "a wrapper... for the title," and every other demo on the page keeps that separation — a Material UI-fluent implementer who saw four unrelated action icons packed into the title row (crowding the stop name itself) would very plausibly move them, both to match the documented Title/Content/Actions separation and because `DialogActions` is exactly the slot built to host this list of buttons.
- **Current expression:** A single `<DialogTitle>` doing double duty as a title (stop name) and a five-button icon toolbar (bookmark, directions, map, open-page, close), styled with custom `sx` to force a `space-between` layout across two inner `Box` groups.
- **Native expression:** Keep the stop name (and, if desired, a single close `IconButton` styled as in the Customization demo) in `DialogTitle`; move the task-specific actions (bookmark, directions, map, open stop page) into a `<DialogActions>` region below `DialogContent`, matching how every other button-bearing example on the Dialog page composes these three regions.
- **Why it matters:** The title row is the one piece of dialog chrome a rider needs to parse fastest (which stop am I looking at, and how do I close this) — MUI's own composition keeps that region visually and semantically separate from a dialog's action list precisely so the title doesn't get overloaded, and every other example on the same page follows that separation. The current version bundles them, which is a documented-composition mismatch even though every individual `IconButton` is itself a valid, correctly-labeled component.
- **Boundary check:** This is a composition-level finding about where components go relative to each other (`DialogTitle` vs. `DialogActions`), not about how any individual `IconButton` is implemented — it does not touch props, deprecations, or a11y mechanics of the buttons themselves.

### Finding 2 — `RouteUpdateNotice` hand-rolls a clickable notice band instead of using `Alert`'s documented message+action composition

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** high
- **User task:** From `RouteUpdateNotice.tsx` — when the app detects the local route/stop database is older than the server's latest, it shows a small, non-blocking notice on the route page; tapping it triggers a database refresh (`renewDb`).
- **Repository evidence:** `src/components/route-eta/RouteUpdateNotice.tsx` lines 29–33: `<Box sx={rootSx} onClick={renewDb}><Typography>⁉️ {t("db-renew-text")}</Typography></Box>`. `rootSx` (lines 38–49) hand-styles a bordered, padded, pointer-cursor rectangle to read as a notice band. There is no `Alert`/`AlertTitle` import in this file, and the whole container — not a distinct sub-element — carries the click handler.
- **Authority evidence:** `https://mui.com/material-ui/react-alert.md`. Its opening line (VERBATIM, re-checked against the fetched page): *"Alerts display brief messages for the user without interrupting their use of the app."* Its "Actions" section (VERBATIM): *"Add an action to your Alert with the `action` prop. This lets you insert any element—an HTML tag, an SVG icon, or a React component such as a Material UI Button—after the Alert's message, justified to the right."*, illustrated with `<Alert severity="success" action={<Button ...>UNDO</Button>}>...</Alert>`. The page's own "Anatomy" section shows the component is composed of a distinct icon region, message region, and optional action region as siblings, not one clickable surface. (Note for honesty: the same page states this component "is no longer documented in the Material Design guidelines, but Material UI will continue to support it" — this does not affect its status as documented, shipped vocabulary in the installed 5.15.11 package, but is worth naming.)
  - **Authority category:** component guidance.
- **Evidence mode:** VERBATIM — the load-bearing claim (Alert exists specifically for a brief, non-blocking message with an optional attached action) is directly quotable from the component's own introduction and "Actions" section; the finding's argument reasons from that quoted purpose rather than bridging multiple otherwise-unrelated pages.
- **Applicability argument:** (1) The observed task — a small, dismissable-in-spirit notice ("your data is stale") paired with exactly one follow-up action ("renew it") — is precisely the "brief message... with an optional action" problem `Alert`'s `action` prop is documented for, not a superficial shape match. (2) The current `Box`+`Typography` solves the identical problem: show a short message, offer one action. (3) An `<Alert severity="info" action={<Button onClick={renewDb}>{t(...)}</Button>}>{t("db-renew-text")}</Alert>` would preserve the exact same message and the exact same one-tap refresh behavior. (4) This is a clean, purpose-built substitution: MUI ships a first-class component for exactly this "notice plus action" concept (with theming via `severity`, a default icon, and a documented action slot) where the app instead reimplements the visual shell (border, padding, pointer cursor) on a bare `Box`.
- **Current expression:** A bespoke bordered `Box` (styled via hand-written `sx`) with `Typography` text, where the entire band — not a distinct control — is the click target for the refresh action.
- **Native expression:** An `Alert` (e.g. `severity="info"` or `"warning"`) wrapping the same message text, with the refresh behavior expressed via the documented `action` prop (typically a `Button`), matching the page's own "Actions" example almost element-for-element.
- **Why it matters:** Beyond the one-off styling cost of re-deriving what `Alert` already provides (severity theming, icon, consistent spacing/anatomy), the app's other notice-shaped surfaces should read as the same "kind of thing" to a rider; a hand-rolled notice band next to genuine `Alert` usage elsewhere in a Material UI app is a consistency/maintenance cost the shipped component is built to avoid.
- **Boundary check:** This is a component-selection finding (which component expresses "brief message + one action") — it does not evaluate whether the current `onClick`-on-a-`div` pattern is itself accessible or correctly wired, which is an implementation-mechanics concern this review doesn't own.

## Suppressed (low materiality or weak applicability)

- **`RouteHeader` (`Paper`-based per-route header strip) vs. `AppBar`** — considered because `RouteHeader` functions as a contextual header row (route number, reverse/star/timetable actions) sitting above the map/accordion content. Suppressed: the bounded surface does not include the app's root layout/navigation shell, so it can't be established whether the app already has a global `AppBar` elsewhere (in which case `RouteHeader` is correctly a secondary, in-content info+action strip, for which `Paper` is a documented, valid container) or whether this is meant to be the page's primary app-bar-level chrome. Insufficient evidence to pick a native alternative with confidence — not reported, per "Missing intent."

## Orientation notes

- **`IconButton` used for star/pin/bookmark/notify toggles** (`RouteStarButton.tsx`; `StopAccordion.tsx`'s notification, pin, and star `IconButton`s; `StopDialog.tsx`'s bookmark `IconButton`) — checked against `https://mui.com/material-ui/react-button.md`'s "Icon button" section, which states (VERBATIM, re-checked): *"Icons are also appropriate for toggle buttons that allow a single choice to be selected or deselected, such as adding or removing a star to an item."* This is the app's exact pattern (conditionally rendering a filled vs. outline icon inside an `IconButton`, with `aria-pressed` set on the toggling ones). Confirmed as already-native, documented usage — not a finding.
- **Controlled, single-open `Accordion` list for a route's stops** (`StopAccordionList.tsx` / `StopAccordion.tsx`, driven by `RouteEtaPage.tsx`'s `stopIdx` state) — matches the Accordion page's own controlled-accordion pattern (one panel open at a time via `expanded`/`onChange`) and its stated purpose ("lets users show and hide sections of related content on a page"). The expanded section holds genuinely related content for that stop (live ETA report plus per-stop actions). Confirmed as already-native usage.
- **`Snackbar` for the "copied to clipboard" confirmation** (`StopAccordionList.tsx`) — a brief, auto-dismissing, bottom-anchored notification of a just-completed action, matching Snackbar's documented purpose. Confirmed as already-native usage.

## What was not evaluated

Implementation correctness was not evaluated: prop usage and deprecation status on any `@mui/material`/`@mui/icons-material` component, the manually-set `aria-pressed`/`aria-label` values on the various `IconButton`s (including whether they always reflect true toggle state, e.g. the star buttons that open a collection-selection flow rather than toggling directly), the entirely-`onClick`-on-a-`div` keyboard-accessibility gap on `RouteUpdateNotice` prior to any component change, `sx`/style-object correctness, and hard-coded values (e.g. `StopDialog`'s `marginTop: "90px"` override). General UX and product judgment were also not evaluated — page density, the choice to route between a same-page dialog and separate stop pages, copy/wording, and any cross-page experience consistency beyond the specific component/composition claims above are out of scope for this review.
