# Design-System Native-Expression Review: Checkmate — Incidents page

**Design system:** Material UI (`@mui/material`, `@mui/icons-material`)

**Inferred user task:** An operator monitors uptime incidents across their monitored services. The page shows summary stats (active-incident count, latest incidents, aggregate stats), lets the operator filter a resolved-incidents table by monitor and resolution type and by a time range, inspect an individual incident's full detail (status, monitor, timeline, status code, resolution info) in a modal, and manually resolve an active incident by supplying an optional comment in a second modal. This is a filtered record-list + detail-inspection + record-mutation workflow, not a create/edit form flow.

**Packages / versions:** `@mui/material` resolved to `7.3.7` (declared and locked, exact pin — `client/package.json` + `client/package-lock.json`). `@mui/icons-material` is **not present** in `client/package.json` as a direct dependency and could not be resolved by `resolve_versions.py`; this is consistent with `inspect_surface.py` finding zero `@mui/icons-material` imports anywhere in the bounded surface (all icon glyphs come from `lucide-react` instead — see Orientation notes). `@mui/x-charts` (7.29.1) and `@mui/x-date-pickers` (7.29.4) are also direct dependencies but are not imported by this bounded surface. Material UI v7's current `Grid` API (the `size` prop, not the legacy `item`/`xs` props) is in use throughout, consistent with the resolved v7.3.7 version.

**Authority categories found in this corpus:** Component guidance pages (one page per component, e.g. `react-chip.md`, `react-list.md`, `react-grid.md`) and Guides/Customization pages (theming, responsive UI, composition) are the only meaningful authority tiers this corpus exposes. There is no named task/pattern layer and no composition-recipe tier (nothing analogous to Cloudscape's task patterns) — every judgment below is made at the component-guidance tier, or as an explicit synthesis across component pages, never against an invented composition-tier source.

## Findings

### Finding 1 — Hand-rolled status/attribute pill duplicates `Chip`'s documented job and color API

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Communicating a small set of semantic states (incident active/resolved, monitor status, HTTP status-code category, resolution type) as a compact, color-coded label wherever an incident or its fields are displayed — in the summary cards, the incident table, and the incident-detail dialog.
- **Repository evidence:** `client/src/Components/design-elements/StatusLabel.tsx` defines `ValueLabel` (lines 72–102) and `StatusLabel`: both render a `BaseBox` (a themed `Box`, see `client/src/Components/design-elements/BaseBox.tsx`) containing a manually-drawn 7×7px colored `Box` "dot" plus a `Typography` label, with `sx` hand-setting `color: theme.palette[palette].main`, padding, and border color. The palette key comes from `getStatusPalette`/`getValuePalette`/`getDockerStatePalette` in `client/src/Utils/MonitorUtils.ts` (lines 23–56), which return literal theme palette keys `"success" | "error" | "warning"`. `ValueLabel`/`StatusCodeLabel` (which wraps `ValueLabel`, `client/src/Components/design-elements/StatusCodeLabel.tsx`) are rendered five times inside the bounded surface: `CardSummary.tsx:160` (incident status in the summary list), `CardDetails.tsx:68` (incident status field) and `:128` (status code, via `StatusCodeLabel`), `IncidentTable.tsx:101` (status column) and `:156` (status-code column, via `StatusCodeLabel`).
- **Authority evidence:** `https://mui.com/material-ui/react-chip.md` — component guidance. VERBATIM: "Chips are compact elements that represent an input, attribute, or action." The `Chip` props table documents `color: 'default' | 'primary' | 'secondary' | 'error' | 'info' | 'success' | 'warning' | string` (default `'default'`), pulled directly from the theme palette, plus `variant: 'filled' | 'outlined'` and an `icon`/`avatar` slot for a leading glyph.
- **Evidence mode:** PARAPHRASE — the whole claim (Chip's stated purpose and its palette-keyed `color` prop) is drawn from the single `react-chip.md` page; no bridging across multiple sources was needed to establish that Chip's documented purpose and color API cover this exact shape.
- **Applicability argument:** (1) Task match: the repo's own palette-lookup functions return the identical semantic keys — `"success"`, `"error"`, `"warning"` — that `Chip`'s `color` prop consumes natively; the current code is not adjacent to what `Chip` is for, it is manually reconstructing `Chip`'s own `color` semantics one call site at a time. (2) Current implementation solves the same problem: yes, a compact, color-coded label for an attribute/state — precisely Chip's stated purpose. (3) Proposed alternative preserves the same task: yes, `<Chip label={text} color={palette} size="small" />` communicates identical information. (4) Materiality of the difference: the pattern is hand-implemented independently in `StatusLabel.tsx` (three near-duplicate components: `StatusLabel`, `ValueLabel`, `ColoredLabel`) and re-rendered at five call sites in this surface alone, each re-deriving border/padding/dot styling via `sx` rather than reusing one themed component's `variant`/`color`/`size` API. No MUI page states "don't build a custom status pill, use Chip instead" (no REQUIRED-tier prohibition exists — a hand-rolled `Box` is not itself a documented-vocabulary violation), so I hold the strength at `INFERRED` rather than `RECOMMENDED`, but the applicability match (identical purpose statement, identical palette-key vocabulary) is unusually direct for an `INFERRED` finding.
- **Current expression:** `BaseBox` (styled `Box`) + a manually-positioned colored `Box` dot + `Typography`, with color, border, and padding all set ad hoc via `sx` at each of `StatusLabel`/`ValueLabel`/`ColoredLabel`.
- **Native expression:** `Chip` with `color={paletteKey}` (the existing `getStatusPalette`/`getValuePalette` functions already return valid `Chip` `color` values with no mapping change needed), `variant="filled"` or `"outlined"` to match current visual weight, and `size="small"` for table/card density. The colored-dot affordance, if still wanted, is not itself a `Chip` prop — if it doesn't fit the `icon`/`avatar` slot, that specific visual detail is a legitimate reason to keep a light customization, but the label/color/border shell itself does not need to be reimplemented.
- **Why it matters:** Three near-duplicate hand-rolled components (`StatusLabel`, `ValueLabel`, `ColoredLabel`) exist in the codebase to do what `Chip`'s own `color`/`variant` API already does, each independently maintaining border, padding, and hover behavior instead of inheriting Chip's theme-driven styling (including dark-mode palette handling MUI already manages centrally). This is a maintenance/consistency cost specific to this design system: any future palette or density change to "how we show status" must be hand-applied in three places instead of one themed component.
- **Boundary check:** This is a component-selection judgment — which documented Material UI component is purpose-built for this exact "compact, color-coded attribute" concept — not a claim about `sx`/prop mechanics or generic UX quality.

### Finding 2 — Resolution-type filter uses `Select` where the page's own sibling filter uses the more targeted `ToggleButtonGroup` for the same interaction shape

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Narrowing the incidents list by a single, small, fixed-cardinality, mutually-exclusive facet (as opposed to the monitor filter, whose option set is data-driven and open-ended).
- **Repository evidence:** `client/src/Pages/Incidents/Components/ControlsIncidentFilter.tsx` renders the resolution-type filter (`resolutionTypes = ["all", "manual", "automatic"]`, line 9) as a `Select` + three `MenuItem`s (lines 57–72), imported from the app's `@/Components/inputs` wrapper, which itself wraps `@mui/material/Select` (`client/src/Components/inputs/Select.tsx`). Rendered directly below it on the same page, `client/src/Components/common/controls/HeaderTimeRange.tsx` renders the date-range filter — also a small, fixed, mutually-exclusive option set (`"recent" | "day" | "week" | "month"`, four values) — as `ToggleButtonGroup`/`ToggleButton` with `exclusive` (lines 39–59). The monitor filter, by contrast, is correctly left as `Select` (its option set is the full, data-driven, unbounded list of monitors from `monitorsData`).
- **Authority evidence:** `https://mui.com/material-ui/react-toggle-button.md` — component guidance. VERBATIM: "A Toggle Button can be used to group related options." with a documented "Exclusive selection" mode ("With exclusive selection, selecting one option deselects any other"). `https://mui.com/material-ui/react-select.md` — component guidance. VERBATIM: "Select components are used for collecting user provided information from a list of options," always demonstrated paired with `FormControl`/`InputLabel`, i.e. framed as a form-input control rather than an exclusive-choice filter chip group.
- **Evidence mode:** SYNTHESIS — no single MUI page states a cardinality- or filter-specific rule between `Select` and `ToggleButtonGroup`; the applicability argument bridges (a) `ToggleButtonGroup`'s own "group related options"/"exclusive selection" framing, (b) `Select`'s more generic, form-oriented framing, and (c) the repo's own already-established native answer for a structurally identical filter (`dateRange`) on the same surface.
- **Applicability argument:** (1) Task match: both `resolutionType` and `dateRange` are small (3–4 value), fixed, single-select, mutually-exclusive filter facets driving the same incidents query — not free-form or large/data-driven input, so they are the same shape of task. (2) Current implementation (Select) does solve the filtering problem, just via the more general-purpose, form-oriented component. (3) `ToggleButtonGroup` preserves the same task (same values, same exclusivity, same onChange contract). (4) Materiality: this is the specific case the "same-tier equivalence" rule warns about — neither cited page states a directional preference over the other in the abstract, so on the general MUI-vocabulary question alone this would be a same-tier equivalence and the candidate would need to be suppressed. What keeps it alive here is task-specific, in-surface evidence beyond that tier-classifying pair: the surface has *already* established `ToggleButtonGroup` as its own native answer for this exact interaction shape one control away (`HeaderTimeRange`), so the two structurally identical filters on the same page currently express the same concept two different ways with no apparent reason. I hold materiality at `medium` (not `high`) because `Select` is not wrong, and confidence at `medium` because the "same task" claim rests on shape/cardinality similarity, not an explicit product statement that resolution-type and date-range are meant to feel like one filter family.
- **Current expression:** `Select` + `MenuItem` × 3, sharing a `Stack` row with the monitor `Select` and a conditional "Clear filters" `Button`.
- **Native expression:** `ToggleButtonGroup` (`exclusive`) + `ToggleButton` × 3, mirroring `HeaderTimeRange`'s existing native pattern for the page's other small fixed-set filter.
- **Why it matters:** Design-system consistency within one bounded surface — a design-system-fluent implementer encountering both filters on the same page would notice they are the same interaction shape (small, fixed, exclusive) expressed with two different native controls, and would expect one consistent choice, the way the surface's own `dateRange` filter already demonstrates.
- **Boundary check:** This is a component-selection judgment about which documented control fits a small fixed-cardinality exclusive-choice filter, not a claim that `Select` is broken or that the page's overall filter UX needs a redesign.

## Suppressed (low materiality or weak applicability)

- **`@mui/icons-material` vs. `lucide-react` for all glyphs in this surface** — considered and suppressed, not merely low-materiality: MUI's own icon guidance (`https://mui.com/material-ui/icons.md`) explicitly documents `SvgIcon` for custom SVG icons and the `Icon` component wired to third-party icon fonts (its own worked example integrates Font Awesome), so the design system's own docs affirmatively support a non-`@mui/icons-material` icon source. Reporting "use `@mui/icons-material` instead of lucide-react" would be the exact `Existence does not imply a rule` failure mode this skill's anti-fundamentalism rule targets.
- **Monitor `Select` → `Autocomplete`** — considered. `Autocomplete` ("a normal text input enhanced by a panel of suggested options") could be a better fit if the monitor list is large/searchable, but the bounded surface has no evidence of typical monitor-list cardinality (no pagination, count, or virtualization on that dropdown, and no product statement that the list is expected to grow large). Establishing intent here would require guessing; suppressed rather than reported as `intent-dependent`, since even naming it adds little without that evidence.
- **`SummaryCard` (`BaseBox`-based bordered container) vs. `Card`/`CardContent`** — considered. Visually and structurally very close to `Card`'s documented job ("Cards contain content and actions about a single subject"), but `Card` is itself little more than a themed `Paper` with conventional child slots — MUI does not state a preference against a custom-styled `Box` achieving the same bordered-surface look, and the difference here is closer to a styling/primitive-swap than a compositional one. Low materiality; suppressed.
- **`CardDetails.tsx`'s heavy `Grid` use (29 `Grid` tags) for repeated label/value rows** — considered as a possible "should be `List`/`ListItemText`" finding, then suppressed on inspection of both cited pages: `Grid`'s own guidance frames it as appropriate specifically for layouts needing "both vertical and horizontal arrangement" (`react-stack.md`: "Stack is ideal for one-dimensional layouts, while Grid is preferable when you need both vertical _and_ horizontal arrangement"), which is exactly what a two-column (label-left/value-right) repeated-row layout is — so `Grid` is not a mismatch here. `List`/`ListItemText` was also considered, but `ListItemText`'s documented `primary`/`secondary` pattern renders as a *stacked two-line* item (see the `react-list.md` "Photos"/"Jan 9, 2014" demo), not a left-label/right-value row, so it does not structurally match this surface's shape; `secondaryAction` would structurally fit but every documented `secondaryAction` demo is an interactive control (`IconButton`, `Checkbox`), and `List`'s own framing centers on "primary and supplemental actions," a materially different task from CardDetails' static, read-only field display — the task-match prong of the anti-fundamentalism test fails.

## Orientation notes

- `HeaderTimeRange` (`client/src/Components/common/controls/HeaderTimeRange.tsx`) correctly uses `ToggleButtonGroup`/`ToggleButton` with `exclusive` for the date-range filter — matches `react-toggle-button.md`'s documented "Exclusive selection" composition precisely.
- `ActionsMenu` (`client/src/Components/actions-menu/index.tsx`) correctly uses `IconButton` + `Menu` + `MenuItem` for the per-row kebab action menu — matches `react-menu.md`'s "Menus display a list of choices on temporary surfaces."
- Table pagination (`client/src/Components/design-elements/Table.tsx`, `Pagination`) correctly wraps native `TablePagination`, using its documented `ActionsComponent` slot rather than hand-rolling a page-control widget.
- `DialogIncidentDetails.tsx` and `DialogResolution.tsx` are both thin, correct usages of the app's `Dialog` wrapper, which itself is a straightforward, mechanically-correct composition of `Dialog`/`DialogTitle`/`DialogContent`/`DialogActions` (`client/src/Components/inputs/Dialog.tsx`) — no component-selection issue found in either dialog.
- `CardSummary.tsx`'s `SummaryIncidentItem` (unlike the row patterns discussed under Suppressed) correctly uses `Grid` with real per-breakpoint sizing (`size={{ xs: 12, lg: 5 }}`, etc.) to reflow a multi-field row across breakpoints — a genuine responsive use of `Grid`, not a fixed single-value one.
- `ControlsIncidentFilter`'s monitor `Select` (open-ended, data-driven option set) is an appropriate use of `Select` over `ToggleButtonGroup` — contrast with Finding 2, which is specifically about the fixed-set `resolutionType` filter, not this one.

## What was not evaluated

Implementation correctness — prop usage, deprecated APIs, accessibility mechanics (e.g., whether the hand-rolled `lucide-react` icons carry correct `aria-hidden`/labeling, whether `BaseBox`'s custom `sx` merges correctly with consumer overrides), hard-coded style values, and TypeScript typing — was not assessed; none of the findings above should be read as clearing or flagging that layer. General UX and product judgment (information density, whether two chained dialogs is the right flow for resolving an incident, filter placement, mobile layout quality) was likewise not assessed beyond what was necessary to establish the native-expression judgments above.
