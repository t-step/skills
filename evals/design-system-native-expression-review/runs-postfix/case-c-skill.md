# Design-System Native-Expression Review: WorkspaceDetails.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** View the details of a single workspace resource ("eng-platform-prod"): its stable, cross-cutting identity/configuration facts (name, owner, region, plan tier, created date, status), plus two further groupings of task-specific information about that same resource — its members (a multi-row, comparable collection) and its activity history (a linear read-only log) — reachable by switching tabs, with page-level Edit/Delete actions available throughout. The surface's own code comment (lines 30-33) states this intent explicitly: the general configuration facts are "relevant no matter which tab a user is currently looking at (Members or Activity)," with "Tabs organiz[ing] the rest."

**Packages / versions:** `@cloudscape-design/components` resolved to `3.0.900` (declared range `^3.0.900`, locked via `package-lock.json` in the fixture root at `evals/cloudscape-native-expression-review/cases/case-c-workspace-details/fixture/`).

**Authority categories found in this corpus:** Cloudscape's `llms.txt` index exposes component guidance (112 component pages), a named-pattern/task tier (`Patterns`, including a `resource-management/details` sub-tree with `details-page`, `details-page-with-tabs`, and `details-page-as-hub`), demos, and foundations. This review draws on component guidance and the named-pattern tier, which is directly applicable here (a resource-details-with-tabs surface is one of the pattern tier's own named subjects).

## Findings

### Finding 1: General workspace configuration facts belong in a persistent Details summary container using Key-value pairs, not inside the switchable "Overview" tab as a one-row Table

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Let the user see the workspace's own stable identity/configuration facts (name, owner, region, plan, created date, status) regardless of which tab (Members or Activity) they are currently viewing, while using tabs only to separate the two genuinely distinct, task-specific groupings of related-but-different information.
- **Repository evidence:** `WorkspaceDetails.tsx` lines 34-123. The `Tabs` component (lines 62-120) contains three tabs; the first, `id: 'overview'` (lines 66-91), renders a `Table` with `items={[{}]}` (a single synthetic row) whose six `columnDefinitions` each render one hard-coded property (Name, Owner, Region, Plan, Created, Status via `StatusIndicator`). The source comment directly above the component (lines 30-33) states these are "the workspace's own general configuration facts: stable, read-mostly, and relevant no matter which tab a user is currently looking at (Members or Activity)" — yet the implementation places them inside the very first tab, so they disappear the instant a user switches to Members or Activity.
- **Authority evidence:**
  - `https://cloudscape.design/patterns/resource-management/details/details-page-with-tabs/index.html.md`, building block "D. Details summary container - optional": *"For a **details page with tabs**, this section serves as a summary that is always visible when users switch between the tabs. Use it to display important information that applies to tasks in all the tabs."* Building block "E. Tabs" separately instructs: *"Use tabs to organize information about the resource into mutually exclusive, meaningful content groups... Follow this rule: one tab, one task."*
  - `https://cloudscape.design/patterns/resource-management/details/details-page/index.html.md`, building block "D. Details summary container": *"Place the most relevant information about the resource in this container. To organize content, use [key-value pairs]."* Its writing guidelines add: *"For the details summary container, use this text: General configuration / [Resource type] settings."* The "details page with tabs" page's own building block D explicitly incorporates this by reference ("Follow the guidelines for details page").
  - Authority category: **named pattern** (both are pattern-tier pages, directly cross-referenced with each other).
- **Evidence mode:** SYNTHESIS. The two cited pages are not independently discovered and loosely combined — "details page with tabs" building block D explicitly tells the reader to "follow the guidelines for details page" for this same building block, then adds the tab-specific requirement (always visible across tab switches). Bridging them: page 1 establishes that the details-summary-container building block, when present, must remain visible regardless of active tab and must hold cross-cutting resource information; page 2 (incorporated by direct reference) establishes that this same building block's content should be organized with Key-value pairs. Together they describe one documented building block this surface's own code comment independently confirms is the intended semantic role of this content.
- **Authority strength:** RECOMMENDED. Both source passages use direct imperative language ("Use it to display...", "To organize content, use key-value pairs") describing the building block's function, but neither is phrased as an explicit "Don't do X, instead do Y" prohibition against putting cross-cutting content inside a tab — so REQUIRED would overstate it.
- **Applicability argument:** (1) The observed task — showing facts that apply "no matter which tab" is active — materially matches, almost verbatim, the documented composition's stated problem (a summary "always visible when users switch between the tabs"); this is not a superficial shape match, the surface's own comment states the identical intent. (2) The current implementation solves substantially the same problem (surfacing cross-cutting resource facts) but fails to solve it correctly: it is hidden as soon as the user leaves the Overview tab. (3) The proposed native expression — a `Container` (titled "General configuration") holding a `KeyValuePairs` block, placed between the page `Header` and the `Tabs` — preserves the exact same task and the exact same data, only relocating and re-expressing it. (4) The gap is material enough that an experienced Cloudscape practitioner would restructure the code: the current structure actively defeats its own documented and self-stated purpose (persistent, cross-tab visibility) rather than merely being a stylistically different but equally valid choice.
- **Current expression:** A `Tabs` component whose first tab, "Overview," renders a `Table` with one synthetic row (`items={[{}]}`) and six columns, each a hard-coded single value (Name, Owner, Region, Plan, Created, Status). This content is only visible while the "Overview" tab is active.
- **Native expression:** Move the general configuration facts out of the `Tabs` entirely into a persistent `Container` (header text "General configuration," per the writing guidelines above) placed between the page `Header` and the `Tabs`, and render its content with `KeyValuePairs` (label: Name/Owner/Region/Plan/Created/Status, value: the corresponding fact, with `StatusIndicator` as the Status value — one of KeyValuePairs' own documented recommended value types). The `Tabs` component is then reserved for the two genuinely tab-appropriate groupings already present: Members (multi-row `Table`) and Activity (`List`).
- **Why it matters:** The current structure directly undermines the surface's own stated design intent (per its code comment) and the documented building block's entire reason for existing: cross-cutting resource facts vanish the moment a user checks Members or Activity, exactly the scenario the "always visible" building block exists to prevent. Separately, `Table` is documented as presenting "a two-dimensional table format" of comparable, sortable rows — a semantic mismatch for a single, non-repeating set of resource properties, which `KeyValuePairs` ("lists of properties (labels) followed by their corresponding values") exists specifically to express.
- **Boundary check:** This is a choice about which documented building block (a persistent details-summary container vs. tab content) and which component (KeyValuePairs vs. a single-row Table) the design system's own "details page with tabs" pattern establishes for this exact content — not an implementation defect (no prop, API, or accessibility mechanic is at issue) and not a generic UX opinion (the citation is specific and normatively stated, and the surface's own comment already agrees with the documented intent).

## Suppressed (low materiality or weak applicability)

- **Breadcrumb depth** — `BreadcrumbGroup` shows two levels ("Workspaces" > "eng-platform-prod"), while the "Details page" pattern documents a three-level structure ("[Service name] > [Resources type] > [Resource name/ID]," e.g. "CloudFront > Distributions > SLCCSMWOHOFUY0"). Suppressed: this bounded, single-file surface gives no evidence of the surrounding application's information architecture, so it cannot be established whether "Workspaces" already functions as this app's top-level/service crumb (in which case two levels is correct) or a level is genuinely missing — reporting a confident recommendation either way would exceed the available evidence.
- **Activity list bundles actor + action + object + relative timestamp into one plain string in `List`'s `content` slot**, rather than splitting the timestamp into `List`'s documented `secondaryContent` area (its own component page lists "timestamps, tags, or brief details of the content" as common secondary-content material). Suppressed: the List component page only offers this as an example of common secondary-content usage, not a stated requirement or "don't" rule (anti-fundamentalism: existence of a slot and an illustrative example don't mandate its use), and all information remains equally present and readable either way — materiality is low.

## Orientation notes

- `Tabs` used to switch between "Members" and "Activity" — correct use of the component and matches the "details page with tabs" pattern's guidance to use tabs for "mutually exclusive, meaningful content groups" following "one tab, one task"; neither tab is a hub/navigation case the pattern's "Don't" rule would rule out.
- "Members" tab's `Table<Member>` — correct: a genuine multi-row, comparable collection of users (name/email/role), matching `Table`/"Table view" pattern guidance ("structured, easily comparable" data).
- "Activity" tab's `List` — correct: a linear, read-only sequence of events ("a group of consecutive items displayed one below the other," per the List component's own description), not multi-column sortable data that `List`'s own "Don't" guidance would redirect to `Table`.
- Header actions (`Edit`, `Delete` as global buttons in the `Header`'s `actions` slot) — matches "Details page" building block C: "Header or global buttons - Use when the actions will affect the entire resource. For example: Edit or Delete."
- `BreadcrumbGroup` as the component choice (independent of the depth question above) — matches "Details page" building block A's expectation of a breadcrumb trail leading to the resource.

## What was not evaluated

Implementation correctness — including that the `Edit`/`Delete` buttons and `Tabs.onChange` have no visible wiring to real actions or a delete-confirmation flow, that Overview cell values are hard-coded literals rather than derived from props/state, and any prop-level or accessibility-mechanic details beyond what was needed as supporting evidence above — was not assessed; this skill does not review implementation mechanics. General UX/product judgment (writing/copy quality of the Activity entries, information density, whether a service-level breadcrumb crumb should exist) was likewise not assessed except where explicitly named above as insufficient-evidence and suppressed.
