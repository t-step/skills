# Design-System Native-Expression Review: EndpointScaling.tsx (Endpoint scaling fleet page)

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** An on-call operator reviewing every inference endpoint in the fleet (22 endpoints) to compare request volume, p99 latency, and error rate side by side across all of them, in order to decide which one(s) need a capacity change ("Scale up"). This is stated explicitly in the page's own header description ("Compare request volume, latency, and error rate across endpoints to decide which ones need to scale") and in an in-code comment ("The whole point of this page is comparing invocation volume, p99 latency, and error rate side by side across all endpoints to decide which one(s) need a capacity change").

**Packages / versions:** `@cloudscape-design/components` resolved to `3.0.900` (declared range `^3.0.900`, locked in `package-lock.json`) via `resolve_versions.py --root <fixture root>`. `inspect_surface.py --package-prefix '@cloudscape-design/'` confirms the surface's only design-system imports are `ContentLayout`, `Header`, `Cards`, `StatusIndicator`, `Button`, `Box`, each used exactly once, with no other design-system or native-HTML interactive elements present.

**Authority categories found in this corpus:** Both a component tier (per-component pages, e.g. Cards, Table, Status indicator, Content layout) and an explicit named-pattern/composition tier under `patterns/resource-management/view/` (View resources, Card view, Table view), including a directly quantitative decision table for choosing between Table view and Card view for a given resource collection. This corpus has a genuine composition-level authority tier for this exact question, not just component descriptions.

## Findings

### Finding 1: A 22-item, shared-metadata, sortable-metric comparison task is expressed as Cards rather than the documented Table view

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As stated above — compare volume/latency/error-rate across all 22 endpoints to decide which need scaling.
- **Repository evidence:** `EndpointScaling.tsx` renders all 22 `ENDPOINTS` (line 17: `Array.from({ length: 22 }, ...)`) through a single `Cards` component (lines 46-88) whose `cardDefinition.sections` are identical, purely textual/numeric/status fields across every item: `status` via `StatusIndicator` (line 54), `region` (58-60), `invocationsPerMin` (62-65), `latencyP99Ms` (67-70), `errorRatePct` (72-75), plus a per-item `Button` action (77-83). `cardsPerRow` (line 86) tops out at 3 cards per row even at the widest breakpoint (`{ minWidth: 900, cards: 3 }`), so at most 3 of 22 endpoints are visible at once, and `Cards` provides no column-sort mechanism for any of these metrics.
- **Authority evidence:** `patterns/resource-management/view/index.html.md` ("View resources," named pattern) states a decision table for "Choosing between table view and card view": Table view applies when there are "9 or more resources in 99% of use cases," when metadata is "Shared metadata between resources," and when the metadata type is "Data that is displayed in columns (text, numerical, status, sparkline)"; Card view is scoped to "5 or less resources in 99% of use cases," "Different metadata across resources," and data "displayed as visuals (charts, videos)." The same page states directly: "Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on. Use the card view if users will not be comparing between a large number of resources to determine which to take action on." `patterns/resource-management/view/table-view/index.html.md` ("Table view," named pattern) independently corroborates: "Use table view pattern for static data with multiple attributes displayed in a tabular format," "The best data type for a table view is data that is structured, easily comparable, and sortable," and "Restrain from incorporating graphics in tables. For data sets with a blend of text, images, and data visualizations... refer to the cards view pattern" (this surface has none of the latter). Authority category: **named pattern**.
- **Evidence mode:** SYNTHESIS — the View resources decision table supplies the quantitative/qualitative criteria (item count, shared-metadata, columnar data type) that this surface's data matches on all three axes; the Table view page's own "Do" guidance independently confirms that structured/comparable/sortable, non-graphical data (exactly what `invocationsPerMin`, `latencyP99Ms`, `errorRatePct`, `status`, `region` are) is the table's designed use case. Both sources point the same direction; neither states a same-tier "use either" for this specific data shape.
- **Authority strength:** RECOMMENDED — the View resources criteria are stated as directive ("Use a table if...") but hedged quantitatively ("in 99% of use cases"), not phrased as an absolute prohibition for this specific choice.
- **Applicability argument:** (1) The observed task — comparing shared metrics across many resources to pick which one(s) need action — is verbatim the scenario the View resources page assigns to Table view ("your users will be comparing resources to determine which to take action on"), not a superficial shape match. (2) The current Cards implementation solves exactly this same comparison problem, just with the wrong collection component for it. (3) A Table-based expression preserves the identical task and data — same fields, same per-item "Scale up" action (Table's own building blocks document "Actions in table cells" for exactly this). (4) The gap is material: 22 items is roughly 2.4x the "9 or more" table threshold and over 4x the "5 or less" card threshold; all three decision-table axes (count, shared metadata, columnar data) point the same direction, so this is not a same-tier "either is fine" pairing the anti-fundamentalism rule would require suppressing — every documented criterion concurs, and Cards' inability to sort by latency/error rate/invocations actively works against the page's own stated triage purpose.
- **Current expression:** A `Cards` grid (default styling, max 3 per row) with identical per-item sections for every endpoint, no sorting.
- **Native expression:** The Table view pattern's own building blocks — a full-page `Table` with `columnDefinitions` for status (via `StatusIndicator`), region, invocations/min, p99 latency, and error rate, each independently sortable, plus a row-level action column for "Scale up" (matching the pattern's documented "Actions in table cells" / in-context-actions building block) and the existing `Header` with its counter as the table's header. This lets the operator sort directly by the exact metrics the page says they're comparing, which Cards structurally cannot do.
- **Why it matters:** The page's own stated purpose is to compare metrics across all 22 endpoints to decide which needs a capacity change — precisely the criterion Cloudscape's own decision table assigns to Table view, not Card view. The current Cards layout caps visibility at 3 of 22 endpoints per row and offers no sort, working against the very triage task the page description names, where Table's documented sorting building block is purpose-built for it.
- **Boundary check:** This is about which top-level collection-display component and page pattern (Card view vs. Table view) best expresses a data-comparison/triage task, not about how `Cards` is coded — it is a component/composition-level recommendation, not a prop or accessibility fix.

### Finding 2: `ContentLayout` wraps `Cards` in its default (`container`) variant instead of using the pattern's own full-page variant

- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Same as above — this finding concerns the page-structure mechanism for that same resource-collection task, independent of whether Cards or Table is the collection component (see Finding 1).
- **Repository evidence:** `EndpointScaling.tsx` line 35 wraps the entire page in `<ContentLayout header={...}>`, and the `Cards` component at line 46 is instantiated with no `variant` prop at all, so it uses the documented default. The Cards component API (`components/cards/index.html.json`) confirms `variant` defaults to `'container'` and offers `'full-page'` — "Use this variant when cards are the entire content of a page" — which is exactly this page's situation (Cards is the entire page content), yet that variant is not set.
- **Authority evidence:** `patterns/resource-management/view/card-view/index.html.md` ("Card view," named pattern), under "Don't": *"Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the cards component to implement this pattern."* The identical rule appears verbatim (substituting "table" for "cards") in `patterns/resource-management/view/table-view/index.html.md`'s "Don't" section, so this finding holds regardless of the Finding 1 outcome. Authority category: **named pattern**.
- **Evidence mode:** VERBATIM — the cited sentence is quoted directly from the Card view (and identically from the Table view) pattern page.
- **Authority strength:** REQUIRED — this is an explicit "Don't... Instead" prohibition, the strongest strength this corpus expresses.
- **Applicability argument:** (1) The task at this level is page-structure for a resource-collection view — the same page type this Don't/Instead rule is scoped to ("on this type of page"). (2) The current `ContentLayout` + default-variant `Cards` composition solves the identical page-chrome problem the full-page variant is designed for. (3) Switching to the full-page variant (dropping `ContentLayout`) preserves the same header, counter, and card/table content — no task change. (4) The rule is stated as an explicit prohibition, directly matched by the current code (ContentLayout present, variant unset/default), which is as material a divergence as this corpus documents.
- **Current expression:** `ContentLayout` (a general page-structure component for "expressive use cases") wraps a `Cards` instance left at its default `container` variant.
- **Native expression:** Drop the `ContentLayout` wrapper and set the collection component's `variant` to `"full-page"`, letting it own page-level chrome directly, per the pattern's own building block guidance.
- **Why it matters:** The current composition directly contradicts an explicit, verbatim "Don't... Instead" rule stated identically for both the Card view and Table view patterns, producing page chrome (padding/header treatment) that diverges from how Cloudscape's own documented collection-view pages are structured — a consistency cost against the rest of an app built on this design system, not a stylistic nit.
- **Boundary check:** This is which documented page-structure mechanism (a general `ContentLayout` wrapper vs. the collection component's own purpose-built full-page variant) is correct for this exact resource-collection pattern — a structural composition choice the pattern's own docs name explicitly, not a prop-level implementation detail.

## Suppressed (low materiality or weak applicability)

- **Table with grouped resources** (considered because each endpoint carries a `region` attribute): suppressed. The stated task is flat side-by-side comparison across all endpoints for a scaling decision, not region-based grouping, and the fixture assigns `region` cyclically (`i % 4`) with no product signal that grouping by region is an intended structure — applicability evidence too thin to report.
- **Split view pattern** (considered because a per-item action exists that could one day open a detail panel): suppressed. Nothing in this bounded file indicates a companion detail/inspection view is part of this task; the task as stated is comparison-only across the full set, and recommending a split panel would introduce a UI concept the surface doesn't currently serve.
- **Row/card selection + bulk actions**: suppressed. No `selectedItems`/`onSelectionChange` or bulk-action affordance exists in the code, and nothing about the stated task implies scaling multiple endpoints in one action — only a single per-item "Scale up" action is shown. Recommending selection would invent a capability rather than natively express an existing one.

## Orientation notes

- `StatusIndicator` mapped from `status` (`healthy`/`degraded`/`overloaded` → `success`/`warning`/`error`) is the correct, purpose-built component for a per-resource compact state indicator, and is unaffected by either finding above (it works identically inside a card section or a table cell).
- `Header` with a `counter` reflecting `ENDPOINTS.length` is standard, correct usage for summarizing a resource collection's size.
- The per-item `Button` ("Scale up") is used as an in-context action tied to a single resource, consistent with in-context action usage, and is preserved unchanged by both findings above (as a card-section action today, or as a table row-action column if Finding 1 is adopted).

## What was not evaluated

Implementation correctness (e.g., whether `Box float="right"` is the right mechanism for right-aligning the button, any prop/API-shape or accessibility mechanics of `Cards`, `StatusIndicator`, or `Header`, hard-coded values, or the `cardsPerRow` breakpoint numbers themselves) and general UX/product judgment (visual density, color choices, whether 22 is "too many" endpoints to show at all, copy wording) were not evaluated — their absence here does not mean they were checked and found acceptable.
