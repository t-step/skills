# Design-System Native-Expression Review: MessageQueues.tsx (case-p1-message-queues)

**Design system:** Cloudscape (`@cloudscape-design/components`, `@cloudscape-design/collection-hooks`, `@cloudscape-design/global-styles`)

**Inferred user task:** An operator monitors every message queue in the account side by side and decides which ones need scaling attention right now, by comparing throughput (messages/s) and backlog age (oldest message age) across queues. The operator can search queues by name and — per the surface's own stated intent — narrow the list down to a specific status or region while triaging. This is stated directly in the surface: the in-code comment above the component ("Message Queues: every queue in the account, side by side, so an operator can compare throughput and backlog age across all of them at once to decide which need scaling attention right now. Operators can search by queue name, or narrow the list down to a specific status or region while triaging.") and the `Header` description ("Compare message throughput and backlog age across queues to decide which need scaling attention.") both name the task explicitly.

**Packages / versions:** `@cloudscape-design/components` 3.0.900 (declared `^3.0.900`), `@cloudscape-design/collection-hooks` 1.0.60 (declared `^1.0.60`), `@cloudscape-design/global-styles` 1.0.45 (declared `^1.0.45`) — all resolved against `package-lock.json` in the fixture root via `resolve_versions.py`. No unresolved ranges.

**Authority categories found in this corpus:** Cloudscape's docs expose component guidance (the "Components" section, ~112 pages, each with Do/Don't and usage guidelines) and named patterns (the "Patterns" section, organized under general/resource-management categories). Within Patterns, two overview pages — "View resources" and "Filtering patterns" — carry explicit decision-criteria tables and "use X if Y / use Z if W" prose for choosing between sibling named patterns/components, which is stronger than a plain example or demo. The corpus also has Foundations, Demos, an "About" section, and a separate Gen AI pattern/component subset not relevant to this surface. No separate "composition guide" or "usage guide" tier distinct from Patterns was found; pattern pages themselves carry both the "what" and the "when to use it" guidance.

## Findings

### Finding 1: Full collection of resources rendered as Cards where Cloudscape's own selection criteria point to Table

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As stated above — comparing throughput and backlog age across all 24 queues (a fixed, shared set of fields) to decide which need scaling attention.
- **Repository evidence:** `MessageQueues.tsx` renders all 24 `QUEUES` (lines 18-25) as `Cards` (lines 56-98), one card per queue, with four sections per card: `status` (a `StatusIndicator`, line 69), `region` (line 74), `messagesPerSecond` (line 79), `oldestMessageAgeSec` (line 84). Every item has the identical four fields — there is no per-item variation in what metadata is shown. `useCollection` is configured with `sorting: {}` (line 41) but `Cards` has no column-header sort affordance to attach it to, so despite the collection hook being sort-capable, an operator has no way to sort by throughput or backlog age — the two values the task explicitly says they need to compare to prioritize action.
- **Authority evidence:** cloudscape.design/patterns/resource-management/view/index.html.md ("View resources"), section "Choosing between table view and card view." The page states a decision table:

  | | Table view | Card view |
  |---|---|---|
  | Number of resources in the data set | 9 or more resources in 99% of use cases | 5 or less resources in 99% of use cases |
  | Metadata being displayed | Shared metadata between resources | Different metadata across resources (different types of databases with different data) |
  | Metadata type | Data that is displayed in columns (text, numerical, status, sparkline) | Data that can be displayed as visuals (charts, videos) |

  and, in prose: "Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on. Use the card view if users will not be comparing between a large number of resources to determine which to take action on." Authority category: **named pattern** (the decision criteria live on a single Patterns-tier page, not a component page).
- **Evidence mode:** VERBATIM (the decision table and the "use a table if / use card view if" sentence are direct quotes from cloudscape.design/patterns/resource-management/view/index.html.md, checked character-for-character against the fetched page).
- **Applicability argument:** All four points of the anti-fundamentalism test hold. (1) The task match is not superficial — the "View resources" page's own stated condition is "your users will be comparing resources to determine which to take action on," which is a near-verbatim restatement of this surface's own comment ("compare... to decide which need scaling attention"). (2) The current Cards implementation solves exactly this comparison problem, just via the less-fitting component. (3) Switching to Table preserves the same task — same 24 items, same fields, same filter/paginate interaction, nothing about the user's goal changes. (4) Materiality: 24 items is well past the table threshold ("9 or more... in 99% of use cases") and nowhere near the card threshold ("5 or less"); every queue shares the identical field set (the table's "shared metadata" condition, not card's "different metadata" condition); and all four displayed fields are exactly the types the table row calls out — "text, numerical, status" — not the "visuals (charts, videos)" cards are positioned for. This is a directional criteria table, not an unranked "use either" pairing, so the same-tier-equivalence carve-out does not apply — the criteria clearly resolve toward Table for this dataset.
- **Current expression:** `Cards` (default variant) with four card sections per queue, non-sortable, `cardsPerRow` responsive breakpoints, wrapped by `ContentLayout`.
- **Native expression:** A full-page `Table` with one sortable column per field (name/row header, status, region, messages/s, oldest message age), keeping the same `useCollection`, `TextFilter`, and `Pagination` wiring — `useCollection`'s `sorting: {}` config already anticipates a table's column-sort affordance, which Cards cannot expose the same way.
- **Why it matters:** The chosen component structurally cannot deliver the interaction the surface's own copy promises ("compare... across all of them at once to decide which need scaling attention") for a 24-row, uniform-schema, all-scalar dataset — there is no way to sort by throughput or backlog age, forcing the operator to visually scan cards instead of ranking a column, which is precisely the comparison problem Cloudscape's own criteria table assigns to Table, not Cards.
- **Boundary check:** This is a component/composition-selection question (which named resource-view pattern fits a 24-item, uniform-schema, comparison-driven collection), not an implementation defect in the existing Cards usage (which is itself mechanically correct) and not a generic UX complaint (it is grounded in a specific, cited decision table whose stated conditions this dataset satisfies).

### Finding 2: `ContentLayout` wraps the collection instead of using the pattern's own full-page variant

- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Same as above.
- **Repository evidence:** `MessageQueues.tsx` lines 44-100: `<ContentLayout header={<Header variant="h1" ... />}> <Cards ... /> </ContentLayout>`. No `variant` prop is passed to `Cards`, so it renders in its default (non-full-page) variant, nested inside `ContentLayout`.
- **Authority evidence:** cloudscape.design/patterns/resource-management/view/card-view/index.html.md, "Don't" list: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the cards component to implement this pattern." The identical sentence, with "table" substituted for "cards," also appears verbatim in cloudscape.design/patterns/resource-management/view/table-view/index.html.md's "Don't" list — so the same rule applies whether Finding 1 above is adopted or not. Authority category: **named pattern**.
- **Evidence mode:** VERBATIM (checked against both fetched pattern pages; markdown link brackets around "content layout," "cards," and "table" stripped for quoting, wording otherwise unaltered).
- **Applicability argument:** (1) This page is exactly the scenario the "Don't" targets — a full-collection resource-view page, not a form or detail page. (2) The current composition (`ContentLayout` + default-variant `Cards`) solves the same page-structure problem the "Don't...instead" pairing addresses. (3) Switching to `ContentLayout`-free, full-page-variant Cards (or Table, per Finding 1) preserves the identical task and content — only the page-shell composition changes. (4) This is an explicit, stated prohibition paired with a named alternative, the strongest form of evidence this corpus offers — an experienced Cloudscape implementer would restructure this specifically because the docs say not to do it this way.
- **Current expression:** `ContentLayout` (documented for "expressive use cases") wrapping a default-variant `Cards`.
- **Native expression:** Full-page variant of the collection component (Cards per current code, or Table per Finding 1) as the top-level content, without `ContentLayout`, per the pattern page's own building-block guidance ("Use the 'full-page' variant of the cards component for this pattern").
- **Why it matters:** This is a directly-cited "Don't X, instead Y" pairing the current code violates outright, not a stylistic nuance — Cloudscape's page-structure system distinguishes "expressive" content pages (`ContentLayout`) from full-collection resource-view pages (full-page collection variant) specifically so collection pages get the density, sticky-header, and layout behavior the pattern expects; using `ContentLayout` here departs from that documented structure.
- **Boundary check:** This is a page-structure composition question (which layout primitive wraps a named resource-view pattern), governed by an explicit documented constraint on that pattern — not a prop-usage defect (both components are used in a mechanically valid way) and not general UX critique.

### Finding 3: A single free-text filter is used where the surface's own stated task is filtering by two finite-valued properties

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Per the surface's own comment: operators "search by queue name, or narrow the list down to a specific status or region while triaging." `status` and `region` are both finite two-value enums (`'healthy' | 'backlogged'`, `'us-east-1' | 'us-west-2'`, lines 12-13).
- **Repository evidence:** Only `TextFilter` is wired into the `Cards`' `filter` slot (lines 89-95), bound to `filterProps` from `useCollection`. There is no select-based control for `status` or `region` anywhere in the file — the stated "narrow down to a specific status or region" capability has no dedicated affordance; only free-text entry is available.
- **Authority evidence:** cloudscape.design/patterns/general/filter-patterns/index.html.md: "If users tend to know exactly the value or term they are looking for, use the text filter. If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter. For example: by 'status' or 'type'." The page's own criteria table further contrasts user goals: text filter is for "Find resources that match an exact text query," collection select filter is for "Find resources with overlapping, defined values." Authority category: **named pattern**.
- **Evidence mode:** VERBATIM (checked against the fetched filter-patterns page; the docs' own worked example is literally "status," matching this surface's field name).
- **Applicability argument:** (1) The task match is exact, not superficial: the docs' own example property for the collection select filter is "status" — the same field this surface names as something operators need to narrow by. (2) TextFilter, as currently wired, could partially serve this need only if an operator types the literal enum string, which is not the "choose a defined value" interaction the task describes. (3) Adding a `CollectionSelectFilter` for `status` and `region` alongside the existing `TextFilter` preserves the same task (search by name, narrow by status/region) — the two components are explicitly documented to compose together ("filtered as soon as the user selects a value from a select filter or enters text into the accompanying text filter," collection-select-filter page), so this isn't a replacement, it's completing the composition the surface's own comment already describes. (4) Two finite-valued properties is precisely the collection select filter's stated scope ("if a select filter has two properties, the operator is always and" — matching a two-property `status`+`region` narrowing exactly, with no need for the more complex property filter).
- **Current expression:** `TextFilter` only, matching the free-text half of the stated task ("search by queue name") but not the discrete-narrowing half.
- **Native expression:** A `CollectionSelectFilter` for `status` and `region` composed alongside the existing `TextFilter`, per the documented text-filter-plus-select-filter composition.
- **Why it matters:** The surface's own description of its filtering capability ("narrow the list down to a specific status or region") is not actually deliverable with the component currently wired for it — TextFilter's free-text matching is not the same interaction the docs describe for narrowing by one or two known, finite property values, so the stated task and the implemented control are misaligned exactly where Cloudscape ships a purpose-built component for this dataset shape.
- **Boundary check:** This is a filtering-component-selection question grounded in a cited decision between three named filter patterns for the same stated narrowing task, not a defect in how `TextFilter` itself is wired (which is mechanically correct) and not a generic "add more filters" UX suggestion.

## Suppressed (low materiality or weak applicability)

None — all candidates considered either survived at high materiality (above) or were confirmed as already-native (below); nothing was checked and found to be a marginal/low-materiality deviation.

## Orientation notes

- `StatusIndicator` used for the `status` field (line 69) is exactly the documented job for that component — "communicates the state of a resource... in a compact form that is easily embedded in a card, table, list" — and this holds whether the surrounding collection stays `Cards` or moves to `Table` per Finding 1.
- `Pagination` wired via `paginationProps` (line 96) with `pageSize: 12` against 24 items is a correct, unremarkable use of the pattern's pagination building block; Cloudscape's own guidance to "display the pagination even if the resources set fits in one page" isn't even in tension here since 24 items always spans two pages.
- The `Header` item counter (`counter={\`(${QUEUES.length})\`}`, line 49) follows the documented counter format — a plain total in parentheses, no selection in play.
- `useCollection`'s `filtering.empty` / `filtering.noMatch` strings plus the `Cards`' own `empty` prop align with the pattern's documented empty/no-match state split (top-level empty vs. filtered-to-nothing), and no material issue was found there.

## What was not evaluated

Implementation correctness was not assessed: prop-level API usage on `Cards`/`TextFilter`/`Pagination`/`useCollection`, whether `TextFilter`'s underlying match logic (via `@cloudscape-design/collection-hooks`) actually touches the `status`/`region` fields today, `ariaLabels` completeness, and other accessibility mechanics were not reviewed. General UX judgment (card density, wording, breakpoint choices in `cardsPerRow`) was likewise out of scope and not evaluated.
