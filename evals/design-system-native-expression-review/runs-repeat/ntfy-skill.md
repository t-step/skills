# Design-System Native-Expression Review: ntfy SubscribeDialog / PublishDialog

**Design system:** Material UI (`@mui/material`, `@mui/icons-material`)

**Inferred user task:** These two dialogs are ntfy's core topic-interaction flows: `SubscribeDialog` lets a user start receiving notifications for a topic — pick or generate a topic name, optionally point at a different ntfy server and log in to it, and optionally reserve exclusive ownership of the topic with an access-control level for everyone else. `PublishDialog` lets a user compose and send a single notification to a topic — a required message plus a progressively-revealed set of optional fields (title, tags/emoji, priority, click action, attachment by URL or file, email/call forwarding, scheduled delay). Both are modal, single-purpose, decision-driving tasks (subscribe vs. cancel; send vs. cancel), consistent with MUI's own Dialog framing of "inform users about a task ... require decisions."

**Packages / versions:** `@mui/material` declared `^9.1.2`, locked `9.3.1` (resolved). `@mui/icons-material` declared `^9.1.1`, locked `9.3.1` (resolved). Both fully resolved from `package.json`/`package-lock.json` at `web/`; MUI documentation retrieved reflects current (v9-era) docs.

**Authority categories found in this corpus:** Component guidance (one page per component, e.g. `react-checkbox`, `react-switch`, `react-alert`) and a handful of general technical guides (Composition, Responsive UI, Localization, API design). No named task/product pattern layer and no composition/recipe gallery comparable to what a system like Cloudscape exposes — component pages are the strongest tier available for every judgment below, and that is stated honestly rather than manufacturing a pattern-level citation.

## Findings

### Finding 1: Standalone boolean settings in PublishDialog use Checkbox where MUI's own guidance calls for Switch

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Toggling "render this message as Markdown" and "keep this dialog open to publish another message after sending" — both single, independent binary settings a user flips before or after composing a notification, not a selection among a list of related options.
- **Repository evidence:** `web/src/components/PublishDialog.jsx` lines 387–402 (`markdownEnabled`, rendered as `<FormControlLabel control={<Checkbox .../>} />`, standing alone, not inside a `FormGroup` or list of sibling checkboxes) and lines 757–772 (`publishAnother`, same pattern, standalone in the `DialogFooter`). Neither Checkbox is grouped with other related checkboxes; each is the sole control for its own independent setting.
- **Authority evidence:** MUI's React Checkbox page (`https://mui.com/material-ui/react-checkbox/`) introduction states, verbatim: "If you have multiple options appearing in a list, you can preserve space by using checkboxes instead of on/off switches. If you have a single option, avoid using a checkbox and use an on/off switch instead." Authority category: **component guidance**.
- **Evidence mode:** VERBATIM
- **Authority strength:** REQUIRED (an explicit "avoid X, use Y instead" pairing)
- **Applicability argument:** (1) The observed task — flipping one independent on/off setting, not choosing from a list — is exactly the "single option" case the quoted rule names, not a superficial shape match: neither `markdownEnabled` nor `publishAnother` appears alongside sibling checkboxes forming a list. (2) The current implementation solves precisely that problem (a binary setting toggled by the user). (3) Switching the component to `Switch` preserves the exact same task and state — it's a one-for-one control swap, not a different feature. (4) The gap is concrete and already demonstrated elsewhere in this same codebase: `SubscribeDialog.jsx` (lines 198–223, 224–264) uses `Switch` for its own two single-option settings ("reserve this topic," "use another server") — showing an experienced implementer of this exact app already applies the documented rule correctly one file over, which is exactly the kind of restructuring an MUI-fluent developer would make here too.
- **Current expression:** `Checkbox` + `FormControlLabel`, each standalone, for two independent binary settings in `PublishDialog`.
- **Native expression:** `Switch` + `FormControlLabel` (mirroring `SubscribeDialog`'s own pattern for the same class of setting), for both `markdownEnabled` and `publishAnother`.
- **Why it matters:** This isn't a stylistic quibble — MUI states the rule as an explicit "avoid/use instead" pairing, the surface's sibling dialog already follows it, and departing from it here makes semantically identical "single on/off setting" tasks look and behave differently (checkbox vs. switch) across ntfy's two primary dialogs for no task-driven reason, which is precisely the kind of internal-vocabulary drift this rule exists to prevent.
- **Boundary check:** This is a component-selection judgment (which control represents a boolean state), not an implementation defect (both components are used correctly and accessibly) or general UX critique (it doesn't touch layout, density, or workflow).

### Finding 2: DialogFooter's status/error/success slot is generic text where MUI's Alert exists for this exact job

- **Type:** combined selection + composition
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Communicating transient, non-blocking feedback inside an open dialog — validation/authorization errors ("not authorized," "topic already reserved"), in-progress status ("uploading X of Y, N%"), and success confirmation ("message published!") — without closing the dialog or interrupting the user's ability to keep editing.
- **Repository evidence:** `web/src/components/DialogFooter.jsx` renders every `status` value through a single `DialogContentText` with `aria-live="polite"` (lines 4–27), used identically by `SubscribeDialog.jsx` (`error` state, e.g. lines 113–117, 289) and `PublishDialog.jsx` (`status` state carrying progress text, success text, and — only in the network-failure catch block, lines 186–189 — an ad hoc `<Typography sx={{ color: "error.main" }}>` wrapper). Every other error/status path (login failure, reservation conflict, upload progress, publish success) renders as plain, uncolored text with no severity distinction.
- **Authority evidence:** MUI's React Alert page (`https://mui.com/material-ui/react-alert.md`) states Alert's purpose is to "display brief messages for the user without interrupting their use of the app," supports `error`/`success`/`warning`/`info` severities "each with corresponding icon and color combinations," and documents overriding its default `role="alert"` with `role="status"` specifically for less urgent messages so screen readers announce them without an assertive interruption. The React Snackbar page (`https://mui.com/material-ui/react-snackbar.md`) contrasts Snackbar as fixed-position, floating, breaking out of document flow, versus Alert being "typically integrated into the page layout." Authority category: **synthesis** (built from the Alert page's stated purpose/severity/role mechanics plus the Snackbar page's explicit in-flow-vs-floating contrast, which together establish that the in-layout, non-floating slot this dialog already has is Alert's documented niche, not Snackbar's).
- **Evidence mode:** SYNTHESIS
- **Authority strength:** OPTIONAL (no page states "don't use plain text for this, use Alert instead" — this is a reasoned bridge across two pages' stated purposes, not a direct prohibition, so per this skill's rule a synthesis defaults to a lower strength than its parts)
- **Applicability argument:** (1) The task DialogFooter's status slot performs — a brief, non-interrupting, in-layout message — matches Alert's stated purpose almost exactly, and specifically not Snackbar's (which requires breaking out of document flow, which this footer text does not do). (2) The current code already solves the same problem (transient in-dialog feedback) and, in one spot, has already hand-built a fragment of what Alert provides by default (manually setting `color: "error.main"` on a `Typography` for one specific error path), showing the surface is reaching for Alert's severity semantics without the component. (3) Swapping to `Alert` with `severity` set from the message's actual class (error/success/info) preserves the same task and position. (4) The materiality is concrete, not cosmetic: today, an authorization failure and a "message published!" success confirmation render as visually identical plain text in the same slot — a user gets no color/icon cue distinguishing "this failed" from "this succeeded," which severity-coded Alert would resolve for free, and the one place the surface tried to fix this by hand (the network-error catch block) did so inconsistently with every other error path in the same component.
- **Current expression:** `DialogContentText`/ad hoc-colored `Typography` inside a custom `Box` footer, carrying error, progress, and success text uniformly.
- **Native expression:** Likely `Alert` (with `severity` mapped from the message's actual class, and `role="status"` for the non-urgent progress/success cases per Alert's own documented override) in the same footer position — stated with medium confidence rather than high, since Alert's default padding/border/icon chrome would need to be checked against the footer's compact single-row layout (a fit question this review did not verify visually).
- **Why it matters:** The current approach already imitates part of Alert's severity-coloring behavior in exactly one code path, while leaving every other status/error path in the same component visually undifferentiated — a maintenance and consistency cost against a component the design system ships specifically to standardize this.
- **Boundary check:** This is about which component represents "in-dialog transient feedback" and how it's composed into the footer, not about the `aria-live="polite"` mechanics themselves (out of scope) or a general "the UX of this dialog is confusing" claim.

## Suppressed (low materiality or weak applicability)

- **Chip-based progressive disclosure in PublishDialog** (the row of clickable `Chip`s that reveal optional fields like click URL, email, attachment, delay). Considered as a possible mismatch (e.g., "should this be a `ToggleButton` group instead?"), but MUI's own Chip page documents exactly this use — "Chips with the `onClick` prop defined" act as buttons that "trigger actions" — and `ToggleButton`'s documented purpose ("group related options," implying persistent, mutually-relevant selection state) doesn't match the actual behavior here (a chip disappears once clicked and is replaced by a dismissible field row, not a toggled state on the chip itself). Cleared as already-native usage, not reported.

## Orientation notes

- **`SubscribeDialog.jsx`'s two `Switch` controls** (reserve-topic, use-another-server) are exactly the "single option" case MUI's Checkbox page names, and are correctly implemented as `Switch` — this is the internal-consistency baseline that makes Finding 1 concrete rather than abstract.
- **`EmojiPicker.jsx`'s `Popper` + `ClickAwayListener` + `Fade` composition** for the anchored, searchable emoji panel. Checked against `Popover` (which is built on `Modal` and blocks scrolling/dismisses on click-away by default) versus `Popper` (which does neither by default). MUI's own Popper page states plainly: "Clicking away does not hide the Popper component. If you need this behavior, you can use the Click-Away Listener" — which is precisely the composition used here. Given the panel contains its own internally-scrollable, searchable grid, Popover's default scroll-blocking behavior would be a worse fit than Popper's unblocked scrolling; the surface's choice matches documented guidance rather than diverging from it.
- **`SubscribeDialog.jsx`'s `Autocomplete` with `freeSolo`** for the "use another server" base-URL field (suggesting previously-used base URLs while accepting arbitrary text). Matches the Autocomplete page's stated purpose for `freeSolo`: covering "the primary use case of a search input with suggestions" where "the textbox may contain any arbitrary value, but it is advantageous to suggest possible values."
- **`PublishDialog.jsx`'s disabled "call" `Chip` wrapped in `Tooltip`+`<span>`** (lines 730–742, shown when the account has no verified phone numbers). Matches the Tooltip page's explicit guidance: "By default disabled elements ... do not trigger user interactions so a Tooltip will not activate ... To accommodate disabled elements, add a simple wrapper element, such as a span."

## What was not evaluated

Implementation correctness was out of scope and not assessed as findings, including: the several raw `<div style={{ display: "flex" }}>` layout rows (`Row`/`ClosableRow` in `PublishDialog.jsx`, the topic-entry row in `SubscribeDialog.jsx`) that stand in for MUI's `Stack` component; hard-coded pixel/color/em style values scattered through both files (e.g. `#aaa`, `0.75rem`, inline `marginTop`/`flexShrink`); the raw helper-text `<div>` beneath the base-URL `Autocomplete` in `SubscribeDialog.jsx` where `TextField`'s own `helperText` prop exists; the empty self-closing `<InputLabel />` elements on the priority/call `Select`s; and general accessibility-mechanics correctness (aria-label wiring, focus management) on already-correctly-chosen components. General UX and product judgment were also not evaluated — e.g., whether the emoji-tag-append interaction, the sheer number of chip-revealed optional fields, or the two-dialog subscribe/publish split are good product decisions. These are named here so their absence doesn't read as "checked and fine."
