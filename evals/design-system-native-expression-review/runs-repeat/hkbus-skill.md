# Design-System Native-Expression Review: Route ETA / Stop Detail / Bookmarked Stops (hk-independent-bus-eta)

**Design system:** Material UI (`@mui/material` + `@mui/icons-material`)

**Inferred user task:** Given a specific bus route, let a rider browse its stops in sequence — each stop showing live ETA/fare information and per-stop actions (pin to top, share, favorite/star, set an arrival alarm) — and drill into a single stop's full detail (bookmark toggle, map/directions links, and the list of all routes serving that stop) either as an in-context overlay while browsing the route, or as a dedicated page reached directly or via a bookmark. Separately, a rider can browse and swipe between the stops they have previously bookmarked, viewing the same per-stop route/ETA list for each.

**Packages / versions:** `@mui/material` 5.15.11 (locked, matches declared `^5.15.11`), `@mui/icons-material` 5.15.11 (locked, matches declared `^5.15.11`), resolved from `package.json` + `yarn.lock` at the fixture root. `react` 18.2.0. `@mui/x-date-pickers` `^6.5.0` is declared in `package.json` but not imported anywhere in this bounded surface or its composed files (verified: the only import site in the repo is `src/components/layout/collections/CollectionSchedule.tsx`, outside this review) — excluded from authority scope per the task framing. `react-swipeable-views` `^0.14.0` (third-party, not part of Material UI) is used by `SwipeableStopList.tsx`; noted for context, not treated as MUI authority.

**Authority categories found in this corpus:** Component guidance (per-component pages, one per component, each with an API reference and usage examples/demos) and separate Customization/Guides/Getting-Started tiers (theming, composition mechanics, responsive-UI guidance). Confirmed via the supplied `mui-material-llms.txt` index: its top-level sections are Components, Design Resources, Discover More, Getting Started, Customization, Guides, Integrations, and Migration — there is no separate named task/product-pattern tier (no "Patterns" or task-recipe section comparable to Cloudscape's). Judgments below reason from component guidance and, where a component page documents a specific composition (e.g., a controlled-Accordion example, a Dialog title/actions structure), from that composition example — never from an invented pattern tier this corpus doesn't have.

## Findings

### Finding 1: Repeated hand-rolled "brief, time-sensitive notice" banners where Material UI documents a purpose-built component for exactly that job

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** On the route ETA page, while a rider is browsing a route's stops, the app needs to tell them the underlying schedule/stop data may be stale and offer one action to refresh it — a brief, non-blocking status message layered on top of the primary "browse stops and ETAs" task, not itself the primary task.
- **Repository evidence:**
  - `src/components/route-eta/RouteUpdateNotice.tsx` lines 29-49: a `Box` styled entirely via `sx` (1px solid border, halved theme border-radius, padding, top margin, `cursor: "pointer"`) containing one `Typography` with a literal `"⁉️"` glyph standing in for a severity icon, with `onClick={renewDb}` as its only interactive affordance. Rendered directly from the primary surface file `src/pages/RouteEtaPage.tsx` line 235, immediately under `RouteHeader`.
  - The identical concept is independently reimplemented at least three more times in components rendered directly by the other primary surface file, `src/pages/BookmarkedStopPage.tsx` (lines 87-89: `<NoticeCard/>`, `<BadWeatherCard/>`, `<DbRenewReminder/>`):
    - `src/components/layout/DbRenewReminder.tsx` lines 20-24: the *same* `renewDb` action from `DbContext`, wired to a separately hand-styled `Box` with near-identical `sx` (solid border, radius, padding, `cursor: "pointer"`) to `RouteUpdateNotice` — two independent implementations of one action.
    - `src/components/layout/BadWeatherCard.tsx` lines 27-34: a clickable `Paper variant="outlined"` containing an `ErrorIcon` with `color="error"` plus `Typography` — already reaching for Material UI's own severity color token (`error`) without using the component that owns that vocabulary.
    - `src/components/layout/NoticeCard.tsx` lines 92-143: a `Paper variant="outlined"` containing a `WarnIcon` with `color="warning"`, plus a hand-wired `IconButton`/`CloseIcon` (lines 135-141) that removes the notice from local state — functionally reimplementing Alert's own dismiss behavior.
- **Authority evidence:** `https://mui.com/material-ui/react-alert.md` (component guidance). Verbatim: "Alerts display brief messages for the user without interrupting their use of the app," and the component "gives users brief and potentially time-sensitive information in an unobtrusive manner." The `severity` prop ("success" default, "info", "warning", "error") is documented as having "corresponding icon and color combinations." The `onClose` prop is documented to display a close icon (✕) by default when no custom `action` is supplied. The `action` prop is documented to accept "any element — an HTML tag, an SVG icon, or a React component such as a Material UI Button — after the Alert's message, justified to the right."
- **Evidence mode:** VERBATIM (the applicability argument rests directly on quoted text from the single Alert component page; no cross-page synthesis is needed to establish the semantic match).
- **Applicability argument** (four-point test):
  1. *Task match, not just shape*: "brief, potentially time-sensitive information ... in an unobtrusive manner" is a precise description of what all four instances are doing — a stale-data prompt, a severe-weather warning, and an external service notice are each a transient, non-blocking status message, not merely something that happens to look like Alert's layout.
  2. *Same problem*: each hand-rolled component already delivers exactly that — an inline, unobtrusive message with an optional click action — just without Alert.
  3. *Same task preserved*: swapping the `Box`/`Paper` + `Typography` wrapper for `<Alert severity=... action=...>` (or `onClose`) changes nothing about when the message appears, what it says, or what the action does.
  4. *Material enough to restructure*: the same concept is independently reinvented four times in files the two primary surface pages render directly; two of the four instances (`BadWeatherCard`, `NoticeCard`) already use Alert's own severity color tokens (`color="error"` / `color="warning"`) on ad hoc icons without adopting the component that defines that vocabulary; `NoticeCard` hand-builds a close button that duplicates Alert's built-in `onClose`; and `RouteUpdateNotice`/`DbRenewReminder` implement the identical `renewDb` action twice, independently, as a bare `onClick` on a `Box` with no visible button. This is the pattern an experienced Material UI practitioner would plausibly consolidate onto one component, not just note as an alternative.
- **Authority strength:** OPTIONAL. Alert's documented purpose is an exact semantic match, but nothing in the cited page states "don't build a custom notice box, use Alert instead" — applicability is established by direct description, not by an explicit normative rule, so this is not labeled REQUIRED or RECOMMENDED.
- **Current expression:** Four separately hand-styled `Box`/`Paper` + `Typography` combinations (`RouteUpdateNotice`, `DbRenewReminder`, `BadWeatherCard`, `NoticeCard`), each with its own bespoke border/radius/spacing via `sx`, one literal emoji character standing in for a severity icon, ad hoc `color="error"`/`color="warning"` on two of them, and either a bare `onClick` on the outer `Box`/`Paper` or a hand-wired close `IconButton`.
- **Native expression:** An `Alert` (e.g., `severity="warning"`) carrying the same copy, using the documented `action` prop for the refresh/update control (or `onClose` where the message should also be dismissible without acting) — directly supported by the cited API, and it would replace four independently-drifting bespoke treatments with one theme-driven severity/color system the app already reaches for piecemeal.
- **Why it matters:** Material UI ships one component whose stated job is precisely "brief, time-sensitive, unobtrusive message," including the severity/color vocabulary this codebase already partially uses on raw icons. Reinventing it four times means each instance drifts independently (different border treatments, inconsistent icon choices, no shared dismiss pattern) instead of inheriting one coherent, theme-aware look — a real consistency/maintenance cost for an app otherwise built on Material UI throughout this surface.
- **Boundary check:** This is a component-selection/composition question — which documented Material UI component the app reaches for to express "a brief, non-interrupting, time-sensitive status message with an optional action" — not a judgment about whether the underlying refresh-prompt UX is good, nor about the chosen component's prop/token/accessibility mechanics.

## Suppressed (low materiality or weak applicability)

- **`AccordionActions` vs. the inline icon-button cluster in `StopAccordion.tsx`'s `AccordionDetails`** (lines 135-203): `AccordionActions` is documented as "an optional wrapper that groups a set of buttons," which superficially matches the alarm/info/pin/share/star icon cluster rendered alongside `TimeReport` in each stop's expanded panel. Suppressed because `AccordionActions`'s documented shape is a full-width footer row placed *after* `AccordionDetails`, while the app's layout is a single horizontal row splitting fare/time content (left, `flex: 1`) from a two-row icon cluster (right) — the same visual job the current `Box` layout performs, but a genuinely different problem shape than the one `AccordionActions` addresses. This is fact pattern 1 of the anti-fundamentalism test failing: a superficial "buttons inside an Accordion" match, not a same-problem match.
- **`DialogActions` vs. the title-bar icon cluster in `StopDialog.tsx`** (lines 68-93): bookmark toggle, directions, map, and "view full stop page" are all rendered as `IconButton`s inside `DialogTitle`, alongside a separate close button, and `DialogActions` (documented as "an optional container for a Dialog's Buttons," used in MUI's own examples for the dialog's actionable buttons) is never imported or used. Considered as a candidate, but suppressed: no cited MUI guidance prohibits actionable controls inside a title area, and this app consistently uses compact inline icon-toolbars in other headers (e.g., `RouteHeader.tsx`'s reverse/star/timetable row), suggesting a deliberate, consistent idiom rather than an oversight. Point 4 of the anti-fundamentalism test (would a practitioner plausibly restructure this) is too weak to report with confidence.
- **`Tabs` + `react-swipeable-views` composition** (`BookmarkedStopPage.tsx` → `StopTabbar.tsx` + `SwipeableStopList.tsx`): considered whether this materially diverges from documented Tabs guidance. The current Material UI Tabs documentation makes no reference to `react-swipeable-views` or any swipeable-panel composition, but `@mui/material` ships no native swipeable-panel alternative either — there is no in-system Material UI substitution to recommend. Any concern about `react-swipeable-views` itself (an unmaintained third-party dependency) is a library-choice/implementation matter, not a Material UI native-expression gap, so it is named here only in passing.

## Orientation notes

- **Controlled, single-open Accordion** (`RouteEtaPage.tsx` → `StopAccordionList.tsx` → `StopAccordion.tsx`): `expanded={stopIdx === idx}` is driven from one piece of lifted state so only one stop's accordion is open at a time. This matches the Accordion documentation's own controlled-accordion guidance verbatim: "Use the `expanded` prop with React's `useState` hook to allow only one Accordion item to be expanded at a time."
- **Icon-button toggle affordances** (star/favorite in `StopAccordion.tsx` and `RouteStarButton.tsx`; bookmark in `StopDialog.tsx`; pin and alarm in `StopAccordion.tsx` — each swapping between a filled and an outline icon based on boolean state): this matches Material UI's own stated guidance verbatim, from the Button/IconButton documentation's "Icon button" section: "Icons are also appropriate for toggle buttons that allow a single choice to be selected or deselected, such as adding or removing a star to an item." This is a direct textbook match for this app's repeated star/pin/bookmark pattern — it is *not* a candidate for `ToggleButton`, despite that component existing for boolean state; existence alone isn't evidence, and the cited IconButton guidance affirmatively covers this exact use case.
- **`Snackbar` for transient "copied to clipboard" feedback** (`StopAccordionList.tsx` lines 65-73): matches Snackbar's documented purpose ("brief notifications of processes that have been or will be performed").
- **Scrollable `Tabs`** (`StopTabbar.tsx`: `variant="scrollable" scrollButtons allowScrollButtonsMobile`): matches the Tabs documentation's "Forced scroll buttons" guidance for keeping scroll affordances visible on all viewports, including mobile.
- **`Divider orientation="vertical" flexItem`** used to separate inline button groups within a flex row (`RouteHeader.tsx`, `ReverseButton.tsx`): matches Divider's stated purpose, "a thin, unobtrusive line for grouping elements to reinforce visual hierarchy."
- **`Paper elevation={0}`** used as a flattened, transparent-background section container (`RouteHeader.tsx`, `BookmarkedStopPage.tsx`): a legitimate, documented customization of a first-class Paper prop, not a misuse of the component.

## What was not evaluated

- **Implementation correctness:** manually added `aria-pressed` attributes on `IconButton` in `StopAccordion.tsx` (not a documented IconButton prop), `Dialog` sizing achieved via `sx` targeting `.MuiPaper-root` in `StopDialog.tsx` rather than the documented `fullScreen`/`maxWidth`/`fullWidth` props, hard-coded color/spacing literals throughout (e.g. `#088bce`, literal border widths), and any deprecated-API or prop-correctness questions were not assessed.
- **General UX/product judgment:** whether surfacing route-data staleness at all is the right UX, whether splitting stop detail between a modal dialog and a dedicated page is the right architecture, information density of the per-stop accordion rows, and the overall bookmarking flow were not assessed except where directly necessary to establish the task intent above.
- **Third-party library choices** (`react-swipeable-views`, `string-similarity`, etc.) and their maintenance status are outside this skill's scope.
