# Design-System Native-Expression Review: Message Queues

**Design system:** Cloudscape (`@cloudscape-design/components`, `@cloudscape-design/collection-hooks`)

**Inferred user task:** An operator surveys every message queue in the account at once — comparing throughput (messages/sec) and backlog age across all 24 queues, alongside each queue's health status and region — in order to decide which queues need scaling attention right now. The page's own framing comment and header description state this explicitly: operators are also expected to search by queue name, and to narrow the set down to a specific status or region while triaging.

**Packages / versions:** Resolved from `package-lock.json` (declared ranges in `package.json` all satisfied by the locked versions):
- `@cloudscape-design/components`: declared `^3.0.900`, locked `3.0.900`
- `@cloudscape-design/collection-hooks`: declared `^1.0.60`, locked `1.0.60`
- `@cloudscape-design/global-styles`: declared `^1.0.45`, locked `1.0.45`

**Authority categories found in this corpus:** Both component guidance (per-component pages, e.g. Cards, Table, Text filter, Property filter, Collection select filter) and named patterns (e.g. View resources, Table view, Card view, Filtering patterns) are present and were used below.

## Findings

### Finding 1: A 24-item, uniform, non-visual resource list is expressed as Cards instead of Table

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As above — comparing throughput and backlog age across all queues to decide which need scaling attention.
- **Repository evidence:** `MessageQueues.tsx` renders all 24 `QUEUES` (lines 18-25) through `<Cards>` (lines 56-98, default `variant="container"`, no `variant` prop passed) inside `<ContentLayout>` (lines 44-55). Every item has the identical schema (`MessageQueue` interface, lines 9-16: `name`, `status`, `region`, `messagesPerSecond`, `oldestMessageAgeSec`), and every `cardDefinition` section (lines 65-86) renders plain text or a `StatusIndicator` — no images, charts, or non-columnar content anywhere. `useCollection` is configured with `sorting: {}` (line 41), but no sort control or sortable-column affordance exists anywhere in the JSX, so that configured sorting capability is currently inert. The comment at lines 29-33 states the task is to "compare throughput and backlog age across all of them at once."
- **Authority evidence:** View resources pattern (`https://cloudscape.design/patterns/resource-management/view/index.html.md`), decision table for "Choosing between table view and card view": "Number of resources in the data set | 9 or more resources in 99% of use cases [Table] | 5 or less resources in 99% of use cases [Card]"; "Metadata type | Data that is displayed in columns (text, numerical, status, sparkline) [Table] | Data that can be displayed as visuals (charts, videos) [Card]"; and "Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on." Table view pattern page (`.../view/table-view/index.html.md`): "The best data type for a table view is data that is structured, easily comparable, and sortable," and "Tables enable users to quickly scan and sort columns, to compare metadata across many resources." Authority category: **named pattern**.
- **Evidence mode:** VERBATIM
- **Applicability argument:** (1) Task match — the pattern page frames the table-vs-card choice explicitly around whether "your users will be comparing resources to determine which to take action on," which is verbatim this page's own stated purpose ("compare... to decide which need scaling attention"), not a superficial shape match. (2) The current Cards implementation already solves the same underlying problem (a same-schema, non-visual resource list) — it's mechanically valid, just misfit. (3) A Table preserves the exact same task: all four fields map directly onto columns, same items, same filter/pagination. (4) All three of the pattern's own decision-table factors point the same direction here — 24 resources (well past the "9 or more" table threshold and far past the "5 or less" card threshold), identical metadata across every resource, and pure text/numeric/status data with no visuals — and none point toward cards, so this is not a coin-flip between two valid options.
- **Current expression:** `<Cards>` at its default `container` variant, rendering a responsive 1-3-column card grid inside `<ContentLayout>`; each card lists the four fields as separate labeled sections. `useCollection`'s `sorting` config has no attached UI.
- **Native expression:** A `<Table>` with one sortable column per field, letting operators sort directly by throughput or backlog age — the two metrics the page exists to help compare — instead of only visually scanning cards.
- **Why it matters:** The current composition can display every field, but gives operators no way to rank or sort by the very two metrics the page's own stated purpose calls out ("compare... to decide which need scaling attention"); a Table's sortable column headers are the documented mechanism for exactly this ranking behavior, and Cards has no per-column equivalent.
- **Boundary check:** This is a component/composition-selection judgment — which collection component this design system's own resource-list decision guidance specifies for a uniform, comparison-oriented list — not a claim about API misuse or generic usability.

### Finding 2: The page is wrapped in `ContentLayout` with the collection component at its default variant, instead of the pattern's documented full-page variant

- **Type:** documented composition
- **Materiality:** medium
- **Confidence:** high
- **User task:** As above.
- **Repository evidence:** Lines 44-55: `<ContentLayout header={<Header .../>}> <Cards .../> </ContentLayout>`. `Cards` is left at its default `variant="container"` — no `variant` prop is passed (lines 56-98).
- **Authority evidence:** Card view pattern (`.../view/card-view/index.html.md`), "Don't" list: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the cards component to implement this pattern." The identical rule appears on the Table view pattern page for the table case. The Cards component API confirms `variant` accepts exactly `"container" | "full-page"` (default `'container'`), so "full-page" is a real, currently-available prop value, not a hypothetical one. Authority category: **named pattern** (the "Don't...Instead" statement itself), corroborated by **component guidance** (the Cards API `variant` values).
- **Evidence mode:** VERBATIM
- **Authority strength:** REQUIRED (an explicit "Don't X. Instead, do Y." prohibition, stated identically on both the card-view and table-view pattern pages for this exact page type).
- **Applicability argument:** (1) Task match — this is literally a full-page "collection of resources" view, the exact page type both pattern pages describe. (2) The current implementation solves the same problem (a full-page resource list with no secondary content that would need `ContentLayout`'s header/content visual separation). (3) The native alternative (drop `ContentLayout`, use the collection component's `full-page` variant directly) preserves the identical task — same header, same items, same filter/pagination. (4) This is a direct, named, current-code match to an explicit documented prohibition, not a stylistic alternative — an experienced Cloudscape implementer would recognize the `ContentLayout` + default-variant pairing as the wrong page shell for this pattern.
- **Current expression:** The page root is `ContentLayout` (documented as providing "page structure for expressive use cases" requiring visual separation between header and content), with `Cards` left at its default `container` variant nested inside it.
- **Native expression:** Drop `ContentLayout`; render the collection component (Table, per Finding 1) with `variant="full-page"` as the page root directly, per the pattern's own "Building blocks" item C on both the table-view and card-view pages ("Use the 'full-page' variant of the [table/cards] component for this pattern").
- **Why it matters:** This is stated as an explicit "Don't...Instead" rule on the very pattern page documenting this exact page shape, not a stylistic option — mixing `ContentLayout` with the default `container` variant produces different page chrome (padding, background separation) than the pattern's own full-page layout convention, diverging from how this design system's own examples compose a resource-list page.
- **Boundary check:** This is a documented page-composition rule (which layout container and collection-component variant pairing this design system specifies for resource-collection pages), not an implementation-mechanics detail — the "Don't/Instead" is itself stated as page composition guidance, not a components-API note.

### Finding 3: Status and region are only filterable by guessing exact text, not through the documented 1-2-property filter composition

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** As above, including the stated behavior of narrowing the queue list to a specific status or region while triaging.
- **Repository evidence:** Lines 89-95: only `<TextFilter {...filterProps} .../>` is present in the `filter` slot; no select/multiselect/collection-select-filter control exists anywhere in the file. The `MessageQueue` interface (lines 9-16) has exactly two enumerable properties: `status: 'healthy' | 'backlogged'` and `region: 'us-east-1' | 'us-west-2'`. The page's own comment (lines 32-33) states operators are expected to "narrow the list down to a specific status or region while triaging," in addition to searching by name.
- **Authority evidence:** Filtering patterns page (`.../patterns/general/filter-patterns/index.html.md`): "If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter." Collection select filter page (`.../components/collection-select-filter/index.html.md`): "A select filter helps users find specific items in a collection by choosing one or two properties"; "Use a select filter if users need a maximum of two properties to find a specific item. If more than two are required, use a property filter instead"; and "The collection is filtered as soon as the user selects a value from a select filter or enters text into the accompanying text filter" (documenting the composition of a select filter placed alongside a text filter, combined with "and" logic). Authority category: **named pattern** + **component guidance**.
- **Evidence mode:** VERBATIM
- **Authority strength:** RECOMMENDED (phrased as "use X if Y" — a best-practice match to a stated threshold, not an absolute prohibition on the current text filter — but the surface's own stated behavior lands exactly on that threshold).
- **Applicability argument:** (1) Task match — the page's own stated operator behavior, "narrow... to a specific status or region," is precisely "filter[ing] a resource by only one or two properties," the documented trigger condition for a collection select filter, not a free-text-search behavior. (2) The current `TextFilter` only coincidentally covers part of the same need: `useCollection`'s default filtering scans all fields as text, so typing a literal value like "healthy" or "us-west-2" happens to match — but this is an undiscoverable side effect, not a designed property filter. (3) Adding a select filter alongside the existing `TextFilter` preserves exactly the same task and items — the documented composition explicitly is a select filter next to a text filter, "and"-combined. (4) Material: status and region are the two decision-relevant properties the page's own copy names, yet there is no discoverable, structured way to filter on them today — an experienced Cloudscape implementer would recognize this as the collection select filter's stated use case and would very likely add it.
- **Current expression:** A single `TextFilter` bound to `filterProps`, with no explicit `filteringFunction`, degrading to a generic cross-field substring search with no per-property affordance for status or region.
- **Native expression:** Add a collection select filter (or two) for `status` and `region` — Cloudscape's documented component for exactly a 1-2-property filter — placed alongside the existing `TextFilter` in the `filter` slot, combined with "and" logic per the documented composition, giving operators discoverable dropdowns for the two properties the page's own copy calls out while keeping the text filter for name search.
- **Why it matters:** Without a structured filter, "narrow... to a specific status or region" is only achievable today by guessing the exact literal string into a name-search box — a materially worse fit for a small, finite-value property than the composition Cloudscape's own guidance names as its first choice for exactly this shape of filtering need.
- **Boundary check:** This is a documented composition/component-selection judgment — which filter component this corpus specifies for filtering on a small number of known-value properties versus free text — not a claim about `TextFilter`'s implementation correctness or a generic "add more filters" UX opinion.

## Suppressed (low materiality or weak applicability)

- **Property filter as an alternative to the collection select filter** — considered and ruled out: the surface has exactly two filterable enum properties (status, region), and the property filter's own guidance states "if more than two are required, use a property filter instead" of the simpler select filter, so the property filter would be a heavier composition than this task calls for.
- **Card-view guidance that each card should link to a details view** — the card-view pattern's "Do" list states cards should link to a per-resource details view, which this surface's cards do not do. Suppressed as intent-dependent: the bounded surface contains no evidence (routes, ids-as-links, a second page) that a per-queue details page is or should be part of this product, so recommending one would extend beyond the reviewed task rather than clarify it. It is also moot if Finding 1 is adopted, since the table-view pattern carries no equivalent linking requirement.
- **`CollectionPreferences` (column visibility / density control)** — absent from the surface, but explicitly an "optional" building block on both the table-view and card-view pattern pages; the core comparison task does not depend on it, so its absence is not reported as a finding.

## Orientation notes

- `StatusIndicator` usage (mapping `healthy`→`success`, `backlogged`→`warning`) is idiomatic, correctly-scoped usage — the component's own description names exactly this job: communicating a resource's state "in a compact form that is easily embedded in a card, table, list, or header view."
- `Pagination` with `pageSize: 12` against 24 items matches the documented building block ("Pagination helps users with an extensive number of resources to navigate through them across multiple pages").
- `Header` with a `counter` reflecting the total item count is standard, correctly-scoped usage for a resource-collection page header.
- `useCollection`'s `filtering.empty` / `filtering.noMatch` messaging is present, matching the documented empty/zero-results building blocks.

## What was not evaluated

Implementation correctness — including `TextFilter`'s default cross-field matching mechanics, `StatusIndicator`/`Cards`/`Pagination` prop usage, the hard-coded `cardsPerRow` responsive breakpoints, and the sufficiency of the `ariaLabels` given — was not assessed and its absence from this report is not evidence it is correct. General UX or product judgment (information density, whether four fields is the right amount to surface, copy quality) was likewise not evaluated.
