# Design-System Native-Expression Review: EndpointScaling.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** An on-call operator reviews every inference endpoint in the fleet (22 in this fixture) to compare invocation volume, p99 latency, and error rate side by side across all of them, in order to decide which endpoint(s) currently need a capacity change and trigger scaling for those. This is stated explicitly both in the page's `Header` `description` ("Compare request volume, latency, and error rate across endpoints to decide which ones need to scale") and in the source comment directly above the component (`EndpointScaling.tsx:29-33`).

**Packages / versions:** `@cloudscape-design/components` — declared range `^3.0.900` in `package.json`, resolved/locked to `3.0.900` in `package-lock.json` (via `resolve_versions.py`). Version-sensitivity is low for this review: both findings below rest on `Cards`/`Table`/`ContentLayout` composition guidance and a `variant` prop (`"container" | "full-page"`) that are stable, non-deprecated concepts in this major version line.

**Authority categories found in this corpus:** Both component guidance (individual component pages, e.g. `Cards`, `Table`, `ContentLayout`) and named patterns exist, including a resource-management "view" pattern family with three named pages that directly compare each other: `Card view`, `Table view`, and an overview `View resources` page containing an explicit decision table and "use X if Y" guidance. Foundations and demos also exist in this corpus but were not load-bearing for these findings. No separate "composition guide" tier distinct from named patterns was needed here — the named pattern pages themselves carry the comparative, applicability-relevant guidance.

## Findings

### Finding 1

- **Finding:** The endpoint fleet is rendered as a `Cards` grid, but the stated task — comparing three numeric/status metrics across 22 same-shaped endpoints to pick which to scale — is exactly the scenario Cloudscape's own resource-view guidance assigns to `Table`, not `Cards`.
- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** See "Inferred user task" above — compare volume/latency/error-rate across all endpoints to choose which to scale.
- **Repository evidence:** `EndpointScaling.tsx:17` — `ENDPOINTS` is an array of 22 items, all with the identical shape `{id, region, status, invocationsPerMin, latencyP99Ms, errorRatePct}`. `EndpointScaling.tsx:46-87` — a `Cards` component renders one card per endpoint, with `cardDefinition.sections` exposing the same five data fields (status, region, invocations, latency, error rate) plus an action, per card. `EndpointScaling.tsx:86` — `cardsPerRow={[{cards:1},{minWidth:500,cards:2},{minWidth:900,cards:3}]}` caps visible cards at 3 per row at any viewport, so comparing a given metric (e.g. p99 latency) across the 22 endpoints requires scrolling and re-scanning card-by-card rather than scanning a column. `EndpointScaling.tsx:29-33` and the `Header` `description` (line 40) both state the comparison task explicitly.
- **Authority evidence:** Primary source: Cloudscape "View resources" pattern overview (`https://cloudscape.design/patterns/resource-management/view/index.html.md`), authority category `named pattern`. It contains a direct decision table:

  | | Table view | Card view |
  |---|---|---|
  | Number of resources in the data set | 9 or more resources in 99% of use cases | 5 or less resources in 99% of use cases |
  | Metadata being displayed | Shared metadata between resources | Different metadata across resources |
  | Metadata type | Data that is displayed in columns (text, numerical, status, sparkline) | Data that can be displayed as visuals (charts, videos) |

  and the sentence: "Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on." Corroborating sources (also `named pattern`): `Table view` page (`.../table-view/index.html.md`) — "It's effective for quickly identifying categories or comparing values in a large text and numerical data set," and "Table columns allow for the same metadata type to be displayed across all resources, and allow for easy scanning and comparison of similar metadata." `Card view` page (`.../card-view/index.html.md`) — "Use cards to display non-columnar, yet comparable data" and "Surface only relevant and repeatable information across resources. Treat it as a quick reference for each resource" (cards are framed as a lightweight reference/entry point, not the venue for multi-metric side-by-side comparison).
- **Evidence mode:** VERBATIM — the decision table and the "Use a table if..." sentence are quoted directly from the View resources page and are copy/paste-verifiable against it; the corroborating Table view/Card view quotes are likewise direct quotes from their own pages.
- **Authority strength:** RECOMMENDED. The guidance is phrased as "use a table if..." / statistical thresholds ("99% of use cases"), which is strong, directly on-point preferred-practice guidance — but it is not phrased as an explicit "don't use cards for this, instead use a table" prohibition, so it does not meet this skill's REQUIRED bar.
- **Applicability argument:** (1) Task match: the page's own header description and code comment state the task as multi-metric comparison across all endpoints to decide which to act on — this is verbatim the condition the View resources page attaches to Table ("your users will be comparing resources to determine which to take action on"), not the condition it attaches to Cards ("quick reference," "non-columnar" data). (2) Same problem solved today: the current Cards implementation is already trying to solve this comparison problem — each card exposes all five fields for exactly this purpose, so this isn't a case of inventing a new task. (3) Preserves the task: replacing Cards with Table changes only the visual/scan structure, not the data shown, the per-item action, or the decision the operator makes. (4) Materiality: dataset size (22) is more than double the documented "9 or more" table threshold and over 4x the "5 or less" card threshold; metadata is fully shared and uniform across every item (fails the "different metadata across resources" card criterion outright); every field is text/numeric/status (fails the "visuals — charts, videos" card criterion outright, and squarely matches "text, numerical, status, sparkline" table criterion). All three of the decision table's factors point the same direction with no ambiguity, which is the kind of clean, multi-factor match the anti-fundamentalism rule requires before treating a documented comparison as applicability evidence rather than availability evidence.
- **Current expression:** `Cards` grid (`cardsPerRow` capped at 3 columns), one card per endpoint, each card repeating the same five labeled fields plus a "Scale up" button.
- **Native expression:** A `Table` with one row per endpoint and columns for status, region, invocations/min, p99 latency, error rate, and an actions column/cell (e.g. a "Scale up" `Button`), using `Table`'s native column-based layout, sortable columns (the docs note multi-column sort is meant for "analyz[ing] data across multiple dimensions simultaneously" — directly relevant to comparing latency/error-rate/volume together), and standard row selection/filtering affordances for a 22-item, uniform-schema collection.
- **Why it matters:** With Cards capped at 3 per row, comparing one metric (say, p99 latency) across all 22 endpoints requires scanning down through roughly 8 rows of cards and re-locating the same field position in each — exactly the scan pattern Table's column layout exists to make single-glance instead. This is a documented-guidance mismatch, not a taste preference: the corpus's own decision criteria (dataset size, metadata uniformity, data type) unanimously favor Table for this exact page.
- **Boundary check:** This is a component/composition-selection judgment (which collection-display primitive fits a multi-attribute comparison task across 22 uniform resources), not an implementation defect in the existing `Cards` usage and not a generic "cards feel cluttered" UX complaint — the recommendation is grounded entirely in the design system's own stated dataset-size/metadata/data-type criteria for choosing between its two collection-display components.

### Finding 2

- **Finding:** The page wraps its entire content in `ContentLayout`, with `Cards` as the sole child — but Cloudscape's own Card view pattern guidance explicitly prohibits exactly this composition for a page that is entirely a card collection, and names the specific fix.
- **Type:** documented composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Same as Finding 1 — this finding is about the current implementation's page-structure composition, independent of which collection-display component (Cards or Table) is ultimately used.
- **Repository evidence:** `EndpointScaling.tsx:35-45` and `:89` — `<ContentLayout header={<Header .../>}>` wraps a single `<Cards .../>` as its only content (lines 46-88), with no other page content alongside it. `Cards` is not passed a `variant` prop, so it defaults to `"container"` rather than `"full-page"`.
- **Authority evidence:** Cloudscape "Card view" pattern page (`https://cloudscape.design/patterns/resource-management/view/card-view/index.html.md`), authority category `named pattern`, under its "Don't" list: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the cards component to implement this pattern." Also: "Card collection should not be used for page layout purposes." Corroborated by the `Cards` component API (`https://cloudscape.design/components/cards/index.html.json`), authority category `component guidance`: the `variant` prop's documented allowed values are `"container" | "full-page"`, with `"full-page"` documented for use "when cards are the entire content of a page" — which is exactly this page's structure.
- **Evidence mode:** VERBATIM — the "Don't...Instead" sentence is quoted directly and is copy/paste-verifiable against the Card view pattern page; the `variant` prop values and description are quoted directly from the Cards API reference.
- **Authority strength:** REQUIRED. This is a documented "Don't X, instead do Y" pairing — the skill's own definition of REQUIRED-strength evidence — for the specific rule it states (page-level layout wrapper choice for an all-cards page). This strength claim is scoped to that one rule; it is not license to treat the rest of the Card view page's guidance as mandatory.
- **Applicability argument:** (1) Task/problem match: the documented "don't" is specifically about pages whose entire content is a card collection — this page's only content is `Cards`, matching exactly. (2) Same problem: the current code is already trying to build a card-collection page; the fix doesn't change what's being built, only the structural component used to host it. (3) Preserves task: swapping `ContentLayout` for `Cards`' own `variant="full-page"` mode changes page chrome, not the data or the comparison task. (4) Materiality: the violation is binary and explicit (present or absent), not a matter of degree, and the API confirms a purpose-built prop exists for exactly this case, so an experienced Cloudscape implementer would restructure rather than merely note it as an alternative.
- **Current expression:** `ContentLayout` supplies page structure; a default-variant (`"container"`) `Cards` is nested inside it as the only content, with the page-level `Header` (h1, counter, description) passed to `ContentLayout`'s `header` slot.
- **Native expression:** Drop `ContentLayout`; render `Cards` directly with `variant="full-page"`, passing the same `Header` into `Cards`' own header slot, per the documented pairing of "cards are the entire content of a page" with the `full-page` variant.
- **Why it matters:** This is an explicit, named prohibition in this design system's own pattern documentation, with a named, purpose-built alternative (`variant="full-page"`) that exists specifically to cover this page shape — not a "the docs happen to show it a different way" observation. Note the interaction with Finding 1: this specific "Don't use content layout... instead use the full-page cards variant" rule is scoped to Card view pages. If Finding 1's recommendation (move to `Table`) is adopted, this particular rule no longer applies to the resulting page (no equivalent "don't wrap Table in ContentLayout" prohibition was found in this corpus for Table view pages); it remains a valid, independent finding against the page exactly as it is written today.
- **Boundary check:** This is a composition-level judgment about which page-structuring component wraps a resource collection, governed by an explicit documented rule for that exact page shape — not a prop/API implementation defect and not a general UX opinion about layout aesthetics.

## Suppressed (low materiality or weak applicability)

- Considered whether the single per-endpoint "Scale up" `Button` should be replaced by a multi-select + bulk "Global action" (Cloudscape documents a "Global actions" pattern for bulk operations against selected resources, which would pair naturally with a `Table`'s row-selection). Suppressed: the current implementation has no selection state at all, and introducing multi-select bulk scaling would change the interaction model (act on N endpoints at once) rather than express the same, already-present single-endpoint "Scale up" task more natively — this risks crossing into product-scope expansion rather than native re-expression of the existing task, so it is not reported as a finding.

## Orientation notes

- `StatusIndicator` used inside each card's "status" section (`EndpointScaling.tsx:54`) is correct, documented usage — its own component page states it is meant to be "easily embedded in a card, table, list, or header view," and this usage would remain valid unchanged if Finding 1's `Table` recommendation is adopted.
- The per-card "Scale up" `Button` is correctly placed as an in-context, single-resource action rather than a global action — Card view's own guidance ("Global actions (buttons) should be included in the header, not in each card") does not apply here since scaling a specific endpoint is a per-resource action, not a bulk/global one.
- `Header` usage (`variant="h1"`, `counter`, `description`) matches standard Cloudscape resource-collection page header composition; no issue found.

## What was not evaluated

Implementation correctness was not evaluated: prop usage, any deprecated APIs, `Box float="right"` as a styling mechanism for right-aligning the action button, and accessibility mechanics of `StatusIndicator`/`Button`/`Cards` were not reviewed and their absence from this report should not be read as "checked and fine." General UX and product judgment were also not evaluated: whether these three metrics are the right ones to surface, whether region-based grouping would help, information density, or whether scaling should ever be automated — none of these were assessed by this review.
