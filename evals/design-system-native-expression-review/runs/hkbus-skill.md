# Design-System Native-Expression Review: hk-independent-bus-eta — route ETA / stop detail / bookmarked-stops flow

**Design system:** Material UI (`@mui/material`, `@mui/icons-material`). Authority strictly `@mui/material`'s own documentation — MUI X, Joy UI, Base UI, and Google Material Design/M3 guidance were explicitly excluded. This app declares `@mui/x-date-pickers` in `package.json`, but grepping all 9 reviewed files confirms **no `@mui/x-*` import appears in any of them** — nothing in the bounded surface falls under MUI X authority.

**Inferred user task:** A commuter looks up a specific bus route (`RouteEtaPage.tsx`), sees its ordered list of stops with live ETAs and a map, expands a stop to check timing or opens a stop-detail dialog for bookmarking/directions/navigation (`StopAccordionList.tsx`, `StopDialog.tsx`, `RouteHeader.tsx`). From a stop's dialog, or directly via URL, a rider can also see every route serving that one stop (`StopEtaListPage.tsx`). Separately, a rider manages and revisits previously bookmarked stops, grouped into tabs (`BookmarkedStopPage.tsx`). `AppContext.tsx`/`DbContext.tsx` hold cross-cutting device/geolocation/settings state and the offline route/stop database — they render no meaningful UI themselves (`AppContext.Provider`/`DbContext.Provider` only).

**Packages / versions:** `@mui/material` `^5.15.11` → resolved to locked `5.15.11`; `@mui/icons-material` `^5.15.11` → resolved to locked `5.15.11` (both resolved from `yarn.lock` via `resolve_versions.py`). Versions are pinned and current enough that the fetched docs apply directly.

**Authority categories found in this corpus:** Component guidance only (one page per component — App Bar, Alert, Dialog, Accordion, Snackbar, etc., each with a stated purpose, prop reference, and illustrative demos) plus a small set of generic cross-cutting Guides (Composition, Responsive UI, customization internals) that describe styling/composition *mechanics*, not named user-task patterns. There is **no separate task/pattern-level or composition-guide tier** comparable to a system like Cloudscape's named patterns — no page in this corpus documents "how to build a route detail screen" or "how to build a stop-bookmarking flow." Every finding below reasons from a single component's own stated purpose and/or its own demo, never from an invented pattern layer.

## Findings

### Finding 1: Route header hand-rolls a screen action bar instead of using AppBar/Toolbar

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Every route-detail screen needs a persistent bar identifying the current route and route-scoped actions: reverse direction, star/bookmark the route, and view its timetable.
- **Repository evidence:** `src/components/route-eta/RouteHeader.tsx:25-43` — a `Paper` (`elevation={0}`, transparent background, `sx={PaperSx}` flex row) contains, left to right: `ReverseButton` (leading icon action), a centered `Box` holding the route number (`RouteNo`) plus `RouteStarButton` on one row and a `Typography` destination caption below, then a `Divider orientation="vertical"` and `TimetableButton` (trailing icon action). This is rendered as the first element of `RouteEtaPage.tsx:234`, i.e., it functions as this screen's top bar. Confirmed by `inspect_surface.py`: this file imports `Box, Divider, Paper, SxProps, Theme, Typography` from `@mui/material` — no `AppBar` or `Toolbar` import anywhere in the bounded surface.
- **Authority evidence:** `https://mui.com/material-ui/react-app-bar.md` (App Bar component page). Authority category: **component guidance**. Quoted: *"The App Bar displays information and actions relating to the current screen."* The page also states AppBar "can transform into a contextual action bar or be used as a navbar," and documents the `Toolbar` sub-component (used inside AppBar) supporting a leading element, a `flexGrow`-ed title/content area, and trailing elements — the same leading-icon / centered-title / trailing-icon shape `RouteHeader` builds by hand with `Box` + custom `sx`.
- **Evidence mode:** VERBATIM (the purpose statement quoted above is copied literally from the App Bar page and is the load-bearing citation; the leading/title/trailing `Toolbar` layout is drawn from the same page's own component description, not from an invented composition tier).
- **Authority strength:** RECOMMENDED (the docs describe AppBar as the component whose stated job is exactly "information and actions relating to the current screen" — not an equally-valid alternative among several — but there is no explicit "don't build your own header, use AppBar instead" prohibition, so this does not rise to REQUIRED).
- **Applicability argument:**
  1. Task match: `RouteHeader` literally displays route information (title, destination) and route-scoped actions (reverse, star, timetable) for the currently viewed screen — this is not a superficial shape match, it is the named job the App Bar page describes.
  2. Current implementation solves the same problem: yes, `Paper` + manual flex `sx` produces the identical leading-icon / title / trailing-icon layout AppBar/Toolbar is built to express.
  3. Preserves the same task: yes — swapping `Paper` for `AppBar` (`position="static"` or `"relative"`, not the default `"fixed"`) and wrapping the content in `Toolbar` changes no product behavior, only which design-system primitive expresses it.
  4. Materiality of the difference: I checked whether a persistent global `AppBar`/`Toolbar` already exists elsewhere in the app (`src/App.tsx`, `src/components/layout/Root.tsx`) — it does not; the app has no app-shell `AppBar` at all. That confirms rather than weakens applicability here: MUI explicitly documents AppBar as usable as a **contextual**, per-screen action bar (not only global chrome), and there is no competing/duplicate AppBar already claiming that role elsewhere in the app that this recommendation would collide with.
- **Current expression:** A `Paper`-based flex row with fully custom `sx` positioning for the leading button, centered title block, divider, and trailing button.
- **Native expression:** An `AppBar` (non-fixed `position`) containing a `Toolbar` with the reverse action, a `flexGrow`-ed title block (route number + star + destination caption), a `Divider`, and the timetable action — the same composition MUI's own AppBar/Toolbar demonstrates for "information and actions relating to the current screen."
- **Why it matters:** This is the component MUI ships specifically for this named job, including its own theming slot (`theme.components.MuiAppBar`) and elevation/color conventions that the rest of a MUI-based app would use consistently. Building the same shape from `Paper` + hand-tuned `sx` forgoes that shared vocabulary and theming surface for a bespoke one-off, at exactly the place (the screen's top bar) where a MUI-fluent implementer would reach for AppBar first.
- **Boundary check:** This is a component/composition judgment — which named MUI component expresses "screen title + leading/trailing actions" — not a critique of `RouteHeader`'s API usage, styling values, or accessibility mechanics, and it does not propose a different user task.

### Finding 2: Route-update notice hand-rolls a clickable banner instead of using Alert's `action` slot

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** high
- **User task:** Tell the rider, without interrupting their current route view, that fresher route data exists, and let them trigger a refresh.
- **Repository evidence:** `src/components/route-eta/RouteUpdateNotice.tsx:29-49` — a `Box` (custom bordered `sx={rootSx}`) whose entire surface is `onClick={renewDb}`, containing a single `Typography` with an emoji and translated text (`⁉️ {t("db-renew-text")}`). No `Alert` import anywhere in this file or the rest of the bounded surface.
- **Authority evidence:** `https://mui.com/material-ui/react-alert.md` (Alert component page). Authority category: **component guidance**. Quoted: *"Alerts display brief messages for the user without interrupting their use of the app."* And, on the `action` prop: *"Add an action to your Alert with the `action` prop. This lets you insert any element—an HTML tag, an SVG icon, or a React component such as a Material UI Button—after the Alert's message, justified to the right."*
- **Evidence mode:** VERBATIM.
- **Authority strength:** RECOMMENDED (Alert's stated purpose is precisely "brief message, not interrupting the app" plus a documented mechanism for exactly this kind of embedded action; there is no explicit prohibition against a custom notice box, so not REQUIRED).
- **Applicability argument:**
  1. Task match: this is exactly a brief, non-blocking message with a follow-up action — not a superficial resemblance, it's the component's stated purpose.
  2. Current implementation solves the same problem: yes, same "show message, let user act" job.
  3. Preserves the same task: yes, an `Alert` with `action={<Button onClick={renewDb}>…</Button>}` (or an equivalent icon action) communicates the identical message and triggers the identical `renewDb` behavior.
  4. Materiality: this is the one component in the whole corpus whose documented purpose is "brief message + optional action, non-interrupting" — using a bespoke bordered `Box` here forgoes that purpose-built vocabulary for a one-off visual treatment (custom border, ad hoc emoji-as-icon) an experienced MUI implementer would not need to invent.
- **Current expression:** An entirely-clickable custom `Box` with a hand-styled border and an emoji prefix standing in for severity/iconography.
- **Native expression:** An `Alert` (severity chosen to match the message's attention level — the corpus doesn't establish which, see below) with the renew action surfaced via the `action` prop, e.g. a `Button`, rather than making the whole block an implicit click target.
- **Why it matters:** Beyond this one instance, adopting Alert buys the app the design system's shared severity/color/icon vocabulary for "important but non-blocking" messages — consistency an experienced MUI implementer would expect any such notice to carry, rather than each notice reinventing its own border/emoji treatment.
- **Boundary check:** This is about which documented component embodies "brief message with an action," not about the specific border color values, the `onClick`-on-a-`Box` accessibility mechanics, or a broader UX judgment about whether the notice should exist at all.

### Finding 3: StopDialog's near-full-height styling is intent-dependent on whether it's meant as a full-screen dialog

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Show a rider the routes serving one stop, plus stop-scoped actions (bookmark, directions, map, "view full stop page", close), in a way that feels immediately reachable from the route view.
- **Repository evidence:** `src/components/route-eta/StopDialog.tsx:67-99` — a `Dialog` (no `fullScreen` prop) whose `DialogTitle` contains a manually flexed `Box` of five `IconButton`s (bookmark toggle, directions, map, "arrow outward" to the full stop page, close) built with `sx={titleSx}` (`justifyContent: "space-between"`). Separately, `rootSx` (lines 103-112) forces the dialog's `Paper` to near-viewport height via `marginTop: "90px"` and `height: "calc(100vh - 100px)"`.
- **Two plausible readings:**
  1. **Full-screen-dialog intent:** the near-full-height styling signals the product wants this to behave as a full-screen modal. If so, MUI's Dialog page documents a specific composition for exactly that: the `fullScreen` boolean prop (optionally driven by `useMediaQuery` for responsive full-screen), paired in its own "Full-screen dialogs" example with an `AppBar`/`Toolbar` title row (close `IconButton`, `Typography` title, trailing action) — a materially different and more idiomatic path than reverse-engineering full height with hand-tuned `margin`/`height` and a bare `Box` title row.
  2. **Deliberately partial-height sheet intent:** the current sizing is a deliberate design choice (a large-but-not-full-height overlay, not meant to read as a true full-screen destination). If so, the current `DialogTitle`-based construction is already a reasonable expression of that task, and adopting `fullScreen`/AppBar-in-dialog would misrepresent the intended, smaller-than-full-screen surface.
- **Authority evidence:** `https://mui.com/material-ui/react-dialog.md` (Dialog component page). Authority category: **component guidance**. Relevant facts, bridged: Dialogs are described as *"purposefully interruptive, so they should be used sparingly"* (general Dialog framing); the API documents a boolean `fullScreen` prop; and the page's "Full-screen dialogs" section demonstrates — as an example, not a stated rule — pairing that prop with an `AppBar`/`Toolbar` title bar. Per the skill's own rule that examples illustrate rather than mandate, the `AppBar`-in-dialog composition is not asserted as a requirement, only as the documented shape MUI itself demonstrates for this exact scenario.
- **Evidence mode:** SYNTHESIS (bridges the general Dialog purpose statement, the `fullScreen` prop's existence, and the full-screen example's title-bar shape — none of these alone settles which reading applies here).
- **Authority strength:** INFERRED (a synthesis across a demo-illustrated composition does not inherit the underlying page's authority; per the Missing-intent handling this is deliberately not phrased as REQUIRED or RECOMMENDED since the two readings aren't resolved).
- **What would resolve it:** Whether this dialog is intended to read, product-wise, as a full-screen "stop detail" destination (closer in weight to `StopEtaListPage.tsx`, which shows the same "routes serving a stop" content as a standalone full page) or as a deliberately bounded quick-look overlay layered on top of the route view. Nothing in the bounded surface — file names, copy, or surrounding code — settles this, so it is reported without a recommended direction.
- **Current expression:** `Dialog` sized to near-full-height via hand-written `sx` overrides, with a `DialogTitle` built from a plain `Box` of `IconButton`s.
- **Native expression:** Not asserted with confidence — depends on the unresolved intent above.
- **Why it matters:** If the full-screen reading is correct, the current approach reaches the same visual result MUI's own full-screen dialog composition documents, but via hand-tuned pixel values instead of the dedicated `fullScreen` prop and its paired title-bar composition — a maintenance/consistency gap against how the rest of a MUI app would build the same shape. If the partial-height reading is correct, no material gap exists.
- **Boundary check:** This candidate is about which documented Dialog composition (if any) applies to this screen's product intent, not about the specific `marginTop`/`height` pixel values themselves (an implementation detail, cited only as evidence that near-full-height sizing is happening) — those exact values are explicitly out of this skill's scope and are not the finding.

## Suppressed (low materiality or weak applicability)

- **StopAccordionList.tsx — stop list expressed as a scrollable stack of per-stop accordions.** Considered whether MUI's `Stepper` (documented for step-by-step process flows) would be a more native fit for an ordered sequence of physical bus stops. Suppressed: this is the classic superficial shape match the anti-fundamentalism rule warns against — `Stepper` documents wizard-like *process* progression, not a scrollable index of addressable records, and the observed task (expand any stop, jump to any stop's detail, non-linear navigation via the map's `onMarkerClick`) does not match a step-by-step process. Additionally, the actual `Accordion` usage lives in `StopAccordion.tsx`, outside the bounded surface, so any component-selection judgment about the accordion itself can't be made from what was reviewed here — only the controlled, single-open-at-a-time composition visible from the parent was observable (see Orientation notes).
- **StopDialog.tsx — five `IconButton`s laid out in a plain `Box` (`titleSx`, `justifyContent: "space-between"`).** Considered whether `Stack` (MUI's documented layout container for arranging elements with consistent spacing) would be more native than `Box` here. Suppressed: `Box` and `Stack` are both valid, undifferentiated MUI layout primitives for this job — no component page states a preference between them for a plain icon row, so this is an equally-valid alternative, not a material finding.
- **BookmarkedStopPage.tsx — root `Paper` (`elevation={0}`, `square`) used as the page's outer flex container with a full-bleed background image.** Considered whether `Box` would be the more honest choice since the elevation is zeroed out. Suppressed: low materiality — `Paper` at `elevation={0}` is still a documented, valid MUI surface primitive, and no authority establishes a rule against using it as a plain container; this reads as an equally-valid stylistic choice.
- **StopEtaListPage.tsx — page header expressed as a centered `Typography` (`variant="h6"`) plus a `Divider`, above a scrollable list.** Considered whether a stronger documented composition applies. Suppressed: no authority in this corpus establishes a composition-level rule for a simple label-above-a-list; `Typography` + `Divider` is an unremarkable, valid combination for this job, and the list itself (`StopRouteList`) is outside the bounded surface.

## Orientation notes

- **Snackbar for the "copied to clipboard" confirmation** (`StopAccordionList.tsx:65-73`, `autoHideDuration={1500}`) is exactly the documented Snackbar job — "brief notifications of processes that have been or will be performed" — correctly and natively used.
- **`Dialog` as the chosen component for `StopDialog.tsx`** is itself a correct, native selection independent of Finding 3 above: the task (stop info, decisions like bookmarking, multiple actions) matches Dialog's stated purpose ("critical information, require decisions, or involve multiple tasks"); only the specific full-screen-vs-partial composition question is unresolved.
- **Bookmark toggle icon swap** (`StopDialog.tsx:71-73`, `BookmarkIcon`/`BookmarkBorderIcon` swapped on `IconButton` by state) is the standard, correctly-applied MUI filled/outline icon-toggle idiom.
- **Vertical `Divider` with `flexItem`** separating the title block from `TimetableButton` in `RouteHeader.tsx:39` matches the Divider component's documented purpose — "a thin, unobtrusive line for grouping elements to reinforce visual hierarchy."
- **`AppContext.tsx` / `DbContext.tsx`** render no meaningful UI (`.Provider` wrappers only) and import no `@mui/material`/`@mui/icons-material` components — nothing to evaluate at the native-expression level in these two files.
- **`@mui/x-date-pickers` (declared elsewhere in this app's `package.json`) does not appear in any of the 9 reviewed files** — confirmed via grep across the full bounded surface; MUI X authority correctly plays no role in any finding above.

## What was not evaluated

General UX/product judgment was also not evaluated — e.g., whether showing "routes serving a stop" in both a modal (`StopDialog.tsx`) and a full page (`StopEtaListPage.tsx`) is the right information architecture, whether the route/stop navigation flow overall is easy to use, or any other product-redesign-shaped critique. Their absence from this report should not be read as "checked and fine" — they were not this skill's job.
