# Design-System Native-Expression Review: Checkmate — Incidents page

**Design system:** Material UI (`@mui/material`). `@mui/icons-material` was named as in-scope for this round but is not imported anywhere in this bounded surface (confirmed via `inspect_surface.py`), so no findings touch it. No `@mui/x-*` or `@mui/lab` imports were found in the bounded surface; none needed to be excluded.

**Inferred user task:** This is a team's incident-monitoring/triage surface (`/incidents[/:monitorId]`). It gives an overview of monitoring incidents across (optionally, one) monitor: three summary panels (whether any incidents are currently active, the most recent incidents, and aggregate stats like total count/most-affected monitor/average resolution time), a table of currently-active incidents (shown only when any exist), and a filterable, paginated, auto-refreshing table of resolved incident history (filterable by monitor and by resolution type — manual vs. automatic — and by a date range). From either table, a row can be opened into a read-only details dialog (status, monitor, timeline, HTTP status code, downtime, and — for resolved incidents — resolution metadata), and an active incident can be manually resolved via a separate confirmation dialog that accepts an optional free-text comment.

**Packages / versions:** `@mui/material` resolved to `7.3.7` (locked, via `resolve_versions.py` against `package.json`/`package-lock.json`). `@mui/icons-material` has no declared range and no lockfile entry — it is not used in this surface, so this is informational only, not a caveat on any finding below.

**Authority categories found in this corpus:** Component guidance pages only (one page per component, e.g. `react-select.md`, `react-chip.md`, `react-card.md`, `react-dialog.md`), plus general cross-cutting guides (Composition, Responsive UI, Testing, TypeScript, etc.) and customization/theming references. There is no named task/pattern layer and no per-task composition/usage-guide tier the way some other design systems' corpora expose (per this skill's step 3, this absence is recorded rather than a composition tier being invented). All authority cited below is therefore `component guidance`; no finding below claims a `named pattern` or `guide`-level category because this corpus does not have one that speaks to these tasks.

## Findings

### Finding 1: `resolutionType` rendered as plain colored text instead of Chip, unlike the table's other status-like cells

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium-high
- **User task:** Scanning a paginated incident table where each row surfaces several categorical/status attributes at a glance — open/resolved state, HTTP status-code class, and how the incident was resolved (manual vs. automatic).
- **Repository evidence:** `IncidentTable.tsx`, `getHeaders()`. The `status` column (lines 95–111) renders `<ValueLabel value={isActive ? "negative" : "positive"} text={...} />` — a shared, BaseBox-based colored pill with a status dot. The `statusCode` column (lines 151–162) renders `<StatusCodeLabel statusCode={row.statusCode} message={row.message} />`, which itself wraps the same `ValueLabel` pill (confirmed in `Components/design-elements/StatusCodeLabel.tsx`, line 29). The `resolutionType` column (lines 129–150) instead renders a bare `<Typography variant="body2" color={row.resolutionType === "manual" ? theme.palette.warning.main : theme.palette.success.main} textTransform="capitalize">{row.resolutionType}</Typography>` — color-only text with no pill/badge container, in the same table as the two pill-rendered columns.
- **Authority evidence:** Authority category: `component guidance`. Source: MUI React Chip page (`https://mui.com/material-ui/react-chip.md`). VERBATIM: "Chips are compact elements that represent an input, attribute, or action." Also VERBATIM: "You can use the `color` prop to define a color from theme palette," with the documented palette values including `success`, `warning`, and `error` — the same semantic palette entries (`warning.main`/`success.main`) this cell already selects by hand.
- **Evidence mode:** VERBATIM for the two quoted sentences (copy/paste-verifiable against the fetched page); PARAPHRASE for the applicability claim that a manual/automatic resolution type is "an attribute" in the sense the Chip page describes.
- **Authority strength:** OPTIONAL — the Chip page documents representing "an attribute" via its `color` prop as one supported, idiomatic way to render exactly this kind of categorical value. It states no explicit preference over plain colored text and contains no "Don't … instead" pairing ruling the current approach out, so this does not rise to RECOMMENDED or REQUIRED.
- **Applicability argument:** (1) `resolutionType` is a categorical attribute value (manual vs. automatic), the same kind of value the two neighboring columns (`status`, `statusCode`) already render — Chip's stated purpose ("represent … an attribute") matches this directly, not a superficial shape coincidence, since it is the identical conceptual job the neighboring cells solve differently. (2) the current implementation already solves the same problem — communicating a categorical value via a semantic palette color — just without a chip/pill container, so it's functionally equivalent to what a `color`-prop `Chip` would do. (3) the proposed native expression preserves the exact same semantics and even the same chosen colors (warning/success); nothing about the task changes. (4) materiality: within one table, the same "categorical attribute" concept is expressed two different ways already (a `ValueLabel` pill, reused for both `status` and `statusCode`) and then a third way (raw colored text) for `resolutionType` — an experienced MUI practitioner scanning this file would plausibly notice the third column doesn't share a visual/component vocabulary with the other two, and MUI ships exactly one primitive built for this job.
- **Current expression:** `resolutionType` cell renders `<Typography color={...}>{row.resolutionType}</Typography>` — colored text only, visually inconsistent with the pill-style status indicators used two columns over in the same row.
- **Native expression:** A small, color-driven `Chip` (e.g. `<Chip size="small" color={row.resolutionType === "manual" ? "warning" : "success"} label={...} />`), using MUI's own attribute-representation primitive and its documented `color` prop instead of manually resolving `theme.palette.*.main` onto raw `Typography`.
- **Why it matters:** the table currently expresses the same conceptual value (a categorical attribute) through two different visual patterns instead of one consistent, documented MUI primitive. That's a legibility cost in a table specifically meant to be scanned quickly for status information, and it's a missed opportunity to use the one component MUI's own docs describe as being for exactly this job, rather than a third bespoke pattern layered onto an already-established one.
- **Boundary check:** this is a judgment about which MUI primitive best represents a categorical attribute value in one table cell, not a critique of the styling mechanics (the specific colors chosen, capitalization, or contrast/accessibility of the text) or a general "this table is confusing" UX claim.

### Finding 2: Summary panels hand-roll Card's header/content split on a generic `Box`

- **Type:** combined selection + composition
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Presenting a triage/overview dashboard of three distinct topic areas — active-incident alert state, the most recent incidents, and aggregate incident stats — as three side-by-side, self-contained summary panels above the incident tables.
- **Repository evidence:** `CardSummary.tsx`, shared `SummaryCard` wrapper (lines 52–79): `<BaseBox padding={8} flex={1}><Stack><Typography variant="eyebrow">{title}</Typography>{children}</Stack></BaseBox>`, reused by `SummaryCardActiveIncidents` (85–124), `SummaryCardLatestIncidents` (183–200), and `SummaryCardStats` (206–236), laid out as a responsive row via `Stack direction={{xs:"column", md:"row"}}` in `index.tsx` (lines 171–178). `BaseBox` (`Components/design-elements/BaseBox.tsx`, lines 4–18) is a plain MUI `Box` manually styled with `theme.palette.background.paper`, a 1px `theme.palette.divider` border, and `theme.shape.borderRadius` — reconstructing an outlined elevated surface by hand.
- **Authority evidence:** Authority category: `component guidance`. Source: MUI React Card page (`https://mui.com/material-ui/react-card.md`). VERBATIM: "Cards contain content and actions about a single subject." Also documented: `Card` is "a surface-level container for grouping related components"; `CardHeader` is "an optional wrapper for the Card header"; `CardContent` is "the wrapper for the Card content." (Card is built on `Paper` — it forwards unmatched props to the root `Paper` element.)
- **Evidence mode:** PARAPHRASE — the quoted sentences above are verbatim, but mapping Card's stated purpose and header/content split onto these three specific panels is the reviewer's own reasoning, not a statement the source makes about this task.
- **Authority strength:** INFERRED — the Card page describes what Card is for and how `CardHeader`/`CardContent` divide responsibility, but does not itself state that a hand-built title-plus-content box on a generic surface should be replaced with `Card`. The applicability step (this task matches Card's stated purpose closely enough to warrant the swap) is the reviewer's inference, not something the source asserts as a rule.
- **Applicability argument:** (1) each of the three summary widgets is a titled, self-contained surface holding data "about a single subject" (active-incident state; latest incidents; aggregate stats) — a materially close match to Card's stated purpose, not merely a superficial shape coincidence, since each genuinely is one bounded topic with a header and a body. (2) the current `SummaryCard` wrapper already solves the identical structural problem Card/CardHeader/CardContent solve — a title region plus a content region inside a bordered surface — independently reconstructed on a generic `Box`. (3) the proposed native expression is a pure component substitution: it changes nothing about what data is shown, how it's grouped, or the responsive three-panel layout. (4) materiality is real but not high: because `BaseBox` already visually approximates an outlined `Card` (same background/border/radius tokens), the result today is not visibly broken — the cost is forfeiting Card's built-in header/content/actions vocabulary and any app-wide `MuiCard`/`MuiCardHeader` theme customization (which would apply automatically to real `Card` usage but not to a hand-rolled `Box`), which is a consistency/maintenance argument more than a visible one.
- **Current expression:** three panels built from a shared `BaseBox` (styled `Box`) plus a manually placed `Typography variant="eyebrow"` acting as a header and a `Stack` of children acting as the body — a hand-rolled reconstruction of Card's header/content split.
- **Native expression:** `<Card><CardHeader title={title} /><CardContent>{children}</CardContent></Card>` (or a themed wrapper built on `Card` rather than `Box`), preserving the same three-panel dashboard layout and content exactly.
- **Why it matters:** `BaseBox` is documented (by its own implementation) as a generic, theme-aware `Box` wrapper, pressed into service here for a job — grouping content and a header about a single subject in a surface-level container — that MUI ships a semantically matching, purpose-built component for. Staying on `Box` forfeits Card's documented header/content/actions structure and any theme-level `Card`/`CardHeader` customization the rest of an MUI-based app would otherwise inherit automatically — a real but modest consistency/maintenance cost, tempered by the fact that `BaseBox` is deliberately reused throughout this codebase as a generic bordered-surface primitive, not invented just for this one job.
- **Boundary check:** this is a judgment about which MUI component is intended for "a titled, self-contained content panel" (Card) versus a generic container (Box) pressed into that role, not a critique of the visual styling, the `eyebrow` typography variant, or the responsive `Stack` layout wrapping the three panels.

## Suppressed (low materiality or weak applicability)

- **Monitor filter `Select` (`ControlsIncidentFilter.tsx`, lines 40–56) vs. `Autocomplete`.** MUI's own Select page explicitly routes "more advanced features, like combobox, multiselect, autocomplete, async or creatable support" to Autocomplete (VERBATIM), and this Select's option list is populated from every monitor on the team (`monitors?.map(...)`) with no visible cap and no search/typeahead. Suppressed because the bounded surface gives no evidence of typical monitor-count scale for this app — reporting a confident Autocomplete recommendation without that evidence would be exactly the "the docs show it this way, with no applicability evidence" pattern this skill's materiality bar rules out. The resolution-type `Select` in the same component (a fixed 3-item enum) is not affected by this concern and is not suppressed — see Orientation notes.
- **Active-incidents table stacked above Resolved-incidents table (`index.tsx`, lines 187–235) vs. MUI `Tabs`.** Tabs' own docs describe organizing content "at the same level of hierarchy," but active vs. resolved incidents plausibly differ in operational priority for a monitoring page — hiding active incidents behind a tab click would be a materially different (arguably worse) expression of the underlying task, not a native-expression improvement. No MUI authority states a preference either way. Weak applicability; suppressed rather than reported as a finding.
- **`CardDetails.tsx`'s repeated label/value `Grid` rows (Overview / Analysis / Resolution Details sections, e.g. lines 59–93, 99–146, 155–202) vs. `List`/`Table`.** Considered whether MUI's List or Table components would better express these. List's documented examples are repeated homogeneous items (mail folders, contacts); Table's stated purpose is "sets of data," which implies multiple comparable records. Neither documented purpose materially matches a single incident's heterogeneous field/value description panel — this looks like a superficial shape match ("rows of stuff") rather than the same problem List or Table are documented to solve. No component in this corpus is intended for exactly this "record detail" concept, so reasoning stops here rather than forcing a finding onto a documented alternative that doesn't actually apply.
- **Extending Finding 1's Chip recommendation to the shared `ValueLabel`/`StatusCodeLabel` wrappers themselves.** Those wrappers are used throughout the rest of the app, not just this surface; replacing their internal implementation with `Chip` would be a codebase-wide design-elements library change, well beyond this bounded surface's own file-local choices, and is out of scope for this review.

## Orientation notes

- `IncidentTable.tsx` + the shared `Table`/`Pagination` wrappers (`Components/design-elements/Table.tsx`): compose MUI `Table`/`TableContainer`/`TableHead`/`TableBody`/`TableRow`/`TableCell` directly, and extend `TablePagination` through its documented `ActionsComponent` extension point rather than reimplementing pagination controls from scratch — correct, documented usage.
- `ControlsIncidentFilter.tsx`: the resolution-type `Select` (a fixed, 3-item, mutually exclusive enum: all/manual/automatic) and its `MenuItem` composition match Select's own stated purpose, "collecting user provided information from a list of options."
- `DialogResolution.tsx` / `DialogIncidentDetails.tsx` (via the shared `Dialog` wrapper in `Components/inputs/Dialog.tsx`): compose `Dialog`/`DialogTitle`/`DialogContent`/`DialogActions` matching MUI's documented Dialog structure, and blend the documented "Confirmation dialog" pattern ("require users to explicitly confirm their choice before an option is committed") with the documented "Form dialog" pattern (collecting the optional resolution comment) — an appropriate combination for a consequential, optional-detail action, not a misuse of either documented example.
- `ActionsMenu` (`Components/actions-menu/index.tsx`), composed into each table row: `IconButton` + anchored `Menu` + `MenuItem` list matches MUI's documented basic Menu composition.
- `HeaderTimeRange` (`Components/common/controls/HeaderTimeRange.tsx`), composed directly into this page for the resolved-incidents date-range control: `ToggleButtonGroup` with `exclusive` for a small (4-option), mutually exclusive date-range selector matches ToggleButtonGroup's documented exclusive-selection behavior for grouped related options.
- `Divider` between the active-incidents table and the resolved-incidents section (`index.tsx`, line 208): matches Divider's documented purpose of providing "a thin, unobtrusive line for grouping elements to reinforce visual hierarchy."

## What was not evaluated

Implementation correctness was not assessed: prop/API usage, the MUI `Grid` version/`size`-prop usage, hard-coded style values (e.g. the manual palette-to-color mapping in Finding 1, or BaseBox's manually reconstructed border/radius tokens), and app-owned accessibility mechanics (e.g. `aria` wiring on `ActionsMenu`'s `IconButton`) were not reviewed and their absence here is not a clean bill of health. General UX/product judgment — information density, whether the row-click-to-open-details affordance duplicating the per-row menu's "Details" action is confusing, overall page information architecture, or copy/labeling — was likewise out of scope and not assessed.
