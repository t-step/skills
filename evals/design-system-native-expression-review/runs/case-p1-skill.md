# Design-System Native-Expression Review: MessageQueues.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`, `@cloudscape-design/collection-hooks`)

**Inferred user task:** An operator views every message queue in the account side by side to compare throughput (messages/second) and backlog age (oldest message age) across all of them at once, in order to decide which queues need scaling attention right now. The surface also states operators can search by queue name or narrow the list to a specific status or region while triaging. All 24 queues share an identical schema (id, name, status, region, messagesPerSecond, oldestMessageAgeSec) — this is a resource-collection triage/comparison view, not a creation, editing, or single-resource detail flow.

**Packages / versions:** `@cloudscape-design/components` 3.0.900 (resolved, locked), `@cloudscape-design/collection-hooks` 1.0.60 (resolved, locked). Both fully resolved from `package.json`/`package-lock.json` — no unresolved semver range to caveat.

**Authority categories found in this corpus:** Component guidance (per-component pages under `/components/`) and named patterns (a distinct pattern/task layer under `/patterns/`, including a "View resources" overview page that explicitly branches into Table view, Card view, and Split view sub-patterns, plus a separate Filtering patterns page). Foundations and demos also exist but were not load-bearing for these findings. This corpus does have a genuine pattern/task tier distinct from component guidance, so composition-level findings below are grounded in named-pattern authority, not manufactured from component pages alone.

## Findings

### Finding 1

- **Finding:** A 24-item, single-schema, comparison-driven queue list is expressed as `Cards` when Cloudscape's own "View resources" decision criteria — resource count, shared metadata, and columnar data type — point directly at `Table`.
- **Type:** `combined selection + composition`
- **Materiality:** `high`
- **Confidence:** `high`
- **User task:** As stated above — compare throughput and backlog age across all 24 queues (identical schema) to decide which need scaling attention now.
- **Repository evidence:** `MessageQueues.tsx` lines 9–25 define `QUEUES` as 24 objects sharing exactly one schema (status, region, messagesPerSecond, oldestMessageAgeSec). Lines 29–33 (source comment) state the task as cross-item comparison. Lines 56–98 render this via `Cards`, with `cardDefinition.sections` (lines 65–86) mapping each of the four comparable fields to a card section — i.e., re-deriving column-like structure inside a card, one card per queue. `useCollection` is configured with `sorting: {}` (line 41) and its `collectionProps` are spread onto `Cards` (line 57), but `Cards` has no `sortingColumn`/sort-affordance prop in this file — the sorting state the code already wired up has no UI it can attach to under the current component choice, which only `Table` would expose natively.
- **Authority evidence:** The "View resources" patterns page (`https://cloudscape.design/patterns/resource-management/view/index.html.md`) gives an explicit table/card decision table: table view for "9 or more resources in 99% of use cases" vs. card view for "5 or less resources in 99% of use cases"; table view when there is "shared metadata between resources" vs. card view for "different metadata across resources"; table view for "data that is displayed in columns (text, numerical, status, sparkline)" vs. card view for "data that can be displayed as visuals (charts, videos)." It states directly: *"Use a table if the resources share the same metadata, and your users will be comparing resources to determine which to take action on."* The child pages reinforce this: the Table view pattern (`https://cloudscape.design/patterns/resource-management/view/table-view/index.html.md`) states *"The best data type for a table view is data that is structured, easily comparable, and sortable"* and *"Use table view pattern for static data with multiple attributes displayed in a tabular format."* The Card view pattern (`https://cloudscape.design/patterns/resource-management/view/card-view/index.html.md`) frames its own fit as "small sets of similar resources" and points to table view when the need is "quickly identifying categories or comparing values in a large text and numerical data set."
  - **Authority category:** `named pattern`
- **Evidence mode:** `VERBATIM`
- **Authority strength:** `RECOMMENDED` (the criteria are framed as "use X if Y" decision guidance with quantified thresholds, not an absolute "don't/instead" prohibition against Cards for this data shape — but the thresholds are explicit and this surface sits far on the table side of them: 24 resources vs. the stated "9 or more... 99% of use cases," identical shared schema, and purely columnar text/numeric/status data, none of it visual).
- **Applicability argument:** (1) Task match: the surface's own stated purpose — compare structured metrics across every queue to decide which needs action — is close to a verbatim restatement of the View-resources page's own stated table-view trigger ("comparing resources to determine which to take action on"). (2) Same problem solved: the current `Cards` composition already reconstructs column-like sections (status, region, throughput, age) per card purely to support that comparison — it is solving the tabular-comparison problem, just via a container documented for a different shape of problem (small, visually-mixed, differently-shaped resource sets). (3) Preserves task: swapping to `Table` changes no data, no filtering/pagination behavior, and no user goal — it is the same collection, same fields, same triage task. (4) Materiality of the gap: 24 uniform, purely columnar records is roughly 5x past the stated "9 or more" table threshold and squarely past the "5 or less" card threshold; the schema is 100% shared across all items (not "different metadata across resources," the stated card trigger); and the code has already built (but cannot expose) sort state that only `Table` would surface — a concrete, code-level signal a Cloudscape-fluent implementer would restructure this rather than merely note it as an alternative.
- **Current expression:** `Cards` with `cardDefinition.sections` simulating four columns per card, wrapped by `TextFilter` + `Pagination` inside `ContentLayout`.
- **Native expression:** `Table` (from `@cloudscape-design/components/table`) with `Header`, `columnDefinitions` for name/status/region/throughput/age (status rendered via `StatusIndicator` inside a cell, unchanged), and `collectionProps`/`filterProps`/`paginationProps` from the same `useCollection` call, now also exposing the already-configured sort state via `sortingColumn`. This is a supported alternative directly implied by the cited pattern criteria; the exact column set is not itself re-derived from any single citation, so the specific column list is a reasonable but not independently-cited implementation detail.
- **Why it matters:** The current composition asks an operator to visually re-derive four aligned columns across up to 24 separate card boxes to compare throughput and backlog age — exactly the comparison Cloudscape's own decision criteria say `Table` is built to make efficient (sortable, structured, columnar), and exactly the shape Cloudscape's own criteria say `Cards` is not intended for at this count and this schema-uniformity. It also strands the sorting state the code already set up (`sorting: {}`) with no component that can expose it.
- **Boundary check:** This is a component/composition-level judgment — which collection container fits a stated comparison task, per the design system's own documented decision criteria — not an implementation-correctness note (nothing here is misuse of `Cards`' own API) and not a generic UX complaint (the citation is task-specific, quantified, and drawn from a named pattern page, not "cards feel dense").

### Finding 2

- **Finding:** The surface's own stated task — "narrow the list down to a specific status or region while triaging" — has no filtering control at all; only free-text `TextFilter` (for name search) is implemented, when Cloudscape's own filtering-pattern guidance names a different, specific component for filtering by exactly this shape of need (one or two fixed-value properties).
- **Type:** `component selection`
- **Materiality:** `medium`
- **Confidence:** `high`
- **User task:** Same overall task as Finding 1; specifically the sub-task of narrowing the 24-queue list by `status` (2 possible values: healthy/backlogged) or `region` (2 possible values: us-east-1/us-west-2), as stated in the source comment (lines 29–33) and the `Header` description (line 50, "Compare... to decide which need scaling attention").
- **Repository evidence:** Lines 89–95: the only filtering control rendered is `TextFilter` (`{...filterProps}`, `filteringPlaceholder="Find message queue"`). `useCollection`'s `filtering` config (lines 36–39) only configures `empty`/`noMatch` text for free-text matching — there is no property-based filtering configuration or control anywhere in the file, despite `status` and `region` being explicit, small-cardinality fields on every item (lines 12–13) and explicitly named in the task description as filter dimensions.
- **Authority evidence:** The Filtering patterns page (`https://cloudscape.design/patterns/general/filter-patterns/index.html.md`) states: *"Text Filter is recommended when users tend to know exactly the value or term they are looking for"* (free text search); and, for the property case, *"the common behavior of users is to filter a resource by only one or two properties, use the collection select filter. For example: by 'status' or 'type'."* — a near-literal match to this surface's two named filter dimensions (status, region). The Collection select filter component page (`https://cloudscape.design/components/collection-select-filter/index.html.md`) confirms it composes directly with a text filter for exactly this combined "search by name, narrow by property" shape: *"The collection is filtered as soon as the user selects a value from a select filter or enters text into the accompanying text filter."* The Property filter component page states the boundary the other direction: *"If only two are required, use the collection select filter instead"* of property filter — reinforcing that with exactly two properties (status, region), collection select filter, not a bespoke absence of any control, is the documented fit.
  - **Authority category:** `named pattern` (Filtering patterns page), corroborated by `component guidance` (Collection select filter and Property filter component pages).
- **Evidence mode:** `VERBATIM`
- **Authority strength:** `RECOMMENDED` (phrased as "use X" guidance keyed to property count, not a "don't ever" prohibition against the current TextFilter-only state; TextFilter itself remains correctly used for the name-search half of the task).
- **Applicability argument:** (1) Task match: the stated task explicitly names both a free-text need (queue name) and a fixed-property need (status, region) — this is exactly the two-part shape the Filtering patterns page addresses by name. (2) Same problem solved: nothing here invents a new goal — the surface's own comment already claims this filtering capability; the finding is that the component chosen to serve it (none, for the property half) doesn't match the documented one. (3) Preserves task: adding a collection select filter for status/region changes no data model and no other behavior. (4) Materiality: status and region are exactly 2 low-cardinality properties on every record — the precise case the docs single out by name ("status," "type") for collection select filter, distinct from property filter (reserved for >2 properties or multi-value-per-property needs, per the Property filter page) and distinct from stretching `TextFilter` to informally substring-match a typed status/region string, which is undiscoverable and unlisted in the UI.
- **Current expression:** A single `TextFilter` bound to `useCollection`'s free-text filtering only; no UI exists for status or region narrowing at all.
- **Native expression:** `TextFilter` retained for name search, paired with a `CollectionSelectFilter` (or an equivalent `useCollection`/`collection-hooks` property-filtering config) for `status` and `region`, per the documented "select filter... enters text into the accompanying text filter" combined composition. The exact prop wiring is not independently cited and is a reasonable implementation detail, not a re-derived authority claim.
- **Why it matters:** The task as the surface itself describes it is presently unimplementable through discoverable UI for its property-filtering half — an operator cannot narrow to "backlogged" or "us-west-2" without literally typing that value into a name-search box and hoping it substring-matches, which is both undocumented behavior and not what Cloudscape's own filtering-pattern guidance recommends for this exact two-property shape.
- **Boundary check:** This is a component-selection judgment against the design system's own named filtering-pattern guidance for a task the surface already claims to support, not a "the feature is missing, add it" implementation note and not generic UX advice — the citation is specific to property count and property type, matching this surface's exact fields.

## Suppressed (low materiality or weak applicability)

- Property filter (instead of collection select filter) for status/region — considered and suppressed: the Property filter page itself states collection select filter is the documented fit when "only two [properties] are required," which is exactly this case (status, region); recommending property filter here would be availability, not applicability, reasoning.
- `StatusIndicator` type mapping (`healthy` → `success`, `backlogged` → `warning`) — considered and suppressed: this is a semantic/color judgment about status severity, not a component-selection or composition question; `StatusIndicator` is already the correct, documented component for this job.
- `ContentLayout` as the page wrapper around the collection — considered and suppressed: this matches documented full-page collection usage regardless of whether the collection itself is `Cards` or `Table`; no material difference to flag.

## Orientation notes

- `Header` usage (`variant="h1"`, `counter`, `description`) inside `ContentLayout` — correct, standard usage for a full-page collection header; no finding.
- `StatusIndicator` as the vehicle for the `status` field — correct, documented use of the component for compact resource-state display; no finding.
- `Pagination` paired with `useCollection`'s `paginationProps` — correct, standard composition; no finding.
- Split view (table/card + detail panel) was considered as a candidate composition and explicitly not recommended: nothing in this surface (no row/card click behavior, no selection-driven actions, no navigation) establishes a detail-inspection sub-task, so recommending it would be inventing intent the surface doesn't currently express — correctly withheld rather than guessed.

## What was not evaluated

Implementation correctness (React/TypeScript patterns, prop usage mechanics, accessibility implementation details, hard-coded values) and general UX/product judgment (information density, card sizing, color choices, whether 24 queues is the right page size at all) were not assessed — their absence here should not be read as "checked and fine."
