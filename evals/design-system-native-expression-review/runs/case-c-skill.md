# Design-System Native-Expression Review: WorkspaceDetails.tsx

**Design system:** Cloudscape (`@cloudscape-design/components`)

**Inferred user task:** View a single workspace's details on a details page: its own general configuration (name, owner, region, plan tier, created date, status), the full list of members and their roles, and a log of recent workspace activity — with page-level Edit/Delete actions available. The three groupings are organized as tabs (Overview, Members, Activity) under a breadcrumb + header shell.

**Packages / versions:** `@cloudscape-design/components` — declared range `^3.0.900`, locked and resolved to `3.0.900` (resolved via `scripts/resolve_versions.py` against the fixture's `package-lock.json`).

**Authority categories found in this corpus:** Component guidance (per-component pages), named task/product patterns (including a dedicated resource-management "details" pattern family: "Details page," "Details page with tabs," "Resource details," plus "Table view," "Card view," delete patterns, etc.), demos, and foundations. This corpus has a genuine pattern/composition tier, not just component pages — confirmed by inspecting the discovery index (`cloudscape-llms.txt`) as a table of contents and then fetching the linked pages themselves.

## Findings

### 1. Overview tab's workspace properties: Table (one synthetic row) inside a tab → Key-value pairs in an always-visible summary container

- **Type:** combined selection + composition
- **Materiality:** high
- **Confidence:** high
- **User task:** Viewing a single workspace's own general configuration (name, owner, region, plan, created date, status) — data the surface's own code comment describes as "relevant no matter which tab a user is currently looking at."
- **Repository evidence:** `WorkspaceDetails.tsx` lines 34–91. `ContentLayout`/`Header`/`BreadcrumbGroup` wrap a `Tabs` component whose first tab (`id: 'overview'`, `label: 'Overview'`) renders a `Table` given exactly one synthetic row (`items={[{}]}`, `trackBy={() => 'workspace-overview-row'}`) and six `columnDefinitions`, each `cell` callback ignoring its row argument and returning a fixed literal (`'eng-platform-prod'`, `'Priya Nair'`, `'us-east-1'`, `'Team'`, `'Jan 12, 2026'`) or a `StatusIndicator` for status. `ariaLabels.tableLabel` is literally `"Workspace general configuration"`. The code comment directly above the component (lines 30–33) states: *"A single workspace's details -- name, owner, region, plan tier, created date, and status are the workspace's own general configuration facts: stable, read-mostly, and relevant no matter which tab a user is currently looking at (Members or Activity). Tabs organize the rest."* The developer's own stated intent already matches Cloudscape's documented "always visible" summary-container semantics — the implementation just encodes that intent as a `Table` with one synthetic row, living inside a selectable tab.
- **Authority evidence:**
  - "Details page" pattern (`https://cloudscape.design/patterns/resource-management/details/details-page/index.html.md`), building block D, "Details summary container": *"Place the most relevant information about the resource in this container. To organize content, use key-value pairs."* Component-specific writing guidance for the same building block: *"For the details summary container, use this text: General configuration / [Resource type] settings."*
  - "Details page with tabs" pattern (`https://cloudscape.design/patterns/resource-management/details/details-page-with-tabs/index.html.md`), building block D, "Details summary container - optional": *"Follow the guidelines for details page ... For a details page with tabs, this section serves as a summary that is always visible when users switch between the tabs. Use it to display important information that applies to tasks in all the tabs."* Building block E, "Tabs," separately gives the kind of content that belongs *inside* tabs instead: *"Examples of content that can be grouped into sections in a single tab: logs, charts, and data visualization for monitoring, key-value pairs, and descriptions."*
  - Authority category: **named pattern** (two pages of the same "Resource details" pattern family — the tabs-variant page explicitly delegates to the base "Details page" page for this exact building block).
- **Evidence mode:** SYNTHESIS. The finding bridges two pages of the same documented pattern family, but the bridge is the pattern's own authored cross-reference ("Details page with tabs" building block D literally says "follow the guidelines for details page" for this exact block), not an independent inferential leap on my part. Each individual claim is independently well-supported by its own source: "use key-value pairs to organize this container's content" (VERBATIM from "Details page"), and "this container is always visible across tabs, distinct from tab content" (VERBATIM from "Details page with tabs").
- **Authority strength:** RECOMMENDED. Neither cited passage is phrased as an explicit "Don't … instead" prohibition (nothing forbids a `Table` here by name), so `REQUIRED` is not warranted. But both passages are direct, unambiguous building-block instructions inside Cloudscape's own named pattern for this exact page type ("use key-value pairs"; "this section serves as a summary that is always visible"), which is materially stronger than an unstated preference — hence `RECOMMENDED` rather than `OPTIONAL`/`INFERRED`. Per the skill's rule that a `SYNTHESIS` does not automatically inherit its parts' strength: I'm assigning `RECOMMENDED` here specifically because the two-source bridge is the pattern's own authored cross-reference rather than my own speculative combination, so the synthesis is exactly as reliable as its two constituent, independently-`RECOMMENDED` parts.
- **Applicability argument** (four-point test):
  1. *Task match, not superficial:* This is literally the same building block Cloudscape's pattern names ("Details summary container") holding the same kind of content — general, read-mostly resource properties (name, owner, region, plan, status) — further corroborated by the fixture's own `"Workspace general configuration"` aria-label and code comment, which independently describe the exact "relevant regardless of active tab" semantics the pattern documents for this container.
  2. *Current implementation solves the same problem:* Yes — a single, conceptually-always-relevant set of workspace properties, currently just misplaced (as a selectable tab, hidden whenever Members or Activity is active) and mis-componentized (`Table` instead of `KeyValuePairs`).
  3. *Preserves the same task:* Yes — moving this content to an always-visible summary container and rendering it with `KeyValuePairs` instead of `Table` changes neither the information shown nor the actions available; Members and Activity remain tabs exactly as now ("Tabs organize the rest," per the file's own comment).
  4. *Materiality:* Yes — the current expression actively defeats the file's own stated design intent: information described as "relevant no matter which tab" is, as implemented, visible only when the Overview tab happens to be selected — the opposite of "always visible." And a `Table` sized to one synthetic row with six wide text columns is a materially worse structural fit for label/value data than `KeyValuePairs`'s layout, which is purpose-built for exactly six-or-fewer named properties of one resource. An experienced Cloudscape implementer would restructure this on sight, not merely note it as an alternative.
- **Current expression:** A `Table` inside the "Overview" tab of a `Tabs` component, given exactly one synthetic row and six columns whose cells ignore their row argument and return fixed literals (or a `StatusIndicator`).
- **Native expression:** Move the general-configuration content out of `Tabs` and into a details summary `Container` (labelled "General configuration," per the pattern's own writing guidance) positioned so it stays visible regardless of the active tab; render its content with `KeyValuePairs` instead of `Table`; drop the "Overview" tab so `Tabs` organizes only "Members" and "Activity" (matching the file's own comment, "Tabs organize the rest").
- **Why it matters:** Two concrete, design-system-specific consequences. (a) `Table` is documented, on its own component page, as a collection component intended for comparing structured attributes across *multiple* items; its features (rectangular row/column layout, `trackBy`, selection semantics) are meaningless for a single synthetic row and a poor structural fit for label/value data — `KeyValuePairs` is Cloudscape's documented component for exactly that content shape. (b) Placing this content inside a tab contradicts both the pattern's documented behavior for this container ("always visible when users switch between the tabs") and the file's own stated intent: a user who switches to Members or Activity currently loses all visibility into workspace status, plan, and region, which the surface's own comment says should not happen.
- **Boundary check:** This is a component/composition alignment finding, not implementation correctness or general UX — it recommends a specific documented component substitution (`Table` → `KeyValuePairs`) plus a specific documented composition change (tab content → always-visible summary container), both grounded in Cloudscape's own named pattern for this exact page type, not a subjective usability complaint.

## Suppressed (low materiality or weak applicability)

- **Delete button has no wired behavior.** `<Button>Delete</Button>` (line 53) has no `onClick` or any observable delete flow. Whether it should route through Cloudscape's documented delete-confirmation patterns ("delete with simple confirmation" / "delete with additional confirmation") can't be judged from static markup with no delete behavior implemented at all — there is nothing to compare against a documented composition. Suppressed rather than guessed, per "Missing intent."
- **Activity tab's `List` of hardcoded log-entry strings.** Checked the `List` component's own guidance directly: its only stated "don't" concerns multi-column sortable data ("Don't use a list to display multiple columns of sortable data that users need to compare. Use a table instead."), which doesn't apply to single-line chronological entries. No named pattern in this corpus specifically addresses activity/audit logs, so there is no stronger authority pointing at an alternative. Suppressed as an already-defensible, correctly-used component choice, not a finding.
- **Breadcrumb depth.** Two levels (`Workspaces` → `eng-platform-prod`) versus the "Details page" pattern's three-level example (`[Service name] > [Resources type] > [Resource name/ID]`). Plausible the surrounding app has no separate "service" scope above "Workspaces," in which case two levels is a faithful adaptation. This bounded file alone can't establish whether a service tier exists elsewhere in the app; suppressed as low-materiality and unresolvable from this surface.

## Orientation notes

- **Members tab (`Table<Member>`, lines 96–107).** Correct, native use of `Table` for a genuine multi-item resource collection (three rows, `name`/`email`/`role`, `isRowHeader` on name, `trackBy="email"`, `empty` state) — matches `Table`'s documented purpose of comparing structured attributes across multiple items, consistent with Cloudscape's resource-management "Table view" pattern shape. No finding.
- **Outer page shell.** `ContentLayout` + `Header` (`variant="h1"`, `actions`) + `BreadcrumbGroup` + `Tabs` is the standard, documented composition for a Cloudscape "details page with tabs." No finding on the shell itself — only on what the Overview tab currently holds (finding #1, above).
- **`StatusIndicator` inside a table cell (line 83).** Matches the component's documented purpose (communicating a resource's state in a compact form embeddable in a card, table, list, or header view). Correct usage independent of the `Table`/`KeyValuePairs` finding above — `KeyValuePairs` values can embed `StatusIndicator` exactly the same way.
- **Header actions (lines 50–55).** `SpaceBetween direction="horizontal"` wrapping two `Button`s (Edit, Delete) inside `Header`'s `actions` slot is the standard, documented composition for page-level global actions on a details page. No finding.

## What was not evaluated

Implementation correctness — no `onClick`/handlers wired on the Edit/Delete `Button`s, hard-coded `MEMBERS`/`ACTIVITY` data, `StatusIndicator` prop usage, `ariaLabels` wording/i18n, `Table` column sizing, TypeScript generic usage on `Table<Member>` — and general UX/product judgment — whether Edit/Delete should require confirmation, whether Activity should support pagination/filtering, information density, or whether three groupings is the right split beyond what's cited in finding #1 — were not evaluated; their absence here should not be read as "checked and fine."
