# Design-System Native-Expression Review: ntfy web — Subscribe/Publish dialog surface

**Design system:** Material UI (`@mui/material`, plus `@mui/icons-material` for icon imports)

**Inferred user task:** This bounded surface is a pair of dialog-driven forms in a pub/sub notification client: (1) *subscribe to a topic*, with an optional reservation of exclusive write access to that topic and an optional alternate/self-hosted server, falling back to a login step if the topic requires auth; and (2) *compose and publish a notification message to a topic*, a single always-visible core (title/message/tags/priority) plus a long tail of optional decorations (click URL, email, phone call, delayed delivery, an attachment supplied either as a URL or an uploaded/dragged/pasted file) that are progressively revealed. `ReserveTopicSelect` is a reusable permission-level chooser used from the subscribe flow; `DialogFooter` is a shared footer combining a status/error line with the dialog's action buttons; `AttachmentIcon` renders a small file-type glyph in the attachment preview row; `EmojiPicker` is a searchable emoji-insertion popup opened from the tags field.

**Packages / versions:** `@mui/material` declared `^9.1.2`, locked/resolved `9.3.1`; `@mui/icons-material` declared `^9.1.1`, locked/resolved `9.3.1` (resolved from `package.json`/`package-lock.json` under `ntfy/web`).

**Authority categories found in this corpus:** Component guidance only. Each retrieved MUI page (Dialog, Alert, Popper, Popover, Select, Chip, Switch, ToggleButton, IconButton) documents what that one component is/does and, occasionally, an explicit built-in-behavior contrast with a sibling component (e.g. Popper vs. Popover). No separate task/pattern layer, composition guide, or named workflow ("form dialog pattern," "progressive disclosure pattern," etc.) exists in this corpus beyond a single "Form dialogs" example embedded in the Dialog page itself. No such tier was invented; findings below reason from component pages only, dropping to `SYNTHESIS`/`INFERRED` whenever a claim required bridging more than one page.

## Findings

### Finding 1: Shared `DialogFooter` status/error line bypasses `DialogContentText`'s documented container and duplicates `Alert`'s documented job by hand

- **Type:** combined selection + composition
- **Materiality:** medium
- **Confidence:** medium-high
- **User task:** Both dialogs need to report a brief, transient status/result message (validation error, login failure, upload-progress text, publish success/failure) next to the dialog's action buttons, without interrupting the rest of the open dialog.
- **Repository evidence:** `DialogFooter.jsx:1-29` renders `props.status` inside `<DialogContentText component="div" aria-live="polite" ...>` as a sibling of `<DialogActions>{props.children}</DialogActions>`, both children of a plain `<Box sx={{ display:"flex", flexDirection:"row", justifyContent:"space-between", ... }}>` — never nested inside a `<DialogContent>`. `SubscribeDialog.jsx:266,334` pass a plain translated error string as `status`. `PublishDialog.jsx:186-189` is the one place any severity is expressed: on a failed publish, `setStatus(<Typography sx={{ color: "error.main", maxWidth: "400px" }}>{e}</Typography>)` — hand-applying `color: "error.main"` to a bare `Typography`, which `DialogFooter` then wraps a second time in `DialogContentText`.
- **Authority evidence:** `https://mui.com/material-ui/react-dialog.md` — DialogContentText is documented as "a wrapper for text inside of `<DialogContent />`" (component guidance). `https://mui.com/material-ui/react-alert.md` — "Alerts display brief messages for the user without interrupting their use of the app," with a `severity` prop (`success`/`info`/`warning`/`error`) that ships "corresponding icon and color combinations" (component guidance).
- **Evidence mode:** SYNTHESIS — combines the Dialog page's statement of DialogContentText's intended container relationship with the Alert page's statement of Alert's purpose and built-in severity theming. Neither page discusses the other, and neither describes a dialog footer specifically; the bridge — that a dialog's transient status/error line is exactly the "brief message" job Alert exists for, and that DialogContentText's documented role ties it to DialogContent rather than a footer row — is this review's own inference, not a sentence either source contains.
- **Authority strength:** OPTIONAL. Neither cited page states a prohibition ("don't hand-color status text — use Alert instead," or "never render DialogContentText outside DialogContent"); per the skill's own rule, a synthesis defaults to `OPTIONAL`/`INFERRED` rather than borrowing `REQUIRED`/`RECOMMENDED` from its parts, and that default is not overridden here.
- **Applicability argument:** (1) Task match: PublishDialog's error/progress path is literally "brief, non-interrupting status information," matching Alert's stated purpose closely, not just superficially. (2) Same problem: the current code already solves this exact problem — it just does so by manually replicating one piece of what Alert ships by default (a severity color), via ad hoc `sx`, only in the one branch where a developer clearly felt the need for it. (3) Same task preserved: swapping in `Alert` (severity-driven) for the error/status slot keeps the same information in the same place for the same reason. (4) Materiality: `DialogFooter` is shared by every dialog and login step in this surface, so the current single free-text slot's inability to natively express severity is a repeated gap, not a one-off — but only one of the four call sites (the publish-failure path) ever needed and improvised a severity treatment, and the DialogContentText-outside-DialogContent structural point is a documented-role deviation rather than a broken behavior, which keeps this below `high`.
- **Current expression:** A single free-text `status` slot, rendered as `DialogContentText` outside `DialogContent`, with one call site hand-styling error color via `sx={{ color: "error.main" }}` on a `Typography`.
- **Native expression:** Route status/result messaging that needs severity (validation/login/publish errors, upload outcomes) through `Alert` with an explicit `severity`, and keep any purely-informational status text as `DialogContentText` living inside `DialogContent`. The exact footer layout (where an `Alert` should sit relative to `DialogActions`) is not itself documented anywhere retrieved, so that specific arrangement is left uncertain rather than prescribed with confidence.
- **Why it matters:** The current single-purpose free-text slot already had to be worked around once (the publish-failure branch) to express something `Alert` provides out of the box; every other caller of the same shared component still has no severity treatment at all for its error strings, which is the kind of inconsistency a shared, purpose-built severity component is meant to prevent.
- **Boundary check:** This is about which documented component (`Alert`, and `DialogContentText`'s documented container role) best expresses "a brief status/severity message next to a dialog's actions," not about whether the current `sx` usage is technically correct or a general judgment that the footer "looks plain."

### Finding 2: `EmojiPicker` hand-assembles `Popper` + `ClickAwayListener` + `Fade`, duplicating behavior `Popover` documents as its default

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium
- **User task:** An emoji-search-and-insert overlay, anchored to the tags row's emoji `IconButton` in `PublishDialog`, opened on click, dismissed by clicking outside it.
- **Repository evidence:** `EmojiPicker.jsx:3` imports `Popper`, `ClickAwayListener`, `Fade` from `@mui/material`. Lines 47-113 wire `<Popper open={open} anchorEl={props.anchorEl} placement="bottom-start" ... transition>`, whose render-prop child is `<ClickAwayListener onClickAway={props.onClose}>` wrapping `<Fade {...TransitionProps} timeout={350}>` around the search field and emoji grid. `PublishDialog.jsx:404-409` triggers it from a plain `DialogIconButton` and renders it in a `Suspense` boundary.
- **Authority evidence:** `https://mui.com/material-ui/react-popper.md` — "Clicking away does not hide the Popper component" (must be added via Click-Away Listener), and Popper "doesn't include built-in transition animations," supporting them only via external render-prop wiring (component guidance). `https://mui.com/material-ui/react-popover.md` — "Popover blocks scrolling and dismisses on click-away by default, unlike Popper," is "constructed on the Modal component," and "uses the Grow transition by default" (component guidance).
- **Evidence mode:** SYNTHESIS — bridges what the Popper page explicitly says Popper lacks (click-away dismissal, transitions) with what the Popover page explicitly says Popover ships by default (both of those, plus scroll blocking). Neither page mentions emoji pickers or discusses the other in the context of this task; the inference that Popover is therefore the closer documented fit for "an anchored overlay that should dismiss on outside click and animate" is this review's own bridge.
- **Authority strength:** OPTIONAL. No retrieved text says "don't hand-assemble Popper for this — use Popover." Popper is presented as a legitimate, documented lower-level primitive in its own right, and nothing prohibits composing it manually.
- **Applicability argument:** (1) Task match: the picker needs exactly the two behaviors Popover ships by default and Popper explicitly does not — click-away dismissal and an open/close transition. (2) Same problem: the current code solves that same problem, just by wiring two extra components (`ClickAwayListener`, `Fade`) around `Popper` instead of using the composite that already bundles them. (3) Same task preserved: an anchored, dismissible, animated picker either way. (4) Materiality caveat, weighed honestly: Popover also blocks background scrolling by default because it's Modal-based, and the picker here opens from inside an already-open `Dialog` — avoiding a second scroll lock is a real, defensible reason an experienced implementer might deliberately choose `Popper` over `Popover` for this specific nested case, which keeps this below `high` and short of a clear-cut violation.
- **Current expression:** `Popper` + `ClickAwayListener` + `Fade` individually composed by hand in `EmojiPicker.jsx`.
- **Native expression:** `Popover`, anchored the same way, would fold click-away dismissal and transition into the component itself — stated as a supported but uncertain alternative, since the docs don't resolve whether Popover's default scroll-blocking is wanted for a picker nested inside an already-open dialog.
- **Why it matters:** the code independently re-derives, field by field, precisely the two behaviors the Popover page names as its differentiator from Popper — the kind of duplication a composite component exists to remove — and this is a second, independent occurrence of that same shape of gap within this bounded surface (distinct from Finding 1).
- **Boundary check:** This is about which documented overlay component (`Popper` as primitive vs. `Popover` as composite) best matches an anchored, dismiss-on-click-away picker — not whether the current `Popper` wiring works correctly, and not a general opinion that the picker "feels homemade."

## Suppressed (low materiality or weak applicability)

- **Priority `Select` (5-item, icon-illustrated, exclusive choice in `PublishDialog`) vs. `ToggleButtonGroup`:** `ToggleButtonGroup`'s own documented exclusive-selection example is icon-only and shaped very similarly to ntfy's priority picker, but `Select`'s own page states an equally applicable, undifferentiated purpose ("collecting user provided information from a list of options") with no stated preference between the two for small fixed sets. Suppressed as an equally-valid documented alternative, not a citable violation.
- **`Switch` used to reveal deferred form sections (`reserveTopicVisible`, `anotherServerVisible` in `SubscribeDialog.jsx`) vs. `Checkbox`:** MUI's own Switch page describes it only as toggling "a single setting" and points readers to an external, non-MUI article for the Switch-vs-Checkbox distinction — there is no MUI-owned normative statement to cite for this app's specific "reveal more of a not-yet-submitted form" use, so this was suppressed for lack of citable applicability rather than reported as `INFERRED`.
- **`EmojiDiv` (bespoke `styled("div")` grid buttons in `EmojiPicker.jsx`) vs. `IconButton`:** `IconButton`'s docs describe app-bar/toolbar and icon-toggle usage, not a dense search-result grid; no statement requires `IconButton` for this shape of UI, and the real gap here (button semantics/keyboard focus) reads as an app-owned accessibility-implementation concern, out of this skill's scope.
- **Chip-triggered progressive disclosure of `PublishDialog`'s optional fields (click/email/call/delay/attach) vs. `Accordion`/`Collapse`:** considered and rejected — `Accordion`'s stated purpose ("show and hide sections of related content") targets larger content blocks, not six independently-revealed single fields, and `Chip`'s own page takes no prescriptive stance on this usage ("trigger actions" fits a reveal-one-field job as well as anything documented). No stronger alternative surfaced.
- **`AttachmentBox`'s icon + editable filename + size + close row vs. `Chip`'s avatar/label/delete composition:** structurally close (avatar-like icon, label, delete action are all things `Chip` documents), but this row requires an inline-editable filename, which `Chip`'s label is not documented to support — suppressed as not applicable given that hard requirement.

## Orientation notes

- `SubscribeDialog`/`PublishDialog`'s field areas — `TextField`/`Autocomplete`/`Select` inside `DialogContent`, submission controls inside `DialogActions` via `DialogFooter` — match the Dialog page's own "Form dialogs" description ("Form dialogs allow users to fill out form fields within a dialog," with "TextField components within DialogContent and submit functionality via DialogActions buttons").
- `ReserveTopicSelect.jsx`'s `Select` + `MenuItem` + `ListItemIcon` + `ListItemText` composition for the permission-level chooser is a standard, idiomatic MUI menu-item-with-icon composition.
- `SubscribeDialog.jsx`'s `Autocomplete freeSolo` for the "use another server" base-URL field matches Autocomplete's documented purpose — "a normal text input enhanced by a panel of suggested options" — fitting a task of picking among known servers or typing a new one.
- Both dialogs' `fullScreen={useMediaQuery(theme.breakpoints.down("sm"))}` is idiomatic use of MUI's documented responsive media-query hook to make dialogs full-screen on small viewports.

## What was not evaluated

Implementation correctness — `slotProps` usage, prop/API currency for this resolved `9.3.1`, `aria-label`/`role="row"` mechanics on plain `div`s, keyboard/focus handling in the hand-rolled `EmojiDiv` grid, and other app-owned accessibility implementation details — was not audited. General UX/product judgment — whether ten-plus optional publish fields should be split across more or fewer dialogs, the overall drag-and-drop attachment flow, field ordering, or any other holistic usability question — was likewise not evaluated; its absence here should not be read as "checked and fine."
