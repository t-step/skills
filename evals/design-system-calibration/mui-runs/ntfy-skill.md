# MUI Native-Expression Review: ntfy Subscribe/Publish dialogs

**Inferred user task:** This bounded surface lets a user (1) subscribe to (and optionally reserve) an ntfy pub/sub topic on a chosen server, including an inline login step when the topic requires auth (`SubscribeDialog.jsx`), and (2) compose and publish a message to a topic — title, body, tags/emoji, priority, and optional click-URL/email/phone-call/attachment/delay metadata, with drag-and-drop or paste-to-attach a file (`PublishDialog.jsx`). `ReserveTopicSelect`, `DialogFooter`, `AttachmentIcon`, and `EmojiPicker` are small composed pieces supporting those two flows (permission-level picker, shared status/action footer, file-type icon, and an anchored emoji search panel).

**MUI packages / versions:** `@mui/material` declared `^9.1.2`, locked `9.3.1`; `@mui/icons-material` declared `^9.1.1`, locked `9.3.1` (both resolved cleanly from `package.json`/`package-lock.json` — no unresolved range).

## Findings

### Finding 1 — AttachmentBox hand-composes a file-item row where MUI's own Avatar and List docs demonstrate this exact shape

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** medium-high
- **User task:** Once a file is attached to a message (via drop, paste, or file picker), the user sees which file is attached (type icon + editable filename + size/error), can rename the filename inline, and can remove the attachment.
- **Repository evidence:** `PublishDialog.jsx` lines 822–870 (`AttachmentBox`): a `Box` (`display:flex, alignItems:center`) contains `AttachmentIcon` as the leading element, a nested `Box` with `ExpandingTextField` (editable filename, primary content) and `Typography` (size + optional error, secondary content), and a `DialogIconButton` wrapping a `Close` icon as the trailing remove action. `AttachmentIcon.jsx` (lines 34–54) renders a raw `<Box component="img">` (optionally `Link`-wrapped) selecting between five local SVGs by MIME type — no `Avatar`, `ListItemAvatar`, `ListItemText`, or `List` component is used anywhere in this composition.
- **MUI evidence (tier: component docs — `react-avatar.md` and `react-list.md`; no dedicated pattern page exists in this corpus, see note below):** `react-avatar.md`'s own worked examples include an icon-avatar wrapping a file-type icon (e.g. `InsertDriveFileIcon`) captioned "Q4 budget spreadsheet, last edited by Remy Sharp" — Avatar's documented scope explicitly covers representing a file, not just a person. `react-list.md`'s "Avatar with text and icon" example composes `ListItemAvatar` (wrapping an `Avatar`) + `ListItemText` (`primary`/`secondary`) + a `secondaryAction` `IconButton` (delete), and states the secondary action is "a separate target" from the row's main content. Authority strength: **RECOMMENDED** — these are the components' own worked compositions for this item shape, not a stated "Don't...instead" prohibition.
- **Applicability argument:** (1) task match is precise, not superficial: "one item, leading type icon, editable/primary text, secondary metadata text, trailing remove action" is structurally identical to the List doc's own "Avatar with text and icon + secondaryAction delete" example, and Avatar's own file-icon example uses the same "file with a caption" shape `AttachmentBox` expresses. (2) the current `Box`/`img`/`Typography`/`IconButton` assembly solves the identical problem the documented composition targets — leading icon, editable label, metadata, remove action. (3) swapping to `ListItemAvatar`/`Avatar`/`ListItemText`/`secondaryAction` preserves the exact same task: same icon, same editable filename, same size/error text, same remove button — no behavior change. (4) this clears the "would a fluent MUI implementer restructure" bar because the current code reconstructs, piece by piece, a shape MUI's own docs already assemble for the same content — right down to a raw `<img>` standing in for `Avatar`'s icon-avatar mode. **Tier honesty note:** MUI's `llms.txt` index has no separate "Patterns" section the way Cloudscape's does; this finding's compositional evidence comes from two component pages' own worked examples (Avatar's, List's), not from a task/pattern-level page. It is reported as a genuine composition-level observation, not inflated into "official pattern guidance."
- **Current expression:** Nested `Box`/`Typography`/custom `ExpandingTextField`/raw `<img>` (via `AttachmentIcon`) assembled by hand into a row.
- **Native expression:** `ListItemAvatar` (housing an `Avatar` with the type-appropriate icon or an image thumbnail) + `ListItemText` with the editable filename as `primary` and size/error as `secondary`, with the remove control as the item's `secondaryAction` — same information and interactions, expressed through the components MUI's own docs assemble for this shape.
- **Why it matters:** This is the single-item, leading-icon/primary-secondary-text/trailing-action shape MUI's Avatar and List docs are built to express. The hand-rolled version forgoes that composition's built-in structural conventions (`ListItemText`'s primary/secondary semantics, `secondaryAction`'s documented "separate target" behavior) for an equivalent-looking, independently reinvented `Box` layout — a real consistency/maintenance cost against the rest of an MUI app, not a cosmetic one.
- **Boundary check:** This is about which MUI components (`Avatar`/`ListItemAvatar`/`ListItemText`/`ListItem` `secondaryAction`) express "one file item with icon, editable text, metadata, and a remove action," not whether the current `Box`/`img`/`IconButton` markup is implemented correctly, and not a generic "this could look nicer" opinion — it's anchored to the components' own worked examples for this exact shape.

### Finding 2 — EmojiPicker hand-assembles Popper + ClickAwayListener + Fade to reproduce Popover's built-in behavior

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Clicking the emoji icon button in the Publish dialog opens a small, searchable emoji grid anchored to that button; picking an emoji appends it to the Tags field; clicking outside the panel (or otherwise) closes it.
- **Repository evidence:** `EmojiPicker.jsx` imports `Popper`, `ClickAwayListener`, `Fade` from `@mui/material` (line 3) and composes them directly: `<Popper open={open} anchorEl={props.anchorEl} placement="bottom-start" ... transition>` wrapping `<ClickAwayListener onClickAway={props.onClose}><Fade {...TransitionProps} timeout={350}>...</Fade></ClickAwayListener>` (lines 47–51). `PublishDialog.jsx` wires the anchor via `emojiPickerAnchorEl` state, set in `handleEmojiClick` (line 272–274) and cleared in `handleEmojiClose` (line 280–282).
- **MUI evidence (tier: component docs — `react-popper.md`, `react-popover.md`):** `react-popper.md`: "A Popper can be used to display some content on top of another... Clicking away does not hide the Popper component. If you need this behavior, you can use the Click-Away Listener... The open/close state of the popper can be animated with a render prop child and a transition component." `react-popover.md`: "A Popover can be used to display some content on top of another... Popover blocks scrolling and dismisses on click-away by default, unlike Popper... Popover uses Grow by default... built on top of the Modal component." Authority strength: **RECOMMENDED** (the docs frame Popper's lack of dismiss-on-click-away as an opt-in workaround via `ClickAwayListener`, not a prohibition on this composition).
- **Applicability argument:** (1) task match: an anchored floating content panel dismissed by clicking elsewhere is exactly Popover's stated purpose, not a superficial resemblance. (2) the current implementation solves the identical problem — Popper for positioning, `ClickAwayListener` for outside-click dismissal, `Fade` for the open/close transition are the same three responsibilities Popover already bundles. (3) switching to Popover preserves the same task: same trigger, same anchored panel, same dismiss behavior — no semantic change. (4) materiality: the developer independently reassembled the exact set of concerns (position, dismiss, transition) Popover exists to combine, which is the specific signal this skill's four-point test looks for rather than "MUI has a Popover so use it." One genuine counter-consideration keeps confidence at medium rather than high: Popover's default scroll-blocking may be undesirable for a lightweight picker already living inside a modal `Dialog`, and nothing in the retrieved docs says whether that's configurable away — so this isn't a clean drop-in substitution without further checking.
- **Current expression:** `Popper` + `ClickAwayListener` + `Fade` manually composed, each covering one job Popper's own docs describe as left to the developer.
- **Native expression:** Compose the same anchored panel with `Popover` (`anchorEl`/`open`/`onClose`), letting its built-in click-away dismissal and `Grow` transition replace the hand-wired `ClickAwayListener`/`Fade` — unless the scroll-block tradeoff noted above is a deliberate reason to keep `Popper` (not resolvable from the code alone; see "Suppressed" note it is *not* — this stayed a reported finding, not suppressed, because the core duplication is still real).
- **Why it matters:** Two mechanisms now do the job of one component in the same codebase; hand-rolling the click-away/transition behavior Popover ships by default is duplicated logic with its own drift risk (the 350ms `Fade` timeout and `ClickAwayListener` wiring must be kept in sync by hand instead of inherited from a single component's defaults).
- **Boundary check:** This is about which MUI overlay component was chosen for the job (Popper vs. Popover), not about whether the current Popper/ClickAwayListener/Fade code is implemented correctly (it is) — it reconstructs a documented behavior a different, more specific component already provides.

### Finding 3 — Upload progress is text-only where MUI's own Linear Progress examples are built around this exact scenario

- **Type:** component selection
- **Materiality:** medium
- **Confidence:** medium
- **User task:** While an attachment uploads as part of publishing a message, the user needs visible, quantified feedback on transfer progress.
- **Repository evidence:** `PublishDialog.jsx` lines 164–176 (`progressFn`) build a translated status string with loaded/total/percent and call `setStatus(...)` with it; that string is the only progress feedback and is rendered through `<DialogFooter status={status}>` (line 753) into a `DialogContentText` (`DialogFooter.jsx` lines 14–24) — plain text, no progress-bar element, no `aria-valuenow`-style semantics.
- **MUI evidence (tier: component docs — `react-progress.md`):** Determinate progress applies when you "can specify... display how long an operation will take," via `variant="determinate"` and a `value`; the Linear variant's own examples are built around "file uploads, buffered loading, and contextual progress display," and the docs show the percentage displayed "alongside the progress bar" rather than as a stand-alone substitute for it. Authority strength: **RECOMMENDED** (docs demonstrate pairing bar + text; they do not prohibit text-only feedback).
- **Applicability argument:** (1) task match is close, not superficial — "file upload with known loaded/total bytes" is the literal example MUI's Linear Progress documentation is built around. (2) the code already computes the exact `value` a determinate `LinearProgress` needs (`Math.round((loaded*100)/total)`) and discards it as a percentage baked into a string instead of feeding it to the component built to visualize it. (3) adding a `LinearProgress` alongside the existing text preserves the same task (informing the user of upload progress); it does not change what's being communicated. (4) materiality is real but not severe: MUI's docs treat the bar as the primary visual affordance with text as a supplement, so text-only is a narrower expression of the same concept than the design system's demonstrated composition — but because text-only remains a valid, accessible way to convey the same information, and nothing in the docs marks text-only as wrong, this stays medium rather than high.
- **Current expression:** A translated status string is the sole feedback mechanism, threaded through `DialogContentText`.
- **Native expression:** Pair the existing percent value with `<LinearProgress variant="determinate" value={percent} />` in the same footer area, keeping the text as the accessible label MUI's own examples show alongside the bar.
- **Why it matters:** The app already computes the value a purpose-built component is designed to visualize; surfacing only the text half of MUI's own documented pairing misses the component that most directly expresses "quantified progress of a running operation" as a design-system concept, not a cosmetic one.
- **Boundary check:** This is about which component expresses "upload progress," not whether the existing text/`aria-live` status implementation is correctly built (it is), and not a generic "add a progress bar, it'd look nicer" opinion divorced from a specific MUI citation.

## Suppressed (low materiality or weak applicability)

- **Chip-triggered optional-field reveal in `PublishDialog`** (clickable `Chip`s for click-URL/email/call/attach/delay/topic-reset that reveal a hidden `TextField`/`Select` row): considered as a possible component mismatch, but Chip's own documented purpose explicitly includes "trigger actions," which is exactly this usage — no applicability gap found, suppressed for weak evidence of a better fit.
- **`ExpandingTextField` (hand-rolled auto-width filename editor in `AttachmentBox`)**: considered as a bespoke UI concept; no MUI component targets "auto-width inline text edit" in the retrieved docs, so there is no applicable native alternative to recommend — suppressed under the anti-fundamentalism rule (no evidence of a more appropriate concept, not just no citation found).
- **`SubscribeDialog`'s conditional page swap (`SubscribePage` → `LoginPage` inside one `Dialog`, with a "Back" button) versus `Stepper`**: considered; Stepper documents numbered/wizard progress through known steps, while this is a conditional two-screen interruption (an auth branch, not a linear sequence) — same shape ("more than one screen in a dialog"), different problem. Fails point 1 of the four-point applicability test, suppressed.

## Orientation notes

- `Autocomplete` (`freeSolo`, base-URL field in `SubscribeDialog.jsx`) matches Autocomplete's documented purpose — "a normal text input enhanced by a panel of suggested options" — confirmed native.
- `Select` + `MenuItem` + `ListItemIcon` + `ListItemText` in `ReserveTopicSelect.jsx` (permission-level picker with icon+label options) is a standard MUI Select composition — confirmed native.
- `Switch` + `FormControlLabel` + `FormGroup` for the "reserve topic" / "use another server" toggles in `SubscribeDialog.jsx` is straightforward, documented Switch/FormGroup usage — confirmed native.
- `Dialog`/`DialogTitle`/`DialogContent`/`DialogContentText`/`DialogActions` are used per their documented roles throughout both dialogs; the shared custom `DialogFooter` wrapper (status text + `DialogActions` in one flex row) doesn't contradict any Dialog-doc guidance, even though that exact combined-row layout isn't itself demonstrated on the Dialog page — no material finding either way, confirmed as at-worst-neutral.

## What was not evaluated

Implementation correctness — prop/API usage, `slotProps`/`inputProps` mechanics, hard-coded style values flagged by `inspect_surface.py` (hex color and px/em/rem literals in `SubscribeDialog.jsx` and `PublishDialog.jsx`), the raw `<input type="file">` native element standing in alongside MUI components, and a11y wiring details (e.g. the empty `<InputLabel />` on the Select fields) — and general UX/product judgment (form density, whether this many optional fields belong behind chip-reveals at all, whether the reserve-topic/another-server mutual exclusivity is good product design) are both out of this skill's scope and were not assessed here.
