# Material UI Native-Expression Review: Route ETA → Stop Detail flow (hk-independent-bus-eta)

**Inferred user task:** A transit rider looks up a bus route, scrolls a per-stop list to see live ETAs for each stop along that route (optionally centered on their geolocation), expands a stop to see its arrival times and fares, and can drill into a fuller stop detail (all routes serving that stop, walking directions, map location, bookmarking) either inline via a dialog or by navigating to a dedicated stop page. Riders can also bookmark stops for quick return access from a separate bookmarked-stops tab.

**MUI packages / versions:** `@mui/material` and `@mui/icons-material`, declared `^5.15.11`, resolved via `yarn.lock` to locked version `5.15.11` for both (`resolve_versions.py`, root `hk-independent-bus-eta/package.json` + `yarn.lock`). This is a fully resolved exact version, not a semver range, so "docs may not fully apply" is a smaller concern than the unresolved-range case — but the authority corpus fetched for this review is served at `mui.com/material-ui/*.md`, which documents MUI's current live major (the discovery index's own Migration section lists upgrade guides through v9), a materially newer major than the installed v5.15. Component *purpose/semantics* text (what Alert, Accordion, App Bar, List, Dialog are documented to be "for") is the kind of guidance that tends to survive across majors, and is what every finding below relies on — but any prop/API-shape detail would need separate confirmation against v5 docs specifically, which this review did not do (out of scope anyway — see "What was not evaluated").

## Findings

### Finding 1: Bespoke clickable notice box duplicates Alert's documented job

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Inform the rider, without blocking their current task, that the route data may be stale, and give them a one-tap way to refresh it.
- **Repository evidence:** `src/components/route-eta/RouteUpdateNotice.tsx:29-33` — a plain `Box` (styled via `sx`: border, padding, `cursor: pointer`) wrapping a `Typography` ("⁉️ {db-renew-text}"), with `onClick={renewDb}` on the `Box` itself. Conditionally rendered above the route content in `RouteEtaPage.tsx:235`.
- **MUI evidence:** `react-alert.md` (component docs, tier 1): "The Alert component is designed to 'display brief messages for the user without interrupting their use of the app.'" It documents an `action` prop ("any element ... positioned after the message") for exactly the kind of "here's an action to take" affordance this notice needs, plus `severity` (`info`/`warning`/etc.) for visual weight, and explicitly distinguishes Alert from Dialog: alerts "should not be confused with alert dialogs... which are intended to interrupt the user."
- **Applicability argument:** (1) The observed task — a brief, non-blocking, dismissable/actionable status message about data staleness — is exactly Alert's stated purpose, not a superficial shape match; there's no different underlying problem being solved. (2) The current bespoke `Box`+`Typography`+`onClick` already solves that same problem, just without the componentized semantics (no `role`, no severity-driven color/icon, the whole message area is a single ambiguous click target rather than a distinct action). (3) Swapping to `Alert` with `severity="warning"` (or `info`) and an `action` button preserves the exact same task — same message, same "click to renew" behavior — no product change. (4) This clears the "would a fluent implementer restructure it" bar: it's not just a nicer-looking alternative, the current markup lacks the severity-driven visual language and accessible semantics that the rest of an MUI app would use for the same class of message, so it reads as inconsistent with how MUI apps typically express "renew stale data" banners.
- **Current expression:** Hand-styled `Box` (manual border/padding via `sx`) containing a `Typography`, whole box clickable to trigger `renewDb`.
- **Native expression:** `Alert` with an appropriate `severity` and an `action` (e.g., a button/icon labeled "renew") for `renewDb`, rather than a whole-box click target.
- **Why it matters:** The current implementation has no severity-driven visual language (color/icon) tying it to the rest of an MUI app's notification vocabulary, and makes the entire notice a single ambiguous click target instead of a clearly labeled action — a documented, purpose-built component exists for exactly this "brief, non-interrupting message with an optional action" job and the current code re-solves the same problem from scratch.
- **Boundary check:** This is about which MUI concept expresses "non-blocking status message with an action," not about how the existing `Box` markup is styled or coded — it's a component-selection question, not an implementation-correctness or generic-UX critique.

### Finding 2: Route-screen header built from Paper+Divider where App Bar's stated purpose matches — but global chrome is unverified

- **Type:** intent-dependent
- **Materiality:** n/a (intent-dependent; not scored until resolved)
- **Confidence:** medium (on the observation), low (on which native expression is actually correct, pending the missing evidence below)
- **User task:** Show the rider the current route's identity (number, destination) and route-scoped actions (reverse direction, star/favorite, view timetable) at the top of the route screen.
- **Repository evidence:** `src/components/route-eta/RouteHeader.tsx:26-43` — a `Paper` (`elevation={0}`, transparent background) laid out with flex `Box`es containing `ReverseButton`, a `RouteNo` + `RouteStarButton` row, a caption `Typography`, a vertical `Divider`, and `TimetableButton`. Rendered as the first visible element of `RouteEtaPage.tsx:234`, i.e., functioning as the route screen's topmost per-screen header.
- **MUI evidence:** `react-app-bar.md` (component docs, tier 1): "The App Bar displays information and actions relating to the current screen" and "provides content and actions related to the current screen. It's used for branding, screen titles, navigation, and actions," typically composed with `Toolbar` as its content container.
- **Applicability argument:** The documented purpose of App Bar ("information and actions relating to the current screen") is close to a word-for-word match for what `RouteHeader` does (route identity + route-scoped actions, positioned as the screen's top element). That satisfies points 1–3 of the four-point applicability test reasonably well — same problem, same task preserved by an `AppBar`/`Toolbar` swap. Point 4 (would a fluent implementer actually restructure this) is where this stays unresolved: whether `AppBar` is the right call depends on information outside this bounded surface — specifically, whether the app already has a global/root `AppBar` elsewhere in its shell. If it does, a second App-Bar-semantic element nested inside page content would collide with that global chrome (duplicate "app bar" landmarks, elevation/position conflicts) and the current `Paper`-based *section* header would in fact be the more correct choice precisely because it's *not* claiming to be the app's primary app bar. If it doesn't, `RouteHeader` is effectively serving as this screen's app bar and the purpose-built component is being bypassed for a bespoke composition.
- **Current expression:** `Paper` + manual flex `Box` layout + `Divider` for a route-scoped title/actions bar.
- **Native expression:** Not asserted with confidence — plausibly `AppBar`/`Toolbar` (with `position="static"` or similar, to avoid conflicting with any existing global bar) if no global App Bar already exists for this app shell; otherwise the current `Paper` composition is likely already the right call specifically *because* it avoids that collision.
- **Why it matters:** Named only conditionally — if no global App Bar exists, the app is missing the componentized "screen-level actions bar" vocabulary AppBar/Toolbar was built for; if one does exist, no material issue.
- **Boundary check:** This is a component-selection question, not general UX — but per the skill's "Missing intent" guidance, the deciding evidence (does a global `AppBar` already exist elsewhere in the app's shell, outside the 7-file/one-hop bounded surface reviewed here?) is not available from the reviewed surface, so it's reported as `intent-dependent` rather than guessed.

## Suppressed (low materiality or weak applicability)

- Fare text in `StopAccordion.tsx` (`AccordionSummary` secondary line, full-width-space-separated "車費/假日車費/樂悠車費" values) as a candidate for MUI `Chip` (`react-chip.md`'s "Chips are compact elements that represent an input, attribute, or action" is a plausible semantic fit for per-fare-type values) — suppressed: no documented normative signal that fare figures specifically should be chips rather than text, and Typography is a fully valid way to present this data; would be aesthetic preference dressed as a citation.
- `Accordion` itself as the per-stop container (`StopAccordionList.tsx`/`StopAccordion.tsx`) as a candidate to replace with `List`/`ListItemButton` — checked and cleared: Accordion's documented purpose ("show and hide sections of related content on a page") is a genuine match for what's happening (each stop's live-ETA content is shown/hidden per stop), and the controlled single-open behavior already follows MUI's own documented pattern (see Orientation notes). No applicability gap to report.
- `StopDialog.tsx`'s title-row icon cluster (bookmark, directions, map, "open full page," close — 5 `IconButton`s) as a candidate for `ButtonGroup`/`SpeedDial` — suppressed: these are independent, non-mutually-exclusive actions rather than a set of grouped/exclusive choices or a single FAB's fanned-out sub-actions, so `IconButton` row is the semantically correct choice, not a violation.

## Orientation notes

- `StopAccordion`/`StopAccordionList` single-open-at-a-time behavior (driven by `stopIdx` from the parent, `expanded={stopIdx === idx}`) matches MUI's own documented controlled-accordion pattern: "Use the `expanded` prop with React's `useState` hook to allow only one Accordion item to be expanded at a time" (`react-accordion.md`). Already native.
- `Snackbar` in `StopAccordionList.tsx` for the "copied to clipboard" confirmation after a share action matches its documented purpose ("used for brief notifications of processes that have been or will be performed," `react-snackbar.md`). Already native.
- `Dialog` in `StopDialog.tsx` for the expanded stop-detail view (multiple routes, directions, map, bookmark, navigate) matches Dialog's documented purpose of surfacing more substantial task-related content than a brief message would carry (`react-dialog.md`: "Dialogs inform users about a task and can contain critical information..."). Already native; the component choice itself is correct even though the fixed `sx` sizing used to approximate a full-screen presentation was not evaluated (see below).
- The independent icon actions in `StopAccordion.tsx` (alarm toggle, info, pin, share, star — each an `IconButton` with distinct `aria-label`/`aria-pressed`) are individually addressable, non-exclusive actions, which is the correct job for `IconButton`, not `ToggleButtonGroup` or `ButtonGroup`. Already native.

## What was not evaluated

- **Implementation correctness**, named but not judged: `StopDialog.tsx`'s `sx` overrides (`marginTop: "90px"`, `height: "calc(100vh - 100px)"`, `width: "100%"`) approximate a full-screen dialog presentation via hard-coded style values rather than MUI's documented `fullScreen` prop/responsive pattern — this is a props/hard-coded-style-value question, not a component-selection question (Dialog is already the right component here), so it's out of this skill's scope and not reported as a finding. Also out of scope: aria mechanics already present on `IconButton`s (`aria-label`, `aria-pressed`), deprecated-prop usage, and any other API-shape correctness questions.
- **General UX/product judgment**, not evaluated: information density of `StopAccordion`'s action rail, whether a modal `Dialog` and a separate full-page route (`StopEtaListPage.tsx`) both rendering near-identical stop content is confusing to navigate, whether bookmark ("star"/collection) and bookmark ("stop" save) are two UI concepts riders can tell apart, or any other usability/navigation-architecture judgment. Any of these could imply a different navigation structure, which would be a product decision outside this skill's remit, not a component/pattern alignment finding.
- **Out of bounded surface, not read:** `StopTabbar` and `SwipeableStopList` (imported by `BookmarkedStopPage.tsx`) were not opened — their names suggest possible overlap with MUI `Tabs`/swipeable-view patterns, but making that claim without reading them would be exactly the kind of unverified assertion this review avoids. `AppContext.tsx`/`DbContext.tsx` were noted only as existing context providers, not read for implementation.
