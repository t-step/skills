# Material UI Native-Expression Review: Checkmate — Incidents page

**Inferred user task:** This page lets a team monitor and manage incidents (downtime/outage events) detected across their monitors: view a live count/summary of active incidents, filter and page through active and resolved incidents (by monitor and resolution type, with a separate time-range control for resolved history), inspect a single incident's full detail record, and resolve an active incident (manually, with an optional comment) — all without leaving the list context.

**MUI packages / versions:** `@mui/material` resolved to exact version `7.3.7` (locked in `package-lock.json`, matches the declared range in `package.json`). `@mui/icons-material` was requested as a package prefix but has **zero imports** anywhere in the bounded surface — all icon glyphs in this surface come from `lucide-react` instead (`CircleCheck`, `TriangleAlert`, `Bell`, `Wrench`, `Globe`, `ChevronDown`, `Settings`), routed through a shared `Icon` wrapper. This is an icon-asset/branding choice, not a component/pattern concept, so it is noted here rather than treated as a finding. Separately: `@mui/lab` is declared in the repo's `package.json` but is **not imported anywhere in this bounded surface or its directly-composed wrapper files** (confirmed by grep over the 8 files plus the `design-elements`/`inputs`/`actions-menu` wrapper layer they invoke) — it is out of scope for this run regardless, both because it's absent here and because it falls outside this round's frozen `@mui/material` authority snapshot.

## Findings

### 1. Hand-rolled colored "attribute" labels where a Chip is the documented purpose-built component for exactly this job

- **Finding:** The surface represents incident status (active/resolved) and resolution type (manual/automatic) — both compact, categorical "attribute" values — via bespoke, hand-styled primitives (a custom pill built from a bordered `Box` + a manually-colored dot + `Typography`, and in one place just color-tinted `Typography` text) rather than MUI's `Chip` component, whose documented purpose is precisely this job.
- **Type:** `component selection`
- **Materiality:** `high` — the same conceptual job (compact colored attribute display) recurs at least four times across the bounded surface using two different bespoke implementations, not a one-off.
- **Confidence:** `high`
- **User task:** See above — specifically the sub-task of letting a user scan a table/detail view and immediately read an incident's status or resolution category at a glance.
- **Repository evidence:**
  - `IncidentTable.tsx:101-109` — status column renders `<ValueLabel value={isActive ? "negative" : "positive"} text={...} />` for every row.
  - `IncidentTable.tsx:134-146` — resolutionType column renders a plain `<Typography color={theme.palette.warning.main | success.main}>` with no pill/border at all, for the same class of categorical data.
  - `CardDetails.tsx:68-76` — the details dialog's "Status" field reuses the same `ValueLabel`.
  - `CardSummary.tsx:160-164` — the "Latest Incidents" summary card reuses `ValueLabel` again for each listed incident's status.
  - `ValueLabel` itself (defined in the shared `Components/design-elements/StatusLabel.tsx`, outside the 8 bounded files but invoked repeatedly from within them) is implemented as: a `BaseBox` (a styled `@mui/material/Box`) with manual padding/border/color, containing a manually-drawn 7px circular `Box` as a status dot, plus `Typography` for the label — i.e., a from-scratch reimplementation of a colored, iconed, compact label.
- **MUI evidence (component page, `RECOMMENDED` strength):** `react-chip.md` states Chip's purpose as *"Chips are compact elements that represent an input, attribute, or action"*, and documents a `color` prop accepting theme palette values including `'error'` and `'success'` specifically to *"convey different states or categories,"* plus an `icon` prop for a leading visual marker. This is not a generic "MUI has a component for labels" observation — the doc's own purpose statement is worded as "attribute," which is exactly the semantic category (status, resolution type) this surface is displaying.
- **Applicability argument:** (1) The observed task — showing a small set of mutually-exclusive categorical values (active/resolved; manual/automatic) as a compact, colored, at-a-glance label — matches Chip's stated problem, not just its shape; a Chip is not being proposed for prose or for an action, it's being proposed for exactly the "attribute" case the docs name. (2) The current `ValueLabel`/colored-`Typography` implementations solve the identical problem today (a colored compact label conveying state). (3) Swapping to `Chip color="success"|"error"` (with `icon` for the current dot) preserves the same information and the same task; nothing about the incident-management flow changes. (4) This clears the "would an experienced practitioner restructure it" bar because the current code isn't merely a valid alternative styling of a label — it manually reimplements a themed color mapping, a leading marker, and compact-pill layout that `Chip` provides as first-class, documented props, and it does so inconsistently within the same table (a bordered pill in one column, bare colored text in the adjacent column) for the same class of data.
- **Current expression:** A custom `BaseBox`-based pill with a hand-drawn colored dot (for status), and separately, unstyled color-tinted `Typography` with no container at all (for resolution type) — two different bespoke treatments of the same conceptual "attribute label" job within one table.
- **Native expression:** `Chip` with `color="success"|"error"|"warning"` mapped from the same status/resolutionType values, optionally using the `icon` prop in place of the hand-drawn dot, applied consistently to both the status and resolutionType columns/fields.
- **Why it matters:** Beyond the general case for using the purpose-built primitive, this is a documented, theme-driven `color` API doing work the surface currently reimplements by hand (manual `theme.palette[palette].main` lookups duplicated across three files), and the surface is internally inconsistent about which of two hand-rolled treatments to use for the same category of data (status vs. resolutionType), which a single shared `Chip` usage would resolve as a side effect.
- **Boundary check:** This is about which MUI concept was chosen for the "show a compact categorical attribute" job, not about how `ValueLabel` is coded (that's implementation) and not a general "this could look nicer" aesthetic complaint — the recommendation is grounded in Chip's own stated purpose matching this exact semantic category.

## Suppressed (low materiality or weak applicability)

- **Monitor filter `Select` vs. `Autocomplete`** (`ControlsIncidentFilter.tsx:40-56`) — `react-select.md`/`react-autocomplete.md` say Autocomplete is for "advanced" cases (combobox/search/async/multiselect) and Select is fine for simple predefined-list selection; the docs state no option-count threshold. The bounded surface gives no evidence the monitor list is large or that search is needed (monitor count is dynamic/unknown from this surface alone) — this would be "MUI has a more advanced component" with no applicability evidence behind it, exactly the case the anti-fundamentalism rule warns against. Suppressed rather than reported.
- **`BaseBox`-as-card (`SummaryCard` in `CardSummary.tsx`, section groupings in `CardDetails.tsx`) vs. MUI `Card`** — Card's stated purpose ("surfaces that display content...on a single topic") plausibly matches the three summary panels and the detail-dialog sections. But there is no documented "don't use Box/Paper for this, use Card instead" pairing (Paper's own guidance only says prefer Box/Container for a *generic* container, which doesn't resolve this case either way), and `BaseBox` is an established, app-wide bordered-surface convention reused far beyond this one page — recommending a one-page swap to `Card` would trade description-level similarity for cross-app inconsistency. Suppressed.
- **`CardDetails.tsx`'s hand-rolled two-column `Grid` key/value layout** (repeated `Grid size={2}`/`size={10}` "label" + "value" cell pairs, `CardDetails.tsx:59-202`) vs. MUI `List`/`ListItemText` (`primary`/`secondary`) — `react-list.md` documents `ListItemText` primary/secondary text for label/value-shaped content, but nothing in the retrieved guidance states a preference for List over a Grid-based field layout for this kind of dense, multi-row record inspector; this reads as a layout-taste question with no citable normative pull either way. Suppressed.

## Orientation notes

- **Two paginated `Table` instances (active incidents, resolved incidents)** built on wrapped `Table`/`TableContainer`/`TablePagination` (confirmed in the shared `design-elements/Table.tsx` these components invoke) match `react-table.md`'s stated purpose and its explicit steer that `DataGrid` is for cases needing built-in large-dataset handling — this surface does externally-driven filtering and server-side pagination instead, so plain `Table` is the better-fitting choice, and the app's `DataGrid`-class package (`@mui/x-*`) is correctly absent from this surface.
- **Row-level actions via a `Menu` opened from an `IconButton`** (`ActionsMenu`, wired from `IncidentTable.tsx:171`) matches `react-menu.md`'s documented icon-button-triggered action-menu pattern (its own examples pair `IconButton` triggers with `Menu`).
- **Resolution confirmation `Dialog`** (`DialogResolution.tsx`) matches `react-dialog.md`'s confirmation-dialog guidance: explicit Cancel/Confirm actions, a single input, no ambiguous copy.
- **Read-only incident-detail `Dialog`** (`DialogIncidentDetails.tsx`) matches Dialog's stated purpose of informing users about a task and presenting critical information without leaving context.
- **`Select` for the fixed 3-value resolution-type filter** (`ControlsIncidentFilter.tsx:57-72`) is an uncontested, correct fit — a small, static option set with no search/multiselect/async need.

## What was not evaluated

Implementation correctness — deprecated props, exact API usage inside the wrapped `design-elements`/`inputs` components, hard-coded style/token values (the `inspect_surface.py` run reported none in the 8 bounded files, but this skill does not certify implementation mechanics either way), and accessibility mechanics on already-chosen components. General UX/product judgment — table density, whether a Dialog-based detail view (vs. a dedicated, addressable incident page/route) is the right information architecture, and overall visual hierarchy — none of this was assessed; its absence should not read as "checked and fine." The `@mui/lab` package declared elsewhere in the repository was checked and confirmed unused in this bounded surface, so it was not otherwise evaluated.
