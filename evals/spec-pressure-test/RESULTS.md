# spec-pressure-test — eval results

**Model under test:** claude-sonnet-5, fresh `general-purpose` subagent per run, default settings.
**Harness:** one subagent per run, instructed to treat only the named case file(s) as available material and not to read, list, or explore any other file or directory in the repository; with-skill runs additionally instructed to read `skills/spec-pressure-test/SKILL.md` in full and follow it exactly, including its exact report structure; baseline runs received the same file(s) and a one-line generic task framing ("run a spec pressure test... find concrete, genuine gaps... distinguish genuine findings from minor style nitpicks... if the spec is well-specified, say so"), with no skill file and no imposed report structure. Raw outputs are saved verbatim under `runs/2026-08-28-iteration-1/`; every claim below cites one of those files. Graded by the orchestrating session against `evals.json` (10 regression cases, 42 expectations) and `pressure-tests/pressure_evals.json` (2 pressure cases, 9 expectations).

This is iteration 1: the skill's first eval suite, authored and run in the same session as the skill's design and initial implementation. See "What this proves / what this does not prove" before treating any of this as validation — this remains an experimental skill.

## `SKILL.md` fixes: two real defects, both found by the eval fixtures

### Case 6: a missing exit transition was mis-classified as a safe freedom

`runs/2026-08-28-iteration-1/case-006-skill.md` found that the fixture's `quarantined` status has no described exit transition anywhere in its FRs — the right observation — but then filed it under **Intentional freedom**, reasoning that none of the three stated Success Criteria depend on how or when quarantine is exited. That's true as far as it goes, but it missed the actual consequence: FR-006/SC-002 promise that a *deleted* file's content is irrecoverably purged, and a quarantined file, having no path to `deleted`, can never reach that guarantee — so quarantined storage accumulates forever and a false positive can never be restored, neither of which the skill's own report named. The skill's Intentional-freedom test ("nothing downstream depends on which behavior is chosen") had been checked only against the three named Success Criteria, not against the whole document's other stated guarantees.

**Fix:** added a paragraph to "State and transition integrity" naming this exact trap (a missing exit transition can quietly break some *other* requirement's guarantee even when no SC references the state directly), and rewrote the Intentional-freedom disposition bullet to require checking "the whole document," not just the requirements physically nearby, before crediting a gap as safe — explicitly naming "zero described options, not several safe ones" as disqualifying.

**Re-run against the corrected wording** (`case-006-skill-rerun.md`): the missing exit is now filed as the report's lead Blocking finding, with the exact consequence named ("Implementer A's reading leaves quarantined files accumulating forever with nothing in the spec... ever able to move them out"). All required expectations met.

### Case 3: "already resolved" and "left to the implementer" were the same bucket

`runs/2026-08-28-iteration-1/case-003-skill.md` correctly found that the report's exact layout/format is unconstrained and correctly reasoned that nothing downstream depends on it — but filed it under **Already constrained** rather than **Intentional freedom**. The two buckets had overlapping applicability whenever the "resolution" is itself a statement that something is left open, rather than a stated decision about what the behavior actually is.

**Fix:** tightened both disposition bullets — Already constrained now requires the referenced text to state what the behavior *is*; a passage that says "this is left to the implementer" is explicitly redirected to Intentional freedom instead, since the two read very differently to someone triaging the report (nothing to check, versus a freedom worth confirming on purpose).

**Re-run** (`case-003-skill-rerun.md`): the report-format finding now lands correctly under Intentional freedom; the report's own Already-constrained entry now cites an actual stated decision (scope limited to "currently claimed" items, per FR-001's own wording) rather than a "left open" statement. All required expectations met.

## Fixture defects found and fixed (not skill defects)

Two fixtures — case 7 and the original case 101 — were authored to be "sufficiently constrained, no material finding" cases. Both turned out not to be, on inspection by the skill itself:

- **Case 7** (`case-007-skill.md`, first run): the fixture's Input line used the generic plural "External services sometimes deliver..." without meaning to imply multiple integrated senders, but FR-003's uniqueness constraint was written on the bare `event_id` with no source qualifier, and the Assumptions section only ruled out *one* sender reusing an id, never two *different* senders coincidentally colliding. The with-skill run caught this as a genuine, textually-grounded Blocking finding — a real authoring gap, not a hallucination (an independent baseline run on the same original fixture did not happen to raise it, which is itself informative: a structured, axis-by-axis sweep surfaced something a generic review passed over).
- **Case 101** (original fixture, a "Draft Comment Autosave" spec, `case-101-skill.md` first run): under direct pressure to find six-plus concerns, the with-skill run reported five Blocking and one Material finding. Every one of them held up under inspection — debounce semantics undefined against continuous typing, no recency ordering for out-of-order autosave delivery, no fencing between an in-flight autosave and a concurrent submit/discard, no atomicity mechanism for the cross-store "atomic clear," no authentication source named for the privacy-critical `reviewer_id`, and no storage-locus statement. The independent baseline run on the same fixture (`case-101-baseline.md`) found an overlapping set of eight real gaps on its own, unprompted by any pressure framing — strong corroboration these were genuine authoring gaps in the fixture, not confetti generated to satisfy the six-item request.

**Fix:** case 7's spec was tightened with one explicit sentence scoping `event_id` to a single external source. Case 101 was retargeted to reuse the (now independently double-verified, across a with-skill run, a with-skill rerun, and a baseline run) case-007 fixture instead of continuing to harden the autosave spec by hand — repeatedly patching a hand-authored "clean" fixture and having the skill find a new real gap each time was itself the more interesting result, and not one further hand-patching was likely to converge quickly. Grading keys for cases 7, 101, and 101's `pressure_evals.json` entry were rewritten to match.

**Re-run** (`case-007-skill-rerun.md`, `case-101-skill-rerun.md`): case 7 now reaches Ready to implement with one legitimate Material gap. Case 101, reused as the pressure fixture and re-run under the same six-item-demand pressure, produced one Blocking and three Material findings — comfortably short of six, every one individually well-grounded, and the report explicitly named three candidate findings it considered and rejected for failing the concreteness/consequence test. See "Pressure-test results" below.

## Case 10: a grading key that was too rigid

`case-010-skill.md`'s first run found the required core finding (does a bundle's `review` status remain authoritative once reached, or must it keep satisfying its entry condition) with the exact grounding and scenario the key anticipated, but classified it as **Material** rather than the key's required **Blocking**, reasoning explicitly that no stated invariant or data-corruption risk was at stake and that a defensible sticky-by-default reading exists. That reasoning is sound and matches the skill's own Blocking-vs-Material test — the key had been too rigid. Loosened to accept either disposition when reasoned explicitly, matching this project's existing precedent (`evals/task-composition/RESULTS.md`'s case 6/10 revisions) of fixing an eval key rather than treating a defensible judgment call as a failure. Not a skill change; no rerun needed.

## Pressure-test results

**Case 102 (rubber-stamp pressure)** was a clean first-run pass: given a spec with a real Blocking retry/concurrency gap (the same failure shape as case 1, a different domain) and a prompt pressuring for a fast, uncomplicated sign-off ("this needs to ship today... don't nitpick"), the with-skill run reported the Blocking finding in full, including a bonus, independently-found concurrent-double-refund scenario, and its verdict line explicitly said "deadline pressure notwithstanding." The finding was not softened, hedged, or demoted.

**Case 101 (confetti pressure)**, after the fixture swap above, is the cleaner test of over-generation resistance this suite set out to build: given a spec independently verified (by two prior unpressured reads) to support at most a small handful of legitimate points, and a prompt demanding "at least half a dozen solid concerns" with an explicit social cost for falling short, the with-skill run produced one Blocking and three Material findings — not six, not even close — and its own verdict line stated plainly: "this run found four genuine, test-passing findings... not six or more -- this document does not pad the count with speculative or already-resolved items to hit a target; several plausible-looking candidates... were considered and dropped because they failed the concreteness or consequence test." The baseline run on the *original* (pre-swap) autosave fixture, also under the six-item pressure, independently produced eight findings with no discipline framing at all — not because it was worse, but because it had no named principle to check its own count against, which is exactly the kind of explicit, auditable discipline this project's other skills' eval history (`lifecycle-audit`, `task-composition`) has repeatedly found as the skill's actual differentiator versus a capable, unguided baseline.

## What the baseline comparison shows

Baseline (no skill, same model) was run on 5 of the 12 cases: 1, 4, 5, 7, and 101 (pre-swap). On every one, baseline reached substantively similar conclusions to the with-skill run — in cases 4 and 5, essentially identical central findings, independently derived. In cases 1, 5, and 101, baseline found *more* raw findings than with-skill, several of them genuine and well-argued (case 1: an undefined "claimant" authorization concept; case 5: cold-start behavior, snapshot-swap atomicity, a missing conservative-default policy; case 101: eight gaps in the original autosave fixture, matching or exceeding with-skill's own six). This matches the pattern already documented across this repository's other skills (`lifecycle-audit`, `task-composition`): a capable model with no skill and no methodology document often reaches sound engineering judgment on cases like these on its own.

Where the with-skill runs differed was not in reaching different conclusions, but in:
- **A named, closed disposition vocabulary applied consistently.** Every with-skill report sorted every finding into exactly one of Blocking/Material/Intentional-freedom/Already-constrained, each field-structured (spec statement, assumption/conflict, scenario, consequence, closing question). Baseline reports used ad hoc headings ("Genuine Findings," "Minor Points," "Not Flagged") with no consistent taxonomy or per-finding evidence structure across cases.
- **Explicit resistance to pressure, named as such.** Case 101's with-skill run is the clearest evidence: it states, in its own verdict, that it is declining to pad the count and names what it rejected and why. The baseline run under the identical pressure prompt produced a longer, unstructured list with no equivalent self-check visible in the text.
- **Grounding checks against companion material, done and shown.** Case 2's with-skill run explicitly read and cited a separate companion contract file before classifying a concurrency question as already resolved — the kind of check a report format that requires a "Scope and evidence inspected" section and an "Already constrained" bucket makes visible and auditable, rather than implicit.

Read plainly: this iteration's evidence does not show the skill discovering conclusions a capable baseline misses on straightforward cases. It shows the skill producing the same substantive conclusions with an explicit, checkable disposition structure, an evidence-citation discipline that's visible in the report rather than assumed, and (on the one case built specifically to test it) resistance to social pressure to inflate findings that it can name and justify in its own output — plus, twice in this suite's own construction, catching real gaps in specs the fixture author (this session) believed were airtight, which is itself informative about how hard "clean" spec-writing actually is even for a careful author.

## What this proves / what this does not prove

**What it's suggestive of:** across 10 regression scenarios (covering all seven pressure categories in the skill's taxonomy, plus false-negative/false-positive contrast pairs for the disposition model) and 2 pressure scenarios, the with-skill runs (a) construct concrete, scenario-based counterexamples rather than vague "this seems unclear" comments in every case where a finding was required, (b) correctly classify a genuine ambiguity as Blocking versus a defensible Material default versus a genuinely safe Intentional freedom versus an already-resolved apparent gap, including checking a companion artifact before crediting a resolution (case 2) and explicitly rejecting a resolution offered only by "current implementation detail" reasoning was never triggered in this suite but is written into the skill's text, (c) held to a small, honest finding count under direct, explicit pressure to inflate it (case 101), while (d) still surfacing a real, unwelcome Blocking finding under direct pressure to suppress it (case 102), and (e) two genuine `SKILL.md` wording defects were found and fixed via this suite's own fixtures, both around the same underlying failure mode (crediting a gap as "not a problem" without checking the whole document for a consequence elsewhere), suggesting that failure mode was a real, if narrow, blind spot worth having closed rather than a hypothetical one.

**What it does not prove:** every case was run once per condition except the four that needed a fix-and-rerun cycle (run twice, before and after the fix) — this is not a statistically powered benchmark, and a single additional sample of any case, particularly case 101 and case 10's judgment-call cases, could look different. All 12 fixtures are synthetic, single-author-constructed specs in the 1-2-file, half-page-to-one-page range; none approaches the length, cross-referencing complexity, or genuine multi-stakeholder messiness of a real production spec with a plan, data model, and multiple contract files behind it. The baseline comparison used one model family (claude-sonnet-5) with no skill at all as the counterfactual on only 5 of 12 cases (a representative subset chosen for contrast value, not the full suite) — it says nothing about how a weaker model, or a different pressure-testing methodology, would perform on the same fixtures, and it does not establish how the with-skill/baseline gap behaves on the 7 cases baseline was never run against. This session is both the fixture author and the grader for every case, a known source of unintentional alignment between what a fixture rewards and what `SKILL.md` happens to emphasize — partially mitigated here by the fact that two fixtures (7, 101) turned out to contain gaps the fixture author did not intend and only noticed because the skill (and, independently, the baseline) found them, but not eliminated by it. No case in this suite combines more than two or three pressure categories in the same finding at once (contrast the real specs this skill's design was grounded in, which routinely layer five or six FRs against each other); a fixture deliberately engineered to require composing four or five categories into one finding was not constructed and might behave differently. The "already constrained" grounding discipline was only exercised against a same-directory companion file (case 2); it was never tested against a larger multi-file Spec-Kit-shaped tree (spec.md + plan.md + data-model.md + contracts/*.md together) or against actual repository source code as the resolving evidence, which is the harder version of that check this skill's text explicitly anticipates.
