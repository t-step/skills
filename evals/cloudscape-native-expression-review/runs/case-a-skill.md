# Cloudscape Native-Expression Review: FleetNodes.tsx

**Inferred user task:** The page presents an operator's read-only, canonical inventory of every compute node backing an inference fleet, so the operator can scan for unhealthy nodes and over/under-utilized CPU/memory capacity across the fleet. There is no create/edit/delete workflow; the only per-row action is an external link out to the AWS console for that node.

**Cloudscape packages / versions:** `@cloudscape-design/components` 3.0.900 (resolved), `@cloudscape-design/collection-hooks` 1.0.60 (resolved) — both pinned exact versions in the lockfile, no unresolved range.

## Findings

**Finding:** The table's single filtering property set (status, region, instance type — each a fixed, small enum) is exposed only through a free-text `TextFilter`, when the data shape and stated task match Cloudscape's documented criteria for `PropertyFilter` instead.
**Type:** combined component + pattern
**Materiality:** medium
**Confidence:** high
**User task:** See above — scanning a fleet for unhealthy status and abnormal utilization.
**Repository evidence:** `src/pages/FleetNodes.tsx` lines 45–56 (single `TextFilter` wired via `useCollection`'s `filtering`) and lines 139–145 (`<TextFilter {...filterProps} .../>`). Three of the seven data columns are discrete-valued: `status` (`in-service`/`draining`/`unhealthy`, line 14), `region` (3 values, line 25), `instanceType` (3 values, line 26); `cpuUtilization`/`memoryUtilization` are numeric.
**Cloudscape evidence:** Filter Patterns page (`patterns/general/filter-patterns`): "If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter"; "For complex products with large collection of resources, use the property filter so that users can combine multiple properties, values, and operators"; text and collection-select filters suit "Simple resource (small set of properties)" while property filter handles "Complex resource (large set of properties)." Table component docs: filtering exists as "one of three filtering mechanisms... text filtering, collection select filter, or property filter" — TextFilter is not the only or default option.
**Applicability argument:** The surface has three independent discrete-valued properties (status, region, instance type), which exceeds the documented one-or-two-property threshold the docs draw between collection-select filter and property filter — this is a directly observed fact about the current schema, not a scale assumption. The stated task ("scan for unhealthy or over/under-utilized capacity") is exactly a multi-criteria triage task (e.g., unhealthy nodes in a given region), which a single free-text field cannot express as a combinable query — it can only substring-match one term at a time and has no operators for the numeric utilization fields. PropertyFilter's documented support for discrete-value tokens (the docs' own example, "State = Active, Pending, Canceled," is structurally identical to this page's `status` field) and combinable operators covers both the categorical fields and, for the numeric utilization fields, threshold-style queries the task explicitly cares about ("over/under-utilized"). The one caveat: the docs also gate PropertyFilter on "large collection of resources," and this fixture's mock data is only 24 items — the property-count criterion supports the finding independent of scale, but the "large collection" framing is inferred from the page's own framing ("canonical inventory of every compute node... backing the inference fleet," which is a real-fleet, not toy, collection) rather than concretely evidenced in this bounded surface.
**Current expression:** A single `TextFilter` matching free text against item fields, combined with existing column sort for each field.
**Native expression:** A `PropertyFilter` exposing `status`, `region`, and `instanceType` as discrete-token properties (matching the documented "State = Active, Pending, Canceled" pattern) and `cpuUtilization`/`memoryUtilization` as operator-comparable numeric properties, replacing the plain `TextFilter` and its `filterProps`/`filteringText` wiring.
**Why it matters:** The current composition cannot express the compound triage query the page's own stated purpose calls for (e.g., "unhealthy AND us-east-1," or "cpuUtilization > 80") without manually scanning rendered rows — sorting only approximates this by re-ordering, one field at a time, rather than isolating a subset. This is a documented, criteria-based mismatch between the filtering mechanism chosen and the shape of the data being filtered, not a matter of taste.
**Boundary check:** This is a component/pattern-selection question (which of the three documented filtering mechanisms fits a three-discrete-property, numeric-threshold-relevant dataset), not an implementation-correctness question about how `TextFilter` itself is wired, and not a general UX complaint — it cites the filter-patterns page's own stated selection criteria.
**Authority strength:** RECOMMENDED — the docs phrase this as "use X if Y," not as an absolute prohibition on TextFilter.

## Suppressed (low materiality or weak applicability)

- **Node ID column (row header) is not a link to a details page.** Table docs state "use the first table column for users to navigate to a details page that shows more information about the item" (a documented Do). But this bounded fixture shows no evidence an in-app node-detail page exists or is in scope — the page's own per-row action already provides an external "Console" link, which plausibly already serves as the "go see more about this item" affordance, just outside the app. Recommending the ID column become a link would assume an unestablished in-app capability; treated as intent-dependent and not reported as a confident finding.
- **CPU/memory utilization rendered as plain percentage text rather than a graphical gauge.** No Cloudscape component is documented as the native fit for a steady-state utilization readout in a table cell (ProgressBar's documented purpose is operation-in-progress completion, not a gauge), so there's no citable component substitution to recommend — suppressed for lack of applicable evidence, not evaluated further as a chart/dataviz concern.

## Orientation notes

- **Macro-pattern choice (Table, not Cards or a custom list).** Confirmed correct: the Table View resource-management pattern's stated problem — helping users "quickly identify categories or compare values in a large text and numerical data set" — matches this page's task precisely (comparing status/region/instance/utilization across many nodes).
- **`StatusIndicator` for the three-state `status` field**, mapped `in-service → success`, `draining → in-progress`, `unhealthy → error`. Matches the component's documented semantic purpose for exactly this kind of enum-state display.
- **Inline `Button` (variant `inline-link`) inside a dedicated "Actions" column** for the per-row external console link. Matches the Table docs' recommendation to "use the inline buttons and inline button dropdowns when featuring actions in a table cell" for singular-item, in-context actions — this is not a case needing a bulk/toolbar action instead.
- **No row-selection column.** Correct given there is no bulk or per-item action beyond the external console link; docs recommend selection only "if the user can take action on the items in the collection," which doesn't apply here.
- **`Header` with `counter={"(${NODES.length})"}` next to the table title.** Matches the documented Do to "always show total item count next to the table title."
- **Filtering/pagination/sorting present at all.** Correct given 24 items, above the docs' "only use filtering, pagination, and sorting if there are more than five items" threshold.

## What was not evaluated

Implementation correctness — API/prop usage on `Table`, `CollectionPreferences`, `useCollection`, the `stickyHeader`/`resizableColumns` mechanics, accessibility wiring (`ariaLabels`, `isRowHeader`), and hard-coded values — is `cloudscape-implementation-audit`'s domain and was not assessed here. General UX/product judgment (page density, whether an operator needs additional context beyond this table, whether a details page or dashboard view should exist elsewhere in the product) was likewise not evaluated; this review only judged whether the chosen Cloudscape components and composition natively express the task the page already performs.
