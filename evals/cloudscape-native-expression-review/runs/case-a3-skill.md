# Cloudscape Native-Expression Review: Endpoints

**Inferred user task:** View, monitor, and initiate creation of inference endpoints across the account — a full-account resource inventory (26 rows, sortable/filterable by ID, status, region, model, throughput, and last-deploy time) with per-row operational status (`in-service` / `updating` / `failed`) and a primary "Create endpoint" action. Nothing in the bounded file establishes navigation to a per-endpoint details view (no router import, no `onClick`/`href` on any cell).

**Cloudscape packages / versions:** `@cloudscape-design/components@3.0.900` (declared `^3.0.900`, resolved via lockfile), `@cloudscape-design/collection-hooks@1.0.60` (declared `^1.0.60`, resolved via lockfile). Both fully resolved — no unresolved-range caveat applies.

## Findings

### Finding 1 — Full-page resource table wrapped in `ContentLayout` with `variant="container"` instead of the documented full-page table view pattern

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** high
- **User task:** Viewing/managing the complete set of inference endpoints in the account as a stand-alone, top-level resource list page (not a table nested inside some other page's content).
- **Repository evidence:** `fixture/src/pages/Endpoints.tsx` lines 52–67 and 156–157: the entire surface is `<ContentLayout header={<Header variant="h1" counter=... description=... actions=<Button variant="primary">Create endpoint</Button>>Endpoints</Header>}><Table variant="container" ... stickyHeader ... /></ContentLayout>`. This is the only content on the page — a 6-column, 26-row inventory with `TextFilter`, `Pagination`, and `CollectionPreferences` all present.
- **Cloudscape evidence:** Table component docs (`https://cloudscape.design/components/table/index.html.md`), Variant section: "**Container** — This table variant has its own visual container with shadows and borders. Use this variant to feature a table in a stand-alone container with its own hierarchy. For example: when using a table on a details page." vs. "**Full page** — This variant is for implementing the full page table view pattern. Use it for presenting and managing a table with many columns within a stand-alone page." Same page, Header subsection: "Use the h1 variant of the header component with the full page table. Use the h2 variant of the header component with the container table." Table View pattern page (`https://cloudscape.design/patterns/resource-management/view/table-view/index.html.md`), "Don't" list: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the table component to implement this pattern." — and the pattern's applicability boundary: "Don't use the table view pattern for tables that aren't overly content-heavy. Instead, if a table only has a few columns, use a bordered table inside the content layout component."
- **Applicability argument:** (1) The observed task — a stand-alone, full-account resource inventory with 6 columns, 26 rows, filtering, pagination, and preferences — matches the table-view pattern's stated problem ("collection of resources in a tabular format... quickly identifying categories or comparing values in a large text and numerical data set"), not the "container on a details page" or "a few columns" bordered-table carve-outs the docs explicitly exclude. Six columns plus a preferences panel is squarely "content-heavy," not "a few columns." (2) The current implementation already solves the same problem the pattern addresses (listing/filtering/paginating a resource collection) — it's not solving a different problem. (3) The proposed native expression (drop `ContentLayout`, use `Table variant="full-page"`, pair it with the `awsui-h1-sticky` header variant) preserves the exact same task; nothing about the resource, its data, or its actions changes. (4) The current composition isn't a minor style choice — it mixes signals from both variants: an `h1` header (a full-page-table signal, per the docs' explicit h1↔full-page/h2↔container pairing) wrapped in a `container` table inside `ContentLayout` (a details-page signal). This internal inconsistency, plus an explicit "Don't ... Instead" pairing naming this exact composition, is exactly the kind of thing a Cloudscape-fluent implementer would restructure, not merely note as an alternative.
- **Current expression:** `ContentLayout` wrapping a `Table` with `variant="container"`, `Header variant="h1"`.
- **Native expression:** Drop `ContentLayout`; render `Table variant="full-page"` directly as the first element in the page's content slot (paired with `contentType="table"` on the surrounding `AppLayout`, which sits outside this bounded file and should be verified there), keeping the existing `h1` header, counter, description, and primary action as-is — they already fit the full-page pattern's header building block.
- **Why it matters:** This is a documented "Don't ... Instead" pairing for exactly this composition (container table + ContentLayout on a stand-alone resource list), not a stylistic preference — the current composition also self-contradicts the docs' own h1/full-page ↔ h2/container variant-pairing rule, which is independent, corroborating evidence that the page is expressing the full-page pattern's *content* (h1, counter, description, primary create action, sticky header) through the *container* pattern's structural components.
- **Boundary check:** This is a table/pattern-variant selection question — which of Cloudscape's two documented, differently-scoped table compositions matches this page's actual role in the app — not a UX opinion or an implementation defect; the variant prop and page wrapper are themselves the concept being chosen, not how either is coded.

### Finding 2 — `TextFilter` used where the column set matches Cloudscape's stated `PropertyFilter` profile

- **Type:** component selection
- **Materiality:** medium-high
- **Confidence:** medium-high
- **User task:** Finding specific endpoints within a 26-row account-wide inventory that has three enum/discrete-valued columns (`status`: in-service/updating/failed; `region`: 3 values; `model`: 3 values) plus a free-text identifier and two numeric/date columns.
- **Repository evidence:** `fixture/src/pages/Endpoints.tsx` lines 121–126: `<TextFilter {...filterProps} filteringPlaceholder="Find endpoint" filteringAriaLabel="Filter endpoints" />`, filtering the full 6-column set (`status` cell at lines 86–91, `region` at 92–98, `model` at 99–105 — all rendered from small, fixed value sets).
- **Cloudscape evidence:** Text filter docs (`https://cloudscape.design/components/text-filter/index.html.md`), "Don't" list: "Don't use a text filter for collections that have a large set of values; use the property filter instead." Property filter docs (`https://cloudscape.design/components/property-filter/index.html.md`) and the Filtering patterns page (`https://cloudscape.design/patterns/general/filter-patterns/index.html.md`): property filter is positioned for "complex resource (large set of properties)" collections where users "combine multiple properties, values, and operators," versus text/collection-select filter for "simple resource (small set of properties)"; property filter's own guidance further recommends multi-select (`tokenType="enum"`) tokens specifically for "properties with discrete values or finite sets... State = Active, Pending, Canceled" — a near-exact analog of this surface's `status` column.
- **Applicability argument:** (1) The observed task — locating endpoints among several independently filterable, partly-enum-valued properties — matches the documented property-filter problem (multi-property, discrete-value filtering), not a simple single-known-term search. (2) The current `TextFilter` solves the same underlying problem (narrowing the visible rows) the property filter addresses, just less precisely — it can only match substrings across the row, with no way to isolate "status = failed" or "region = us-west-2" directly. (3) Swapping to `PropertyFilter` preserves the same task exactly — same data, same filtering goal, more structured expression of it. (4) This is material, not cosmetic: `status` (with a `failed` state that operators would plausibly want to isolate), `region`, and `model` are exactly the "discrete values / finite sets" case the property-filter docs give as their own worked example, and text filter's own docs draw the line specifically at "a large set of values." I weigh this evidence honestly against the table-view pattern's own "Filter - optional" building block, which illustrates a generic "Text filter" in that slot ("helps users... quickly find one or several resources with a matching query") — but that description is scoped to the *table-view pattern's* generic composition, not a ruling on which filter component fits a given column shape; the component-level guidance on both `TextFilter` and `PropertyFilter` is the more specific, directly on-point authority for that choice, and neither text-filter's nor property-filter's own page treats the pattern-page mention as overriding the property/value-count criterion.
- **Current expression:** Single `TextFilter` matching free text against the entire row.
- **Native expression:** `PropertyFilter` with `filteringProperties` for `status`, `region`, and `model` (each using `tokenType="enum"` multi-select tokens per the discrete-value guidance), plus `id` for free-text/prefix matching — via `useCollection`'s `propertyFiltering` option in place of `filtering`.
- **Why it matters:** With `TextFilter`, a user cannot directly ask "show only failed endpoints in us-west-2" — the documented failure mode text-filter's own guidance calls out for collections with a large set of values across multiple properties, which is precisely this table's shape.
- **Boundary check:** This is a choice between two Cloudscape filtering *components* for the same filtering task based on the shape of the underlying data, not an implementation defect in how the current `TextFilter` is wired or a general usability complaint.

### Finding 3 — First (identifier) column doesn't navigate to a details view

- **Type:** intent-dependent
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Same inventory task as above; this finding turns on whether an individual `Endpoint` (id, status, region, model, throughput, last-deployed) is meant to be individually opened/inspected — e.g., to see why one is `failed` — or whether this table is a self-contained, non-drilldown summary.
- **Repository evidence:** `fixture/src/pages/Endpoints.tsx` lines 77–84: the `id` column (`isRowHeader: true`, `cell: (item) => item.id`) renders plain text with no `Link`, `onClick`, or route. No router/navigation import appears anywhere in the file.
- **Cloudscape evidence:** Table component docs, Columns subsection (prose, not a code sample): "Use the first table column for unique identifiers of the items that are represented in the table (for example: name, id, and ARN). Also use the first table column for users to navigate to a details page that shows more information about the item." (`RECOMMENDED` — phrased as a "Do," not a "Don't ... instead" prohibition.)
- **Applicability argument:** The per-row `status` field includes a `failed` state and an `updating` transition state, which is the kind of operational detail (why did this fail? what's the update progress?) that plausibly warrants a dedicated details view — a reading the cited guidance directly supports. But the bounded surface gives no evidence either way that an endpoint details route exists in this app: no router, no `Link`, no navigation handler anywhere in the file, and the case's bounded surface is this file alone. I can't tell whether this table is meant to be the terminal view of an endpoint (a valid, if less common, native expression) or the entry point to a details page (the more typical expression for a resource with per-item operational state and a create flow). Reporting a confident "add a Link here" recommendation would guess at product intent the evidence doesn't establish.
- **Current expression:** Plain-text row-header identifier cell, no navigation affordance.
- **Native expression:** Uncertain — if endpoints are individually addressable resources elsewhere in the app, the first column should render as a `Link` to that details page per the cited guidance; if this table is intentionally a flat, non-drilldown summary, the current plain-text cell is already correct and no change is warranted.
- **Why it matters:** Named because it's directly actionable evidence tied to Finding 1 (adopting the full-page table pattern is the point at which a team would naturally also decide this), not because either reading is confirmed.
- **Boundary check:** This is about whether a documented column-role convention (identifier column ↔ navigation) applies to this specific resource, not a UX opinion about whether linking "would be nicer" — but it's withheld as `intent-dependent` because the file alone can't establish whether a destination exists.

## Suppressed (low materiality or weak applicability)
- **`CollectionPreferences` omits `visibleContent`/column-visibility control** — Table component docs list "which columns are visible or set to hidden" as part of the preferences building block, and this surface's `CollectionPreferences` only exposes page size and wrap-lines. With only 6 columns and no indication users need to hide any of them, this reads as a minor completeness gap rather than a component/pattern misselection — no applicability evidence that this specific 6-column table needs visibility controls. Suppressed as low materiality.
- **Single-column sort only, no multi-column sort** — Table docs describe multi-column sort as an optional feature "useful when users need to analyze multi-dimensional data" (e.g., sort by status then date). Nothing about this task's evidence (a flat operational inventory) indicates users need simultaneous multi-dimensional sort; this would be manufacturing a finding without applicability evidence. Suppressed.
- **`requestsPerSecond`/`lastDeployed` treated as plain sortable columns rather than a data-visualization or timestamp-pattern element** — Cloudscape ships dedicated timestamp-formatting and data-vis guidance, but nothing in the observed task (a tabular inventory, not a monitoring dashboard) suggests these columns need anything beyond what a table cell already provides. Suppressed as weak applicability — this would be reaching for "Cloudscape has a component for this" without task-level justification.

## Orientation notes
- `StatusIndicator` for the `status` column, mapped `in-service → success`, `updating → in-progress`, `failed → error` — semantically correct, purpose-built usage, and correctly placed as the second column per the Table docs' "Use the second column for status when status is relevant" guidance.
- `useCollection` (from `@cloudscape-design/collection-hooks`) driving filtering, sorting, and pagination together, with `collectionProps`/`filterProps`/`paginationProps` spread onto `Table`/`TextFilter`/`Pagination` — correct, documented integration pattern for wiring collection state to these three components as a set.
- Primary "Create endpoint" action placed as a `Button variant="primary"` inside `Header`'s `actions` slot — correct placement per the documented global-actions-in-header convention.
- `Pagination` + `CollectionPreferences` paired to let users control page size — matches the documented preferences/pagination building-block relationship.

## What was not evaluated
Implementation correctness was not assessed: prop-level API usage (`ariaLabels` completeness, whether `sortingComparator`/`sortingField` values are wired correctly, `resizableColumns`/`stickyHeader` mechanics), hard-coded logic such as the inline `statusType` mapping function, date formatting via `toLocaleString`, numeric right-alignment/formatting for `requestsPerSecond`, TypeScript typing, and any accessibility implementation details on top of the already-correct component choices. General UX/product judgment was also not assessed: page density defaults, the specific wording of the header description and empty/placeholder copy, whether 10/20 are the right page-size options, and any cross-page/navigation-flow concerns beyond what's necessary to state Finding 3's ambiguity. None of this should be read as "checked and fine" — it's simply outside this skill's scope.
