# Cloudscape Native-Expression Review: ApiKeys.tsx

**Inferred user task:** A service owner views and manages the small set of API keys their own integrations use: scanning label/masked-identifier/status/creation-date for each key, filtering or sorting that list, and creating new keys via the primary header action. The header description also frames revocation ("Revoke a key immediately if it may have been exposed") as part of this page's intended purpose, though no revoke control exists anywhere in this bounded surface.

**Cloudscape packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked and resolved to `3.0.900`; `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked and resolved to `1.0.60` (both resolved from `fixture/package-lock.json`, no unresolved range).

## Suppressed (low materiality or weak applicability)

- **Table view vs. Card view, based on the 8-row item count.** Cloudscape's View resources pattern (`patterns/resource-management/view/index.html.md`) gives item-count guidance — "9 or more resources in 99% of use cases" for Table view, "5 or less resources in 99% of use cases" for Card view — that could suggest Card view fits a list this small better. Suppressed: 8 rows sits in the ambiguous gap between both stated thresholds (not clearly under 5, not at/over 9, and the source itself hedges with "in 99% of use cases"), and the same page's metadata-type criterion decisively favors Table here — all four columns (label, masked key, status, created date) are exactly the "data displayed in columns (text, numerical, status)" the guidance names for Table view, with none of the "visuals (charts, videos)" that would favor Card view. Weak, contradicted applicability.
- **Inline Copy to clipboard on the "Key" column.** Copy to clipboard's documented inline-variant use case is "a long URL within a table or an Amazon Resource Name (ARN) within a list of key-value pairs" (`components/copy-to-clipboard/index.html.md`) — a plausible category match for a per-row identifier rendered as plain text in a table cell. Suppressed at low confidence: the displayed value is a masked reference (`sk-••••7f3a`), not a working credential, and nothing in this bounded surface establishes that a service owner needs to copy this partial identifier elsewhere (a support ticket, a CLI argument, a log lookup) rather than just visually distinguish rows. Plausible but unevidenced applicability, below the reporting bar.
- **Missing revoke / per-row action despite the header's own stated task.** The header description promises revocation, but the table has no row action, no `selectionType`, and no header action besides "Create API key" — nothing implements it anywhere in this file. Considered as a possible in-context/global-actions pattern gap (Cloudscape's Actions pattern documents a specific composition — an actions column, or selection paired with a header action — for exactly this "act on one resource in a table" job), but suppressed as a finding for this skill specifically: this is a total absence of any implementation, not a case of one Cloudscape concept chosen over a better-fitting one, so it fails the component/pattern-alignment boundary check and belongs to a different, out-of-scope review layer (product completeness).

## Orientation notes

- **`ContentLayout` + `Table variant="container"` for this 4-column table** — confirmed as the documented, correct composition, not a superficial mismatch. The Table view pattern's own "Don't" list (`patterns/resource-management/view/table-view/index.html.md`) states: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the table component," immediately followed by "Don't use the table view pattern for tables that aren't overly content-heavy. Instead, if a table only has a few columns, use a bordered table inside the content layout component." ApiKeys.tsx (4 columns, `ContentLayout`, `Table variant="container"`, which renders as a bordered table) is precisely the second, few-columns composition the pattern names as the correct alternative — REQUIRED-strength guidance confirming this choice, not contradicting it.
- **`TextFilter` for filtering** — Filtering patterns (`patterns/general/filter-patterns/index.html.md`) documents text filter for a "simple resource (small set of properties)" where users "know exactly the value or term they are looking for." Four flat, non-nested properties (label, id, status, createdAt) is a simple resource; TextFilter matches, rather than under- or over-powering, the task compared to collection-select-filter or property-filter.
- **`Pagination` shown for an 8-row, single-page result set** — the Table view pattern's own pagination building block states explicitly: "Display the pagination even if the resources set fits in one page." `pageSize: 10` against 8 rows (pagination effectively inactive) is the documented default behavior, not a native-expression miss.
- **`Header` composition (`variant="h1"`, `counter`, `description`, `actions`)** — matches the Header component's own documented slots (counter, description, actions demonstrated together in its docs) and mirrors the header building block shown in the Table view pattern itself.
