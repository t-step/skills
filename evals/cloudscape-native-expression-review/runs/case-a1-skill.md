# Cloudscape Native-Expression Review: StorageVolumes.tsx

**Inferred user task:** An operator-facing inventory page for every block storage volume provisioned in the account. The page's sole job (per its own header, columns, and inline comment) is to let an operator see each volume's status, size, throughput, and attachment, sort/browse the list, and specifically locate volumes that are unattached (`status: 'available'`) or in an error state (`status: 'error'`) to audit capacity. There is no other content, no creation/edit/delete flow, and no navigation into a per-volume detail view.

**Cloudscape packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved). `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60` (resolved). Both fully resolved against the lockfile, so current `cloudscape.design` docs apply without a version caveat.

## Findings

### Finding 1 — Stand-alone resource-inventory page built with `ContentLayout` + `Table variant="container"` instead of the Table view pattern's `full-page` variant

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** high
- **User task:** As above — a stand-alone, whole-page inventory/view of all storage volumes, with no other page content.
- **Repository evidence:** `src/pages/StorageVolumes.tsx` — the entire return value is `<ContentLayout header={...}><Table variant="container" .../></ContentLayout>` (lines 56–156). The file's own comment states: "This page has one job -- list every volume... Nothing on the page besides the table" (lines 32–36). The table already carries the full set of Table view pattern building blocks: `useCollection` sorting/filtering/pagination, `TextFilter`, `Pagination`, `CollectionPreferences`, `resizableColumns`, `stickyHeader`.
- **Cloudscape evidence:**
  - Table view pattern (`https://cloudscape.design/patterns/resource-management/view/table-view/index.html.md`): "Don't use the content layout component on this type of page. Instead, use the 'full-page' `variant` of the table component to implement this pattern." (with a carve-out: "if a table only has a few columns, use a bordered table inside the content layout component.")
  - Table component (`https://cloudscape.design/components/table/index.html.md`): container variant — "Use this variant to place a table inside a container with other content, such as key-value pairs." Full-page variant — "Use it for presenting and managing a table with many columns within a stand-alone page."
  - Content layout component (`https://cloudscape.design/components/content-layout/index.html.md`): "Don't use the content layout component for productive use cases such as resources creation, view, edit, and delete."
- **Applicability argument:** (1) The observed task — a stand-alone page whose only content is a resource table — is exactly the problem both the Table view pattern and the Content layout "don't" statement name: a resource *view* page, explicitly called out as a productive use case ContentLayout should not be used for. (2) The current implementation solves the same "let an operator view/audit the resource collection" problem the pattern targets, just through the discouraged composition. (3) The proposed native expression (`Table variant="full-page"`, no `ContentLayout` wrapper) preserves the identical task — same columns, same filter/sort/paginate/preferences behavior — it only changes page-structure composition, not what the page does. (4) This is material, not cosmetic: the container variant's own documented purpose ("with other content, such as key-value pairs") does not describe this page — there is no other content — and the table already exhibits every full-page-pattern building block (filter, sort, paginate, resize, sticky header, preferences), which is itself evidence this was built as a full inventory page rather than the "few columns, simple bordered table" case the carve-out describes. Two independent doc sources (the pattern page and the component page) converge on the same directive, which raises confidence above a single ambiguous citation.
- **Current expression:** `ContentLayout` wraps a `Table` with `variant="container"` as the page's only content.
- **Native expression:** `Table variant="full-page"` as the page root (typically paired with `contentType="table"` on the surrounding App layout, and the sticky/h1 header pattern the page already uses), with `ContentLayout` removed.
- **Why it matters:** The container variant is documented for tables sharing a page with other content; this page has none, so the composition doesn't match the component's own stated purpose. The `ContentLayout` "don't" statement names resource-view pages specifically. Staying with the current composition also forfeits the full-page variant's space/density handling meant for "many columns within a stand-alone page," and diverges from how a Cloudscape-fluent implementer would compose a dedicated resource-inventory page elsewhere in the same app — a consistency cost, not just an aesthetic one.
- **Boundary check:** This is a page-structure/component-selection judgment — which layout component and `Table` variant correctly express a stand-alone resource-listing page — grounded in Cloudscape's own explicit "don't/instead" guidance, not a general opinion about density, spacing, or visual polish.

### Finding 2 — `TextFilter` used as the only filtering mechanism for a page whose stated task centers on filtering by a single discrete-valued `status` property

- **Type:** combined component + pattern
- **Materiality:** medium
- **Confidence:** medium
- **User task:** Same as above, with emphasis on the specific stated sub-task: "so an operator can audit capacity and find unattached or errored volumes" (line 33–35) — i.e., locate volumes by `status` (`attached` / `available` / `error`), not by an arbitrary known search term.
- **Repository evidence:** `src/pages/StorageVolumes.tsx` lines 120–126 — the table's only `filter` slot is a `TextFilter`. The `status` column (lines 84–90) is the table's one discrete/enumerable-valued column, rendered via `StatusIndicator`, with exactly three possible values.
- **Cloudscape evidence:**
  - Filtering patterns (`https://cloudscape.design/patterns/general/filter-patterns/index.html.md`): decision guidance — "know exactly the value or term they're looking for" → text filter; "filtering typically involves only one or two properties" → collection select filter is the better fit; property filter is reserved for many properties, multiple values per property, or complex ("or"/"not") operators.
  - Collection select filter (`https://cloudscape.design/components/collection-select-filter/index.html.md`): "Use a select filter for commonly used properties and values," citing a canonical example — Status: Error, Loading, Pending, Stopped, Success — closely matching this page's `status` property. Also states it "works alongside" `TextFilter` for combined ID lookup + property browsing.
  - Text filter (`https://cloudscape.design/components/text-filter/index.html.md`): documented purpose is locating a resource by a term the user already knows.
- **Applicability argument:** (1) The task the page's own comment states — finding volumes "unattached or errored" — is a property-based query against one discrete-valued column, not a "I know the exact term" search; this materially matches the filter-patterns doc's stated criterion for collection select filter over text filter, and its canonical status example is close to a direct match. (2) `TextFilter`'s default full-row substring matching happens to let a user type "error" and get a hit, so it partially solves the same problem, but only as an undocumented side effect of substring search, not a designed status-browsing affordance. (3) The proposed native expression (a `Select`-based collection filter for `status`, composed alongside the existing `TextFilter` for ID lookup — a combination the docs explicitly support) preserves the same two sub-tasks already present (find by ID, find by status) without inventing a new one. (4) I rate confidence medium rather than high because the filter-patterns doc explicitly allows text filter for "simple resources" too, so this is a "docs show a better-fitting alternative" finding, not an unambiguous prohibition — the applicability case rests on matching the specific status-browsing sub-task named in the code, not on TextFilter being invalid in general.
- **Current expression:** A single `TextFilter` searching across the full row via `useCollection`'s default filtering.
- **Native expression:** Keep `TextFilter` for ID lookup, and compose it with a `Select`-driven collection select filter scoped to the `status` property (per the documented "works alongside" pairing), so the three status values are directly selectable rather than reachable only via an implicit substring match.
- **Why it matters:** The page's one stated filtering need is a property/value query (status), which is exactly the shape of task Cloudscape's own filtering-pattern guidance assigns to a select filter rather than a free-text one. Leaving it as text-only makes the specific, stated "find errored/unattached volumes" workflow depend on the user guessing that typing the literal status string will substring-match, instead of presenting the three valid values directly — a discoverability gap tied to the filtering component chosen, not a generic "add more filters" UX opinion.
- **Boundary check:** This is a component-selection judgment about which documented filtering component matches the property-based query the page's own stated task requires, not a general usability critique about filter quantity or layout.

## Suppressed (low materiality or weak applicability)

- **Property filter instead of text/select filter** — considered and rejected: the filtering-patterns doc reserves property filter for many properties, multiple values per property, or "and"/"or"/"not" operator combinations; this table has one discrete property and no evidenced need for multi-value or boolean-combination queries, so property filter's added complexity isn't supported by the task (see Finding 2, which recommends the lighter-weight collection select filter instead).
- **Card view instead of table** — not reported: the card view pattern is documented for "a blend of text, images, and data visualizations"; this dataset is pure text/numeric, which is exactly what the table view pattern's own stated purpose targets, so table is already the right component.
- **Split view (table + split panel for per-volume detail)** — not reported: no evidence of an unaddressed detail-inspection need — all six volume attributes are already fully visible as table columns, and there's no route/action suggesting a per-volume detail view exists or is wanted.
- **Table with grouped/nested resources** — not reported: the data is a flat list with no parent-child or shared-characteristic grouping evidenced in the fixture.
- **Density settings pattern (comfortable/compact toggle in `CollectionPreferences`)** — not reported: documented as an optional preference, not a required building block; no evidence in the task that density is a problem here beyond the existing page-size and wrap-lines preferences already present.

## Orientation notes

- `StatusIndicator` for the `status` column matches its documented purpose ("communicates the state of a resource... in a compact form... embedded in a... table").
- `useCollection` + `Pagination` + `CollectionPreferences` composition (sorting, page-size preference, wrap-lines preference) matches the standard Table view pattern building blocks.
- `Header` with `variant="h1"` and a `counter` reflecting the collection size is the documented composition for a collection-page header.
- `trackBy="id"` and `isRowHeader` on the `id` column follow standard table row-identity/header conventions for this component.

## What was not evaluated

Implementation correctness was not assessed: `useCollection`/`filteringFunction` field-coverage mechanics, whether `ariaLabels` and other accessibility wiring are complete and correctly implemented, prop-level API currency against `3.0.900`, and hard-coded values (e.g. `minWidth` numbers) are all out of scope for this review. General UX/product judgment — page-size defaults, column ordering, information density, or whether 28 rows justifies pagination at all — was likewise not evaluated; its absence here should not be read as "checked and fine."
