# Cloudscape Native-Expression Review: WorkspaceDetails

**Inferred user task:** View a single workspace's details — its stable identifying/configuration facts (name, owner, region, plan, created date, status), plus two related groupings a user may want to inspect separately: its members and its recent activity. The page itself documents this intent in its leading comment: general configuration is described as "relevant no matter which tab a user is currently looking at."

**Cloudscape packages / versions:** `@cloudscape-design/components` resolved to locked version `3.0.900` (declared range `^3.0.900`) via `scripts/resolve_versions.py`. Fully resolved — no version-applicability caveat needed.

## Findings

### Finding 1: Workspace general configuration is buried inside an "Overview" tab as a fabricated single-row Table, instead of living in a persistent key-value-pairs summary outside the tabs

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** high
- **User task:** Let a user see a workspace's stable identifying facts (name, owner, region, plan, created, status) at a glance, independent of which sub-grouping (Members/Activity) they're currently browsing.
- **Repository evidence:** `src/pages/WorkspaceDetails.tsx` lines 34–91. The `Tabs` component's first tab (`id: 'overview'`) renders a `Table` (lines 73–89) with a single synthetic row (`items={[{}]}`, `trackBy={() => 'workspace-overview-row'}`) and six `columnDefinitions` whose `cell` functions all ignore their row argument and return hard-coded literals (e.g. `cell: () => 'eng-platform-prod'`). The code's own comment (lines 30–33, 70–72) states this data is "general configuration... relevant no matter which tab a user is currently looking at" — yet it is placed *inside* one specific tab, requiring a click to reach, and hidden entirely while Members or Activity is active.
- **Cloudscape evidence:** The "Details Page with Tabs" pattern (`patterns/resource-management/details/details-page-with-tabs/`) defines the details summary container as the place for "important information that applies to tasks in all the tabs," explicitly "always visible when users switch between the tabs" — the opposite of the current placement. Within that summary container, the sibling "Details Page" pattern (`patterns/resource-management/details/details-page/`) specifies the format explicitly: "Details summary container (primary information using key-value pairs)." The `key-value-pairs` component docs (`components/key-value-pairs/`) confirm its purpose is exactly this shape: "lists of properties (labels) followed by their corresponding values," recommended for "displaying read-only property information... resource identifiers and metadata." The `table` component docs (`components/table/`) state tables are for collections benefiting from row/column comparison, recommend reserving tables for "more than five items in the collection," and note the borderless table variant exists specifically "to place a table inside a container with other content, such as key-value pairs" — i.e., Table and KeyValuePairs are documented as distinct, non-interchangeable primitives, and this surface has inverted which one belongs where.
- **Applicability argument:** (1) The observed task — showing one resource's own properties — is exactly the "Details Page" pattern's stated problem (viewing "all the available information about a single resource... at a glance"), not a superficial shape match. (2) The current Table implementation solves the identical problem the pattern addresses (surfacing the same six properties), just through a workaround: a table forced to one fabricated row so its columns can stand in for property labels. (3) The proposed native expression — a `KeyValuePairs` component inside a persistent summary container, placed above/alongside the `Tabs` rather than inside one — preserves the exact same task and data, changing only structure. (4) The mismatch is material, not cosmetic: it changes *when* the information is visible (gated behind a tab click vs. always present) and requires the item-count/comparison semantics of Table to be faked (single synthetic row, ignored cell arguments) rather than using the primitive purpose-built for this exact shape. An experienced Cloudscape implementer would restructure this, not merely note it as an alternative.
- **Current expression:** A `Tabs` component whose first tab, "Overview," contains a `Table` with one synthetic row and six columns standing in for six properties of the single workspace.
- **Native expression:** Move the general configuration facts into a details summary container (e.g., a `Container`/`Header` combination or the `ContentLayout`'s content area) rendered above/alongside the `Tabs`, using `KeyValuePairs` for the six properties. Reserve the `Tabs` for the genuinely tab-appropriate groupings already present — Members and Activity — consistent with "Details Page with Tabs" naming key-value pairs and descriptions as *tab* content only for information that is not cross-tab-relevant (this page's general configuration explicitly is, per its own comment).
- **Why it matters:** The current structure makes the workspace's status and identity — the facts the page comment itself says should be visible "no matter which tab" — invisible by default (Overview is shown initially here, but selecting Members or Activity hides them entirely), directly against the documented purpose of the details-summary/tabs split. It also forces Table into a shape it isn't designed for (a fixed single row with static cell functions), producing code that fights the component's own data model instead of using the primitive Cloudscape ships for exactly this job.
- **Boundary check:** This is a component-and-pattern alignment question — which Cloudscape primitive represents "one resource's properties" and where the documented details-page pattern places it — not an implementation-mechanics defect (the Table is used correctly per its own API) and not a generic UX complaint (the objection is anchored to an explicit, named Cloudscape pattern and component-purpose citation, not a general density/hierarchy preference).

## Suppressed (low materiality or weak applicability)

- **Members tab `Table<Member>` with 3 rows, below the "more than five items" table-usage guideline.** Suppressed: that guideline is advisory ("consider"), not a prohibition, and the three columns (name, email, role) are genuinely comparable attributes across multiple distinct entities — the exact shape Table is documented for — unlike the Overview tab's single-entity property grid. No applicability failure found.

## Orientation notes

- `ContentLayout` + `BreadcrumbGroup` + `Header` (with action `Button`s in `SpaceBetween`) as the page shell — matches the documented Details Page building blocks (breadcrumbs, page title, header actions). No issue found.
- `Tabs` used to separate Members and Activity — both are genuinely tab-appropriate, self-contained groupings ("one tab, one task"), consistent with "Details Page with Tabs" guidance on what belongs inside tabs.
- `Members` tab's use of `Table<Member>` for a list of entities with comparable attributes (name/email/role) — correct primitive for this shape; see "Suppressed."
- `Activity` tab's use of `List` for a vertical sequence of activity-log text entries — matches `List`'s documented purpose ("a group of consecutive items shown one below the other," supporting secondary text). No documented Cloudscape pattern or component page was found that mandates a different treatment (e.g., a dedicated activity-feed/timeline component) for this exact shape, so no finding is reported here; this was checked, not skipped.

## What was not evaluated

Implementation correctness — prop usage, the fabricated `trackBy`/single-row mechanics of the Overview Table, accessibility (`ariaLabels`), deprecated APIs, and any hard-coded style values — is `cloudscape-implementation-audit`'s domain and was not assessed here beyond what was needed as supporting evidence for Finding 1. General UX judgment (e.g., breadcrumb depth, whether "Edit"/"Delete" as bare `Button`s vs. a `ButtonDropdown` is well-organized, whether Activity needs pagination or timestamps) was also not evaluated; it is out of this skill's scope unless anchored to a specific Cloudscape citation, and none of those items met that bar.
