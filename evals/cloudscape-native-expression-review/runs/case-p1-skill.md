# Cloudscape Native-Expression Review: MessageQueues.tsx

**Inferred user task:** An operator-facing collection view listing all message queues in the account (24 items) so the operator can compare throughput (`messagesPerSecond`) and backlog age (`oldestMessageAgeSec`) across every queue side by side, in order to decide which queues need scaling attention right now. Secondary sub-task: narrowing the list by queue name, and by the two discrete attributes `status` (healthy/backlogged) and `region` (us-east-1/us-west-2) while triaging. Source: page comment at `fixture/src/pages/MessageQueues.tsx:29-33` and the `Header` `description` prop at line 50, which state this in almost identical words.

**Cloudscape packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved). `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60` (resolved). Both fully resolved via `scripts/resolve_versions.py` against `fixture/package-lock.json`; no version-uncertainty caveat applies to the findings below.

## Findings

### Finding 1: The page should be expressed as the documented Table view resource-management pattern, not Cards inside ContentLayout

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** high
- **User task:** as stated above — comparing two numeric metrics (throughput, backlog age) and two discrete attributes (status, region) across 24 structured, non-visual resources to decide which need scaling attention.
- **Repository evidence:** `fixture/src/pages/MessageQueues.tsx` — the whole surface is `<ContentLayout>` (line 45) wrapping a single `<Cards>` (line 56) driven by `useCollection` with `filtering`/`pagination`/`sorting` config (lines 35-42), rendering one card per queue with four `sections`: `status` (via `StatusIndicator`), `region`, `messagesPerSecond`, `oldestMessageAgeSec` (lines 66-83). All four fields are plain text/numeric/enum values — no imagery, no rich or variable-shaped content per card. `inspect_surface.py` confirms the JSX inventory: `ContentLayout`, `Header`, `Cards`, `TextFilter`, `Pagination`, `StatusIndicator`, one each, no native HTML standing in for any of them.
- **Cloudscape evidence:**
  - Card view pattern (`https://cloudscape.design/patterns/resource-management/view/card-view/index.html.md`): "A collection of resources represented as cards. It's effective for glancing at small sets of similar resources with text, numerical, and imagery data sets."
  - Table view pattern (`https://cloudscape.design/patterns/resource-management/view/table-view/index.html.md`): "The table view pattern is a collection of resources in a tabular format. It's effective for quickly identifying categories or **comparing values** in a large text and numerical data set." Its "Do" list: "Use table view pattern for static data with multiple attributes displayed in a tabular format. The best data type for a table view is data that is structured, easily comparable, and sortable." Its "Do" list also: "Restrain from incorporating graphics in tables. For data sets with a blend of text, images, and data visualizations… refer to the cards view pattern" (i.e., the inverse cue: no-graphics/structured-numeric data is table territory).
  - Table component page (`https://cloudscape.design/components/table/index.html.md`): "Right-align quantitative numeric data within table cells to make them easier to compare and contrast… This consistency helps users to quickly scan lists and compare values" — a comparison affordance (aligned numeric columns plus native per-column sort) that Cards' per-card-section layout does not provide.
  - Both the Card view and Table view pattern pages independently state, under "Don't": "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the [cards/table] component to implement this pattern" — `REQUIRED` strength (explicit "Don't X, instead Y" pairing) for the container-structure sub-point, regardless of which of the two view components is ultimately used.
- **Applicability argument:** (1) The task-match is not superficial: the page's own header description and code comment use the pattern page's own vocabulary — "compare … across queues" is exactly the verb the Table view pattern uses to describe its purpose ("comparing values in a large text and numerical data set"), while Card view's stated purpose is "glancing," a materially different verb for a materially different task (quick individual review vs. cross-item comparison to make a scaling decision). (2) The current Cards implementation does solve the display/filter/paginate mechanics of the same problem, just via the pattern documented for a different primary purpose. (3) Table view preserves the identical task — same 24 items, same four attributes, same filter/paginate/decide workflow — it changes only the container concept, not the product goal, so this is not a redesign. (4) The difference is material: Cards' section-per-card layout cannot align the two numeric columns for at-a-glance scanning the way a table can, and Cards has no built-in per-column click-to-sort — both directly relevant to a task defined as "decide which queues need scaling attention" by ranking on throughput/backlog age. An experienced Cloudscape implementer building an operator triage view over structured numeric data described this way would reach for Table, not Cards.
- **Current expression:** `ContentLayout` (default app-content wrapper) containing a single `Cards` component with `cardDefinition.sections` for each attribute, no per-attribute sort affordance in the UI (only `sorting: {}` passed to `useCollection`, unused by `Cards`), one `TextFilter` and one `Pagination`.
- **Native expression:** Replace `Cards` with `Table`, using the `columnDefinitions` equivalent of the current four `sections` (status, region, throughput, backlog age), enabling column sort (the pattern's "Sort" building block) so the operator can rank by throughput or backlog age directly, right-aligning the two numeric columns per the Table component's own writing/data guidance. Per both pattern pages' "Don't," drop `ContentLayout` and use the `full-page` variant of `Table` (or `Cards`, if this finding were rejected) as the page's own container, matching the documented Table view building block "C. Table — use the 'full-page' variant… for this pattern."
- **Why it matters:** The stated task is explicitly a cross-item numeric comparison/ranking task, which is the Table view pattern's own stated reason for existing, while the current Cards + ContentLayout composition is the reference shape for a different documented purpose ("glancing at small sets"). This is not a cosmetic swap: Cards lacks the aligned-column scan and native per-column sort that a "which of these 24 needs attention first" workflow depends on, and the container choice separately collides with an explicit, repeated "Don't … Instead" rule in both relevant pattern pages.
- **Boundary check:** This is a pattern/component alignment question — which established Cloudscape resource-view pattern (and its constituent components) matches the documented comparison-oriented task — not an implementation-correctness issue (no prop/API defect is being cited) and not a generic UX complaint (the recommendation rests entirely on the two pattern pages' own stated purpose language and the Table component's own comparison-oriented data guidance).

## Suppressed (low materiality or weak applicability)

- **TextFilter → Collection select filter or Property filter, to make narrowing by `status`/`region` more structured/discoverable.** The code comment ("narrow the list down to a specific status or region") is a real, surface-level match to the Filtering patterns page's own example for Collection select filter ("If the common behavior of users is to filter a resource by only one or two properties, use the collection select filter. For example: by 'status' or 'type'" — `https://cloudscape.design/patterns/general/filter-patterns/index.html.md`), which made Property filter or Collection select filter look like a plausible, even textbook-matching upgrade. Suppressed anyway: both the Card view and Table view pattern pages' own "Filter - optional" building block specify plain **text filter** as the standard/reference filter component for exactly this resource-view pattern ("Text filter helps users with an extensive number of… rows to quickly find one or several resources with a matching query. The entire set of columns are used as a base for the filter."). Recommending a filter-component swap here would mean treating a component's mere existence and a superficial criteria-table match as sufficient applicability evidence, while the documented reference composition for this exact page type already uses text filter — precisely the anti-fundamentalism trap this skill is built to reject. Current `TextFilter` also technically satisfies the stated task (typing "healthy" or "us-west-2" narrows correctly, since it searches all columns), so the current implementation is not solving a materially different problem than the proposed alternative would. Downgraded to suppressed rather than reported.

## Orientation notes

- `TextFilter` + `Pagination` as the filter/pagination mechanism: confirmed against both Card view and Table view pattern pages' own "Filter - optional" and "Pagination - optional" building blocks, which independently prescribe exactly this combination as the reference implementation — correct regardless of which collection component (Cards or Table) is ultimately used.
- `StatusIndicator` used for the `status` field with a `success`/`warning` type mapping for `healthy`/`backlogged`: a plausible, semantically consistent usage; not independently verified against the component's own dedicated guidance page in this pass (see "What was not evaluated"), so not asserted as a confirmed-native finding, only noted as unremarkable.
- Only 2 filterable/discrete attributes (`status`, `region`) and 24 items: consistent with the Filtering patterns page's "Complexity of the resource: Simple resource (small set of properties)" criterion, which is itself part of why the more complex `Property filter` was suppressed above rather than promoted.

## What was not evaluated

Implementation correctness was out of scope and not reviewed: `Cards`/`Table` prop shapes and API usage, the unused `sorting: {}` config passed to `useCollection` (whether it's dead configuration is an implementation question, not a pattern-selection one), `StatusIndicator`'s own component-level guidance and a11y mechanics, `ariaLabels` completeness, and any deprecated-prop or token-usage concerns. General UX/product judgment (page density, whether triage-by-scaling is the right product feature at all, information hierarchy beyond the component/pattern question) was likewise not evaluated — only whether the chosen Cloudscape concepts natively express the already-existing stated task.
