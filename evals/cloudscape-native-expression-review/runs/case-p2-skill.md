# Cloudscape Native-Expression Review: SecurityGroups.tsx

**Inferred user task:** An operator's canonical inventory of every security group in the account: view all groups with their VPC, inbound/outbound rule counts, and status; find groups by name via text filter; and select a batch of groups (e.g., unused ones) to delete in a single bulk action. The page has no other content or purpose beyond presenting and managing this one resource collection.

**Cloudscape packages / versions:** `@cloudscape-design/components` declared `^3.0.900`, locked `3.0.900` (resolved). `@cloudscape-design/collection-hooks` declared `^1.0.60`, locked `1.0.60` (resolved). Both resolved via `scripts/resolve_versions.py` against `fixture/package-lock.json`.

## Findings

### Finding 1: Hand-rolled checkbox selection stands in for Table's native selection mechanism

- **Type:** component selection
- **Materiality:** high
- **Confidence:** high
- **User task:** Operator selects a batch of security groups (individually or via "select all on page") and deletes them in one bulk action.
- **Repository evidence:** `fixture/src/pages/SecurityGroups.tsx` lines 40, 55–81, 111–129. Selection state is a local `useState<Set<string>>` (`checkedIds`), manipulated by hand-written `toggleOne`/`toggleAllOnPage` functions, and rendered as two raw `<input type="checkbox">` elements — one in the `select` column's `header` (lines 112–119) and one in its `cell` (lines 121–128) — each wired to its own `onChange`. `useCollection` (line 42) is called without a `selection` option, and `Table` (lines 99–108) is never given `selectionType`, `selectedItems`, or `onSelectionChange`. `inspect_surface.py` confirms exactly two native `input` elements (lines 113, 122), both `type="checkbox"`, and no other design-system-matching selection primitive in the file.
- **Cloudscape evidence:**
  - Table component docs (`https://cloudscape.design/components/table/index.html.md`): "The selection and sorting state of table component are controlled... For the selection state, set the `selectedItems` property and `onSelectionChange` event listener" (normative dev-guide text, not an example). Selection types section: "**Multi** — Allows multiple items to be selected at a time by using checkboxes for each item... Use for collections that support bulk actions." Client-side-table guidance: "When you are using collection hooks, make sure that the selection is also controlled by the hook." Usage guideline: "To prevent users from performing actions on items they may not know are selected, reset item selection across pagination, sorting, filtering, page size changes... Always include the number of selected items in the header item counter." "Don't" list: "Don't show the number of selected items if nothing has been selected."
  - Collection hooks dev guide (`https://cloudscape.design/get-started/dev-guides/collection-hooks/index.html.md`): `useCollection` accepts a `selection` option ("Selection configuration. If you want to use the selection feature with default settings, provide an empty object"); its worked example passes `selection: {}` to `useCollection`, spreads the returned `collectionProps` onto `Table` together with `selectionType="multi"`, and reads `selectedItems` back from `collectionProps` — the header counter is then rendered as `` selectedItems.length ? `(${selectedItems.length}/${allItems.length})` : `(${allItems.length})` ``.
  - Table view pattern (`https://cloudscape.design/patterns/resource-management/view/table-view/index.html.md`), building block J ("Selection - optional"): "Table rows can be selected individually or in bulk (multiple selection) via the checkboxes mechanism... Any actions triggered after selection only affects the selected visible rows. Selection is overwritten by: Table sorting, Pagination, Preferences, and as soon as they are no longer visible on the page."
- **Applicability argument:** This is exactly the documented "collections that support bulk actions" scenario the `Multi` selection type is built for — a per-row checkbox, a page-level "select all," and a header bulk action ("Delete selected") driven by the selection count. The current implementation reproduces this exact interaction shape with raw HTML rather than the mechanism Cloudscape ships and documents for it. It also concretely diverges from a stated behavioral expectation: because `checkedIds` lives outside `useCollection`'s selection option, it is never reset by sorting, filtering, or pagination the way the docs require ("reset item selection across pagination, sorting, filtering... to prevent users from performing actions on items they may not know are selected") — an operator can select groups, change sort/filter/page, and still fire "Delete selected" against groups no longer visible on screen. This preserves the same task; it does not change what the page does, only how the selection mechanism is expressed.
- **Current expression:** Local `Set<string>` state, two independent raw `<input type="checkbox">` elements with manual `onChange` handlers wired into custom `columnDefinitions` cells, disconnected from `useCollection`.
- **Native expression:** Pass `selection: {}` to `useCollection`, spread `collectionProps` onto `Table` with `selectionType="multi"`, and derive the header's disabled state, count, and eventual delete payload from the resulting `selectedItems` (as shown in Cloudscape's own collection-hooks dev-guide example).
- **Why it matters:** Beyond the wrong-vocabulary concern, the hand-rolled mechanism drops a documented safety property (selection must reset across filter/sort/pagination) that the native mechanism provides automatically when wired through `useCollection`'s `selection` option — a real bulk-delete-blast-radius risk for a page whose whole purpose is deleting selected resources. It also means standard selection-adjacent affordances Cloudscape ships for free (shift-click/shift-space range selection, `allItemsSelectionLabel`/`itemSelectionLabel` alternative text, `isItemDisabled` for inactive rows) are unavailable and would each need to be reimplemented by hand.
- **Boundary check:** This is about which selection mechanism (custom checkboxes vs. `Table`'s documented `selectionType`) expresses the same bulk-selection task, not about whether the current checkboxes are individually well-built — a component-vocabulary question, not implementation correctness or general UX.

### Finding 2: Stand-alone resource table wrapped in `ContentLayout` + `Table variant="container"`, where Cloudscape documents `Table variant="full-page"` (no `ContentLayout`) for this exact page shape

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** medium (see caveats below)
- **User task:** Same as above — a dedicated, full-page resource-inventory table with no other page content, used to browse and bulk-manage security groups.
- **Repository evidence:** `fixture/src/pages/SecurityGroups.tsx` lines 84–185: the entire return value is `<ContentLayout header={<Header .../>}><Table variant="container" .../></ContentLayout>` — no other siblings inside `ContentLayout`, confirmed by `inspect_surface.py`'s tag inventory (`ContentLayout: 1`, `Header: 1`, `Table: 1`, nothing else at that level). The in-file comment states the page's entire job: "list every group, its VPC, rule counts, and status, and let an operator pick a batch... Nothing on the page besides the table." The table itself carries 7 columns (selection, name, VPC, inbound rules, outbound rules, status, created) mixing text, an id-shaped reference, two numeric counts, a status indicator, and a timestamp.
- **Cloudscape evidence:**
  - Table component docs, Variant section: "**Container** — ...Use this variant to feature a table in a stand-alone container with its own hierarchy. For example: when using a table on a details page." "**Full page** — This variant is for implementing the full page table view pattern. Use it for presenting and managing a table with many columns within a stand-alone page... Use this variant in conjunction with `contentType="table"` on the App Layout."
  - Table view pattern (`.../patterns/resource-management/view/table-view/index.html.md`), building block C: "Use the 'full-page' variant of the table component for this pattern." "Don't" list: "Don't use the content layout component on this type of page. Instead, use the 'full-page' variant of the table component to implement this pattern." — an explicit prohibition paired with a named alternative. The same "Don't" section immediately carves out an exception: "Don't use the table view pattern for tables that aren't overly content-heavy. Instead, if a table only has a few columns, use a bordered table inside the content layout component, with the default app layout content max-width."
- **Applicability argument:** Applying the anti-fundamentalism four-point test: (1) the observed task — a dedicated, full-page, sole-purpose resource inventory table — is precisely the problem statement the table-view pattern addresses ("table view of all user resources within the service"), not a superficial shape match; (2) the current implementation solves that exact problem (list + filter + paginate + bulk-manage one resource collection, nothing else on the page); (3) the proposed native expression (`Table variant="full-page"`, header moved to `Table`'s own `header` slot, `ContentLayout` removed) preserves the identical task and even the identical header content/actions; (4) the pattern page states the difference as a "Don't X, instead do Y" pairing (`REQUIRED`-strength for that specific rule), which is about as material as this skill's evidence bar gets. The residual uncertainty is the pattern doc's own carve-out for tables with "a few columns" — this table has 7 columns spanning several distinct data types (id/name, VPC reference, two numeric counts, status, timestamp), which reads as closer to "many columns" than "a few," but the docs never state a numeric threshold, so I can't fully close that gap from citation alone.
- **Current expression:** `ContentLayout` supplies the page header and wraps a `Table` with `variant="container"` as the page's sole content.
- **Native expression:** Drop `ContentLayout`; render `Table` directly with `variant="full-page"`, moving the `Header` (with its `counter` and `Delete selected` action) into `Table`'s own `header` prop, per the table-view pattern's building blocks C/D.
- **Why it matters:** The pattern page's own guidance frames `container` as for a table nested inside a page with its own broader hierarchy (e.g., alongside other content on a details page), while `full-page` is the variant built for exactly the "nothing else on the page" shape this surface has. Beyond the documented instruction itself, this composition choice interacts with `contentType="table"` on the surrounding `AppLayout` (outside this bounded file) for space/behavior optimizations the `container` + `ContentLayout` combination doesn't get — a real, design-system-specific cost of picking the wrong variant/wrapper pairing for a page that will only ever be this one table.
- **Boundary check:** This is a judgment about which documented page-composition variant (`container` inside `ContentLayout` vs. `full-page` standalone) matches the page's own stated shape and Cloudscape's explicit guidance for that shape — not a critique of how either variant is implemented, and it preserves the exact same user task, so it is not a redesign.

## Suppressed (low materiality or weak applicability)

- **Delete confirmation pattern (delete-with-simple-confirmation / one-click-delete / delete-with-additional-confirmation).** The "Delete selected" `Button` (line 91) has no `onClick` at all — no delete flow of any kind is wired up in the bounded surface. There is no current expression of a deletion interaction to compare against Cloudscape's delete patterns, so applicability can't be established; reporting a recommendation here would mean inventing behavior that doesn't exist in the file. Not evaluated further.
- **Header counter format (`(${GROUPS.length})` never reflecting selection count).** Genuinely tied to Finding 1 (the docs' `(${selected}/${total})` counter convention only becomes reachable once selection is wired through `collectionProps`), so folded into Finding 1's "Why it matters" rather than reported as an independent finding — it isn't a separate component/pattern choice, just a downstream symptom of the same one.
- **Column count threshold for the "few columns" carve-out in the table-view pattern.** No numeric threshold is documented anywhere fetched in this session; I judged 7 mixed-type columns as closer to "many" than "a few," but flagged this honestly as the reason Finding 2's confidence is `medium` rather than `high`, instead of suppressing the finding or overclaiming certainty.

## Orientation notes

- `TextFilter` used as a single filter across the full column set, paired with `useCollection`'s `filtering` option — matches the table-view pattern's documented "Filter" building block ("the entire set of columns are used as a base for the filter"). Confirmed native.
- `Pagination` + `useCollection`'s `pagination: { pageSize: 10 }` — matches the documented pagination building block; table-view pattern explicitly recommends pagination over progressive loading for this shape, and no progressive loading is present. Confirmed native.
- `stickyHeader` is used together with a header action (`Delete selected`), consistent with the Table docs' "Don't use sticky header in tables without actions in the header" rule (this table has one). Confirmed native, not a finding.
- `StatusIndicator` used for the `active`/`unused` status column — matches its documented purpose ("communicates the state of a resource... in a compact form... easily embedded in a card, table, list"). Confirmed native.
- Sorting via `useCollection`'s `sorting` option with `sortingField` per column, single-column sort — matches the table-view pattern's default single-column sort behavior. Confirmed native.

## What was not evaluated

Implementation correctness was not assessed: whether the raw checkboxes' keyboard/focus/ARIA behavior is individually well-built, whether the missing `onClick` on the delete button is a defect, prop-level API usage, and any deprecated-prop or hard-coded-styling concerns. General UX and product judgment (information density, column ordering, whether 10-per-page is a good default, copy wording) were likewise not evaluated — their absence here reflects scope, not a clean bill of health.
