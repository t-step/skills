# Cloudscape Native-Expression Review: Certificates (list + details)

**Inferred user task:** View the fleet of TLS certificates an account manages in a full-page, filterable/sortable table, then drill into a single certificate's own long-lived record — its identity, the domains it covers, the resources it's attached to, and its renewal history — and perform whole-resource actions (Renew, Revoke) on it. `CertificatesTable.tsx` is the fleet list; `CertificateDetails.tsx` is the per-certificate details page it navigates to via react-router (`/certificates/:certId`).

**Cloudscape packages / versions:** `@cloudscape-design/components` ^3.0.900 (locked 3.0.900, resolved), `@cloudscape-design/collection-hooks` ^1.0.60 (locked 1.0.60, resolved). Both fully resolved; no version-drift caveat needed.

## Findings

### 1. "View details" navigation belongs on the identifier column, not a separate Actions column

- **Type:** combined component + pattern
- **Materiality:** high
- **Confidence:** high
- **User task:** Scan a table of certificates and open any one certificate's own details page.
- **Repository evidence:** `CertificatesTable.tsx` lines 55-56 mark `domain` as `isRowHeader: true` but render it as plain text (`cell: (c) => c.domain`). The row's only navigation to `CertificateDetails.tsx` is implemented in a separate, dedicated `actions` column (lines 66-75) as `<Button variant="inline-link" onClick={() => navigate(...)}>View details</Button>`.
- **Cloudscape evidence:** Table component usage guide (`https://cloudscape.design/components/table/?tabId=usage`, "Do" list, "Columns"): "Use the first table column for unique identifiers of the items that are represented in the table (for example: name, id, and ARN). Also use the first table column for users to navigate to a details page that shows more information about the item." The same page's cell guidance: "Use the primary link variant instead of the secondary link variant in table cells... to help users distinguish links from other text content." Separately, the Button usage guide (`https://cloudscape.design/components/button/?tabId=usage`) documents the `inline-link` Button variant specifically for real per-row actions in an actions column ("a download button placed in table cells within the actions column").
- **Applicability argument:** (1) The observed task — scan identifiers, open a details page per row — is exactly the problem the "first column" guidance addresses, not a superficial shape match. (2) The current code already solves substantially the same problem (it does navigate to the details page); it only misplaces the affordance. (3) Moving the navigation onto the `domain` cell (as a `Link`, primary variant) preserves the identical task and destination — no product semantics change. (4) The difference is material: today the dedicated `Actions` column exists solely to hold a navigation link, not an actual action, which collides with the Button/inline-link doc's own stated purpose for that column (real per-row actions like download/edit/delete) and forfeits the standard identify+navigate affordance Cloudscape tables give the row-header column everywhere else.
- **Current expression:** Identifier (`domain`) column is inert text; a same-purpose, separately-columned Button performs the navigation.
- **Native expression:** Render the `domain` cell itself as a `Link` (primary variant) to `/certificates/${c.id}`, keeping the identifier and its details-page entry point on one column. Reserve the `Actions` column for genuine per-row actions if/when they exist (e.g., Renew, Revoke at the row level), using inline buttons/inline button dropdowns as documented — not for the primary "view details" navigation.
- **Why it matters:** This is the documented, cross-console convention for how every Cloudscape resource table exposes drill-down, and it's what gives table scanning its predictability (first column = what this row is + where clicking it goes). As implemented, the table instead carries a same-purpose duplicate mechanism in an `Actions` column that has no other content, which is inconsistent with how that column is documented to be used and with how the rest of a Cloudscape-based product would behave.
- **Boundary check:** This is about which column/component should carry row identification vs. navigation vs. action — a composition/selection question — not an implementation defect (nothing here is broken or inaccessible) and not generic UX opinion (it's grounded directly in the Table component's own first-column guidance).
- **Authority strength:** RECOMMENDED (stated as an affirmative "Do," not phrased as a "Don't X, do Y" prohibition).

## Suppressed (low materiality or weak applicability)

- **Attached resources / Domains covered rows as links to their own resource pages** — the nested "Attached resources" table lists Application Load Balancers, which in a real AWS console are independently addressable resources. Whether this app supports navigating to an ALB's own details page can't be established from this bounded two-file surface, and the current non-navigating containers already match Cloudscape's own "Related resources container (E) — optional... Use when showing related sections that don't require navigating to a different page" building block for the plain Details page pattern. Suppressed rather than reported as `intent-dependent`: naming it wouldn't be actionable without knowing whether an ALB details route exists elsewhere in the product.
- **Filtering/pagination/sorting present on a 4-item mock table** — Table's usage guide says "Only use filtering, pagination, and sorting if there are more than five items." The fixture's hardcoded `CERTIFICATES` array has 4 rows, under that threshold. Suppressed: the surface's own code comment frames this as "the fleet of TLS certificates this account manages," and the 4-item array is illustrative mock data, not evidence of the real expected fleet size — treating literal fixture-data size as the true item count would be over-reading a demo dataset.
- **Full-page Header not using the `awsui-h1-sticky` variant** — Table's usage guide suggests pairing `stickyHeader` with that Header variant so the title shrinks on scroll. This is a specific prop/variant compliance detail rather than a component/pattern selection question — better suited to `cloudscape-implementation-audit`.
- **Breadcrumb omits a "service name" tier** — the documented Details page breadcrumb structure is `[Service name] > [Resources type] > [Resource name/ID]`; the fixture's breadcrumb is just `Certificates > api.example.com`. Whether a service-level tier applies depends on app-wide navigation structure outside this bounded two-file surface, so it isn't reported as a finding here.

## Orientation notes

- `CertificateDetails.tsx`'s structure — `BreadcrumbGroup`, an `h1` page title matching the last breadcrumb, `Header` actions (Renew, Revoke) for whole-resource operations, a `KeyValuePairs`-based "General configuration" summary container, and additional self-contained containers for domains/attached resources/renewal history — matches the canonical "Details page" building blocks (A–G) at `https://cloudscape.design/patterns/resource-management/details/details-page/` closely, confirmed against that page directly (not inferred from the discovery index).
- None of the nested resource lists (Domains: 3, Attached resources: 2, Renewal history: 3) exceed the "more than 10 items" threshold that the Details page guide's own "Don't" explicitly cites as the trigger to switch to the "Details page as a hub" pattern instead — confirmed the current plain-container structure, not a hub, is the documented fit here.
- `CertificatesTable.tsx`'s `variant="full-page"` Table with an `h1` `Header` (title + item counter), `resizableColumns`, `stickyHeader`, `TextFilter`, and `Pagination` matches the full-page "table view" pattern's building blocks; `TextFilter` specifically is an appropriate choice given the certificates shown have no obvious need for multi-attribute property filtering.

## What was not evaluated

Implementation correctness — deprecated props, `aria-label`/`ariaLabels` completeness, the placeholder `href="#"` breadcrumb entry in `CertificateDetails.tsx`, whether `Button`-driven `navigate()` calls have the accessibility properties an anchor-based `Link` would give for free, and any other API-usage/token-level mechanics — was not assessed; that is `cloudscape-implementation-audit`'s domain. General UX or product judgment beyond the Cloudscape-documented patterns cited above (e.g., whether Renew/Revoke should require confirmation, or how this page fits into a larger multi-page information architecture) was also not evaluated.
