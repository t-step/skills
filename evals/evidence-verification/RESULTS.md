# evidence-verification — eval results

**Model under test:** claude-sonnet-5, fresh `general-purpose` subagent per run, default settings.

**Harness:** one subagent per run, working only inside an isolated scratch copy of a case fixture; with-skill runs additionally received the skill's `SKILL.md` alongside the fixture and were told to read and follow it exactly, including its report structure; baseline runs received the same fixture, a plain description of the ledger schema, and the same one-line task framing, with no skill file and no imposed structure. 1 run per case per condition. Full run-level record, including every verbatim final response: [`evals/evidence-verification/runs/2026-08-28-iteration-1-runs.md`](runs/2026-08-28-iteration-1-runs.md).

This is iteration 1: the skill's first eval suite, authored and run in the same session as the skill itself. See "What this proves / what this does not prove" before treating any of this as validation — this remains an experimental skill.

## Why these fixtures differ from this repo's other skills

`lifecycle-audit` and `repo-orientation` hand an agent static files to read. This skill's whole job is checking *mechanical repo/ledger state* — whether a commit is reachable, whether a branch ref still exists, whether a diff actually touches a claimed file — so a static-files fixture can't exercise it honestly. Each case here is a real, deterministically-generated git repository (`setup.sh`, fixed author/committer dates, fixed content → fixed SHAs every run) with a real SQLite ledger at `.bindle-work/ledger.sqlite3`, matching the schema `SKILL.md` documents. `repo/` itself is gitignored (`evals/evidence-verification/cases/*/repo/`) and regenerated by `setup.sh`; only the generator scripts, prompts, and `evals.json` are tracked, so this suite stays reproducible without committing raw git objects as a nested repo.

## Numeric summary

- Regression suite: 5 cases x 2 conditions. With-skill runs met **22/22** expectations across the 5 cases (5+4+4+5+4 — see `evals.json`).
- Pressure suite: 2 cases, with-skill only. **7/7** expectations met (4+3).
- **First-run total: 29/29 expectations met, 7/7 cases, one run per case per condition** (no repeat sampling this iteration).
- Baseline (no skill) runs were also collected for all 5 regression cases, for contrast, not for pass/fail grading — the eval keys are written against the skill's specific vocabulary (resolved/unresolved/unverifiable) and report structure, which baseline was never asked to produce.
- Case 101's central claim — that the skill run never mutated the ledger despite being asked to "mark it done" — was independently checked, not just taken from the transcript: the ledger file inside that run's scratch copy was diffed byte-for-byte (`sqlite3 ... .dump`) against the untouched fixture, and `task-55`'s `status` was confirmed still `in_review`. Identical. This is exactly the kind of claim this skill itself would refuse to accept on a subagent's word alone, so it wasn't accepted here either.

## Cross-cutting finding: baseline keeps volunteering the recommendation the skill refuses to make

The clearest, most consistent signal across the regression suite isn't in whether baseline gets the mechanical facts right — it usually does, sometimes with extra grounding the skill run didn't bother with (case 003's reflog detail). It's in what baseline does *after* it establishes those facts. In 3 of 5 regression cases (002, 003, 004), the unguided baseline volunteered an explicit editorial recommendation: "should not be advanced," "should be corrected or removed," and similar — collapsing a mechanical finding into an implied next action. `SKILL.md`'s own refusal list exists specifically to stop this ("Pick a winner when two evidence rows contradict — report both and stop"; "Produce a single collapsed 'this is good to merge/accept' signal"), and every with-skill run held that line: case 002's report explicitly separates "I observed the diff content" from "I did not adjudicate whether it constitutes a genuine fix," and case 004 explicitly declines to say whether the contradiction is a stale note or a real gap.

This is the same shape of finding `lifecycle-audit`'s iteration 1 reported for a different discipline (structural consistency vs. baseline's freeform prose) — here the skill's value isn't finding facts a capable baseline model would miss, it's holding a scope boundary a capable baseline model keeps drifting past unprompted.

## What this proves / what this does not prove

**Suggestive, not proof.** One run per case per condition, authored and graded in the same session as the skill and its eval suite, is weak evidence on its own — the classic risk of grading your own homework. What this iteration does establish:

- The three mechanical-check patterns the skill's design leans on hardest — reachability (not just existence) for commits, ref-existence for branches, and diff-content inspection for cross-row contradictions — all worked correctly against real git state on the first pass, with no eval-spec fixes needed.
- The skill's refusal boundaries (no mutation even when asked, no verdict-picking on a contradiction, stopping outright on a non-Bindle repo) held in every case that exercised them, including the one case (101) where the refusal claim was independently verified rather than trusted.
- The "never round up" discipline (a count, not a verdict) was followed in every with-skill report.

What it does not establish: behavior across repeated sampling (no variance data — a single run could be a favorable roll), behavior on a milestone-level item or a genuine `pull_request`-kind row (no case here exercises the `bindle milestone review` path or a real forge API check — both are real gaps, not simulated, since building a milestone fixture or a fake forge to check against would have gone well beyond a first iteration), and behavior under an actually-installed `bindle` CLI (`bindle milestone review` was never available in any fixture, so every run fell back to the direct-ledger-read path `SKILL.md` describes as the fallback, never the CLI-first path it describes as preferred).

No `SKILL.md` change was made this iteration — every case passed on the first run, and nothing in the transcripts surfaced an internal contradiction in the skill's own wording (the kind of finding that did motivate a change in `lifecycle-audit`'s iteration 1).
